# Task-engine platform comparison: Hatchet, Inngest, Trigger.dev

Research date: 2026-10-28. Web research only. Sources are official docs unless noted. "Not found" means the item could not be verified. It does not mean the platform lacks the feature.

Terminology: each platform's "tenant", "account" or "org" is the platform's *customer*. None of them provides isolation for *your* end-tenants. End-tenant isolation always comes from a key expression on the job (concurrency key, rate-limit key, and so on).

## 1. Hatchet (v1 engine; OSS + Hatchet Cloud)

| 1 | Architecture | Yes | **Storage:** Postgres is the source of truth. RabbitMQ is optional (`SERVER_MSGQUEUE_KIND` = `rabbitmq` or `postgres`; the self-host default is RabbitMQ). It is used for inter-service pub/sub at high throughput and holds no state. **Components:** API server, engine (scheduler, task controller, OLAP controller, ticker, dispatcher), dashboard. Workers connect over bidirectional gRPC. **Deploy:** Hatchet Lite (single image), Docker Compose, Helm/K8s, embedded mode, or Cloud. Autoscaling, multi-region and SSO are Cloud-only. **License:** MIT. **SDKs:** Python, TypeScript, Go, Ruby. | https://docs.hatchet.run/v1/architecture-and-guarantees ; https://docs.hatchet.run/self-hosting ; https://github.com/hatchet-dev/hatchet |

| 2c | Per-tenant concurrency limits | Yes | `max_runs` per key. | 4 | Concurrency: global / per key / per worker | Yes / Yes / Yes | Global: a constant CEL key such as `'global'`. Per key: `expression` + `max_runs`. | 6 | Worker model | Yes | **Push over long-lived bidirectional gRPC stream** from the engine's dispatcher to workers, which register their tasks. **Heartbeat every 4 s; worker marked INACTIVE after 30 s without one**, and its in-flight tasks are re-queued (states ACTIVE/INACTIVE/STOPPED). Worker labels/affinity and sticky assignment exist. | https://docs.hatchet.run/v1/faq ; https://docs.hatchet.run/v1/architecture-and-guarantees ; issue #5225 https://github.com/hatchet-dev/hatchet/issues/5225 |

| 9 | Delayed / scheduled / cron | Yes | Scheduled runs: `hatchet.scheduled.*` with list/update/bulk_delete/bulk_update; the scheduled time is the enqueue time. Cron: `on_crons` declaratively or `create_cron` dynamically, 5 or 6 fields (seconds allowed), UTC. | llms-full.txt |

Code between checkpoints must be deterministic. **Declared before the task starts: yes.** DAG tasks take `wait_for=[...]` with `SleepCondition`, `UserEventCondition` and `ParentCondition`. `or_()` groups are OR'd and groups are AND'd (CNF). | 11 | Dependencies | Yes (static DAG + dynamic children) | DAG via `parents=[...]` at **definition time**, with `skip_if` / `cancel_if` (`ParentCondition` CEL on parent output). | 12 | Cancellation | Yes (cooperative) | Cooperative signal: `ctx.exit_flag` (Py), `ctx.cancelled` / `abortController.signal` (TS), `ctx.Done()` (Go). Self-cancel with `ctx.aio_cancel()`. | 13 | Dedup / idempotency / singleton | Yes | `idempotency=` with **`TTLBasedIdempotencyConfig`** (one run per key per window) or **`StatusBasedIdempotencyConfig`** (key held until the run is terminal; duplicates raise a collision). Singleton semantics via concurrency `max_runs=1` plus **`CANCEL_NEWEST`** (keep existing, drop new) or **`CANCEL_IN_PROGRESS`** (latest wins, cancel previous). **No latest-wins debounce.** | https://docs.hatchet.run/v1/idempotency ; https://docs.hatchet.run/home/concurrency |
| 14 | Progress / state / logs | Yes | `ctx.log(line)` writes to a searchable per-run log sink (Go `PutLog`). `ctx.put_stream` / `putStream` streams data to subscribers. Durable-task checkpoints are the event log. Task outputs pass to children via the parents' outputs. **No mutable per-run metadata/progress object** like Trigger.dev's `metadata` was found. Additional metadata is set at trigger time. | https://docs.hatchet.run/reference/python/context ; https://docs.hatchet.run/v1/streaming |
| 15 | Search / filter / retention | Yes | **Additional metadata** (string KV) on runs, events, crons and schedules; it propagates parent → child and event → run. Run filtering uses OR semantics; event filtering uses AND (JSONB containment). Retention: self-host default **30 days** per tenant (`SERVER_LIMITS_DEFAULT_TENANT_RETENTION_PERIOD`). Cloud: 1 day with no card, 7 days pay-as-you-go, 90+ days Custom. | https://docs.hatchet.run/v1/additional-metadata ; https://docs.hatchet.run/self-hosting/data-retention ; https://hatchet.run/pricing |
| 16 | Lifecycle events / webhooks out | Partial | Inbound webhooks (Stripe, GitHub, Slack, Linear, Svix presets; CEL event-key and scope). Event filters. Run streams. Alerting, OpenTelemetry and Prometheus metrics. **No generic outbound lifecycle webhook found.** | https://docs.hatchet.run/v1/webhooks ; https://github.com/hatchet-dev/hatchet |
| 17 | Scale numbers | Yes | Load-tested to **10k tasks/s** (README). At least 5 Postgres transactions per task. Cloud bursts above 5k tasks/s, and more than 1B tasks/month (Apr 2025). A Postgres-only deployment does "hundreds of tasks/sec per engine instance". Latency under 50 ms, about 25 ms P95 with hot workers. Cloud pay-as-you-go limits: 100 workers, 10k slots, 1,000 crons. | https://github.com/hatchet-dev/hatchet ; https://news.ycombinator.com/item?id=43572733 ; https://docs.hatchet.run/v1/architecture-and-guarantees ; https://hatchet.run/pricing |
| 18 | Philosophy / criticisms | — | "Postgres is enough": durability over raw throughput. They accept more resource use than Redis/RMQ queues. ## 2. Inngest (Cloud + self-hostable single binary)

## Cross-cutting notes for the in-house design

- **Fairness on a shared queue.** Hatchet `GROUP_ROUND_ROBIN` gives true round-robin across keys out of the box. Inngest provides per-key virtual queues ("best effort"), and its strict key-queue scheduling is Enterprise-only. Trigger.dev added virtual-time fair queuing across keys only in Sep 2026, opt-in. All three treat **fairness separately from limits**.
- **Per-tenant limits** are always a CEL or trigger-time key on the job, with a small number of stacked constraints (Inngest 2, Trigger.dev 1 inline + 2 named, Hatchet a list). Hatchet `max_runs` and Inngest `priority` accept expressions for tier-based limits. Trigger.dev v4.7.4 has runtime per-key overrides.
- **Waits declared before start.** Only Hatchet supports this declaratively (`wait_for` / `skip_if` / `cancel_if` on DAG tasks). Inngest waits are registered only when code reaches them, and events sent earlier are missed. Trigger.dev waitpoint tokens can be created before the wait, but the wait itself is imperative.
- **Dependencies.** Hatchet has a static DAG at definition time plus runtime children. Inngest and Trigger.dev have code-only parent/child. **None supports adding edges between existing runs.**
- **Fencing of stale workers** is not documented by any of them. Hatchet explicitly accepts duplicate execution after heartbeat-loss reassignment (4 s / 30 s).
