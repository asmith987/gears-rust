# Queue / workflow services: comparison research for the multi-tenant task engine

Researched 2026-10-28. Facts marked **(verified)** were checked against the official page during this session. Everything else comes from prior knowledge of the official docs, and the cited URL is where it is documented. Re-check any number before quoting it in a design doc. "not found" means I could not confirm it.

Support levels: **Yes**, **Partial**, **No**, **N/A**. A **[Pro]**, **[Ent]** or **[paid]** tag marks a feature that needs a paid tier.

## 1. BullMQ (OSS, MIT) + BullMQ Pro (paid)

| # | Item | Support | How | Source |
|---|---|---|---|---|
| 1 | Architecture | Yes | Node.js/Bun library. All state lives in Redis (Lua scripts, sorted sets, lists, streams). There is no server: producers and workers embed the library. The core is MIT. **BullMQ Pro** is a closed paid add-on (groups, batches, observables) costing **$1,395/yr or $139/mo per deployment** for orgs under 100 employees, with Enterprise/Embedded licences at custom prices **(verified)**. Redis Cluster needs `{hash-tag}` queue prefixes. | https://bullmq.io/#pricing , https://docs.bullmq.io/guide/going-to-production |
| 2a | Per-tenant fairness | Yes [Pro] | **Groups**: a job carries `group: { id }`. Workers take jobs from groups **round-robin**, so one heavy group cannot starve the others. There is "no hard limit on the amount of groups" and empty groups use no Redis resources. Ungrouped jobs in the same queue take precedence over grouped jobs **(verified)**. OSS has no fairness. | https://docs.bullmq.io/bullmq-pro/groups |
| 2b | Per-tenant concurrency | Yes [Pro] | A worker-level group concurrency sets the default limit per group. `queue.setGroupConcurrency(groupId, n)` overrides it for one group ("local group concurrency"). The override is stored in Redis and must be cleaned up manually **(verified)**. | https://docs.bullmq.io/bullmq-pro/groups/local-group-concurrency |
| 2c | Per-tenant rate limit | Yes [Pro] | `WorkerPro` option `group.limit {max, duration}` limits each group independently. `worker.rateLimitGroup(job, ms)` plus `throw Worker.RateLimitError()` handles a 429 from an external API. `getGroupRateLimitTtl()` reports the remaining limit **(verified)**. Pro also has **max group size** (rejects adds over the cap) and **pause/resume a single group**. | https://docs.bullmq.io/bullmq-pro/groups/rate-limiting , https://docs.bullmq.io/bullmq-pro/groups/max-group-size , https://docs.bullmq.io/bullmq-pro/groups/pausing-groups |
| 2d | AuthZ | No | BullMQ has no authorization model. Anyone with Redis access can do anything. Redis ACLs are the only control. | https://docs.bullmq.io/guide/connections |
| 3 | Priorities | Yes | `opts.priority`: 1 is highest, up to 2,097,152. Priority 0 or unset is processed before any prioritized job, in FIFO order. `job.changePriority()`. Pro adds **priorities within a group** ("prioritized intra-groups"). | https://docs.bullmq.io/guide/jobs/prioritized , https://docs.bullmq.io/bullmq-pro/groups/prioritized |
| 4 | Concurrency limits | Yes | **Per worker**: the `concurrency` option. **Global** (across all workers): `queue.setGlobalConcurrency(n)`. **Per group**: Pro, see 2b. | https://docs.bullmq.io/guide/workers/concurrency , https://docs.bullmq.io/guide/queues/global-concurrency |
| 5 | Rate limiting | Yes | The worker `limiter: {max, duration}` is enforced **queue-wide** across workers. `worker.rateLimit(ms)` + `Worker.RateLimitError` handles manual 429s. A global rate limit via `queue.setGlobalRateLimit` exists in recent 5.x (not verified). Per-group limits are Pro only. | https://docs.bullmq.io/guide/rate-limiting |
| 6 | Worker model | Partial | **Pull**. Each worker takes a **lock** with a per-worker token (`lockDuration`, default 30 s) and renews it automatically. A stalled checker (`stalledInterval`, `maxStalledCount`, default 1) moves jobs whose lock expired back to wait, or to failed once the limit is reached **(verified for behaviour; defaults not verified)**. **Fencing is partial**: the processor receives the lock `token`, and completing or moving a job checks it ("Missing lock for job" error). Side effects a stale worker already made are not fenced. Common stall cause: CPU-bound processors that block the event loop. | https://docs.bullmq.io/guide/workers/stalled-jobs , https://docs.bullmq.io/guide/workers |
| 7 | Retries / DLQ / redrive | Partial | `attempts` + `backoff: {type: 'fixed'|'exponential', delay}`, or a custom `backoffStrategy`. `UnrecoverableError` skips retries. There is **no separate DLQ**: exhausted jobs go to the **failed** set. `job.retry()` and `queue.retryJobs()` re-run them manually, and the UI can too. | https://docs.bullmq.io/guide/retrying-failing-jobs |
| 8 | Timeouts | Partial | No built-in per-job execution timeout in the OSS API (Bull 3's `timeout` was dropped). Implement it with an `AbortSignal` or a timer in the processor. Pro **observables** make cancel-on-timeout easier. | https://docs.bullmq.io/guide/workers/cancelling-jobs , https://bullmq.io/#pricing |
| 9 | Delayed / cron | Yes | `opts.delay` (ms) puts the job in the delayed ZSET. **Job Schedulers**: `queue.upsertJobScheduler(id, {pattern \| every}, template)` for cron and fixed intervals. They replace the older repeatable jobs. | https://docs.bullmq.io/guide/jobs/delayed , https://docs.bullmq.io/guide/job-schedulers |
| 10 | Waits | Partial | **waiting-children** state: a parent waits until its children finish. `job.moveToDelayed(ts, token)` + `DelayedError` parks a running job, and `job.moveToWaitingChildren(token)` + `WaitingChildrenError` does the same until children finish ("process step jobs" pattern). There is **no external-signal / human-input wait primitive**. The usual workaround is to delay and poll, or to add a child job later. | https://docs.bullmq.io/patterns/process-step-jobs , https://docs.bullmq.io/guide/flows |
| 11 | Dependencies | Yes | **Flows**: `FlowProducer.add({name, children:[...]})` builds trees, and the parent reads `job.getChildrenValues()`. Options: `failParentOnFailure`, `continueParentOnFailure`, `ignoreDependencyOnFailure`, `removeDependencyOnFailure`. **Children can be added after creation** with `queue.add(..., {parent: {id, queue}})`, then the running parent calls `moveToWaitingChildren`. Children can live in other queues. | https://docs.bullmq.io/guide/flows , https://docs.bullmq.io/guide/flows/fail-parent |
| 12 | Cancellation | Partial | Queued jobs: `job.remove()` (fails if locked). Active jobs: **cooperative** cancellation. The processor receives `signal` (AbortSignal) and `worker.cancelJob(id, reason)` / `cancelAllJobs()` abort it. This works only in the worker that owns the job, and `cancelJob` does **not** fail the job by itself. A user comment (not release notes) says 6.4.0 (Oct 2026) adds cross-worker cancel via "Relay" pub/sub. | https://docs.bullmq.io/guide/workers/cancelling-jobs , https://docs.bullmq.io/guide/relay/examples/cancelling-jobs-on-other-workers |
| 13 | Dedup / idempotency / latest-wins | Yes | `opts.deduplication: {id, ttl?, extend?, replace?, delay?, keepLastIfActive?}`. Modes: **simple** (until the job completes or fails), **throttle** (`ttl`), **debounce** (`delay`+`ttl`+`extend`+`replace`, where the newest data wins), and **keepLastIfActive** (at most 1 active + 1 waiting with the latest data). A `deduplicated` event fires on a skipped add **(verified)**. A custom `jobId` also dedups while the job exists. | https://docs.bullmq.io/guide/jobs/deduplication |
| 14 | Progress / metadata | Yes | `job.updateProgress(number\|object)` emits a `progress` event. `job.updateData()`, `job.log()`, and `returnvalue`. | https://docs.bullmq.io/guide/jobs/job-data , https://docs.bullmq.io/guide/events |
| 15 | Search / UI / retention | Partial | Getters such as `getJobs(states)`, `getJobCounts()` and `getJob(id)`. There is **no indexed search** by attribute. UIs: **Taskforce.sh** (paid SaaS) and OSS **bull-board**. Retention is per job via `removeOnComplete/removeOnFail: {count, age}`. Otherwise jobs live in Redis until removed, bounded only by memory. | https://docs.bullmq.io/guide/queues/auto-removal-of-jobs |
| 16 | Events | Yes | `QueueEvents` (Redis Streams, global: completed, failed, progress, delayed, deduplicated...) and local `Worker` events. The stream is trimmed (`maxLenEvents`), so events are **not durable**. | https://docs.bullmq.io/guide/events |
| 17 | Scale / limits | Partial | No hard payload or delay limits are published; the limit is Redis memory and single-thread CPU. No official throughput numbers were found in the docs. Production guide: Redis `maxmemory-policy noeviction` is required. | https://docs.bullmq.io/guide/going-to-production |
| 18 | Philosophy / pitfalls | n/a | A Redis-native library that is fast and simple. Pitfalls: Redis is the database (persistence, eviction, failover and loss windows), at-least-once delivery so processors must be idempotent, stalls from a blocked event loop, the multi-tenancy features are in paid Pro, no authz, events are lossy. | https://docs.bullmq.io/guide/going-to-production |

## 2. Sidekiq (OSS LGPL / Pro / Enterprise)

| # | Item | Support | How | Source |
|---|---|---|---|---|
| 1 | Architecture | Yes | Ruby, Redis-backed, multi-threaded worker processes. **Pricing (verified):** OSS is free under LGPL. **Pro** is $99/mo or $995/yr, unlimited use (batches, reliability, expiring jobs, worker metrics). **Enterprise** starts at **$269/mo per 100 threads** (rate limiting, cron, unique jobs, rolling restarts, historical metrics, multi-process, encryption, Web UI authz). | https://sidekiq.org/ |
| 2a | Per-tenant fairness | No | No fair scheduling across tenants. Queues are read in **strict order or random-weighted order** (`queues: [[a,3],[b,1]]`). Isolating tenants means one queue per tenant, which does not scale to many tenants. | https://github.com/sidekiq/sidekiq/wiki/Advanced-Options |
| 2b | Per-tenant concurrency / rate | Partial [Ent] | **Enterprise rate limiters** with a dynamic key: `Sidekiq::Limiter.concurrent("api-#{tenant_id}", n, ...)`, plus `bucket`, `window`, `leaky`, `points` and `unlimited`. **Caveat (verified):** "limiting is not throttling". Jobs are still fetched. Over the limit, the job raises `OverLimit` and is **rescheduled with backoff** (about 5 min plus jitter, up to 20 times, then normal retries). Limiters cannot be composed, and they need NTP-synced clocks. | https://github.com/sidekiq/sidekiq/wiki/Ent-Rate-Limiting |
| 2c | AuthZ | Partial [Ent] | Only Web UI authorization (Enterprise). No job- or tenant-level authz. Redis access means full control. | https://sidekiq.org/ |
| 3 | Priorities | Partial | Only through queue ordering or weights. There is no per-job priority. | https://github.com/sidekiq/sidekiq/wiki/Advanced-Options |
| 4 | Concurrency limits | Partial | **Per process**: the `concurrency` thread count. **Per queue per process**: Sidekiq 7 **capsules** (`config.capsule("x") { concurrency 1; queues [...] }`). **Global / per key**: Enterprise `Limiter.concurrent`, a distributed semaphore with `lock_timeout` reclaim. | https://github.com/sidekiq/sidekiq/wiki/Advanced-Options , https://github.com/sidekiq/sidekiq/wiki/Ent-Rate-Limiting |
| 5 | Rate limiting | Yes [Ent] | Enterprise limiters (see 2b). OSS has none. | https://github.com/sidekiq/sidekiq/wiki/Ent-Rate-Limiting |
| 6 | Worker model | Partial | **Pull** (blocking Redis fetch). OSS "basic fetch" **can lose in-progress jobs** if the process crashes. **Pro `super_fetch`** moves jobs into a per-process private list and recovers orphans on restart. There is no per-job visibility timeout or heartbeat (process heartbeats only), no stalled-job lease and **no fencing**. | https://github.com/sidekiq/sidekiq/wiki/Reliability |
| 7 | Retries / DLQ / redrive | Yes | Default **25 retries** with exponential backoff (about 20 days). `sidekiq_retry_in` sets custom backoff and `sidekiq_retries_exhausted` runs a hook. Exhausted jobs go to the **Dead set** (default cap 10,000 jobs / 6 months). Retry or delete them from the Web UI or the API. Death handlers are available. | https://github.com/sidekiq/sidekiq/wiki/Error-Handling |
| 8 | Timeouts | No / Partial [Pro] | No execution timeout (the docs discourage Ruby `Timeout`). Pro **Expiring Jobs** (`expires_in`) drops a job that has *not started* by its deadline. | https://github.com/sidekiq/sidekiq/wiki/Pro-Expiring-Jobs |
| 9 | Delayed / cron | Yes | `perform_in` / `perform_at` put jobs in the scheduled ZSET, which a poller checks every few seconds. **Cron**: Enterprise **Periodic Jobs**, leader-elected. OSS users rely on the sidekiq-cron gem. | https://github.com/sidekiq/sidekiq/wiki/Scheduled-Jobs , https://github.com/sidekiq/sidekiq/wiki/Ent-Periodic-Jobs |
| 10 | Waits | No | No suspend or wait-for-signal. The only "wait for others" mechanism is batch callbacks. Human input means re-enqueueing later yourself. | https://github.com/sidekiq/sidekiq/wiki/Batches |
| 11 | Dependencies | Partial [Pro] | **Batches** with `on(:complete \| :success \| :death)` callbacks, child batches nested inside parent batches, and workflows built by chaining callbacks. **Jobs can be added later only from inside a job already in the batch** ("reopen"). Adding from outside or from callbacks is unsafe **(verified)**. Pending batches expire after 30 days, and successful batch data is kept 24 h. | https://github.com/sidekiq/sidekiq/wiki/Batches , https://github.com/sidekiq/sidekiq/wiki/Really-Complex-Workflows-with-Batches |
| 12 | Cancellation | Partial | Queued or scheduled jobs can be deleted via the API or Web UI (`Sidekiq::ScheduledSet`, `Queue#each ... delete`, which is O(n)). Running jobs: **no API**. The FAQ pattern is to have the job poll a "cancelled" flag you store in Redis. Sidekiq 7.3+ **Iterable jobs** check for cancellation between iterations. | https://github.com/sidekiq/sidekiq/wiki/FAQ , https://github.com/sidekiq/sidekiq/wiki/Iteration |
| 13 | Dedup | Partial [Ent] | Enterprise **Unique Jobs**: `sidekiq_options unique_for: 10.minutes, unique_until: :success \| :start`. The lock key is class + args + queue, and `sidekiq_unique_context` customizes it. The docs call it "**best effort, not a 100% guarantee**" and say lock windows over a few minutes are "a code smell" **(verified)**. There is no latest-wins / replace. | https://github.com/sidekiq/sidekiq/wiki/Ent-Unique-Jobs |
| 14 | Progress / metadata | Partial | No per-job progress API. Batch `Status` gives total, pending and failures, plus a Rack JSON endpoint for progress bars. Iterable jobs persist a cursor. | https://github.com/sidekiq/sidekiq/wiki/Batches , https://github.com/sidekiq/sidekiq/wiki/Iteration |
| 15 | Search / UI / retention | Partial | **Web UI**: queues, busy, retries, scheduled, dead, metrics (Ent adds historical). The API iterates sets with no indexes. Successful jobs are **not retained** at all. The dead set is capped. | https://github.com/sidekiq/sidekiq/wiki/API , https://github.com/sidekiq/sidekiq/wiki/Monitoring |
| 16 | Events | Partial | Server/client **middleware**, lifecycle events (startup, quiet, shutdown), death handlers and batch callbacks. There is no external event stream. | https://github.com/sidekiq/sidekiq/wiki/Middleware |
| 17 | Scale / limits | not found | No official payload or throughput limits found. Best practice is small JSON-native args (IDs, not objects). | https://github.com/sidekiq/sidekiq/wiki/Best-Practices |
| 18 | Philosophy / pitfalls | n/a | "Simple, efficient": jobs must be **idempotent and transactional** (at-least-once). Pitfalls: OSS loses in-flight jobs on crash, Redis is the system of record, the important features (reliability, batches, limits, uniqueness, cron) are paid and closed source, limiters reschedule instead of throttle (wasted fetches, delays), no fairness. | https://github.com/sidekiq/sidekiq/wiki/Best-Practices |

## 3. AWS SQS (Standard, FIFO, fair queues)

| # | Item | Support | How | Source |
|---|---|---|---|---|
| 1 | Architecture | Yes | Fully managed, regional, pay-per-request (64 KB chunks billed as requests). Standard queues are at-least-once with best-effort order. FIFO queues are ordered within a message group and exactly-once within the dedup window. | https://aws.amazon.com/sqs/pricing/ |
| 2a | Per-tenant fairness (**fair queues**, 2025) | Yes | On **standard** queues, setting `MessageGroupId` = tenant id turns on fair queues automatically. SQS watches **in-flight** distribution: a tenant with disproportionately many in-flight messages is a "noisy neighbor", and SQS **prefers returning other tenants' messages** to keep their dwell time low. No consumer changes, no throughput cap, unlimited tenants. CloudWatch `...InQuietGroups` metrics **(verified)**. On standard queues, MessageGroupId does **not** enforce ordering. | https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-fair-queues.html |
| 2b | FIFO message groups | Partial | In FIFO queues, at most one batch per group is in flight at a time, so groups give per-key ordering and **implicit per-group concurrency = 1**. Pitfall: FIFO scans only the first **120,000** messages to find available groups, so a large backlog in one group can block groups sent later **(verified via search)**. | https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/avoid-backlog-with-the-same-message-group-id.html |
| 2c | Per-tenant concurrency / rate | No | "Amazon SQS does **not limit the consumption rate per tenant**" **(verified)**. Fair queues only reorder. Per-tenant caps need a queue per tenant or consumer-side logic. Lambda event source mapping `MaximumConcurrency` is per queue, not per tenant. | https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-fair-queues.html |
| 2d | AuthZ | Yes (per queue) | IAM identity policies plus queue resource policies, ABAC on queue tags, SSE-KMS. The granularity is the **queue**, not the message or tenant. | https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-authentication-and-access-control.html |
| 3 | Priorities | No | Use separate queues and poll the high-priority queue first. | https://aws.amazon.com/sqs/faqs/ |
| 4 | Concurrency limits | Partial | No server-side concurrency setting. In-flight cap is about **120,000 per queue** (standard and FIFO) **(verified)**. Consumers control their own concurrency. Lambda ESM `MaximumConcurrency` ranges 2–1000. | https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/quotas-queues.html |
| 5 | Rate limiting | No | None for consumers. FIFO API TPS quotas (300/s per partition without high throughput) are service limits, not tenant limits. | https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/quotas-messages.html |
| 6 | Worker model | Yes | **Pull** with `ReceiveMessage` (long poll up to 20 s, batches of 10). **Visibility timeout**: default 30 s, max **12 h** **(verified)**. Heartbeat means extending it with `ChangeMessageVisibility`. There is no stalled detector beyond the timeout expiring. **Fencing is partial**: each receive returns a new `ReceiptHandle`, and delete or visibility changes must use the latest one. `ApproximateReceiveCount` tracks attempts. | https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html |
| 7 | Retries / DLQ / redrive | Yes | Retry happens implicitly when visibility expires. **No backoff policy**: emulate it with `ChangeMessageVisibility`. A **RedrivePolicy** `maxReceiveCount` moves messages to a **DLQ**. **DLQ redrive** uses `StartMessageMoveTask` or the console. | https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html |
| 8 | Timeouts | Partial | Only the visibility timeout (lease). No execution timeout. | same as 6 |
| 9 | Delayed / cron | Partial | `DelaySeconds` per message (standard) or per queue (FIFO), **max 15 min** **(verified)**. No cron: use EventBridge Scheduler. | https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/quotas-messages.html |
| 10 | Waits | N/A | Not a workflow engine. | — |
| 11 | Dependencies | No | — | — |
| 12 | Cancellation | No | `DeleteMessage` needs a receipt handle, so you **cannot cancel a message by ID before it is received**. `PurgeQueue` deletes everything. | https://docs.aws.amazon.com/AWSSimpleQueueService/latest/APIReference/API_DeleteMessage.html |
| 13 | Dedup | Partial (FIFO) | FIFO `MessageDeduplicationId` (or `ContentBasedDeduplication`): duplicates within a **5-minute window** are accepted but not delivered, and the ID is tracked even after delete **(verified)**. In high-throughput mode, `DeduplicationScope=messageGroup`. Standard queues have no dedup, and there is no latest-wins. | https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/using-messagededuplicationid-property.html |
| 14 | Progress / metadata | No | Up to 10 message attributes at send time, immutable. | quotas-messages (above) |
| 15 | Search / UI / retention | No | No browse or search: the console can only poll messages. CloudWatch gives approximate counts and age. **Retention: default 4 days, max 14 days** **(verified)**. | https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/quotas-messages.html |
| 16 | Events | Partial | No per-message lifecycle events. Integrates as a source for Lambda, EventBridge Pipes and SNS fan-in. | — |
| 17 | Scale / limits | Yes | Message **1 MiB** max (raised from 256 KiB; up to 2 GB with the S3 extended client). Standard throughput is "nearly unlimited". FIFO is 300 TPS per action per partition (3,000 msg/s batched), and high-throughput FIFO reaches **70,000 TPS / 700,000 msg/s** in the largest regions. Delay max 15 min, retention max 14 days, visibility max 12 h, batch max 10 messages, in-flight about 120k **(all verified)**. | https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/quotas-messages.html |
| 18 | Philosophy / pitfalls | n/a | A dumb, durable, infinitely scalable pipe. Pitfalls: at-least-once delivery (standard), no per-tenant limits, no priorities, no cancel-by-ID, no inspection, 14-day ceiling, short (15 min) delay, FIFO group head-of-line blocking, visibility timeout must exceed processing time or be heartbeated. | — |

## 4. AWS Step Functions (Standard / Express)

| # | Item | Support | How | Source |
|---|---|---|---|---|
| 1 | Architecture | Yes | Managed state machines in **Amazon States Language** (JSON/YAML). **Standard** runs up to 1 year with exactly-once state transitions and is billed per state transition. **Express** runs up to 5 min, at-least-once, billed per request plus duration. | https://docs.aws.amazon.com/step-functions/latest/dg/choosing-workflow-type.html , https://aws.amazon.com/step-functions/pricing/ |
| 2 | Multi-tenancy / fairness | No | No tenant concept. Quotas are per account and region (StateTransition token bucket of 5,000/s in big regions, open executions 1M). IAM works per state machine and execution role. Tenant isolation means separate accounts or state machines. Per-tenant concurrency is a DIY pattern (DynamoDB semaphore). | https://docs.aws.amazon.com/step-functions/latest/dg/service-quotas.html |
| 3 | Priorities | No | — | — |
| 4 | Concurrency limits | Partial | `Map.MaxConcurrency`. Distributed Map runs up to **10,000 parallel child executions** **(verified)**. No per-state-machine or global cap. | https://docs.aws.amazon.com/step-functions/latest/dg/state-map-distributed.html |
| 5 | Rate limiting | No (user) | Only account-level API and transition throttles **(verified)**. | service-quotas (above) |
| 6 | Worker model | Yes | Push to Lambda and 200+ services, or **pull** via **Activities** (`GetActivityTask` long poll). `HeartbeatSeconds` + `SendTaskHeartbeat`. **Task tokens fence stale workers**: a timed-out task gets a **new token**, so a late `SendTaskSuccess` with the old token is rejected **(verified)**. | https://docs.aws.amazon.com/step-functions/latest/dg/connect-to-resource.html |
| 7 | Retries / DLQ / redrive | Yes | `Retry` takes `ErrorEquals`, `IntervalSeconds`, `BackoffRate`, `MaxAttempts`, `MaxDelaySeconds` and `JitterStrategy`. `Catch` routes to fallback states. **Redrive** (`RedriveExecution`) restarts a failed Standard execution from the failed step within **14 days** **(verified)**. | 9 | Delayed / cron | Partial | **Wait** state (`Seconds`, `Timestamp`, `SecondsPath`) up to the 1-year execution limit. Cron uses EventBridge Scheduler to start executions. | https://docs.aws.amazon.com/step-functions/latest/dg/state-wait.html |
| 10 | Waits / human input | Yes | **`.waitForTaskToken`** pauses until `SendTaskSuccess` / `SendTaskFailure`, up to 1 year, with `HeartbeatSeconds` guarding against lost tokens **(verified)**. Tokens must be sent from the same account. `.sync` waits for a job (Batch, ECS, a nested SFN execution). Express supports only Request/Response. | https://docs.aws.amazon.com/step-functions/latest/dg/connect-to-resource.html |
| 11 | Dependencies | Partial | Parallel, Map, Choice, and nested executions (`states:startExecution.sync`). The DAG is **static in the definition**. Steps cannot be attached to a running execution, though Map iterates over dynamic input. | https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html |
| 12 | Cancellation | Yes | `StopExecution`. Cancelling `.sync` child tasks is **best effort** **(verified)**. | connect-to-resource (above) |
| 13 | Dedup / idempotency | Partial | The **execution name** is unique per account and region. A Standard `StartExecution` with the same name and input while the execution is open is idempotent. A name cannot be reused for 90 days. Express has no idempotency. No latest-wins. | https://docs.aws.amazon.com/step-functions/latest/apireference/API_StartExecution.html |
| 14 | Progress / metadata | Partial | Execution history events and current state in `DescribeExecution`. Variables. Map Run counters. There is no progress API. | — |
| 15 | Search / UI / retention | Partial | Console graph and event views. `ListExecutions` filters by state machine and status only, with no attribute search. **History limit 25,000 events** per execution (the execution fails when it is reached). **Retention 90 days** after close (reducible to 30). Express history only goes to CloudWatch Logs **(all verified)**. | https://docs.aws.amazon.com/step-functions/latest/dg/service-quotas.html |
| 16 | Events | Yes | EventBridge "Step Functions Execution Status Change" events, plus CloudWatch metrics. | https://docs.aws.amazon.com/step-functions/latest/dg/eventbridge-integration.html |
| 17 | Scale / limits | Yes | Payload **256 KiB** per state, input or output. Request 1 MB. Standard max 1 year, Express 5 min. StartExecution (Standard) bucket 1,300 refilling at 300/s in big regions. StateTransition 5,000/s (800/s in other regions). Open executions 1M. Names 80 characters **(all verified)**. | service-quotas (above) |
| 18 | Philosophy / pitfalls | n/a | A declarative orchestrator, not a queue. ## 6. Celery (brief)

Celery is a Python, broker-agnostic (RabbitMQ or Redis; SQS is experimental), BSD-licensed, free task framework. Features: `retry` / `autoretry_for` with backoff; `countdown` / `eta` scheduling; **celery beat** for cron; **canvas** primitives `chain`, `group`, `chord` that are static at creation; `soft_time_limit` / `time_limit`; `rate_limit` per task type **per worker**, not global; priorities on RabbitMQ (`x-max-priority`), only emulated on Redis; `revoke(terminate=True)` for cancellation, held in worker memory; `update_state` for progress; Flower for the UI. It has **no per-tenant fairness or limits**, no built-in dedup, and no DLQ (it relies on broker features). Well-known pitfalls:

- ETA tasks held in worker memory.
- Redis visibility-timeout redelivery of long ETA tasks.
- Prefetch hurting fairness (needs `-O fair` and `worker_prefetch_multiplier=1`).
- `acks_late` semantics.
- Chords on Redis being fragile.

Sources: https://docs.celeryq.dev/en/stable/userguide/tasks.html , https://docs.celeryq.dev/en/stable/userguide/canvas.html , https://docs.celeryq.dev/en/stable/userguide/optimizing.html

## Cross-system takeaways for the in-house engine

1. **Fairness** comes in two shapes:
   - **Round-robin across groups** (BullMQ Pro groups): strict rotation, combined with per-group concurrency and rate limits.
   - **In-flight-skew-aware reordering** (SQS fair queues): no limits, only dwell-time protection for quiet tenants, and noisy tenants can still use idle capacity.

   Everything else needs a queue per tenant (Cloud Tasks, Sidekiq), which runs into queue-count quotas.
2. **Per-tenant concurrency and rate as first-class settings** exist only in BullMQ Pro (paid; `setGroupConcurrency`, `group.limit`). Sidekiq Enterprise's keyed limiters are **post-fetch reject-and-reschedule**, not admission control.
3. **Leases and fencing**: SQS uses visibility timeouts plus receipt handles, BullMQ uses a lock token plus a stalled checker, Step Functions uses a task token that is regenerated on timeout (the strongest fencing). Sidekiq has no lease at all.
4. **Dependencies added later**: BullMQ allows them via `opts.parent` + `moveToWaitingChildren`. Sidekiq allows them only from inside a batch job. Step Functions and Celery canvas are static.
5. **Durable waits and human input**: only Step Functions (`waitForTaskToken`, up to 1 year, heartbeat-guarded) has them. The queues need delay-and-poll.
6. **Dedup windows**: SQS FIFO 5 min, Cloud Tasks names up to 24 h, Sidekiq Ent "best effort". Only BullMQ has **latest-wins** (debounce `replace`, `keepLastIfActive`).
7. **Retention**: SQS 14 days, Cloud Tasks 31 days, Step Functions history 90 days / 25k events, Redis-based systems unbounded but memory-bound with no indexed search.
