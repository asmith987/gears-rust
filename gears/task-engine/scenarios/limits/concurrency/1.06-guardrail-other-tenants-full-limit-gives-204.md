# A tenant worker never learns that another tenant is at its limit: `204`, not `429`

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-queue-concurrency` (PRD.md:429) · `cpt-cf-task-engine-fr-queue-depth` (PRD.md:455) · DESIGN.md:2451-2452, :2513 |
| Phase | p1 |
| Test level | E2E |

`429` means "an eligible task was skipped for capacity". Eligibility is decided by scoped reads: a tenant worker's candidate reads carry its PDP constraints and never visit other tenants' tasks (DESIGN.md:2451, :2513). So a full limit in tenant A is invisible to tenant B's worker, which gets a plain `204` when B has nothing to do. The answer reveals nothing about A.

## Setup
- **reports** (`per_tenant_concurrency_limit: 5`): `{tenant_a}` has 5 tasks `claimed` and 10 `queued`. `{tenant_b}` has nothing queued.

## Request (`T0`)
```http
POST /api/task_engine/v1/tasks/claim HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-b-token>
Content-Type: application/json

{ "worker_id": "reports-b-1", "session_id": null,
  "queues": ["gts.cf.core.tasks.queue.v1~acme.reports._.render.v1"], "max_tasks": 1, "timeout_secs": 2 }
```

## Expected response
- `204 No Content` at `T0+2s`; not `429`.

```http
HTTP/1.1 204 No Content
```
