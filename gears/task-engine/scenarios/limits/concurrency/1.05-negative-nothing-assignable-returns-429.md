# Nothing assignable because of a full limit → `429` (quota `concurrency`) with `Retry-After: 1`, at the end of the long-poll

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-queue-concurrency` (PRD.md:429, :1480) · DESIGN.md:1226, :2411-2419 · ADR-0005:71 · ADR-0008:78 |
| Phase | p1 |
| Test level | E2E |
| Gaps | G-CLM-09, G-CLM-10, G-SEC-03, G-WIRE-14 |

A claim that assigns nothing answers `429` only when at least one eligible task was skipped because a limit was full; the worker then backs off for `Retry-After` instead of hammering the queue. Contrast with [`204`](1.06-guardrail-other-tenants-full-limit-gives-204.md) when nothing was eligible. "A long-poll claim keeps waiting until its timeout before it returns either answer" (PRD.md:429): a worker blocked only by capacity is parked like an idle one and retried on `slotReleased` or the watcher tick; if no slot frees in time it gets `429` at the end, not at once.

## Setup
- **reports** (`per_tenant_concurrency_limit: 5`): `{tenant_a}` has 5 tasks `claimed` by `reports-7f9c-1` and 2 more `queued`. No other tenant has queued work. No slot is freed during the request.

## Request (`T0`) — representative case `timeout_secs: 0`
```http
POST /api/task_engine/v1/tasks/claim HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "worker_id": "reports-7f9c-2", "session_id": null,
  "queues": ["gts.cf.core.tasks.queue.v1~acme.reports._.render.v1"], "max_tasks": 1, "timeout_secs": 0 }
```

## Expected response
- `429 Too Many Requests`, `resource_exhausted`; one violation with `subject: "concurrency"`; no `context.reason`.
- `resource_type`/`resource_name` = the queue (G-CLM-10).
- `Retry-After: 1` (the claim poll interval rounded up, G-CLM-09); the violation's `retry_after_seconds` is the same value.
- The body shows no usage figure (no `used`, no limit value).

```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/problem+json
Retry-After: 1
```
```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.resource_exhausted.v1~",
  "title": "Resource Exhausted",
  "status": 429,
  "detail": "no task could be assigned: every eligible task is held back by a concurrency limit",
  "instance": "/api/task_engine/v1/tasks/claim",
  "trace_id": "<trace>",
  "context": { "resource_type": "gts.cf.core.tasks.queue.v1~",
               "resource_name": "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1",
               "violations": [ { "subject": "concurrency", "description": "a concurrency limit is full for every eligible task", "retry_after_seconds": 1 } ] }
}
```

## Notes
- `Retry-After` = `claim_poll_interval_ms` rounded up to seconds (1 s at defaults), also after a long-poll (G-CLM-09, G-SEC-03). The quota subject is `concurrency` without a dimension, and `resource_type`/`resource_name` name the queue (G-CLM-10, G-WIRE-14). A claim naming several queues carries the queue base type as `resource_type` and no `resource_name` (G-CLM-10, case `several queues`).
- During the long-poll wait the claim is retried each queue-watcher tick (a queue blocked only by capacity keeps matching the probe, DESIGN.md:958); each retry may count in `te_claim_capacity_skipped_total`, so tests do not assert its exact increase.
