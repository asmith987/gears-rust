# A concurrency slot is freed on every exit from `claimed`/`running`: release, park and completion

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-queue-concurrency` (PRD.md:427-429) · `cpt-cf-task-engine-fr-release` (PRD.md:687) · `cpt-cf-task-engine-fr-wait-conditions` (PRD.md:550, :1485) · DESIGN.md:532, :546, :952, :958, :1593, :2136, :2960 · ADR-0005:61 |
| Phase | p1 |
| Test level | Both — E2E for the release and park rows and the same-node "complete" row; Integration for the cross-node "complete" row (two nodes) |
| Gaps | G-CLM-23 |

Only `claimed` and `running` tasks count against concurrency limits (PRD.md:427), and slots are released on every exit from those states (ADR-0005:61), in the same transaction as the exit. A release "ends the lease, frees the task's concurrency slots, … and moves the task to `queued`" in one step (PRD.md:687); parking a running task releases its slots too (DESIGN.md:532, :1593), so a long wait never keeps other work of the tenant from running; a completion frees the slot and wakes a long-poll claim parked behind the full limit, through the local `slotReleased` signal or, across nodes, the queue watcher.

## Setup
- **reports** (`per_tenant_concurrency_limit: 5`): `reports-7f9c-1` holds 5 `running` tasks of `{tenant_a}`, `{task_1}` … `{task_5}` (tokens `{lt_1}` … `{lt_5}`; `{task_1}` created `T0`). `{task_6}` of `{tenant_a}` (created `T0+10s`) is `queued`. A claim now would get `429`.

## Exchange 1 — representative case: release without delay
```http
POST /api/task_engine/v1/tasks/{task_1}/release HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "lease_token": "{lt_1}" }
```
→ `200 OK`, `{task_1}` `queued`.

## Exchange 2 — claim
```http
POST /api/task_engine/v1/tasks/claim HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "worker_id": "reports-7f9c-2", "session_id": null,
  "queues": ["gts.cf.core.tasks.queue.v1~acme.reports._.render.v1"], "max_tasks": 1, "timeout_secs": 0 }
```

## Expected response
- Exchange 2: `200 OK` with one claim, for `{task_1}`: back in `queued`, it keeps its `created_at` and is older than `{task_6}`.

## Cases

| Case | Exchange 1 (frees the slot) | Exchange 2 (claim) | Expected | Side effects | Notes |
|---|---|---|---|---|---|
| release | as above | as above, sent after Exchange 1 | `200`, `{task_1}` | `queue_tenant(reports, {tenant_a}) used changes by -1` (release) then `+1` (claim); `{task_1}`.attempt is unchanged by the new claim ([attempt counting](../../worker/claim/1.05-positive-attempt-counting-across-claims.md)) | PRD.md:687, DESIGN.md:546 |
| park | `POST /tasks/{task_1}/wait-conditions` with `{ "lease_token": "{lt_1}", "mode": "all", "park": true, "conditions": [ { "kind": "timer", "resume_at": "2026-11-03T11:00:00Z" } ] }` → `200`, `task_state: waiting` | as above, sent after Exchange 1 | `200`, `{task_6}` | `queue_tenant(reports, {tenant_a}) used changes by -1` (park) then `+1` (claim); `queue_global(reports) used` likewise; task `{task_1}` state is `waiting`; lease `{lt_1}` is invalid (later calls get LEASE_LOST); when the timer fires `{task_1}` returns to `queued` and needs a free slot to be claimed again | PRD.md:550, :1485, DESIGN.md:532, :1593 |
| complete wakes a parked claim | at `T0'+3s`: `POST /tasks/{task_1}/complete` with `{ "lease_token": "{lt_1}", "result_code": "success", "output": {"url": "https://files.example.com/r-1.pdf"} }` → `200`, `{task_1}` `completed` | sent **before** Exchange 1, at `T0'`, with `"timeout_secs": 30`; no answer yet (every eligible task is skipped for capacity, so the claim parks) | `200` with one claim for `{task_6}`, sent shortly after `T0'+3s`: at once when both calls hit the same node; within one jittered poll interval plus `claim_saturation_ttl_ms` (≈ 1.45 s) when they hit different nodes. Not at `T0'+30s`, and not `429` | `queue_tenant(reports, {tenant_a}) used changes by -1` (complete) then `+1` (claim): it stays 5 and never reaches 6; task `{task_6}` state is `claimed` | DESIGN.md:952, :958, :2136, :2960; G-CLM-23 |

## Notes
- The cross-node bound of the "complete" row is decided (G-CLM-23): one jittered poll interval plus `claim_saturation_ttl_ms` (≈ 1.45 s at defaults). A watcher tick does not bypass the node's saturation cache (DESIGN.md:2136, cleared early only by a **local** `slotReleased`); config validation rejects `claim_saturation_ttl_ms ≥ 0.8 × claim_poll_interval_ms`, so an entry made at one tick has expired by the next.
