Three depth limits cap `queued` tasks, each checked against a sampled count:

- `tenant_max_queue_depth` caps one tenant's `queued` tasks in one queue, so a client that polls, times out and resubmits cannot grow the queue forever. Under the accepted change admission is refused while the latest per-tenant count, taken every `queue_depth.sample_secs`, is at or above the limit.
- `queue_max_queue_depth` caps all tenants' `queued` tasks in one queue, a sampled ceiling (DESIGN.md:1669). A tenant well under its own limit is still refused when the queue as a whole is full, and learns only that the `queue` limit is full, not who fills it.
- `global_max_queue_depth` caps the `queued` tasks of all queues in one task domain: the last line of defence (PRD.md:459). Also a sampled ceiling, it refuses creates into any queue of the domain, even a queue that is empty.

The maintenance leader takes every depth sample (queue, domain, per tenant) and the queue counts in one pass (G-CLM-13). Depth is checked after the dedup and idempotency lookup, inside the create transaction (G-CLM-24). The `429` names only the full dimension and shows no usage figures (PRD.md:455).

## Setup (representative case: `tenant`)
- Engine config: `queue_depth.overrides: [{ pattern: "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1", tenant_max_queue_depth: 3 }]`; `queue_depth.sample_secs: 5` (default).
- `{tenant_a}` has 3 `queued` tasks in **reports**, created at `T0`; no worker claims. The test waits until `GET /queues/{reports}` (as `{admin}`) shows a `sampled_at` later than the third create (G-CLM-13).

Authorization: Bearer <creator-a-token>

## Expected response
- `429 Too Many Requests`, `resource_exhausted`; one violation with `subject: "queue_depth.tenant"`; no `context.reason`; `resource_type`/`resource_name` = the queue (G-CLM-10).
- `Retry-After` is an integer in [15, 30] (`queue_depth.retry_after_secs` 30, jittered uniformly in [base/2, base], G-CLM-09); the violation's `retry_after_seconds` is the same value.
- No count or limit value appears in `detail` or `context`.

## Notes
- Nothing is stored, so the client may retry later with the same `Idempotency-Key`.
- The quota subject `queue_depth.<dimension>` carries code and dimension (G-CLM-10, G-WIRE-14); depth dimensions use the `429` names, never `queue_global`/`queue_tenant` (G-CLM-30).
- Tests wait until the queue's `sampled_at` is later than their setup; one leader pass takes the queue, domain and per-tenant samples, so that one timestamp covers all of them. `sampled_at` is shown only to callers holding queue `configure`, and per-tenant samples are never shown to tenants (G-CLM-13, G-OPS-02).
- `Retry-After: 22` is one draw from [15, 30]; tests assert the range (G-CLM-09, G-SEC-03).
- A supersession that ends an old task counted in the same dimension (same queue and tenant while `queued`) is not checked for that dimension (G-CRT-14); that rule lives in `tasks/supersede/`.
- A replay of an accepted create into a full queue gets `409`, never `429`; that rule lives in `tasks/idempotency/` ([replay not refused as full](../../tasks/idempotency/1.06-guardrail-replay-not-refused-as-full.md)). An admin re-enqueue into a full queue is refused like a create; that lives in `dead-letter/` ([re-enqueue refusals](../../dead-letter/1.04-negative-reenqueue-refusals.md), case "depth-full").
