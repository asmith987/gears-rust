# A worker that lost its lease cannot complete the task; the new holder's result is kept

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-lease-fencing` (PRD.md:724, :726) · `cpt-cf-task-engine-fr-execution-semantics` (PRD.md:737) · DESIGN.md:734, :1081, :1321-1324 · ADR-0011:61-63, :79 |
| Phase | p1 |
| Test level | Both — short heartbeat timeout |

The classic zombie: a worker stalls past its lease, the task is requeued and claimed by another process, then the stalled worker wakes up and reports its result. The fenced update `WHERE lease_token = ? AND assignee_subject = ? AND state IN (claimed, running)` matches nothing, so the zombie gets `LEASE_LOST` and the task is untouched. At most one completion is accepted per task.

## Setup
- `{task_1}`: **render** task of `{tenant_a}` on **reports**. At `T0` `reports-7f9c-1` claimed it (session `{session_1}`, lease `{lt_1}`, `lease_epoch: 1`, `attempt: 1`) and started it.
- The process paused at `T0+1s`; `{session_1}` expired at `T0+30s` and `{task_1}` went to `scheduled` (as in [Session expiry requeues tasks](../sessions/1.10-flow-session-expiry-requeues-tasks.md)).
- At `T0+36s` `reports-7f9c-2` (same subject `{worker_a}`) claimed it: session `{session_2}`, lease `{lt_2}`, `lease_epoch: 2`, `attempt: 2`, and started it.

## Exchange 1 — the zombie reports success
At `T0+40s`:
```http
POST /api/task_engine/v1/tasks/{task_1}/complete HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "lease_token": "{lt_1}", "result_code": "success", "output": {"url": "https://files.example.com/r-42-old.pdf"} }
```

- `409 Conflict`, `aborted`, `context.reason = "LEASE_LOST"`. The same subject sent it, so only the token tells the leases apart (ADR-0011:41).

```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.aborted.v1~",
  "title": "Aborted",
  "status": 409,
  "detail": "the lease on this task is no longer held",
  "instance": "/api/task_engine/v1/tasks/{task_1}/complete",
  "trace_id": "<trace>",
  "context": { "reason": "LEASE_LOST" }
}
```

## Exchange 2 — the new holder completes
At `T0+50s`:
```http
POST /api/task_engine/v1/tasks/{task_1}/complete HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "lease_token": "{lt_2}", "result_code": "success", "output": {"url": "https://files.example.com/r-42.pdf"} }
```

- `200 OK`, task `completed`, `result.output.url` is `https://files.example.com/r-42.pdf`, `attempt: 2`.

## Side effects
- After exchange 1: nothing changes; no history row, no outbox row (DESIGN.md:734); metric `te_lease_fencing_rejections_total{op="complete"}` increases by 1.
- After exchange 2: task `{task_1}` state is `completed`; task `{task_1}` result_code is `success`; history of `{task_1}` gains `taskCompleted` with `attempt: 2`, `actor: {worker_a}`.
- subsequent `POST /tasks/{task_1}/complete` with `{lt_1}` returns `409` `LEASE_LOST` (a lost token never becomes valid again, PRD.md:726).

## Notes
- The same refusal for every other worker call with the stale token (checkpoint, progress, start, release, entries) is in [Failed fence returns LEASE_LOST](1.04-negative-failed-fence-returns-lease-lost.md).
