# Every lease-fenced worker call that fails the fence gets LEASE_LOST and writes nothing

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-lease-fencing` (PRD.md:726: "A copied token is useless to anyone else", "worker entries … MUST carry the token and come from that subject") · `cpt-cf-task-engine-fr-task-checkpoint` (PRD.md:383) · `cpt-cf-task-engine-fr-progress` (PRD.md:753) · `cpt-cf-task-engine-fr-release` (PRD.md:689: "A release with a stale token returns `LEASE_LOST`") · `cpt-cf-task-engine-fr-heartbeat` (PRD.md:676: "When a session expires, all of its leases expire together") · DESIGN.md:732, :734, :936, :1081, :1311-1314, :1324, :2682-2695, :2699, :2750-2760 · ADR-0011:31, :61-62, :73, :79, :80 · ADR-0017:59, :80 |
| Phase | p1 |
| Test level | Both — expiry rows integration |
| Gaps | G-EXE-02, G-EXE-08, G-EXE-09, G-EXE-10, G-EXE-12 |

Every worker write (`start`, `progress`, `checkpoint`, `complete`, `release`, worker `entries`) carries `lease_token` and is fenced by `WHERE task_id = ? AND lease_token = ? AND assignee_subject = ? AND state_code IN (claimed, running)` (DESIGN.md:734). A stale token, a live token sent by another subject, a subject of another tenant, an unknown task ID, and a token whose tasks were requeued after session expiry all get the same answer: `409` `aborted`, `context.reason = "LEASE_LOST"`, and nothing is written. Worker calls never answer `404` (G-EXE-09). On a fence miss one unscoped read of the fence columns decides: only when holder and token both match but the scope no longer covers the task is the answer `403 CLAIM_REVOKED` instead ([Worker write authorization outcomes](1.08-guardrail-worker-write-authorization-outcomes.md), G-EXE-08). Token mismatch and holder mismatch are indistinguishable (ADR-0011:62). The lease check also wins the classification over a concurrent payload change, because `CONCURRENT_MODIFICATION` is retryable and `LEASE_LOST` is final (DESIGN.md:2699). The batch heartbeat reports the same loss per lease instead: see [Heartbeat lease_lost cases](../sessions/1.04-guardrail-heartbeat-lease-lost-cases.md).

## Setup
- As in [Zombie complete after reclaim](1.09-flow-zombie-complete-after-reclaim.md), up to the new claim: `reports-7f9c-1`'s session expired, and `{task_1}` is `running` under `reports-7f9c-2` (same subject `{worker_a}`) with `{lt_2}`. The zombie `reports-7f9c-1` still holds `{lt_1}`.
- `{task_1}`'s `context` is `{ "page": 12 }` and its saved `progress` is `{ "percent": 10 }`, both written by the new holder.

## Request
Representative case (**checkpoint**):
```http
POST /api/task_engine/v1/tasks/{task_1}/checkpoint HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "lease_token": "{lt_1}", "checkpoint": { "page": 3 } }
```

## Expected response
- `409 Conflict`, `aborted`, `context.reason = "LEASE_LOST"`. Every row returns this body, with `instance` set to the row's path.

```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.aborted.v1~",
  "title": "Aborted",
  "status": 409,
  "detail": "the lease on this task is no longer held",
  "instance": "/api/task_engine/v1/tasks/{task_1}/checkpoint",
  "trace_id": "<trace>",
  "context": { "reason": "LEASE_LOST" }
}
```

## Side effects
<!-- No side effects: the fenced write matches no row and rolls back. -->
- task `{task_1}` is unchanged in every row: `running` under `{lt_2}`, `context` `{ "page": 12 }`, `revision` unchanged.
- metric `te_lease_fencing_rejections_total{op="<call>"}` increases by 1.
