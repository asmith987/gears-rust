# A worker write re-checks claim: a revoked or narrowed grant releases the task with 403 CLAIM_REVOKED, an unreachable PDP fails closed with 503

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-worker-principals` (PRD.md:961) · `cpt-cf-task-engine-fr-resource-path-access` (PRD.md:943) · `cpt-cf-task-engine-fr-authz` (PRD.md:918) · DESIGN.md:546, :936, :1022 (replaced for scope exclusion), :1195-1236, :1218, :2676, :2691 · ADR-0016:81, :102 |
| Phase | p1 |
| Test level | Integration — grant revocation, PDP outage |
| Depends on | Proposals › Heartbeats and leases › Revocation releases the task however it arrives |
| Gaps | G-EXE-06, G-EXE-08, G-SEC-01, G-SEC-03 |

"Loss of access stops work": every worker write (start, progress, checkpoint, complete, release, waits, entries) checks `claim` again. Every worker call has one failure path (G-EXE-08): on a scoped miss, one unscoped read of the fence columns decides. Holder and token match but the scope (an explicit denial, or constraints that no longer cover the task) excludes it → the engine returns the task to the queue as a voluntary release — no budget, attempt or blacklist change — and answers `403` `CLAIM_REVOKED`; the worker must stop. Anything else is `409 LEASE_LOST` ([1.04](1.04-negative-failed-fence-returns-lease-lost.md)). When the PDP cannot be reached at all, authorization fails closed with `503` without releasing anything (G-SEC-01). Heartbeats do not call the PDP ([Heartbeat during a PDP outage](../sessions/1.06-guardrail-heartbeat-works-during-pdp-outage.md)).

## Setup
- `{task_1}` (`running`) on **reports**, held by `reports-7f9c-1` with `{lt_1}`; `attempt: 1`, `retry_count: 0`, `liveness_requeues: 0`; `context` is `{ "page": 4 }`.
- Representative case (**claim revoked**): at `T0+20s` the operator removes `{worker_a}`'s `claim` grant on **render**; the PDP now denies `claim` on `{task_1}` (but still allows `read`).

## Request
At `T0+25s`:
```http
POST /api/task_engine/v1/tasks/{task_1}/checkpoint HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "lease_token": "{lt_1}", "checkpoint": { "page": 5 } }
```

## Expected response
- `403 Forbidden`, `permission_denied`, `context.reason = "CLAIM_REVOKED"`.

```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.permission_denied.v1~",
  "title": "Permission Denied",
  "status": 403,
  "detail": "the caller may no longer work on this task; it was returned to the queue",
  "instance": "/api/task_engine/v1/tasks/{task_1}/checkpoint",
  "trace_id": "<trace>",
  "context": { "reason": "CLAIM_REVOKED", "resource_type": "gts.cf.core.tasks.task.v1~acme.reports._.render.v1~", "resource_name": "{task_1}" }
}
```

## Side effects
For the releasing (`403`) rows:
- task `{task_1}` state is `queued`; `attempt`, `retry_count` and `liveness_requeues` are unchanged; `resume_pending` is set, so the next claim keeps `attempt: 1` (DESIGN.md:546).
- task `{task_1}`.context is `{ "page": 4 }` (the refused write is not applied).
- lease `{lt_1}` is invalid (later calls get LEASE_LOST).
- `queue_global(reports)` used changes by `-1`; `queue_tenant(reports, tenant_a)` used changes by `-1`.
- timer `execution` for `{task_1}` is removed; timer `queue_timeout` for `{task_1}` is armed at `T0+25s+3600s`.
- history of `{task_1}` gains `taskQueued` with `reason: revoked` and no `actor` (G-EXE-08).
- No liveness failure or blacklist strike is recorded.
