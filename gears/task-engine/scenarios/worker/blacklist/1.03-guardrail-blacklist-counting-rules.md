# What counts toward the blacklist counter, and what does not

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-worker-blacklist` (PRD.md:701, :702, :703) · PRD.md:519, :676, :689, :1479, :1486, :1517 · DESIGN.md:534, :542, :761, :2770-2773, :2806-2814 · ADR-0017:68 |
| Phase | p3 |
| Test level | Integration — p3; counters, durations |
| Gaps | G-EXE-05, G-EXE-10, G-OPS-26 |

The blacklist counts **consecutive** worker-attributed failures per (subject, `worker_id`, queue). Bad input, a broken downstream service or a task that runs too long must never blacklist a healthy worker, and must not wipe out the strikes it already earned. One outage counts once per queue, however many leases it drops. One success on the same queue resets the count; a success on another queue does not.

## Setup
- `te_worker_blacklist({worker_a}, reports-7f9c-1, reports)`: `consecutive_failures = 6`.
- `reports-7f9c-1` runs ten tasks on **reports**; each completes with an error: five with `fault: task` (`code: INVALID_REPORT`, non-retryable), five with `fault: dependency` (`code: RENDER_TIMEOUT`, retryable).

## Request
One of the ten:
```http
POST /api/task_engine/v1/tasks/{task_1}/complete HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{
  "lease_token": "{lt_1}",
  "result_code": "error",
  "error": {
    "domain": "acme.reports",
    "code": "RENDER_TIMEOUT",
    "message": "renderer timed out",
    "fault": "dependency",
    "retryable": true
  }
}
```

## Expected response
- `200 OK`, task `scheduled` (retry). The `fault: task` ones end `dead_lettered` (`INVALID_REPORT` is in `non_retryable_codes`).

## Side effects
- Per row.

## Notes
- A `result_code: error` without `fault` is not covered by the docs; the `TaskError` contract may make `fault` required. Not asserted.
- If the requeue of a session's tasks spans more than one lease duration (very large sessions, `session_requeue_batch` = 500), a second strike is possible; DESIGN.md:2808 relies on the whole session being requeued within one lease window.
- A `warning` result is a success (DESIGN.md:534) and is assumed to reset too. Whether a success also clears `last_liveness_failure_at` is not said; it does not matter for the count.
