# A blacklisted worker's claim skips that queue only, for that (subject, `worker_id`) only

"Stop assigning tasks from a queue to a worker": the claim leaves the blacklisted queue out and answers as if it had nothing. The same process still gets work from queues where it is healthy. The blacklist is keyed by (`subject`, `worker_id`): replicas of one service share a principal, so one faulty replica must not get the whole fleet blacklisted; and `worker_id` is client-supplied and not a credential, so another principal reusing the name builds up its own blacklist state.

## Setup
- (`{worker_a}`, `reports-7f9c-1`) is blacklisted on **reports** until `T0+60m` ([1.01](1.01-positive-tenth-worker-failure-blacklists-worker.md)).
- **reports** has `{task_2}` (tenant A) `queued`; **bulk** has `{task_3}` `queued`.

## Request
```http
POST /api/task_engine/v1/tasks/claim HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "worker_id": "reports-7f9c-1", "session_id": "{session_1}",
  "queues": ["gts.cf.core.tasks.queue.v1~acme.reports._.render.v1"], "max_tasks": 1, "timeout_secs": 0 }
```

## Expected response
- `204 No Content`. No session is touched or returned (G-CLM-16).

## Cases

## Side effects
- Per row. The representative claims nothing.

## Notes
- Blacklisted queues are skipped silently; `204` when nothing else has work (G-OPS-30). DESIGN's error-table row "Worker blacklisted for the queue" → `400` (DESIGN.md:1235) is removed by that decision; there is no `400` case.
- A long-poll claim from a blacklisted worker waits for its timeout before `204`, like any claim with nothing eligible.
- A process that changes its `worker_id` on restart escapes its blacklist history; accepted by ADR-0014:64.
- `workerBlacklisted` is attributed to the worker's tenant (`te_events.owner_tenant_id`, DESIGN.md:1833), so tenant A does not see B's event.
