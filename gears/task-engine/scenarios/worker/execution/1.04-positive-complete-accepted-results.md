# A valid terminal completion ends the task, stores its result and frees its slots

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-structured-io` (PRD.md:269: "validated against the task type's schemas") · `cpt-cf-task-engine-fr-state-result-enums` (PRD.md:1030-1039) · `cpt-cf-task-engine-fr-task-cancel` (PRD.md:346) · `cpt-cf-task-engine-fr-worker-blacklist` (PRD.md:703) · DESIGN.md:534, :535, :551, :576, :736-738, :1047, :1316-1319, :2255, :2919-2960, :2949 |

The holder reports a terminal result: `success` or `warning` with an output that matches the output schema of the type revision the task was created with, or `cancelled` after a cancel was requested. The engine validates the result, then in one transaction runs `finalize()`: frees the slots, moves the task to its terminal state, keeps the token for replay, and records the terminal event. "The task succeeded" means `completed` with `success` or `warning` (PRD.md:1039).

## Setup
- `{task_1}` (`running`) on **reports**, held by `reports-7f9c-1` in session `{session_1}` with `{lt_1}`, `attempt: 1`, started at `T0+2s`. **render** output schema: `{ "url": string }` (required).

## Request
Representative case (**success**), at `T0+40s`:
```http
POST /api/task_engine/v1/tasks/{task_1}/complete HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "lease_token": "{lt_1}", "result_code": "success", "output": {"url": "https://files.example.com/r-42.pdf"} }
```

## Expected response
- `200 OK`, the terminal task.

```json
{
  "id": "{task_1}",
  "state": "completed",
  "attempt": 1,
  "result": { "result_code": "success", "output": { "url": "https://files.example.com/r-42.pdf" }, "error": null, "warnings": [] },
  "terminal_at": "2026-11-03T10:00:40Z",
  "…": "other fields as in CONVENTIONS §5.1"
}
```

## Side effects
Shared by every row:
- `queue_global(reports)` used changes by `-1`; `queue_tenant(reports, tenant_a)` used changes by `-1`.
- timer `execution` for `{task_1}` is removed; timer `lifetime` for `{task_1}` is removed.
- `te_task_state({task_1})` is absent; `te_task_results({task_1})` is present, with `lease_token` kept (DESIGN.md:576, :2949).
- subsequent `POST /tasks/{task_1}/checkpoint` with `{lt_1}` returns `409` `LEASE_LOST`; a repeat of the same completion is a replay ([Idempotent completion replay](../fencing/1.02-positive-idempotent-completion-replay.md)).

Representative only:
- task `{task_1}` state is `completed`; task `{task_1}` result_code is `success`.
- history of `{task_1}` gains `taskCompleted` with `result_code: success`, `attempt: 1`, `actor: {worker_a}`.
- event taskCompleted for `{task_1}` is published to the task-events topic (in the `lifecycle` preset).
- metric `te_tasks_completed_total{queue="…render.v1", result_code="success"}` increases by 1.
