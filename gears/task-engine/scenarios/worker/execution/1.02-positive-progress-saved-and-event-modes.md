# Progress is buffered, saved within one flush interval, and produces events only as its event mode allows

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-progress` (PRD.md:753) · `cpt-cf-task-engine-fr-progress-events` (PRD.md:762-770) · `cpt-cf-task-engine-fr-event-history` (PRD.md:868: "enabled progress events") · DESIGN.md:931-943, :1314, :2067-2068, :2699 · `schemas/types/…task_progressed.v1~` (progress object) · `schemas/types/gts.cf.core.tasks.task.v1~` (`progress_events`) |
| Phase | p1 (progress saved) · p2 (event modes) |
| Test level | Both — flush interval + event modes |
| Gaps | G-WIRE-06, G-EXE-08 |

A worker reports percent, milestone, completed/total units, current stage and ETA. The engine checks the fence, buffers the latest value per task, and writes it at the next flush, so progress read through the API is at most one flush interval old (PRD.md:753). The progress event mode then decides which saved changes produce a `taskProgressed`: `none` (the default) never; `milestones` only when `milestone` or `current_stage` differs from the saved value; `all` on every saved change. At most one event per task per flush, and only together with the saved progress it describes.

## Setup
- `{task_1}` (`running`) on **reports**, held by `reports-7f9c-1` with `{lt_1}`; `progress` is `null`.
- Representative case (**mode none, all dimensions**): flush interval 5 s (global default `progress_flush_interval_secs: 5`; no type, queue or config override); progress event mode `none` (default).

## Request
At `T0+10s`:
```http
POST /api/task_engine/v1/tasks/{task_1}/progress HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{
  "lease_token": "{lt_1}",
  "percent": 45,
  "milestone": "pages_rendered",
  "completed_units": 45,
  "total_units": 100,
  "current_stage": "render",
  "eta": "2026-11-03T10:05:00Z"
}
```

## Expected response
- `200 OK`, empty body (the update is buffered until the next flush). Every row gets the same.

## Side effects
- By `T0+15s` (one flush interval), `GET /tasks/{task_1}` returns:

```json
{
  "id": "{task_1}",
  "progress": { "percent": 45, "milestone": "pages_rendered", "completed_units": 45, "total_units": 100, "current_stage": "render", "eta": "2026-11-03T10:05:00Z" },
  "…": "other fields as in CONVENTIONS §5.1"
}
```
- Two updates sent within one flush interval are merged: only the latest is saved (DESIGN.md:937).
- No `te_task_state.revision` bump (progress is not a payload write, DESIGN.md:2699).
- history of `{task_1}` gains no `taskProgressed` (mode `none`).
- On graceful shutdown of the node the buffer is flushed before connections close (PRD.md:1316); on a crash it is lost (DESIGN.md:942).

## Notes
- `200` with an empty body follows the sequence diagram (DESIGN.md:1314) and the wire review (G-WIRE-06).
- A stale token is refused with `409 LEASE_LOST` before buffering, and a holder whose scope no longer covers the task gets `403 CLAIM_REVOKED` (G-EXE-08; [Failed fence returns LEASE_LOST](../fencing/1.04-negative-failed-fence-returns-lease-lost.md)); a lease lost after acceptance drops the buffered snapshot ([Buffered progress dropped](../fencing/1.05-guardrail-buffered-progress-dropped-after-lease-loss.md)).
