# A checkpoint is merged into the task context as a JSON Merge Patch

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-task-checkpoint` (PRD.md:383) · DESIGN.md:724, :739, :2669-2697 · `schemas/types/gts.cf.core.tasks.task.v1~` (`context`) |
| Phase | p1 (G-EXE-12) |
| Test level | E2E |
| Gaps | G-EXE-12, G-EXE-13, G-WAI-15 |

A checkpoint saves resume data. It is applied to `context` as an RFC 7386 JSON Merge Patch (G-EXE-13): keys it names replace the same keys, keys it does not name are kept, nested objects merge recursively, `null` deletes a key, and arrays are replaced whole. The write is a revision-guarded payload write, the 64 KiB aggregate limit applies to the merged result, and it records `taskCheckpointed`.

## Setup
- `{task_1}` (`running`) on **reports**, held by `reports-7f9c-1` with `{lt_1}`.
- `context` is `{ "page": 3, "cursor": "c-17", "fonts": ["serif"], "stats": { "rows": 300, "errors": 1 } }` (created with it); `revision` is 1.

## Request
```http
POST /api/task_engine/v1/tasks/{task_1}/checkpoint HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "lease_token": "{lt_1}", "checkpoint": { "page": 4, "rows_done": 400 } }
```

## Expected response
- `200 OK` with the merged context.

```json
{ "context": { "page": 4, "cursor": "c-17", "fonts": ["serif"], "stats": { "rows": 300, "errors": 1 }, "rows_done": 400 } }
```

## Cases

| Case | `checkpoint` sent | Merged `context` | Notes |
|---|---|---|---|
| replace and add top-level keys | (representative) | as above | |
| `null` deletes a key | `{ "cursor": null }` | `{ "page": 3, "fonts": ["serif"], "stats": { "rows": 300, "errors": 1 } }` (no `cursor`) | RFC 7386 |
| nested object merges | `{ "stats": { "rows": 400 } }` | `stats` is `{ "rows": 400, "errors": 1 }`; other keys unchanged | |
| array replaced whole | `{ "fonts": ["sans"] }` | `fonts` is `["sans"]` | |

## Side effects
- task `{task_1}`.context is the row's merged context; `revision` advances from `1` to `2`.
- history of `{task_1}` gains `taskCheckpointed` with `attempt: 1`, `actor: {worker_a}`; the payload carries no context data (schema has only `task_id`, `queue`, `actor`, `attempt`).
- event taskCheckpointed for `{task_1}` is not published under the default `lifecycle` preset (PRD.md:898).
- The idempotency fingerprint of the create request is not affected (it is stored, not recomputed, DESIGN.md:718).

## Notes
- PRD's "key by key" (PRD.md:383) is made precise as RFC 7386 (G-EXE-13). Every call that carries a checkpoint (release, set-wait, park) merges the same way and records `taskCheckpointed` (G-WAI-15).
- The checkpoint FR moves from p3 to p1 because release and waits already carry a checkpoint in p1 (G-EXE-12).
