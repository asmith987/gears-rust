# A completion whose result breaks the result rules is refused; the task and lease are unchanged

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-structured-io` (PRD.md:269: "validated against the task type's schemas", `fault` default `task`) · `cpt-cf-task-engine-fr-state-result-enums` (PRD.md:1039: "`cancelled` (the last only after a cancel request)") · DESIGN.md:737 (rules 2 and 3), :1211, :2677-2678 |
| Phase | p1 |
| Test level | E2E |
| Gaps | G-CRT-07, G-EXE-08, G-EXE-17, G-SEC-21 |

Completion results are validated before the fenced write (DESIGN.md:2677-2678): the `output` against the type's output schema, `error` and each `warnings` item against the fixed SDK `TaskError` contract (`domain`, `code`, `message` required; `retryable` boolean; `fault` one of `task`, `dependency`, `worker`; `context` a JSON object), the result code against what a worker may report (`success`, `warning`, `error`, or `cancelled` only after a cancel request), and the code against the presence of `error` (DESIGN.md:737, rule 3). A violation is `400` `invalid_argument` with one field violation per broken rule; the task stays `running` and the lease stays valid, so the worker can send a corrected result or report a failure. When validation fails, one read of the fence columns decides first: a caller that is not the current holder gets `409 LEASE_LOST` instead (G-EXE-17).

## Setup
- `{task_1}` (`running`) on **reports**, held by `reports-7f9c-1` with `{lt_1}`; `cancel_requested: false`; `retry_count: 0`. **render** output schema: `{ "url": string }` (required).

## Request
Representative case (**output fails the output schema**):
```http
POST /api/task_engine/v1/tasks/{task_1}/complete HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "lease_token": "{lt_1}", "result_code": "success", "output": {"link": "https://files.example.com/r-42.pdf"} }
```

## Expected response
- `400 Bad Request`, `invalid_argument`, field violation on `/output/url` with reason `SCHEMA_VIOLATION`; the description names the failed keyword, never the value (G-SEC-21).

```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.invalid_argument.v1~",
  "title": "Invalid Argument",
  "status": 400,
  "detail": "the result does not match the task type's output schema",
  "instance": "/api/task_engine/v1/tasks/{task_1}/complete",
  "trace_id": "<trace>",
  "context": { "field_violations": [ { "field": "/output/url", "description": "failed keyword: required", "reason": "SCHEMA_VIOLATION" } ] }
}
```

## Side effects
<!-- No side effects: validation fails before the fenced write. -->
- In every row except "zombie with an invalid result": task `{task_1}` state is `running`; lease `{lt_1}` stays valid; `retry_count` unchanged; no counter changes.
- subsequent `complete` with `"output": { "url": "https://files.example.com/r-42.pdf" }` returns `200`.

## Notes
- Validation still runs before the fenced write (DESIGN.md:2677-2678); on a validation failure one PK read of the fence columns decides, so a zombie is told `LEASE_LOST`, never asked to resend a corrected result (G-EXE-17).
- The `reason` values come from the documented set (CONVENTIONS §6, G-CRT-07); a user-schema failure is always `SCHEMA_VIOLATION` (G-SEC-21).
