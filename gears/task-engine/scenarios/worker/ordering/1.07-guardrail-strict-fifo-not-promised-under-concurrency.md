# Under concurrent claims order is best effort: tests must not assert strict FIFO

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-assignment` (PRD.md:653) · `cpt-cf-task-engine-fr-tenant-fairness` (PRD.md:411) |
| Phase | p1 |
| Test level | Integration — needs deterministic queue contents; shared e2e queues interfere |
| Depends on | Proposals › Claiming and ordering (accepted: strict FIFO not promised; SKIP LOCKED when taking tasks) — replaces "exact order among claimable rows", DESIGN.md:2506, ADR-0008:46, :126 |
| Gaps | G-CLM-07, G-CLM-08 |

A guardrail on the tests themselves. Even on a `fifo` queue with a concurrency limit of 1, `SKIP LOCKED` and retry backoff can let a later task go first (Proposals › Claiming and ordering, Unchanged). What holds is that no task is given twice and that each claim gets a task no other claim holds; which of several racing claims gets the head task, and in what order the batch is served, is not promised.

## Setup
- **bulk** (`fifo`) holds `{task_1}` … `{task_4}` of `{tenant_a}`, priority 100, created `T0` … `T0+3s`.
- Four worker processes of `{worker_a}` send one claim each at the same moment, `max_tasks: 1`, `timeout_secs: 5`.

## Request (×4, `worker_id` `reports-7f9c-1` … `reports-7f9c-4`)
```http
POST /api/task_engine/v1/tasks/claim HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "worker_id": "reports-7f9c-1", "session_id": null,
  "queues": ["gts.cf.core.tasks.queue.v1~acme.reports._.bulk.v1"], "max_tasks": 1, "timeout_secs": 5 }
```

## Expected response
- Four `200 OK` answers; the four task IDs are pairwise different and together are `{task_1 … task_4}`.

## Must NOT be asserted
- That `claimed_at` (or response time) increases with `created_at`.
- That the worker whose request arrived first gets `{task_1}`.
- On a queue with `global_concurrency_limit: 1`: that tasks start in creation order across retries; a retried task re-enters after backoff (DESIGN.md:538) and later tasks can overtake it.

## Side effects
- tasks `{task_1}` … `{task_4}` state is `claimed`, each with a different `assignment.worker_id`.

## Notes
- Order assertions belong in sequential, single-claimer tests with no limit reached and no concurrent writes ([1.04](1.04-positive-fifo-queue-orders-by-priority-age-id.md)): only there is the queue's documented order exact. Under concurrent claims it is best effort: a task may go ahead of a better one only while another transaction holds the better one (G-CLM-08).
