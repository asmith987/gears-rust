# Across named queues, `critical` tasks go first, oldest first, from any queue

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-assignment` (PRD.md:657) · `cpt-cf-task-engine-fr-priority-dispatch` (PRD.md:396) · DESIGN.md:1525 |
| Phase | p1 |
| Test level | Integration — needs deterministic queue contents; shared e2e queues interfere |
| Depends on | Proposals › Claiming and ordering › Claims across queues (accepted: critical first) — replaces PRD.md:657, DESIGN.md:2460, ADR-0008:71 |
| Gaps | G-CLM-01, G-CLM-02, G-CLM-03, G-CLM-04 |

A claim that names several queues first asks each of them for its next queued `critical` task, in that queue's own order, and takes the oldest offer by `(created_at, task_id)` (G-CLM-02); only then does it rotate between queues for `normal` work (Proposals › Claiming and ordering). A `critical` task therefore never waits behind `normal` work of another named queue, and between two `critical` tasks of different queues the older one wins.

## Setup
- PDP grants `{creator_a}` `expedite` for this scenario. All tasks are `{tenant_a}`, `queued`:
  - **bulk**: `{task_0}` `normal`, created `T0-60s`; `{task_2}` `critical`, created `T0+2s`;
  - **reports**: `{task_1}` `normal`, created `T0`; `{task_3}` `critical`, created `T0+3s`.
- One engine node; `{worker_a}` claims sequentially. Clock `T0+10s`.

## Exchange 1
```http
POST /api/task_engine/v1/tasks/claim HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "worker_id": "reports-7f9c-1", "session_id": null,
  "queues": ["gts.cf.core.tasks.queue.v1~acme.reports._.render.v1",
             "gts.cf.core.tasks.queue.v1~acme.reports._.bulk.v1"],
  "max_tasks": 1, "timeout_secs": 0 }
```
- `200 OK`, one claim for `{task_2}` (oldest `critical` across both queues, though it is in the second-listed queue and `{task_0}` is older).

## Exchange 2 — same request with `session_id: "{session_1}"`
- `200 OK`, one claim for `{task_3}` (the remaining `critical` task).

## Exchange 3 — same request
- `200 OK`, one claim for `{task_0}` or `{task_1}` (normal work by queue rotation, [1.10](1.10-flow-rotation-between-queues-for-normal-work.md)); which one depends on the rotation cursor and is not asserted.

## Exchange 4 (variant) — from the Setup state, one claim with `max_tasks: 3`
- `200 OK` with three claims: `{task_2}` and `{task_3}`, then one of `{task_0}` / `{task_1}` by rotation, in one transaction (G-CLM-03). Which `normal` task is not asserted.

## Side effects
- tasks `{task_2}`, `{task_3}` state is `claimed` before any `normal` task of either queue.

## Notes
- Each queue offers its next `critical` task in its own order (`round_robin`: the tenant turn; `fifo`: priority, then age); the read on `ix_te_task_state_queue_dispatch` only tells whether a queue has any. Across queues the oldest offer wins (G-CLM-02). With one `critical` task per queue, as here, the offer is that task.
- A batch takes every `critical` task it can within its scan budget, then fills the rest by rotation in the same plan; the rotation start advances on every claim round, `critical`-only rounds included (G-CLM-03, G-CLM-04).
- DESIGN.md:2460 and ADR-0008:71, :139 still describe the replaced k-way merge (G-CLM-01).
