# For `normal` work a claim rotates between its queues, starting after the previous claim's start queue

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-assignment` (PRD.md:653, :657) |
| Phase | p1 |
| Test level | Integration — needs deterministic queue contents; shared e2e queues interfere |
| Depends on | Proposals › Claiming and ordering › Claims across queues (accepted: then rotation) — replaces PRD.md:657, DESIGN.md:2460, :2506 |
| Gaps | G-CLM-01, G-CLM-04, G-CLM-05 |

Without `critical` work, a claim starts at the queue after the one the previous claim (of the same waiter group, on the same node) started at, takes tasks in that queue's own order, and moves on to the next queue only while its batch is not full. One queue's old backlog therefore cannot take every claim (Proposals › Claiming and ordering, Why).

## Setup
- All tasks `{tenant_a}`, `normal`, priority 100, `queued`:
  - **reports**: `{r1}` (`T0`), `{r2}` (`T0+1s`);
  - **bulk**: `{b1}` … `{b4}` (`T0+10s` … `T0+13s`).
- **One engine node**; one worker process of `{worker_a}` sends every claim, one after the other, with the same queue list. Clock `T0+20s`.

## Exchanges 1–4 — four claims with `max_tasks: 1`
```http
POST /api/task_engine/v1/tasks/claim HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "worker_id": "reports-7f9c-1", "session_id": "{session_1}",
  "queues": ["gts.cf.core.tasks.queue.v1~acme.reports._.render.v1",
             "gts.cf.core.tasks.queue.v1~acme.reports._.bulk.v1"],
  "max_tasks": 1, "timeout_secs": 0 }
```
- Each `200 OK` with one claim. The four results alternate queues: claims 1 and 3 come from one queue, claims 2 and 4 from the other.
- Inside each queue, its own order holds: `{r1}` before `{r2}`, `{b1}` before `{b2}`.
- Together the four claims are `{r1, r2, b1, b2}`, although `{r1}` and `{r2}` are older than every `bulk` task.

## Exchange 5 — the same claim with `max_tasks: 3`
- **reports** is now empty. `200 OK` with two claims, `{b3}` and `{b4}`: the claim moves on from the empty start queue, and returns fewer than `max_tasks` without waiting.

## Side effects
- tasks `{r1}`, `{r2}`, `{b1}` … `{b4}` state is `claimed`.

## Notes
- **How to test rotation.** The cursor is node memory per waiter group (Proposals › Claiming and ordering; waiter group = domain, subject, compiled scope, sorted queue set, DESIGN.md:2409). Pin the test to one node and one subject and assert alternation, not which queue comes first: the rotation order is the queue set sorted by queue GTS ID, a new waiter group starts at a random position, and every claim round (including `204`/`429` rounds and `critical`-only rounds) advances the start by one (G-CLM-04). Per node, each of n queues starts one round in every n; across nodes, assert only that every queue with ready work is served at some point (G-CLM-05).
- A claim that sees no `critical` task and rotates is the only case shown; `critical` work goes first ([1.09](1.09-flow-critical-first-across-queues-oldest-first.md)).
