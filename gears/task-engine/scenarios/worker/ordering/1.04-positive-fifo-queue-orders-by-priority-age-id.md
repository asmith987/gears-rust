# A `fifo` queue serves all tenants in one order: priority, then age, then task ID

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-tenant-fairness` (PRD.md:411) · `cpt-cf-task-engine-fr-priority-dispatch` (PRD.md:394-399) · DESIGN.md:1525, :2439-2444 |
| Phase | p1 |
| Test level | Integration — needs deterministic queue contents; shared e2e queues interfere |
| Gaps | G-CLM-08, G-CLM-27, G-CLM-29 |

In `fifo` mode there is no tenant turn: every tenant's tasks are in one order by urgency, priority, age and task ID (DESIGN.md:2441). Here priority does rank tenants, which is why `fifo` is meant only for single-tenant or trusted queues (PRD.md:411).

## Setup
- **bulk** (`fifo`) holds, all `queued`, `normal`:
  - `{task_1}` of `{tenant_a}`, priority 100, created `T0`;
  - `{task_2}` of `{tenant_b}`, priority 50, created `T0+1s`;
  - `{task_3}` of `{tenant_a}`, priority 50, created `T0+2s`.
- One worker, no other claimer. Clock `T0+5s`.

## Request (sent three times, one after the other)
```http
POST /api/task_engine/v1/tasks/claim HTTP/1.1
Host: api.example.com
Authorization: Bearer <platform-worker-token>
Content-Type: application/json

{ "worker_id": "platform-ops-1", "session_id": "{session_1}",
  "queues": ["gts.cf.core.tasks.queue.v1~acme.reports._.bulk.v1"], "max_tasks": 1, "timeout_secs": 0 }
```

## Expected response
- Claim 1 → `{task_2}` (priority 50, older of the two 50s); claim 2 → `{task_3}`; claim 3 → `{task_1}` (priority 100, oldest overall but lowest priority).
- Each is `200 OK` with one claim.

## Side effects
- tasks `{task_1}`, `{task_2}`, `{task_3}` state is `claimed`, in that claim order.

## Notes
- `{session_1}` is the session returned by claim 1 (claim 1 sends `null`).
- The task-ID tie-break applies to equal `created_at`; with UUID v7 IDs it matches creation order within a millisecond only approximately, so tests that need it create tasks with a forced equal `created_at` or skip it.
- PRD.md:411 defines `fifo` as "by priority, then age" without urgency; urgency still comes first (PRD.md:396, DESIGN.md:2441), see G-CLM-29. There is no priority aging (dropped, G-CLM-27).
- Order is exact here only because one worker claims sequentially, no limit is reached and nothing else writes the queue (G-CLM-08); see [1.07](1.07-guardrail-strict-fifo-not-promised-under-concurrency.md).
