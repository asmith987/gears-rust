# The order in which a claim lists its queues does not change what it gets

|---|---|
| Requirement | `cpt-cf-task-engine-fr-assignment` (PRD.md:657) · DESIGN.md:2409, :2520 · ADR-0008:126 |
| Phase | p1 |

"The order in which queues are listed does not matter" (PRD.md:657). A worker cannot make a queue win by listing it first: a `critical` task in the last-listed queue still goes before a newer `critical` task in the first-listed one (the oldest offer by `(created_at, task_id)` wins, G-CLM-02), and the listing does not change the waiter group, so it does not reset the rotation.

## Setup
- PDP grants `{creator_a}` `expedite`. All tasks `{tenant_a}`, `queued`:
  - **reports**: `{task_1}` `critical`, created `T0`;
  - **bulk**: `{task_2}` `critical`, created `T0+5s`.
- Clock `T0+10s`.

## Request — **bulk** listed first
```http
POST /api/task_engine/v1/tasks/claim HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "worker_id": "reports-7f9c-1", "session_id": null,
  "queues": ["gts.cf.core.tasks.queue.v1~acme.reports._.bulk.v1",
             "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1"],
  "max_tasks": 1, "timeout_secs": 0 }
```

## Expected response
- `200 OK`, one claim for `{task_1}` (the older `critical` task, in the second-listed queue).

## Side effects
- task `{task_1}` state is `claimed`; `{task_2}` stays `queued`.

## Notes
- For `normal` work, a claim listing `[bulk, reports]` and one listing `[reports, bulk]` from the same subject and node share one waiter group (sorted queue set, DESIGN.md:2409), so they continue one rotation. The rotation follows the queue set sorted by queue GTS ID, not the request order (G-CLM-04).
