# Only the named worker identity can accept a reassigned task, and gets a new lease

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-reassignment` (PRD.md:715) · PRD.md:1521 · DESIGN.md:548, :571, :1074, :1201 · ADR-0014 · ADR-0017:62 |
| Phase | p3 |
| Test level | E2E |
| Gaps | G-OPS-27, G-OPS-41, G-WIRE-21, G-EXE-11 |

The new holder calls accept with its own credentials and the `worker_id` the admin named. It gets a fresh lease token in its own session; the epoch set by the reassignment is kept. Any other identity (another process of the same principal, or another principal using the same `worker_id`) gets the same `404` as for a task with nothing to accept.

## Setup
- `{task_1}` was reassigned to (`{worker_a}`, `reports-7f9c-2`) at `T0`, `lease_epoch: 2`, `handoff_until = T0+30s` ([1.01](1.01-positive-admin-reassigns-running-task.md)), and not yet accepted.
- Process `reports-7f9c-2` runs session `{session_2}`.
- Clock `T0+5s`.

## Request
```http
POST /api/task_engine/v1/tasks/{task_1}/accept HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "worker_id": "reports-7f9c-2", "session_id": "{session_2}" }
```

## Expected response
- `200 OK` with the session, the task (still `running`), a new lease and the authority: the same shape as one claim entry plus its session (G-WIRE-21).

```json
{ "session_id": "{session_2}", "domain": "default", "heartbeat_interval_secs": 10,
  "task": { "id": "{task_1}", "state": "running", "attempt": 1, "…": "other fields as in CONVENTIONS §5.1" },
  "lease": { "lease_token": "{lt_2}", "lease_epoch": 2, "attempt": 1, "lease_secs": 30, "domain": "default" },
  "authority": { "mode": "creator_verified", "checked": [], "checked_at": "2026-11-03T09:55:00Z" } }
```

## Cases

| Case | Differs from the representative request | Expected | Notes |
|---|---|---|---|
| named identity | (representative) | `200` with a new lease; see Side effects | DESIGN.md:548 |
| same principal, other `worker_id` | body `{ "worker_id": "reports-7f9c-1" }` | `404 not_found`, body below; the guarded update matches no row and the hand-off stays open for `reports-7f9c-2` | PRD.md:1521 |
| other principal, same `worker_id` | `Authorization: Bearer <platform-worker-token>`, body `{ "worker_id": "reports-7f9c-2" }` | `404 not_found`, same body; hand-off stays open | ADR-0014 |

`404` body for the refused cases:

```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.not_found.v1~",
  "title": "Not Found",
  "status": 404,
  "detail": "Nothing to accept for task {task_1}",
  "instance": "/api/task_engine/v1/tasks/{task_1}/accept",
  "trace_id": "<trace>",
  "context": { "resource_type": "gts.cf.core.tasks.task.v1~", "resource_name": "{task_1}" }
}
```

## Side effects
- Named identity only:
  - task {task_1} lease_epoch is 2 (kept); `{lt_2}` is a new random token.
  - session {session_2} lease_until is extended to T0+35s; `{task_1}` now belongs to `{session_2}`.
  - `handoff_until` is cleared; the deadline scan no longer considers the hand-off.
  - the accept works like a claim for the new holder (G-OPS-27): `assignment.claimed_at` is `2026-11-03T10:00:05Z`; no assignment deadline, because the task is `running` (a task accepted while `claimed` gets one 60 s from the accept); timer execution for {task_1} is re-armed at `T0+905s` (the full 900 s from the accept); `attempt` stays `1`.
  - Concurrency counters are unchanged by the accept.
  - subsequent heartbeat of `{session_2}` with `{lt_2}` returns `ok`.
  - history of {task_1} gains taskClaimed with `assignee: reports-7f9c-2`, `assignee_subject: {worker_a}`, `attempt: 1`, `handoff: true` (G-OPS-41).
- Refused cases: nothing changes.

## Notes
- `start` is not called again: the task stays `running`, with the deadlines set from the accept (G-OPS-27). A task reassigned while `claimed` stays `claimed`; the new holder may `start` it or finish it directly, since `start` is optional (G-EXE-11).
- The accept is authorized with the caller's own scope (G-OPS-27): the other-principal case assumes `{platform_worker}` has `claim` on the task's queue; a named target without the right gets `404` or `403` from its accept, and the hand-off then expires ([1.03](1.03-positive-accept-window-expires-requeue-no-strike.md)).
- If nobody accepts in time, see [1.03](1.03-positive-accept-window-expires-requeue-no-strike.md).
