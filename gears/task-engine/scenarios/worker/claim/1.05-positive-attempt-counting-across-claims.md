# `attempt` goes up on a claim after a retry or a liveness requeue, and stays the same after a release or a wait resume

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-assignment` (PRD.md:661, :1482, :1485) · `cpt-cf-task-engine-fr-release` (PRD.md:687-689) · `cpt-cf-task-engine-fr-wait-conditions` (PRD.md:550) · DESIGN.md:533, :538, :539, :546, :731, :732, :815, :1491, :2484 |
| Phase | p1 |
| Test level | Both — E2E release/retry rows; integration liveness row |
| Gaps | G-WIRE-05, G-RTY-22 |

`attempt` counts claims that start a new attempt, and only a claim changes it. A retry (a reported retryable failure) or a liveness requeue moves the task to `scheduled` without touching `attempt`; the next claim raises it by one (DESIGN.md:538, :539). A voluntary release (PRD.md:689) and a resume from a wait (PRD.md:1485) set `resume_pending`; the next claim clears the flag and leaves `attempt` unchanged. Every new claim is a new lease, so `lease_epoch` advances in every case. This folder is the home of `attempt` counting.

## Setup (representative case: after a retry)
- `{task_1}` (**render**, **reports**) was claimed once (`attempt: 1`, `lease_epoch: 1`) and failed with a retryable error; it is now `scheduled` with `retry_count: 1`, `attempt: 1`.
- Its `run_after` has passed and it is `queued` again (`T0+20s`).

## Request
```http
POST /api/task_engine/v1/tasks/claim HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "worker_id": "reports-7f9c-1", "session_id": null,
  "queues": ["gts.cf.core.tasks.queue.v1~acme.reports._.render.v1"], "max_tasks": 1, "timeout_secs": 0 }
```

## Expected response
- `200 OK`, one claim for `{task_1}`.
- `lease.attempt` is `2`; `lease.lease_epoch` is `2`; `task.retry_count` is still `1`.

```json
{ "session_id": "{session_2}", "heartbeat_interval_secs": 10,
  "claims": [ { "task": { "id": "{task_1}", "state": "claimed", "attempt": 2, "retry_count": 1, "…": "other fields as in CONVENTIONS §5.1" },
                "lease": { "lease_token": "{lt_2}", "lease_epoch": 2, "attempt": 2, "lease_secs": 30 },
                "authority": { "…": "…" }, "resumed": null } ] }
```

## Cases

Each row starts from `{task_1}` claimed once (`attempt: 1`, `lease_epoch: 1`), then sent back to `queued` by the path in the first column; the claim is the request above (any `worker_id` of `{worker_a}`, e.g. `reports-7f9c-2` after a release).

| Case | How `{task_1}` got back to `queued` | Expected claim | Side effects | Notes |
|---|---|---|---|---|
| first claim | never claimed (`attempt: 0`) | `attempt` 1, `lease_epoch` 1 | `task {task_1}.attempt advances from 0 to 1` | full exchange in [1.01](1.01-positive-claim-single-task.md) |
| after retry | retryable failure → `scheduled` (`retry_count: 1`) → `run_after` reached | `attempt` 2, `lease_epoch` 2, `retry_count` 1 | `task {task_1}.attempt advances from 1 to 2`; history gains `taskClaimed` with `attempt = 2` | DESIGN.md:538, :731 |
| after liveness requeue | session expired → `scheduled` (`liveness_requeues: 1`, `attempt: 1`) → `run_after` reached | `attempt` 2, `lease_epoch` 2 | `task {task_1}.attempt advances from 1 to 2` | DESIGN.md:539; the requeue itself is in `worker/sessions/` |
| after release | `POST /tasks/{task_1}/release` without a delay → `queued` (`T0+30s`) | `attempt` 1 (unchanged), `lease_epoch` 2, `resumed: null` (a release is not a wait) | task `{task_1}`.attempt is 1; history gains `taskClaimed` with `attempt = 1`; `resume_pending` cleared, so a further claim after a retryable failure gets `attempt = 2` | PRD.md:689; DESIGN.md:546, :732, :1491 |
| after wait resume | parked on a timer wait (`resume_at` `T0+60s`), timer fired → `queued` with `resume_pending = true`; clock `T0+61s` | `attempt` 1, `lease_epoch` 2, `resumed` names the wait group with outcome `satisfied` (body below) | task `{task_1}`.attempt is 1; `resume_pending` is cleared; history gains `taskClaimed` with `attempt = 1` | PRD.md:1485; DESIGN.md:533, :815; G-WIRE-05 |

`resumed` in the "after wait resume" row:
```json
{ "wait_group_id": "{wg_1}", "outcome": "satisfied",
  "conditions": [ { "id": "{wc_1}", "kind": "timer", "state": "satisfied", "result": null } ] }
```

## Side effects
- task `{task_1}` lease_epoch is 2 in every row except "first claim" (1).
- history of `{task_1}` gains `taskClaimed` with the row's `attempt`.

## Notes
- Wait framework and timer waits are p1 (PRD.md:546, :568); the shape of `resumed` was agreed in the wire review (G-WIRE-05, G-WAI-08).
- Every claim, including the one after a wait resume, sets a fresh execution deadline of the full execution timeout from the claim (G-RTY-22, G-EXE-10).
- In the release row the claim may come from another process (`reports-7f9c-2`); the attempt rule does not depend on which worker claims.
