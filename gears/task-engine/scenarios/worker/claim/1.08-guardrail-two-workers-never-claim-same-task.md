# Two workers claiming at the same moment never get the same task

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-assignment` (PRD.md:653, :1476) · DESIGN.md:2489-2493 · ADR-0008:44, :137 |
| Phase | p1 |
| Test level | Integration — race |
| Depends on | Proposals › Claiming and ordering › SKIP LOCKED when taking tasks |
| Gaps | G-CLM-07 |

The core safety rule. Two claims that race for the head of one queue must end with each task held by at most one worker. "A task that another claim is taking at that moment is skipped; the claim takes the best task that no other claim holds" (PRD.md:653). With `SKIP LOCKED` the loser skips the taken head row instead of waiting for it.

## Setup
- **reports** holds two `queued` tasks of `{tenant_a}`, `{task_1}` (`T0`) and `{task_2}` (`T0+1s`), nothing else.
- Two worker processes of `{worker_a}`: `reports-7f9c-1` and `reports-7f9c-2`, each without a session, ideally on different engine nodes.

## Exchange — both claims sent concurrently (`T0+10s`)
```http
POST /api/task_engine/v1/tasks/claim HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "worker_id": "reports-7f9c-1", "session_id": null,
  "queues": ["gts.cf.core.tasks.queue.v1~acme.reports._.render.v1"], "max_tasks": 1, "timeout_secs": 5 }
```
```http
POST /api/task_engine/v1/tasks/claim HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "worker_id": "reports-7f9c-2", "session_id": null,
  "queues": ["gts.cf.core.tasks.queue.v1~acme.reports._.render.v1"], "max_tasks": 1, "timeout_secs": 5 }
```

## Expected response
- Both answer `200 OK` with one claim each, and the two task IDs differ: together they are `{task_1, task_2}`.
- Each response has its own `session_id`; neither shows an error for the lost race (the loser "never sees an error", ADR-0008:74).
- Which worker gets `{task_1}` is not asserted.

## Side effects
- tasks `{task_1}` and `{task_2}` state is `claimed`, each with `lease_epoch` 1 and a different `assignment.worker_id`.
- `queue_tenant(reports, {tenant_a}) used changes by +2` in total (never +3: a lost pick returns its reserved slot, DESIGN.md:2495).
- history of each task gains exactly one `taskClaimed`.

## Notes
- Run the race many times (and with `max_tasks` > 1, and with one task only, where one claim must get `204` after its timeout) on every backend (ADR-0008:135-137).
- `te_claim_lost_races_total{queue}` counts planned picks not taken because another transaction holds the row (skipped by `SKIP LOCKED`) or it is no longer `queued` (G-CLM-07). Whether the two plans picked the same row in a given run is timing, so the test does not assert an exact increase.
