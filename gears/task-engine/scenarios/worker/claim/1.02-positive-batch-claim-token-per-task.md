# Batch claim returns up to `max_tasks` tasks, each with its own lease

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-assignment` (PRD.md:655) · DESIGN.md:1064, :2405, :2413, :2427 · ADR-0008:100 |
| Phase | p1 |
| Test level | E2E |
| Gaps | G-EXE-10 |

A worker with free capacity asks for several tasks at once. Each task is chosen, leased and counted as in a single claim and has its own token (PRD.md:655). When fewer tasks are ready than asked for, the claim returns what it has at once instead of waiting to fill the batch (DESIGN.md:2413).

## Setup
- **reports** holds exactly three `queued` tasks of `{tenant_a}`: `{task_1}`, `{task_2}`, `{task_3}` (**render**, priority 100), created in that order at `T0`, `T0+1s`, `T0+2s`.
- `{worker_a}` has no session. Clock `T0+10s`.

## Request
```http
POST /api/task_engine/v1/tasks/claim HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "worker_id": "reports-7f9c-1", "session_id": null,
  "queues": ["gts.cf.core.tasks.queue.v1~acme.reports._.render.v1"],
  "max_tasks": 5, "timeout_secs": 30 }
```

## Expected response
- `200 OK`, returned at once with **3** claims (fewer than `max_tasks`; the batch is not filled by waiting).
- One `session_id` for the whole response; every claim's task carries that session in its assignment.
- The three `lease_token` values are pairwise different; each `lease_epoch` is `1`, each `attempt` is `1`.
- The set of task IDs is `{task_1, task_2, task_3}` (the order of `claims[]` is not asserted).

```json
{ "session_id": "{session_1}", "heartbeat_interval_secs": 10,
  "claims": [
    { "task": { "id": "{task_1}", "state": "claimed", "…": "other fields as in CONVENTIONS §5.1" },
      "lease": { "lease_token": "{lt_1}", "lease_epoch": 1, "attempt": 1, "lease_secs": 30 }, "authority": { "…": "…" }, "resumed": null },
    { "task": { "id": "{task_2}", "state": "claimed", "…": "…" },
      "lease": { "lease_token": "{lt_2}", "lease_epoch": 1, "attempt": 1, "lease_secs": 30 }, "authority": { "…": "…" }, "resumed": null },
    { "task": { "id": "{task_3}", "state": "claimed", "…": "…" },
      "lease": { "lease_token": "{lt_3}", "lease_epoch": 1, "attempt": 1, "lease_secs": 30 }, "authority": { "…": "…" }, "resumed": null }
  ] }
```

## Side effects
- tasks `{task_1}`, `{task_2}`, `{task_3}` state is `claimed`, each `attempt` advances from 0 to 1.
- `queue_global(reports) used changes by +3`; `queue_tenant(reports, {tenant_a}) used changes by +3` (one `+k` per counter row, settled to the 3 won, DESIGN.md:2474, :2495).
- timer `queue_timeout` for each of the three is removed; timer `assignment` for each is armed at `T0+70s`; timer `execution` for each is armed at `T0+910s` (set by the claim, G-EXE-10).
- history of each task gains `taskClaimed`.
- subsequent `POST /tasks/{task_2}/start` with `{lt_1}` returns `409` `LEASE_LOST` (tokens are per task).

## Notes
- `max_tasks` defaults to 1 and is capped by `claim_max_batch` (32), DESIGN.md:1064, :2135; over the cap is [a 400](1.07-negative-claim-request-validation.md) (row "max_tasks above cap").
