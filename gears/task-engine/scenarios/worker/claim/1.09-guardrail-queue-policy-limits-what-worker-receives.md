# A worker allowed to claim only queue Q never receives another queue's task

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-resource-path-access` (PRD.md:943, :1531) · DESIGN.md:1009, :2407, :2448-2459 · ADR-0016:72, :86 |
| Phase | p1 |
| Test level | Integration — queue policy |
| Gaps | G-CLM-14, G-CLM-16 |

Policies can limit per subject which queues it may claim from (PRD.md:943). A claim is authorized once on the base task type. The engine first checks the compiled scope in memory: a named queue that every OR'd constraint provably excludes refuses the claim with `403 QUEUE_NOT_PERMITTED` ([auth/1.12](../../auth/1.12-negative-claim-names-queue-outside-policy.md), the home of that refusal). Whatever it cannot rule out in memory is filtered in SQL: the PDP constraints apply to every candidate read (ADR-0016:72), so a task outside the grant is never a candidate. This scenario shows the SQL side: naming a queue the policy only partly covers never leaks its other tasks.

## Setup
- PDP policy for `{worker_a}` this scenario: `claim` with two OR'd constraints: `queue_id = gts.cf.core.tasks.queue.v1~acme.reports._.render.v1` (**reports**), or `type_id = gts.cf.core.tasks.task.v1~acme.billing._.export.v1~` (**export**, no `queue_id` filter).
- **bulk** holds one `queued` **render** task `{task_2}` of `{tenant_a}` (`T0`). **reports** is empty. `{worker_a}` has no session.

## Request (`T0+5s`)
```http
POST /api/task_engine/v1/tasks/claim HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "worker_id": "reports-7f9c-1", "session_id": null,
  "queues": ["gts.cf.core.tasks.queue.v1~acme.reports._.render.v1",
             "gts.cf.core.tasks.queue.v1~acme.reports._.bulk.v1"],
  "max_tasks": 1, "timeout_secs": 2 }
```

## Expected response
- `204 No Content` after the 2 s timeout: the claim is not refused (the **export** constraint has no `queue_id` filter, so **bulk** "may match", G-CLM-14), and `{task_2}` is not returned (no constraint covers a **render** task in **bulk**).

```http
HTTP/1.1 204 No Content
```

## Cases

| Case | Differs from the representative case | Expected | Notes |
|---|---|---|---|
| bulk task outside the grant | (representative) | `204` after the timeout; `{task_2}` not returned | SQL filter, ADR-0016:72 |
| bulk task inside the grant | **bulk** also holds an **export** task `{task_3}` | `200` with `{task_3}`; `{task_2}` still not returned | the second constraint matches it |
| queue provably excluded | the policy has only the **reports** constraint | `403` `QUEUE_NOT_PERMITTED` naming **bulk** | asserted in [auth/1.12](../../auth/1.12-negative-claim-names-queue-outside-policy.md) (G-CLM-14) |

## Side effects
- Every row: task `{task_2}` state is `queued` (unchanged); a worker allowed on **bulk** claims it normally afterwards.
- The `204` and `403` rows open no session (G-CLM-16).

## Notes
- The firm assertion in every row: `{task_2}` is never in a `200` body.
