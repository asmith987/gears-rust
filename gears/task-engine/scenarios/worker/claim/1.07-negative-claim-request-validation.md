# A claim with a bad `worker_id`, `max_tasks` or queue list is rejected with `400`

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-assignment` (PRD.md:655, :663, :1525) · `cpt-cf-task-engine-fr-dead-letter` (PRD.md:799-801) · `cpt-cf-task-engine-fr-task-domains` (PRD.md:1182, :1506) · `cpt-cf-task-engine-fr-gts-queue` (PRD.md:987, :995) · DESIGN.md:760, :1064, :1223, :2133, :2135, :2404-2433 · ADR-0008:131 · ADR-0014 · `schemas/types/gts.cf.core.tasks.queue.v1~.schema.json` (`kind`) |
| Phase | p1 (row "dead-letter queue" p2, row "two domains" p3) |
| Test level | E2E |
| Depends on | Proposals › Claiming and ordering › Claims across queues (accepted: one domain only) — row "two domains" |
| Gaps | G-CLM-15, G-CLM-18, G-CLM-19, G-SEC-21 |

Claim parameters are validated before any session or PDP work, and a bad request is refused as a whole with `400 invalid_argument` and one field violation, at once (no long-poll wait). The order is fixed (G-CLM-18): syntax and fields → queue registry (unknown `404`, dead-letter, domain; from cached registry data) → PDP and `QUEUE_NOT_PERMITTED` → claim loop. No refusal touches a session.

- Every claim names the worker process it comes from. The worker identity is the pair (authenticated subject, `worker_id`) and is used for the assignment, events and the blacklist. `worker_id` must be 1–128 characters from `[A-Za-z0-9._:-]` (PRD.md:663).
- A batch claim may ask for up to `max_tasks` tasks, "capped by config" (PRD.md:655). DESIGN fixes the cap at `claim_max_batch` (default 32) and rejects anything outside `1 ≤ max_tasks ≤ claim_max_batch` (DESIGN.md:2405). Unlike the long-poll timeout ([1.03](1.03-positive-empty-claim-waits-then-204.md)), the batch size is not silently clamped.
- "The number of queues per claim MAY be capped" (PRD.md:655): `claim_max_queues` (default 16), checked at parse time on the distinct queues, after de-duplication (DESIGN.md:2133, :2433; G-CLM-18). The cap bounds the per-claim work. A missing or empty `queues` list is `REQUIRED`.
- A queue of `kind: dead_letter` only holds parked `dead_lettered` tasks and is never dispatched; a claim naming one is refused even when the other named queues are valid; the engine does not silently drop it (DESIGN.md:2432).
- All queues of one claim must live in one task domain, because a claim is one database transaction. A worker that consumes several domains sends one claim per domain (PRD.md:655; Proposals › Claiming and ordering).
- "Task creation and claims MUST name registered queues" (PRD.md:995). An unregistered queue is `404`, not a validation error ([1.11](1.11-negative-claim-naming-unknown-queue-not-found.md), G-CLM-15).
- `timeout_secs` may not be negative (G-CLM-19); a value above `claim_max_wait_secs` is clamped, not refused.

## Setup
- Default config: `claim_max_batch: 32`, `claim_max_queues: 16`.
- **reports** holds one `queued` task `{task_1}` of `{tenant_a}` (40 for the `max_tasks` rows).
- Row-specific setup is in the table.

## Request (representative case: `worker_id` missing)
```http
POST /api/task_engine/v1/tasks/claim HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "session_id": null,
  "queues": ["gts.cf.core.tasks.queue.v1~acme.reports._.render.v1"],
  "max_tasks": 1, "timeout_secs": 30 }
```

## Expected response
- `400 Bad Request`, `invalid_argument`, at once (no long-poll wait).
- One field violation on `/worker_id`.

```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.invalid_argument.v1~",
  "title": "Invalid Argument",
  "status": 400,
  "detail": "worker_id is required",
  "instance": "/api/task_engine/v1/tasks/claim",
  "trace_id": "<trace>",
  "context": {
    "resource_type": "gts.cf.core.tasks.task.v1~",
    "field_violations": [ { "field": "/worker_id", "description": "required: 1-128 characters from [A-Za-z0-9._:-]", "reason": "REQUIRED" } ]
  }
}
```

## Notes
- The `reason` codes, JSON Pointer paths and check order are decided (G-CLM-18, G-SEC-21); tests assert field, reason and category.
- The dead-letter and domain checks are request validation from cached registry data, not part of `try_claim_once` (DESIGN.md:2432 changes under G-CLM-18): no session opened, no wait.
- An unregistered queue is `404`, not a validation error: [1.11](1.11-negative-claim-naming-unknown-queue-not-found.md). Queues are platform-owned registrations (DESIGN.md:1010), so naming one reveals nothing tenant-private.
- The "two domains" request does not send `domain`. Sending `domain` does not let a claim span domains: every named queue must be in that one domain ([domains/1.07](../../domains/1.07-positive-placement-and-claims-during-a-move.md), case `claim_domain_not_in_set`). `platform-ops-1` is scenario-local (CONVENTIONS §4 lists none for `{platform_worker}`).
