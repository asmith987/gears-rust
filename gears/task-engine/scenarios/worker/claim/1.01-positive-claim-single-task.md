# Claim one task: session, lease, attempt and deadlines in one step

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-assignment` (PRD.md:651-665) · DESIGN.md:530, :1064, :1081, :2404-2420, :2479-2500 · ADR-0008:67-78 · ADR-0017:54-56 |
| Phase | p1 |
| Test level | E2E |
| Depends on | Proposals › Domains › p1 lays the foundation (`domain` on the session and the lease) |
| Gaps | G-CLM-16, G-CLM-20, G-EXE-10 |

The basic claim. A worker with no session names one queue and asks for one task. In one atomic step the engine opens a worker session, moves the task to `claimed`, issues a fresh lease token and epoch, counts the task against the queue's concurrency limits, removes its queue timeout, and arms its assignment deadline and its execution deadline (the claim sets the execution deadline, not `start`, G-EXE-10). The response carries `heartbeat_interval_secs` = max(1, lease / 3), so one late heartbeat never loses the lease (PRD.md:659).

## Setup
- `{creator_a}` created `{task_1}` (**render**, queue **reports**, priority 100) at `T0`; it is `queued`, `attempt: 0`, its queue-timeout timer is armed at `T0+3600s`.
- No other task is queued in **reports**. `{worker_a}` has no session.
- Clock at the request: `T0+5s`.

## Request
```http
POST /api/task_engine/v1/tasks/claim HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "worker_id": "reports-7f9c-1", "session_id": null,
  "queues": ["gts.cf.core.tasks.queue.v1~acme.reports._.render.v1"],
  "max_tasks": 1, "timeout_secs": 30 }
```

## Expected response
- `200 OK`, returned at once (a task was ready; the long-poll does not wait).
- `session_id` is a new ID; `heartbeat_interval_secs` is `10` (lease 30 s from `heartbeat_timeout_secs`, DESIGN.md:530; `max(1, floor(30 / 3))`, DESIGN.md:1081).
- Exactly one claim. `lease.lease_epoch` is `1` (first lease of the task), `lease.attempt` is `1`, `lease.lease_token` is non-empty.
- `domain` is `default` on the response and on the lease (single-domain deployment); worker calls for this task go to that domain.
- `task.state` is `claimed`; `task.assignment` names `{worker_a}` / `reports-7f9c-1` and never contains the token; `assignment.execution_deadline` is `T0+5s` + 900 s.

{ "session_id": "{session_1}", "domain": "default", "heartbeat_interval_secs": 10,

## Side effects
- task `{task_1}` state is `claimed`; `task {task_1}.attempt advances from 0 to 1`; task `{task_1}` lease_epoch is 1.
- `te_worker_sessions({session_1})` is present, `worker_id = reports-7f9c-1`, `lease_secs = 30`; session `{session_1}` lease_until is extended to `T0+35s`.
- timer `queue_timeout` for `{task_1}` is removed; timer `assignment` for `{task_1}` is armed at `T0+65s` (60 s assignment timeout); timer `execution` for `{task_1}` is armed at `T0+905s` (900 s from the claim, G-EXE-10).
- `queue_global(reports) used changes by +1`; `queue_tenant(reports, {tenant_a}) used changes by +1`.
- history of `{task_1}` gains `taskClaimed` with `assignee = reports-7f9c-1`, `assignee_subject = {worker_a}`, `attempt = 1`.
- event `taskClaimed` for `{task_1}` is not published to the task-events topic (default `lifecycle` policy excludes it, PRD.md:898, DESIGN.md:2218).
- metric `te_tasks_claimed_total{queue="…reports.render.v1"}` increases by 1.

## Notes
- The session is opened after authorization, inside the claim transaction that takes the task, and renewed last (DESIGN.md:2498); a claim that takes nothing opens no session (G-CLM-16).
- `heartbeat_interval_secs` is computed from the **session** lease (DESIGN.md:1081, ADR-0013:58), PRD.md:659 says "of the lease"; the two agree only while the session holds one lease length (G-CLM-20).
