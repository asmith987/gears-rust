# The SDK gives back a lease whose handler ended without finishing the task

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-heartbeat` (PRD.md:676: "a worker that stops working on a task MUST release it") · DESIGN.md:703 |
| Phase | p1 |
| Test level | Integration — Rust SDK behaviour |
| Depends on | Proposals › Heartbeats and leases › The SDK releases dropped leases |
| Gaps | G-EXE-07, G-EXE-08, G-EXE-16, G-SEC-01 |

When a handler panics, is aborted, or returns without `complete`, `release` or a wait, its `Lease` is dropped onto a release queue, and the session's heartbeat loop sends the release, retrying until the engine confirms or answers `LEASE_LOST`. There is no engine change; this scenario fixes what the engine observes.

## Setup
- `{worker_a}` runs the SDK worker runtime as `reports-7f9c-1`, session `{session_1}`, holding `{task_1}` (`running`, `{lt_1}`) and `{task_2}` (`running`, `{lt_2}`).
- At `T0+12s` the handler of `{task_1}` panics. The process stays alive.

## Exchange 1 — release from the heartbeat loop
At or before the next heartbeat tick (`T0+20s`), the engine receives:
```http
POST /api/task_engine/v1/tasks/{task_1}/release HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "lease_token": "{lt_1}" }
```
- `200 OK`, `{task_1}` `queued`.

## Exchange 2 — the next batch heartbeat
```http
POST /api/task_engine/v1/tasks/heartbeat HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "session_id": "{session_1}", "leases": [ { "task_id": "{task_2}", "lease_token": "{lt_2}" } ] }
```
- `200 OK`; `{task_1}` is no longer listed.

## Side effects
- task `{task_1}` state is `queued`, `attempt` 1, budgets unchanged; history of `{task_1}` gains `taskQueued` with `reason: released`.
- `{task_1}` does not wait for its execution timeout (900 s) or a session expiry; `{task_2}` is unaffected.
- If exchange 1 gets `503` (PDP unreachable, G-SEC-01; release uses the reserved admission permits, so overload shedding is rare, G-EXE-07), the engine sees the same release again after `Retry-After`, until it answers `200`, `409` `LEASE_LOST` or `403` `CLAIM_REVOKED`; after either refusal it is not sent again. `LEASE_LOST` after the SDK's own release counts as applied (G-EXE-16); `CLAIM_REVOKED` means the engine already released the task (G-EXE-08).

## Notes
- A REST-only worker that forgets to release still holds the task until its execution timeout (Proposals, "Not covered"). A process that dies loses its session as today ([Session expiry](../sessions/1.10-flow-session-expiry-requeues-tasks.md)).
- A handler that is alive but stuck is not covered; the options are Open (Proposals › Heartbeats and leases › Stuck handlers).
