# The SDK retries a shed heartbeat at once and ignores a Retry-After longer than the lease

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-heartbeat` (PRD.md:674) · `cpt-cf-task-engine-fr-execution-semantics` (PRD.md:742) · DESIGN.md:703, :2035 |
| Phase | p1 |
| Test level | Integration — Rust SDK behaviour |
| Depends on | Proposals › Heartbeats and leases › Reserved admission for the execution path (accepted, SDK rule) |
| Gaps | G-EXE-07, G-SEC-03 |

A heartbeat that is shed because the node is overloaded (`503`, G-EXE-07) must not wait out a `Retry-After` that is longer than the lease it is trying to save. The SDK worker runtime retries at once with jitter. This scenario shows what the engine observes.

## Setup
- `{worker_a}` runs the SDK worker runtime; session `{session_1}` holds `{task_1}` (`{lt_1}`), session lease 30 s, last renewal at `T0`, so `lease_until = T0+30s`.
- Engine config `unavailable_retry_after_secs: 60` (default 5, raised here so the hint is longer than the lease).
- At `T0+10s` the node is so overloaded that even the reserved pool is full for a moment.

## Exchange 1 — first heartbeat is shed
At `T0+10s`:
```http
POST /api/task_engine/v1/tasks/heartbeat HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "session_id": "{session_1}", "leases": [ { "task_id": "{task_1}", "lease_token": "{lt_1}" } ] }
```

```http
HTTP/1.1 503 Service Unavailable
Retry-After: 60
Content-Type: application/problem+json

{ "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.service_unavailable.v1~", "title": "Service Unavailable", "status": 503, "detail": "the node is overloaded; retry later", "instance": "/api/task_engine/v1/tasks/heartbeat", "trace_id": "<trace>", "context": { "retry_after_seconds": 60 } }
```

## Exchange 2 — the SDK retries at once
Within about one second (jitter), not after 60 s, the engine receives the same heartbeat again:

```http
POST /api/task_engine/v1/tasks/heartbeat HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "session_id": "{session_1}", "leases": [ { "task_id": "{task_1}", "lease_token": "{lt_1}" } ] }
```

- `200 OK`, `{task_1}` `ok`.

## Side effects
- session `{session_1}` lease_until is extended to about `T0+41s`.
- The `Retry-After: 60` (longer than the 20 s left on the lease) is ignored for heartbeats; for other calls the SDK honours `Retry-After` as today (DESIGN.md:2035).
- If no retry succeeds before `T0+30s`, the SDK fires `lease.lost` on its local monotonic clock and the handler stops (DESIGN.md:703), whatever the engine does next.

## Notes
- The SDK retry budget (how many immediate retries, jitter range) is not specified; a test asserts only that the retry arrives well before `Retry-After` and before `lease_until`.
