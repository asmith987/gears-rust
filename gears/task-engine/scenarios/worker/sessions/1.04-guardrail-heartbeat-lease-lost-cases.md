# A heartbeat reports lease_lost for every lease the caller no longer holds, and renews nothing it should not

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-heartbeat` (PRD.md:674, :676) · `cpt-cf-task-engine-fr-lease-fencing` (PRD.md:726: "A lost token never becomes valid again") · `cpt-cf-task-engine-fr-assignment` (PRD.md:663, worker identity) · DESIGN.md:211, :577, :703, :759, :1067, :1918, :2321, :2744-2755 · ADR-0017:55, :57, :59, :80, :81 · ADR-0011:61 |
| Phase | p1 |
| Test level | Both — expiry rows integration |
| Gaps | G-WIRE-06, G-EXE-01, G-EXE-02 |

A batch heartbeat answers per lease (PRD.md:674: "a result per lease (renewed, or `LEASE_LOST`)"). A lease the caller no longer holds is reported `lease_lost` with no state or cancel flag, so a lost lease reveals nothing about the task. A lost lease does not fail the request: the session is renewed only when it is the caller's own, still active session: every statement on `te_worker_sessions` carries `worker_subject = ctx.subject_id` (DESIGN.md:211; ADR-0017:57), and an expired session is never revived (DESIGN.md:2750-2751). A heartbeat on an unknown, expired or foreign session answers `200` with every listed lease `lease_lost`, without a per-lease read, and the same body in all three cases (G-EXE-01).

## Setup
- `{task_1}` (`running`, `{lt_1}`) and `{task_2}` (`claimed`, `{lt_2}`): **render** tasks of `{tenant_a}` on **reports**, held by `{worker_a}` (`reports-7f9c-1`) in session `{session_1}` (lease 30 s, `heartbeat_interval_secs: 10`); last heartbeat at `T0`, `lease_until = T0+30s` — as in [Batch heartbeat renews the session](1.01-positive-batch-heartbeat-renews-session.md).
- Representative case (**stale lease in batch**): at `T0+8s` an administrator force-cancelled `{task_2}`: it is `cancelled` / `forcibly_cancelled` and its token was cleared (DESIGN.md:577).

## Request
At `T0+10s`:
```http
POST /api/task_engine/v1/tasks/heartbeat HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{
  "session_id": "{session_1}",
  "leases": [
    { "task_id": "{task_1}", "lease_token": "{lt_1}" },
    { "task_id": "{task_2}", "lease_token": "{lt_2}" }
  ]
}
```

## Expected response
- `200 OK`; `{task_2}` is `lease_lost` with no state or cancel flag; `{task_1}` is `ok`.

```json
{
  "session_id": "{session_1}",
  "heartbeat_interval_secs": 10,
  "results": [
    { "task_id": "{task_1}", "outcome": "ok", "state": "running", "cancel_requested": false },
    { "task_id": "{task_2}", "outcome": "lease_lost" }
  ]
}
```

## Side effects
- session `{session_1}` lease_until is extended to `T0+40s`.
- `{task_2}` is unchanged (`cancelled`, `forcibly_cancelled`).
- subsequent `POST /tasks/{task_2}/complete` with `{lt_2}` returns `409` `LEASE_LOST`.

## Cases

| Case | Differs from the representative request | Expected | Notes |
|---|---|---|---|
| stale lease in batch | (representative) | `200`; `{task_2}` `lease_lost`, `{task_1}` `ok`; session renewed to `T0+40s` | A lost lease carries only `task_id` and `outcome` (G-WIRE-06) |
| late heartbeat after session expiry | The process paused past its lease: the session scan expired `{session_1}` at `T0+30.4s` and requeued `{task_1}` to `scheduled` ([Session expiry requeues tasks](1.10-flow-session-expiry-requeues-tasks.md)). At `T0+33s` it sends `leases: [{task_1, lt_1}]` | `200`, every listed lease `lease_lost`; the SDK fires `lease.lost` and the handler stops (DESIGN.md:703). Session `{session_1}` stays expired, `lease_until` not extended; `{task_1}` stays `scheduled`; subsequent `POST /tasks/claim` with `"session_id": "{session_1}"` opens a **new** session and returns its ID (ADR-0017:55) | The expiry guard repeats `lease_until < now`, so only a heartbeat that committed before it wins (DESIGN.md:2750-2751). `200` with all leases lost, not a request-level error (G-EXE-01) |
| heartbeat between expiry and requeue | As the previous row, but the heartbeat lands after step 1 (session `expired`) and before step 2 requeues `{task_1}`: token, holder and state still match | `200`, `{task_1}` `lease_lost`; session stays expired (ADR-0017:80) | An expired session answers every lease `lease_lost` (G-EXE-01, G-EXE-02). A worker **write** in the same window still succeeds, because the fence is token, holder and state; that write is not asserted ([Failed fence returns LEASE_LOST](../fencing/1.04-negative-failed-fence-returns-lease-lost.md), G-EXE-02) |
| foreign session | `{worker_b}` (tenant B, holds `claim`) learned `{session_1}` and `{lt_1}` (for example from a leaked log line) and sends `Authorization: Bearer <worker-b-token>`, `leases: [{task_1, lt_1}]` | `200`, `{task_1}` `lease_lost` (the session is not the caller's, so every lease is `lease_lost` without a per-lease read, G-EXE-01); no state or cancel flag of `{task_1}`. Session `{session_1}` lease_until is **not** extended (stays `T0+30s`): `WHERE session_id = ? AND worker_subject = {worker_b}` matches no row (ADR-0017:57). `{task_1}` stays `running`, held by `{worker_a}`; subsequent heartbeat by `{worker_a}` returns `ok` | A `session_id` is not a credential (DESIGN.md:1918; ADR-0017:81; ADR-0011:61). The session ID is echoed only because the caller sent it. The response is the same as for an unknown session (G-EXE-01) |
| unknown session | `session_id` is a well-formed, never-issued UUID `{session_x}`; `leases: [{task_1, lt_1}]` | `200`, `{ "session_id": "{session_x}", "results": [ { "task_id": "{task_1}", "outcome": "lease_lost" } ] }` with `heartbeat_interval_secs`, the same shape as "foreign session"; `{session_1}` not extended; no session row created | G-EXE-01 |

## Notes
- Whether `te_lease_fencing_rejections_total{op}` counts per-lease heartbeat losses is not stated (DESIGN.md:2321 says "worker-side writes"); not asserted.
- A claim that names a session of another subject opens a new session for the caller (ADR-0017:55); that case belongs to the claim scenarios.
