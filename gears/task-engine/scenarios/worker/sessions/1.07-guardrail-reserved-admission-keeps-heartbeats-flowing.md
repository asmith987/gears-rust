# Under overload claims are shed while heartbeats and completions still pass

| | |
|---|---|
| Requirement | DESIGN.md:2021, :2024, :2032, :2035, :2053 (replaced) · `cpt-cf-task-engine-fr-heartbeat` (PRD.md:674) |
| Phase | p1 |
| Test level | Integration — overload |
| Depends on | Proposals › Heartbeats and leases › Reserved admission for the execution path |
| Gaps | G-EXE-07, G-SEC-03 |

On `main` admission is one 512-permit semaphore per node with a 100 ms acquire timeout (DESIGN.md:2021), so long claim transactions can push heartbeats out. With the accepted change heartbeat, `complete` (including a reported failure and a cancel acknowledgement), `release`, wait set/park and the API cancel first take a permit from a reserved pool (`admission.reserved_execution_permits`, default 64, on top of the shared 512) that claims cannot use, then fall back to the shared pool; `start`, progress and checkpoint do not use it (G-EXE-07). A shed request is `503` with `Retry-After`, never `429`: `429` is for per-caller quotas.

## Setup
- One engine node, `admission.max_inflight_db_requests: 512`, `admission.reserved_execution_permits: 64` (default), `unavailable_retry_after_secs: 5` (default).
- All 512 shared permits are held by in-flight claim transactions; no reserved permit is in use.
- `{worker_a}` holds `{task_1}` (`running`) in session `{session_1}`, lease `{lt_1}`.

## Exchange 1 — a claim is shed
```http
POST /api/task_engine/v1/tasks/claim HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "worker_id": "reports-7f9c-2", "session_id": null, "queues": ["gts.cf.core.tasks.queue.v1~acme.reports._.render.v1"], "max_tasks": 1, "timeout_secs": 30 }
```

- `503 Service Unavailable` after the 100 ms acquire timeout, with `Retry-After: 5`.

```http
HTTP/1.1 503 Service Unavailable
Retry-After: 5
Content-Type: application/problem+json
```
```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.service_unavailable.v1~",
  "title": "Service Unavailable",
  "status": 503,
  "detail": "the node is overloaded; retry later",
  "instance": "/api/task_engine/v1/tasks/claim",
  "trace_id": "<trace>",
  "context": { "retry_after_seconds": 5 }
}
```

## Exchange 2 — a heartbeat at the same moment passes
```http
POST /api/task_engine/v1/tasks/heartbeat HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "session_id": "{session_1}", "leases": [ { "task_id": "{task_1}", "lease_token": "{lt_1}" } ] }
```

- `200 OK`, `{task_1}` `ok`; it took a reserved permit.

## Side effects
- session `{session_1}` lease_until is extended by 30 s.
- No task is claimed; no counter changes.
- A `POST /tasks/{task_1}/complete` sent at the same moment is also admitted on a reserved permit; a `POST /tasks/{task_1}/progress` is not (it uses only the shared pool) and gets the same `503`.

## Notes
- Overload is `503`, so a worker tells it from a claim's capacity `429` (subject `concurrency`) by the status alone (G-EXE-07).
- Expiries that overload still causes count as liveness failures (Proposals, "Unchanged").
