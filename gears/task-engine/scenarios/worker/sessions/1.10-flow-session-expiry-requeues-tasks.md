# A worker that stops heartbeating loses its session, and its tasks are requeued with backoff

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-heartbeat` (PRD.md:676, :678) · `cpt-cf-task-engine-fr-timeouts` (PRD.md:520) · DESIGN.md:539, :2744-2760, :2777-2799, :2854-2866 · ADR-0017:59, :78 |
| Phase | p1 |
| Test level | Both — E2E short heartbeat; integration backoff |
| Gaps | G-EXE-05, G-CLM-30 |

When a worker process stops heartbeating, the session scan marks its session expired and requeues every task of the session as a **liveness failure**: back to `scheduled` with retry-policy backoff on the `max_liveness_requeues` budget, never `retry_count`. ADR-0017:78 requires that this happens within one lease duration plus one scan interval.

## Setup
- `{task_1}` (`running`, `{lt_1}`) and `{task_2}` (`claimed`, `{lt_2}`): **render** tasks of `{tenant_a}` on **reports** (`heartbeat_timeout_secs: 30`, retry `exponential`, `base_interval_secs: 5`, `jitter_factor: 0.2`, `max_liveness_requeues: 20`), both in session `{session_1}` of `reports-7f9c-1`, `liveness_requeues: 0`, `retry_count: 0`.
- The last successful heartbeat was at `T0`, so `lease_until = T0+30s`. `lease_scan_interval_ms: 1000` (DESIGN.md:2082).
- The process is killed at `T0+1s` and sends nothing more.

## Exchange 1 — the session scan runs (no request)
Between `T0+30s` and `T0+31s` the session scan finds `{session_1}` (`status = active AND lease_until < now`), marks it `expired` in its own transaction, then requeues both tasks in a batch of `session_requeue_batch` (DESIGN.md:2744-2760).

## Exchange 2 — read the task
At `T0+32s`:
```http
GET /api/task_engine/v1/tasks/{task_1} HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
```

## Expected response
- `200 OK`; `state: scheduled`, `liveness_requeues: 1`, `retry_count: 0`, `attempt: 1` (bumped only by the next claim, DESIGN.md:539), `assignment: null`.
- `run_after` is the expiry time plus `compute_backoff(n = 1)`: `5 s` shortened by jitter to between `4 s` and `5 s` (DESIGN.md:2862-2866), so between `T0+34s` and `T0+36s`.

```json
{
  "id": "{task_1}",
  "state": "scheduled",
  "attempt": 1,
  "retry_count": 0,
  "liveness_requeues": 1,
  "run_after": "2026-11-03T10:00:35Z",
  "assignment": null,
  "…": "other fields as in CONVENTIONS §5.1"
}
```

## Side effects
- session `{session_1}` is expired.
- task `{task_1}` state is `scheduled`; task `{task_2}` state is `scheduled`; both `liveness_requeues` advance from `0` to `1`.
- lease `{lt_1}` is invalid (later calls get LEASE_LOST); lease `{lt_2}` is invalid (later calls get LEASE_LOST).
- `queue_global(reports)` used changes by `-2`; `queue_tenant(reports, tenant_a)` used changes by `-2`; `{task_1}` and `{task_2}` join the deferred set (re-entry, never refused, DESIGN.md:559).
- timer `scheduled` for `{task_1}` is armed at its `run_after`; timer `lifetime` for `{task_1}` is kept (DESIGN.md:2796).
- metric `te_worker_sessions_expired_total{domain="default"}` increases by 1; metric `te_lease_expired_total{cause="session"}` increases by 2.
- No `taskTimedOut` is recorded: the tasks did not end (DESIGN.md:2799).
- history of `{task_1}` and of `{task_2}` gains `taskRetrying` with `cause: liveness`, `timeout_type: heartbeat`, `liveness_requeues: 1` and `run_after` (G-EXE-05).
- Blacklist (p3): one liveness failure is recorded for (`{worker_a}`, `reports-7f9c-1`) on **reports**, not two (ADR-0017:60, :79).

## Notes
- The `run_after` shown is one possible value inside the jitter window; a test asserts the window.
