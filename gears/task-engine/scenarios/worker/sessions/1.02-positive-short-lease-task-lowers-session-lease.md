# Claiming a task with a shorter lease shortens the session lease and the heartbeat interval

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-heartbeat` (PRD.md:659, :674) · `cpt-cf-task-engine-fr-assignment` (PRD.md:659, :1518) · DESIGN.md:530, :1081, :1921, :2085, :2192, :2498 · ADR-0017:56, :82 |
| Phase | p1 |
| Test level | Both — E2E exchanges 1–2; integration exchange 3 (Rust SDK behaviour) |
| Gaps | G-EXE-03, G-CLM-20 |

A session's lease is the shortest effective lease of any task it has held (DESIGN.md:1921). Claiming a task whose `heartbeat_timeout_secs` is shorter lowers the session lease; the claim response and every later heartbeat return the shorter interval, and the shorter lease applies to every lease of the session. The engine never raises the lease again, even after the short task leaves (ADR-0017:56). Instead the SDK starts a new session once it holds no leases and its session lease is below the default (G-EXE-03).

## Setup
- Session `{session_1}` of `reports-7f9c-1` holds `{task_1}` (**reports**, `heartbeat_timeout_secs: 30`); session `lease_secs: 30`, interval 10 s.
- `{task_2}`: **render** task on **reports**, created by `{creator_a}` with `"timeouts": { "heartbeat_timeout_secs": 12 }` (≥ `trust_limits.min_lease_secs` 10, DESIGN.md:2192); it is `queued`.

## Exchange 1 — the claim lowers the session lease
At `T0`:
```http
POST /api/task_engine/v1/tasks/claim HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "worker_id": "reports-7f9c-1", "session_id": "{session_1}", "queues": ["gts.cf.core.tasks.queue.v1~acme.reports._.render.v1"], "max_tasks": 1, "timeout_secs": 0 }
```

- `200 OK`, `session_id` `{session_1}`, `heartbeat_interval_secs: 4` (`max(1, floor(12 / 3))`, DESIGN.md:1081), `lease.lease_secs: 12`.

```json
{
  "session_id": "{session_1}",
  "heartbeat_interval_secs": 4,
  "claims": [ {
    "task": { "id": "{task_2}", "state": "claimed", "…": "other fields as in CONVENTIONS §5.1" },
    "lease": { "lease_token": "{lt_2}", "lease_epoch": 1, "attempt": 1, "lease_secs": 12 },
    "authority": { "…": "…" },
    "resumed": null
  } ]
}
```

- `te_worker_sessions({session_1})` has `lease_secs = 12`; session `{session_1}` lease_until is extended to `T0+12s`.
- `{task_1}` now also expires if no heartbeat arrives within 12 s.

## Exchange 2 — a heartbeat after the short task left
At `T0+3s` `{task_2}` completes `success`. At `T0+4s`:
```http
POST /api/task_engine/v1/tasks/heartbeat HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "session_id": "{session_1}", "leases": [ { "task_id": "{task_1}", "lease_token": "{lt_1}" } ] }
```

- `200 OK`, `heartbeat_interval_secs: 4`, although the session now holds only the 30 s task.

```json
{
  "session_id": "{session_1}",
  "heartbeat_interval_secs": 4,
  "results": [ { "task_id": "{task_1}", "outcome": "ok", "state": "running", "cancel_requested": false } ]
}
```

## Exchange 3 — the SDK starts a fresh session when idle (integration)
`{worker_a}` runs the SDK worker runtime. At `T0+6s` `{task_1}` completes too, so the process holds no leases and its session lease (12 s) is below the default (30 s). Its next claim:
```http
POST /api/task_engine/v1/tasks/claim HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "worker_id": "reports-7f9c-1", "session_id": null, "queues": ["gts.cf.core.tasks.queue.v1~acme.reports._.render.v1"], "max_tasks": 1, "timeout_secs": 30 }
```
- The SDK sends `session_id: null`. When it takes a task (here `{task_3}`, `heartbeat_timeout_secs: 30`), the answer is `200` with a new `session_id` `{session_2}`, `lease.lease_secs: 30`, `heartbeat_interval_secs: 10`.
- `{session_1}` is never heartbeated again and expires silently: it holds no tasks, so nothing is requeued.

## Side effects
- After exchange 2: session `{session_1}` lease_until is extended to `T0+16s` (`now + 12 s`), not `T0+34s`.
- `te_worker_sessions.lease_secs` of `{session_1}` stays `12` (lowered by the claim, never raised, ADR-0017:56).

## Notes
- If the worker misses the claim response (and keeps heartbeating every 10 s), its session can expire after 12 s and take `{task_1}` with it. Exchange 2 asserts the engine rule: the lease never rises again after the short task leaves; the SDK resets it by opening a new session when idle (Exchange 3, G-EXE-03).
- With `min_lease_secs` 10 the "at least 1 second" floor of PRD.md:659 is never reached (G-CLM-20).
