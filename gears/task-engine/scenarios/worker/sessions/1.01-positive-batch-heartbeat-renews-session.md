# A batch heartbeat renews the worker session and reports on every lease

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-heartbeat` (PRD.md:674, :676) · DESIGN.md:759, :1067, :1081, :1305-1308 · ADR-0017:57, :77 |
| Phase | p1 |
| Test level | E2E |
| Depends on | Proposals › Heartbeats and leases › No PDP call on heartbeat; Proposals › API reads and responses › Bounded responses (single-task heartbeat removed, accepted) |
| Gaps | G-WIRE-06, G-EXE-10 |

One worker process holds two leases in one session. A single batch heartbeat renews the session row, which keeps both leases alive, and answers per lease with `ok`, the task state and the cancel flag. The cost is one session write and one read, whatever the number of leases: no `te_task_state` row is written (ADR-0017:77).

## Setup
- `{task_1}` and `{task_2}`: **render** tasks of `{tenant_a}` on **reports** (`heartbeat_timeout_secs: 30`).
- At `T0` `{worker_a}` claimed both as `reports-7f9c-1` with `max_tasks: 2`: session `{session_1}` (lease 30 s, `heartbeat_interval_secs: 10`), leases `{lt_1}` and `{lt_2}`. `{task_1}` was started; `{task_2}` is still `claimed`.
- At `T0+5s` `{creator_a}` sent a `requested` cancel for `{task_2}`, so `cancel_requested` is `true` on it.
- Session `{session_1}` has `lease_until = T0+30s`.

## Request
At `T0+10s`:
```http
POST /api/task_engine/v1/tasks/heartbeat HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{
  "session_id": "{session_1}",
  "leases": [
    { "task_id": "{task_1}", "lease_token": "{lt_1}" },
    { "task_id": "{task_2}", "lease_token": "{lt_2}" }
  ]
}
```

## Expected response
- `200 OK`, one result per listed lease, in request order.
- `heartbeat_interval_secs` is `10` (`max(1, floor(30 / 3))`, DESIGN.md:1081).
- `{task_2}` carries `cancel_requested: true` and the pending `cancel_request`, which is how the worker learns of the cancel (DESIGN.md:551; G-WIRE-06).

```json
{
  "session_id": "{session_1}",
  "heartbeat_interval_secs": 10,
  "results": [
    { "task_id": "{task_1}", "outcome": "ok", "state": "running", "cancel_requested": false },
    { "task_id": "{task_2}", "outcome": "ok", "state": "claimed", "cancel_requested": true,
      "cancel_request": { "mode": "requested", "requested_by": "{creator_a}", "requested_at": "2026-11-03T10:00:05Z", "reason": null, "grace_until": null, "superseded_by": null } }
  ]
}
```

## Side effects
- session `{session_1}` lease_until is extended to `T0+40s`.
- Exactly one `te_worker_sessions` row is updated; no `te_task_state` row is written (ADR-0017:77, DESIGN.md:759).
- `assignment_deadline` of `{task_2}` and the `execution_deadline` of both tasks (set by the claim, G-EXE-10) are unchanged: a heartbeat never pushes out a per-task deadline (DESIGN.md:806).
- No PDP call is made (Proposals › Heartbeats and leases).
- history of `{task_1}` and `{task_2}` gains nothing (a heartbeat is not a history event, PRD.md:868).

## Notes
- The response shape was agreed in the wire review (G-WIRE-06): `cancel_request` appears only while a cancel is pending.
- Per-lease `lease_lost` outcomes (stale lease, expired session, foreign subject) are in [Heartbeat lease_lost cases](1.04-guardrail-heartbeat-lease-lost-cases.md).
