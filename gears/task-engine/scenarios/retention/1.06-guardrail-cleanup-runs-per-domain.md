# Cleanup runs separately in each task domain

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-retention` (PRD.md:1101) · `cpt-cf-task-engine-fr-task-domains` (PRD.md:1174) · ADR-0010:65 · DESIGN.md:851, :1991 |
| Phase | p3 |
| Test level | Integration — days of clock + cleanup jobs |
| Gaps | G-OPS-35 |

Each domain has its own database, ring and retention loop. The maintenance leader runs each domain's passes as an independent loop, so a failure or a slow pass in one domain does not delay the others, and each domain's results are reported under its own label (G-OPS-35).

## Setup
- Domains `system` (queue **system**) and `default`, as DESIGN.md:2223-2230; `per_type: [{ pattern: "gts.cf.core.tasks.task.v1~cf.system.*", retention_days: 7 }]` (DESIGN.md:2171).
- Both domains have finished tasks past retention.
- At `T0` the `system` database rejects the truncate (lock timeout) on every retry.

## Request
```http
GET /api/task_engine/v1/tasks/{task_default_old} HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
```

## Expected response
- `404 Not Found`: `{task_default_old}` (in `default`, past retention) was removed on schedule.
- An expired task in the `system` domain is still readable; it is removed at the next successful `system` pass.

## Side effects
- metric te_retention_pass_failures_total{domain="system"} increases by 1; nothing is removed in `system` in that pass.
- metric te_retention_removed_total{domain="default", …} increases.

## Notes
- All maintenance loops run under one global advisory-lock leader (DESIGN.md:862, :1980), which runs each domain's passes as an independent loop (G-OPS-35).
- A domain may set its own ring geometry and retention policies; unset values default to the global block (G-OPS-35). The config shape for the per-domain block is not given; this scenario uses the global settings in both domains.
