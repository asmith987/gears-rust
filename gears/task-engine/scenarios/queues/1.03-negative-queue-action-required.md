# Queue endpoints need the queue action, not task rights

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-authz` (PRD.md:918, :923) · `cpt-cf-task-engine-fr-runtime-config` (PRD.md:484) · PRD.md:455 · DESIGN.md:980, :992, :993, :1106, :1129, :1130 · Proposals › Queue operations › Admin queue hold ("Both need the queue `configure` action") |
| Phase | p1 (list, hold, release) · p3 (config) |
| Test level | Integration — queue action vs task rights |
| Depends on | Proposals › Queue operations › Admin queue hold — hold and release cases only |
| Gaps | G-OPS-40, G-SEC-19 |

Task rights do not grant queue visibility or control (DESIGN.md:980). Listing queues needs queue `read`; holding, releasing and changing runtime config need queue `configure` (PRD.md:455, :484). Task `admin` is not enough: hold, release and limits are queue configuration, so a tenant operator who can read queues cannot stop or retune them.

## Setup
- `<readonly-a-token>`: `{reader_a}` has task `read` only, no queue action.
- `<creator-a-token>`: `{creator_a}` has queue `read` but not `configure`.
- Subject `{task_admin}` (root), token `<task-admin-token>`: task `admin` and `read`, queue `read`; no queue `configure`.
- **reports** is not held.

## Request
```http
POST /api/task_engine/v1/admin/queues/gts.cf.core.tasks.queue.v1~acme.reports._.render.v1/hold HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
Content-Type: application/json

{ "reason": "testing" }
```

## Expected response
- `403 Forbidden`, `permission_denied`, `context.reason = "ACTION_DENIED"` (G-SEC-19). The caller may read the queue, so `403`, not `404` (PRD.md:918).
- No PDP detail and no field violations in the body (PRD.md:918, CONVENTIONS §6).

```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.permission_denied.v1~",
```

## Notes
- A caller with neither queue `read` nor `configure` is assumed to get the same `403` on hold and release: queues are not tenant data, so the no-oracle rule (which is about tasks) does not force `404`.
- A list endpoint is not a single-resource request, so the no-oracle `404` rule (PRD.md:918) does not apply; `403` is the fail-closed answer. Whether a PDP that allows queue `read` with constraints narrows the list to the queues it allows is not decided by any gap; not asserted here.
- `POST /admin/config` makes one `configure` check against the queue base type, whatever queues or patterns the body names, and is all-or-nothing (G-OPS-40). Per-queue delegation is not offered; it may come later behind a separate endpoint.
- Generic queue-read isolation (queue `read` grants no task data) lives in `auth/`.
