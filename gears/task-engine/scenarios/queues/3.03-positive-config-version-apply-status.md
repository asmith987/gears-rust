# The config version endpoint shows which domains have applied a version

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-runtime-config` (PRD.md:482) · DESIGN.md:860, :1129-1130 · ADR-0010:74 |
| Phase | p3 |
| Test level | Integration — p3 |
| Gaps | G-OPS-11, G-OPS-39, G-WIRE-12 |

Each task domain has its own database, so a config version is applied per domain, not at one instant (ADR-0010:74). The operator polls the version until every domain has applied it.

## Setup
- Domains `system` and `default` (as DESIGN.md:2223-2230).
- Version 7 was saved at `T0` ([3.01](3.01-positive-runtime-config-save-is-complete-version.md)). At `T0+2s` the `default` domain has applied it; `system` has not run its maintenance pass yet.

## Exchange 1 — At `T0+2s`
```http
GET /api/task_engine/v1/admin/config/7 HTTP/1.1
Host: api.example.com
Authorization: Bearer <admin-token>
```
- `200 OK`; `default` applied, `system` pending.

```json
{ "config_version": 7,
  "domains": [ { "domain": "default", "applied": true }, { "domain": "system", "applied": false } ] }
```

## Exchange 2 — After the `system` maintenance pass
```http
GET /api/task_engine/v1/admin/config/7 HTTP/1.1
Host: api.example.com
Authorization: Bearer <admin-token>
```
- `200 OK`; both domains `applied: true`.

## Notes
- The response shape is G-WIRE-12. Each version is a complete override set (G-OPS-11), so a domain that has applied version 8 has superseded 7; this file reads only the version just saved. A version that was never saved returning `404` is the scenarios' choice; G-OPS-11's decision does not cover it.
- How long a domain may lag is still not bounded: the maintenance loop runs under the single `te-maintenance` leader (DESIGN.md:862, :1980) with no stated interval for the apply step (G-OPS-11 decided only the body). DESIGN.md:1667 calls the same step "RetentionService step 5" while DESIGN.md:860 makes it step 6 (G-OPS-39, no decision recorded).
