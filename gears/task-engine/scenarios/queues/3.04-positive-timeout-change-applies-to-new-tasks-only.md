# A runtime timeout or retry change applies to new tasks; existing tasks keep their values

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-runtime-config` (PRD.md:484) · DESIGN.md:715 |
| Phase | p3 |
| Test level | Integration — p3 |
| Gaps | G-OPS-13, G-OPS-20, G-CRT-04, G-OPS-43 |

Each task stores its resolved timeouts, retry policy and priority at creation (DESIGN.md:715; G-CRT-04). A runtime change of the queue's settings therefore changes new tasks only, never a live task (G-OPS-13). Concurrency and depth limits, by contrast, are checked on every claim and admission, so they apply to all tasks once the domain has the new version.

## Setup
- `{task_7}` on **reports** was created at `T0-1m` with `execution_timeout_secs: 900`; it is `queued`.
- At `T0` version 9 sets `"gts.cf.core.tasks.queue.v1~acme.reports._.render.v1": { "timeouts": { "execution_timeout_secs": 1800 } }`; the `default` domain applies it at `T0+3s`.
- At `T0+10s` `{creator_a}` creates `{task_8}` on **reports**.

## Request
```http
GET /api/task_engine/v1/tasks/{task_7} HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
```

## Expected response
- `200 OK`, `{task_7}.timeouts.execution_timeout_secs: 900` (unchanged).
- `GET /tasks/{task_8}` returns `timeouts.execution_timeout_secs: 1800`.
- `GET /queues/gts.cf.core.tasks.queue.v1~acme.reports._.render.v1` returns `settings.timeouts.execution_timeout_secs: 1800` and `config_version: 9` (G-OPS-43).
- When `{task_7}` is claimed later, its execution deadline is the claim time plus 900 s, its stored value.

```json
{ "id": "{task_7}", "state": "queued",
  "timeouts": { "queue_timeout_secs": 3600, "assignment_timeout_secs": 60, "execution_timeout_secs": 900, "heartbeat_timeout_secs": 30, "lifetime_timeout_secs": 86400 },
  "…": "other fields as in CONVENTIONS §5.1" }
```
