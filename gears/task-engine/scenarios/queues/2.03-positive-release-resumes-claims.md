# Releasing a hold, by call or at `until`, lets claims resume

| | |
|---|---|
| Requirement | Proposals › Queue operations › Admin queue hold (`POST /admin/queues/{id}/release`, `until?`) |
| Phase | p1 |
| Test level | E2E |
| Depends on | Proposals › Queue operations › Admin queue hold |
| Gaps | G-OPS-03, G-OPS-04, G-OPS-05, G-OPS-06, G-OPS-08, G-WIRE-12 |

The incident is over; the operator releases **reports**. The queue's backlog is served again in the usual order (urgency, tenant fairness, priority, age). For planned maintenance the operator can instead hold the queue with `until`, and the engine releases it at that time without another call.

## Setup
- **reports** is held since `T0` by `{admin}` with 12 `queued` tasks.
- Clock `T0+20m`.

## Request
```http
POST /api/task_engine/v1/admin/queues/gts.cf.core.tasks.queue.v1~acme.reports._.render.v1/release HTTP/1.1
Host: api.example.com
Authorization: Bearer <admin-token>
```

## Expected response
- `200 OK`, the queue resource with `"hold": null`.

## Side effects
- No task changes state because of the release itself.

## Notes
- Automatic release: nodes compare `until` with their own clock on their cached hold row; the leader's sweep writes the single event (G-OPS-08). The sweep's timing is not bounded here, so the test waits for the `queueReleased` item at `GET /queues/{id}/events` rather than asserting when it appears (G-OPS-05).
- An `until` that is not in the future is refused (`400`); see [Hold and release edge cases](2.04-guardrail-hold-and-release-edge-cases.md), with releasing a queue that is not held and holding a held queue again.
- The release endpoint has the same name as the worker's task release (`POST /tasks/{id}/release`); they are unrelated.
