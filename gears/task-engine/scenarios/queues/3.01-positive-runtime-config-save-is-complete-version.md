# A runtime config save is a new complete version, recorded once per affected queue

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-runtime-config` (PRD.md:482-487) · DESIGN.md:715, :860, :877, :1129, :1132 · `schemas/types/…config_updated.v1~` |
| Phase | p3 |
| Test level | Integration — p3 runtime config |
| Gaps | G-OPS-05, G-OPS-11, G-OPS-12, G-OPS-13, G-OPS-40, G-OPS-43, G-CLM-21, G-WIRE-12 |

An operator raises the per-tenant concurrency limit of **reports** from 5 to 10 without a restart. Each save is the complete set of runtime overrides: a key not present reverts to the registration or the config default (G-OPS-11). The save returns a version number at once (`202`); each domain applies it later through its maintenance loop. DESIGN asks for one `configUpdated` per queue whose effective settings change, all with the same `config_version`, naming the actor and the keys that changed (DESIGN.md:1129). A queue whose effective value is unchanged gets no event.

## Setup
- The latest saved runtime config version is 6, `{ "queues": {}, "types": {} }` (no runtime overrides).
- **reports** lives in the `default` domain.

## Request
```http
POST /api/task_engine/v1/admin/config HTTP/1.1
Host: api.example.com
Authorization: Bearer <admin-token>
Content-Type: application/json

{ "queues": { "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1": { "per_tenant_concurrency_limit": 10 } } }
```

## Expected response
- `202 Accepted` with the saved version.

```json
{ "config_version": 7 }
```

## Cases

| Case | Differs from the representative request | Expected | Notes |
|---|---|---|---|
| exact queue ID | (representative) | `202 { "config_version": 7 }`; exactly one `configUpdated` (see Side effects) | |
| pattern fans out | latest version 7 is `{ "queues": { "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1": { "queue_max_queue_depth": 20000 } } }`; **bulk** has no override (effective 1,000,000); body repeats the exact-ID entry and adds a pattern: `{ "queues": { "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1": { "queue_max_queue_depth": 20000 }, "gts.cf.core.tasks.queue.v1~acme.reports.*": { "queue_max_queue_depth": 50000, "default_priority": 200 } } }` | `202 { "config_version": 8 }`. configUpdated for **bulk**: `config_version: 8`, `changed_keys: ["queue_max_queue_depth", "default_priority"]`. configUpdated for **reports**: `config_version: 8`, `changed_keys: ["default_priority"]` only, because its exact-ID depth override still wins (G-CLM-21, [precedence](3.02-positive-config-override-precedence.md)). No configUpdated for **default**, **system** or **dead_letter**. Both events carry `actor: "{admin}"` and are enqueued in the `default` domain (DESIGN.md:877). New tasks on **bulk** and **reports** without a priority get 200 once the domain applies version 8; existing tasks keep the priority they were created with (G-OPS-13) | DESIGN.md:1129; G-OPS-11 |
| omitted key reverts | after the representative save (version 7), body `{ "queues": {} }` | `202 { "config_version": 8 }`; one configUpdated for **reports** with `config_version: 8`, `changed_keys: ["per_tenant_concurrency_limit"]`; once applied, `GET /queues/{reports}` shows `limits.per_tenant_concurrency_limit: 5` (the registration) and `config_version: 8` | G-OPS-11 |

## Side effects
- Version 7 is saved in `te_runtime_config` in the `default` domain database (DESIGN.md:1129).
- The `configure` check is made once, against the queue base type (G-OPS-40).
- In the same transaction, exactly one `configUpdated` is recorded and enqueued: `subject` = **reports**, data `{ "queue": "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1", "config_version": 7, "actor": "{admin}", "changed_keys": ["per_tenant_concurrency_limit"] }`.
- event `configUpdated` for queue **reports** is published to the task-events topic; history of queue **reports** gains configUpdated, readable at `GET /queues/{reports}/events` (G-OPS-05).
- The `default` domain's maintenance loop applies version 7 at its next pass (DESIGN.md:860); from then on `GET /queues/{reports}` shows `limits.per_tenant_concurrency_limit: 10` and `config_version: 7` (G-OPS-43), and claims allow up to 10 running tasks per tenant. Apply status per domain is in [3.03](3.03-positive-config-version-apply-status.md).
- No task changes.

## Notes
- A save replaces the whole runtime override set (G-OPS-11); `changed_keys` lists the effective keys that differ from the previous applied version, including keys that revert. The body shape is G-WIRE-12.
- Still not decided: how long a domain may take to apply a version (no interval for the apply step), whether a value outside the trust limits is refused at save, and whether two runtime patterns of equal specificity are refused at save as they are at load (G-CLM-21). Not asserted here.
- Engine-wide `configUpdated` events that name no queue have no read path yet (G-OPS-05); this file uses only queue overrides.
- `default_priority`, timeouts and retry policy are resolved and stored at create, so a change never reaches existing tasks (G-OPS-13, [3.04](3.04-positive-timeout-change-applies-to-new-tasks-only.md)).
- The `configure` refusal is in [Queue action required](1.03-negative-queue-action-required.md).
