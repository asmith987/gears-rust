# Queue introspection shows effective limits and settings, and per-state counts to callers holding queue `configure`

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-queue-introspection` (PRD.md:491-496) · `cpt-cf-task-engine-fr-queue-depth` visibility (PRD.md:457) · DESIGN.md:763, :771, :993, :1106, :1107 |
| Phase | p1 |
| Test level | Both — E2E list and detail as `{admin}`; integration for the read-only caller without `counts` (needs an action-level PDP policy) |
| Gaps | G-OPS-01, G-OPS-02, G-OPS-43, G-CLM-13, G-WIRE-11 |

An operator dashboard lists every queue with the numbers PRD §5.2 asks for: queue depth, running count, concurrency limits, effective depth limits, and the number of tasks in each state. An autoscaler polls `GET /queues/{id}` for one queue instead of listing them all. Both calls need only the queue `read` action; seeing queues gives no task rights, and the reverse (PRD.md:923, DESIGN.md:980). The per-state `counts` and their `sampled_at` are returned only to callers that also hold `configure` on the queue (queues have no `admin` action, G-OPS-02).

## Setup
- `{admin}` (fixture): queue `read` and `configure`, task `admin`.
- Subject `{ops_viewer}` (root tenant), token `<ops-viewer-token>`. PDP grants it queue `read` and **no** task action (so no `admin`).
- **reports** holds, across tenants A and B: 12 `queued`, 3 `running`, 4 `scheduled`, 1 `waiting`. **default** holds 2 `queued`. No other live tasks.
- No config overrides; `queue_depth` config as shipped (DESIGN.md:2175-2181). The applied runtime config version in the `default` domain is 0 (none saved).
- The test waits until `sampled_at` of **reports** is later than the end of its setup (G-CLM-13); call that pass time `T0`.

## Request
```http
GET /api/task_engine/v1/queues HTTP/1.1
Host: api.example.com
Authorization: Bearer <admin-token>
```

## Expected response
- `200 OK`, `{ items }`, unpaged (G-WIRE-11).
- One item per registered queue, including the `dead_letter` queue (kind `dead_letter`, `limits` and `settings` `null`).
- Each dispatch item has `limits` with the **effective** values: concurrency from the registration, `queue_max_queue_depth` from the registration or the config default (1,000,000), `tenant_max_queue_depth` and `tenant_max_deferred_tasks` from config (100,000 each) (PRD.md:443, DESIGN.md:756, :2179). Effective means after config overrides ([Config precedence](3.02-positive-config-override-precedence.md)).
- `settings` carries the effective non-limit settings and `config_version` the runtime config version applied in the queue's domain (G-OPS-43).
- `counts` has one entry per live state, and `sampled_at` is the time of the maintenance leader's sampling pass; counts and every depth sample come from that one pass (G-OPS-01, G-CLM-13). Because the test waited for a pass after setup, the counts below are exact.
- `domains` is the queue's domain set, `["default"]` on a single-domain deployment; the dead-letter queue is not routed and lists none (Proposals › Domains › p1 lays the foundation).
- `hold` is `null` for queues that are not held (Proposals › Queue operations).
- The response contains no task IDs, inputs or tenant identifiers.

## Notes
- Counts cover all tenants: the caller holds `configure` on the queue. A caller without it gets no counts at all, so per-tenant usage is never shown to tenants (G-OPS-02, G-CLM-13).
- A dead-letter queue's counts (`dead_lettered`) and the empty `domains` are the scenarios' shape (S).
- `config_version: 0` for "no runtime config saved" is the scenarios' choice; the draft OpenAPI allows `null`.
