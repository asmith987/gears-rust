# An admin holds a queue

During an incident an operator stops new work from starting on **reports** without cancelling anything. The hold is stored in the queue's domain and shown on the queue; a `queueHeld` event records who held it, why, and until when, and is readable at `GET /queues/{id}/events`.

## Setup
- **reports** is not held; it has 12 `queued` and 3 `running` tasks.
- `{admin}` has queue `configure` (fixture).
- Clock `T0`.

## Request
```http
POST /api/task_engine/v1/admin/queues/gts.cf.core.tasks.queue.v1~acme.reports._.render.v1/hold HTTP/1.1
Host: api.example.com
Authorization: Bearer <admin-token>
Content-Type: application/json

{ "reason": "INC-4711 renderer outage" }
```

## Expected response
- `200 OK`, the queue resource with `hold` set (G-WIRE-12). `{admin}` holds queue `configure`, so `counts` and `sampled_at` are included (G-OPS-02).
- `hold.since` = `T0`, `hold.by` = `{admin}`, `hold.reason` as sent, `hold.until` = `null` (no automatic release). A hold with `until` is in [Release](2.03-positive-release-resumes-claims.md).

```json
{ "id": "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1", "kind": "dispatch",
  "domains": ["default"],
  "limits": { "global_concurrency_limit": 50, "per_tenant_concurrency_limit": 5,
              "queue_max_queue_depth": 1000000, "tenant_max_queue_depth": 100000,
              "tenant_max_deferred_tasks": 100000 },
  "settings": { "default_priority": 100, "…": "as in queues/1.01" },
  "config_version": 0,
  "counts": { "queued": 12, "running": 3, "claimed": 0, "scheduled": 0, "blocked": 0, "waiting": 0 },
  "sampled_at": "2026-11-03T10:00:00Z",
  "hold": { "since": "2026-11-03T10:00:00Z", "by": "{admin}", "reason": "INC-4711 renderer outage", "until": null } }
```

## Side effects
- The hold is stored in the domain of **reports** (`te_queue_holds`, G-OPS-03). The serving node applies it at once; every other node within `runtime_config_poll_secs` (5 s). No claim starts on any node more than 5 s after this response.
- From then on, claims skip **reports** ([What a hold changes](2.02-positive-held-queue-stops-claims-only.md)).
- history of queue `gts.cf.core.tasks.queue.v1~acme.reports._.render.v1` gains queueHeld with data `{ queue, actor: "{admin}", reason: "INC-4711 renderer outage" }` (no `until`), `subject` = the queue ID, `subject_type` = `gts.cf.core.tasks.queue.v1~`, tenant = root (G-OPS-04).
- event `queueHeld` for the queue is published to the task-events topic under the engine-wide default publishing policy (G-OPS-05).
- subsequent `GET /queues/gts.cf.core.tasks.queue.v1~acme.reports._.render.v1/events` as `{admin}` returns `200` with the `queueHeld` item (`actor: "{admin}"`), paged like task history (G-OPS-05).
- No task changes: states, leases, timers and counters of the 15 live tasks are untouched.
- `GET /queues/{id}` shows the same `hold` object.

## Notes
- Propagation: each node caches holds and refreshes them every `runtime_config_poll_secs` (5 s); there is no per-claim read, so a claim that starts on another node in the first 5 s may still take a task (G-OPS-03).
- `queueHeld` and `queueReleased` payloads follow G-OPS-04; their schema files under `schemas/types/` are still to be written.
- Hold edge cases (repeat hold, `until` in the past, dead-letter queue) are in [Hold and release edge cases](2.04-guardrail-hold-and-release-edge-cases.md).
