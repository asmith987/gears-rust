"Held queue: creates accepted, no claims from it, leased tasks finish, timers keep running." A hold never takes a task from its worker and does not freeze time: held time counts toward the queue timeout (G-OPS-07). The representative case: a worker that consumes **reports** and **bulk** keeps getting **bulk** work while **reports** is held, even though **reports** has older and `critical` tasks. The other rows check each operation on a held queue.

## Setup
- **reports** is held since `T0` ([Hold a queue](2.01-positive-hold-queue.md)). It has `{task_1}` (`queued`, `urgency: critical`, created `T0-10m`) for `{tenant_a}`.
- **bulk** is not held. It has `{task_2}` (`queued`, `normal`, created `T0-1m`) for `{tenant_a}`.
- Both queues are in the `default` domain. No concurrency limit is full.

## Request
```http
POST /api/task_engine/v1/tasks/claim HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "worker_id": "reports-7f9c-1", "session_id": null,
  "queues": ["gts.cf.core.tasks.queue.v1~acme.reports._.render.v1", "gts.cf.core.tasks.queue.v1~acme.reports._.bulk.v1"],
  "max_tasks": 2, "timeout_secs": 0 }
```

## Expected response
- `200 OK` with exactly one claim: `{task_2}` from **bulk**.
- `{task_1}` is not claimed although it is `critical` and older; the held queue is left out before the critical-first probe.

```json
{ "session_id": "{session_1}", "domain": "default", "heartbeat_interval_secs": 10,
  "claims": [ {
    "task": { "id": "{task_2}", "queue": "gts.cf.core.tasks.queue.v1~acme.reports._.bulk.v1", "state": "claimed", "attempt": 1, "…": "other fields as in CONVENTIONS §5.1" },
    "lease": { "lease_token": "{lt_1}", "lease_epoch": 1, "attempt": 1, "lease_secs": 30, "domain": "default" },
    "authority": { "mode": "creator_verified", "checked": [], "checked_at": "2026-11-03T09:59:00Z" },

```

## Side effects
- Shared: the hold itself changes no task; only claims from the held queue stop.

## Notes
- The skip sits where blacklisted queues are already removed from the claim's queue set (DESIGN.md:2433), so a held queue costs no scan budget. A hold reaches other nodes within `runtime_config_poll_secs` (5 s), so a claim on another node in the first 5 s may still take a task (G-OPS-03).
- With `timeout_secs: 0` no long poll happens (representative). A claim naming only held queues long-polls and answers `204`; the queue watcher skips held queues. On release the releasing node wakes its parked claims at once; other nodes resume within one refresh plus one poll interval (G-OPS-06, [Release](2.03-positive-release-resumes-claims.md)).
- A `slotReleased` signal (DESIGN.md:758) may wake parked claims after a completion; they find **reports** held and go back to waiting.
- The create response does not tell the producer the queue is held. A producer that wants to know reads `GET /queues/{id}` (needs queue `read`).
- Held tasks stay `queued` and keep counting toward the depth limits, which is the intended back-pressure. The per-tenant check reads a sample, so creates admitted within one sampling interval before the count reached 100 may overshoot by up to one interval of admissions (Proposals › Limits and counters). The refusal itself lives in [limits/depth](../limits/depth/1.02-negative-queue-depth-full-by-dimension.md).
- The "hand-over" moves are never refused by depth limits (DESIGN.md:560), so a long hold can push a tenant's queued count over its limit through timers alone.
- Held time counts toward the queue timeout: queue timers keep firing during a hold, because a queue timeout measures staleness (PRD.md:517). This reverses the proposal's Open-question leaning (G-OPS-07).
