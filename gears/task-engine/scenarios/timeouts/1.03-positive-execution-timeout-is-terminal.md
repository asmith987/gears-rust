# The execution timeout ends a running task even while its worker heartbeats, also at the engine default

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-timeouts` (PRD.md:519) · DESIGN.md:531, :542, :577, :715, :795, :806, :2086, :2204, :2770-2773 · ADR-0017:67 · PRD.md:1479, :1534 |
| Phase | p1 (DLQ routing p2) |
| Test level | Both — E2E with 1–2 s per-task timeouts; integration for exact timing |
| Gaps | G-RTY-01, G-EXE-10 |

A heartbeat renews the worker session, never the execution deadline (DESIGN.md:806). The claim sets `execution_deadline` = claim time + execution timeout, and `start` never moves it (G-EXE-10). A handler stuck in a live process therefore keeps its lease only until `execution_deadline`; then the deadline scan ends the task `timed_out` (DESIGN.md:2771-2772). This is attributed to the task: it is never retried and not counted against the worker (PRD.md:519). Every task has an execution timeout: when no level sets one, the engine default is stored at create and enforced the same way.

## Setup
- `{task_1}`: **render** on **reports** (`execution_timeout_secs: 900`, DLQ **dead_letter**, `max_retries: 3`), `retry_count: 0`.
- Claimed at `T0` by `reports-7f9c-1` in `{session_1}` with `{lt_1}`, so `execution_deadline = T0+900s`; started at `T0+1s` (the deadline does not move). The handler hangs; the process keeps heartbeating every 10 s.

## Exchange 1 — the deadline scan runs (no request)
Between `T0+900s` and `T0+901s` the deadline scan finds `state_code = running AND execution_deadline < now` and calls `finalize(timed_out, dlq_or_failed)` (DESIGN.md:2771-2772).

## Request
The process's next heartbeat, at `T0+905s`:
```http
POST /api/task_engine/v1/tasks/heartbeat HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "session_id": "{session_1}", "leases": [ { "task_id": "{task_1}", "lease_token": "{lt_1}" } ] }
```

## Expected response
- `200 OK`; the session is renewed, and `{task_1}` reports `outcome: lease_lost` (its token was cleared, DESIGN.md:577).

```json
{ "session_id": "{session_1}", "heartbeat_interval_secs": 10,
  "results": [ { "task_id": "{task_1}", "outcome": "lease_lost" } ] }
```

## Side effects
- task `{task_1}` state is `dead_lettered`; result_code is `timed_out`; `retry_count` stays `0` and no `scheduled` timer is armed (never retried).
- `queue_global(reports)` and `queue_tenant(reports, tenant_a)` concurrency used change by `-1`.
- history of `{task_1}` gains `taskDeadLettered` (`result_code: timed_out`) and `taskTimedOut` (`timeout_type: execution`); both are published.
- metric `te_lease_expired_total{cause="execution"}` increases by 1.
- Blacklist (p3): nothing is recorded for `reports-7f9c-1` (DESIGN.md:542, :2773).
- subsequent `complete` with `{lt_1}` returns `409` `LEASE_LOST`.

## Notes
- When the session has also expired and the session scan gets there first, the outcome is the same: see [Session expiry after the execution deadline](../worker/sessions/1.09-guardrail-execution-deadline-wins-over-session-expiry.md).
- The transition table is authoritative (DESIGN.md:542); the state diagram (DESIGN.md:488-489) gains the timeout edge (G-RTY-01, doc edit only).
- A task never started (`start` is optional) is bounded the same way: the deadline also covers `claimed` (G-EXE-10).
- engine-default: **render** is tenant-owned, so its effective timeout is also capped at `trust_limits.tenant_owned.max_execution_timeout_secs` (3600, DESIGN.md:2204); here both give 3600.
