# Lifetime and SLA deadlines run from creation across a retry, a requeue and a wait

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-timeouts` (PRD.md:526) · DESIGN.md:538-539, :532, :554, :2796 · ADR-0003:67 · PRD.md:1479 |
| Phase | p1 |
| Test level | Integration — clock across retry/requeue/wait |
| Gaps | G-EXE-05, G-RTY-02, G-WAI-09, G-WAI-12 |

The lifetime timer and the SLA timer are armed at creation and removed only by a terminal transition (DESIGN.md:554). A retry, a liveness requeue, parking in `waiting` and resuming never move them. Only the state-specific deadlines (queue, scheduled, assignment, execution, wait) are dropped and set again.

## Setup
- `{task_1}`: **render** on **reports**, created at `T0` with `"sla_deadline": "2026-11-03T10:02:00Z"` (`T0+120s`) and `"timeouts": { "lifetime_timeout_secs": 300 }`. Timers `lifetime` at `T0+300s` and `sla` at `T0+120s` are armed.

## Exchange 1 — attempt 1 fails with a retryable error
Claimed `T0+1s` (`{lt_1}`), started `T0+2s`; at `T0+10s`:
```http
POST /api/task_engine/v1/tasks/{task_1}/complete HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{
  "lease_token": "{lt_1}",
  "result_code": "error",
  "error": {
    "domain": "acme.reports",
    "code": "RENDER_TIMEOUT",
    "message": "renderer timed out",
    "fault": "dependency",
    "retryable": true
  }
}
```
- `200 OK`, `state: scheduled`, `retry_count: 1`, `run_after` in `[T0+14s, T0+15s]`.

## Exchange 2 — attempt 2 loses its worker (no request)
Claimed `T0+16s` (`{lt_2}`, `{session_2}`), started `T0+17s`; the process dies; `lease_until = T0+47s`. At `T0+48s` the session scan requeues it: `state: scheduled`, `liveness_requeues: 1`, `run_after` in `[T0+52s, T0+53s]`.

## Exchange 3 — attempt 3 parks on a timer wait
Claimed `T0+54s` (`{lt_3}`), started `T0+55s`; at `T0+60s`:
```http
POST /api/task_engine/v1/tasks/{task_1}/wait-conditions HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "lease_token": "{lt_3}", "mode": "all", "park": true,
  "conditions": [ { "kind": "timer", "resume_at": "2026-11-03T10:06:40Z" } ] }
```
- `200 OK`, `task_state: waiting` (wait resumes at `T0+400s`).

## Exchange 4 — the SLA deadline passes while waiting (no request)
At `T0+120s`: `slaBreached` with `sla_deadline: "2026-11-03T10:02:00Z"`; the task stays `waiting`.

## Exchange 5 — the lifetime deadline passes while waiting
At `T0+300s` the `lifetime` timer ends the task. At `T0+301s`:
```http
GET /api/task_engine/v1/tasks/{task_1} HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
```

## Expected response
- `200 OK`, `state: dead_lettered`, `result.result_code: timed_out`, `attempt: 3`, `retry_count: 1`, `liveness_requeues: 1`.

## Side effects
- The `lifetime` timer row armed at creation (`T0+300s`) and the `sla` timer row (`T0+120s`) are the same rows throughout exchanges 1–3; neither is deleted or re-armed (DESIGN.md:538, :2796).
- After exchange 5: the wait condition and the task's `wait` timer are deleted (finalize step 5, DESIGN.md:2942); the timer wait never resumes the task.
- history of `{task_1}`, in order (lifecycle events of interest): `taskRetrying` (`cause: reported`), `taskRetrying` (`cause: liveness`, `timeout_type: heartbeat`) (G-EXE-05, G-RTY-02), `waitConditionSet`, `taskWaiting` (G-WAI-12), `slaBreached`, `taskTimedOut` (`timeout_type: lifetime`) and `taskDeadLettered`.
