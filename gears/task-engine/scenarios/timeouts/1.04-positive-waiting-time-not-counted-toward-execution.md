# Time spent waiting does not count toward the execution timeout

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-timeouts` (PRD.md:519) · DESIGN.md:531, :532, :731, :795 · queue schema `execution_timeout_secs` |
| Phase | p1 |
| Test level | Integration — clock |
| Gaps | G-RTY-22, G-EXE-10 |

Parking clears `execution_deadline` (DESIGN.md:532), and every claim, including the claim after a resume, sets it again to claim time + `execution_timeout` (G-EXE-10, G-RTY-22). A task that runs 600 s, waits 20 minutes, and resumes gets a fresh 900 s from its new claim; the wait is not counted.

## Setup
- `{task_1}`: **render** on **reports** (`execution_timeout_secs: 900`), claimed at `T0` (`{lt_1}`, `attempt: 1`), so `execution_deadline = T0+900s`; started at `T0+1s`.
- At `T0+600s` the worker parks on a timer wait with `resume_at = T0+1800s` (request as in [Deadlines survive](1.08-flow-deadlines-survive-retries-requeues-and-waits.md), exchange 3). `execution_deadline` is cleared.
- At `T0+1800s` the task resumes to `queued`; `reports-7f9c-2` claims it at `T0+1801s` (`{lt_2}`, `attempt: 1`, resumed claims do not bump it, DESIGN.md:731) so `execution_deadline = T0+2701s`; it starts it at `T0+1802s` (the deadline does not move).

## Request
At `T0+2000s`, well past the first run's deadline `T0+900s`:
```http
POST /api/task_engine/v1/tasks/heartbeat HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "session_id": "{session_2}", "leases": [ { "task_id": "{task_1}", "lease_token": "{lt_2}" } ] }
```

## Expected response
- `200 OK`; `{task_1}` is `ok`, `state: running`.

```json
{ "session_id": "{session_2}", "heartbeat_interval_secs": 10,
  "results": [ { "task_id": "{task_1}", "outcome": "ok", "state": "running", "cancel_requested": false } ] }
```

## Side effects
- No `taskTimedOut` was recorded at `T0+900s` (the task was `waiting`, with no execution deadline).
- If the handler never finishes, the deadline scan ends it at `T0+2701s` as in [1.03](1.03-positive-execution-timeout-is-terminal.md).

## Notes
- Decided per claim (G-RTY-22): each claim gets the full execution timeout, not a budget shared across the runs of one attempt; the lifetime timeout bounds the total. A task that parks often has no other bound on its total running time.
