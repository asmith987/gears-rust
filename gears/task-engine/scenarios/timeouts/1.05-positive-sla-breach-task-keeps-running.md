# Passing the SLA deadline publishes slaBreached and the task keeps running

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-timeouts` (PRD.md:522) · DESIGN.md:524, :784, :2735 · `sla_breached.v1` schema · PRD.md:1514 |
| Phase | p1 |
| Test level | Both — E2E short SLA; slaBreached via history |
| Gaps | G-EXE-10 |

An SLA deadline is a report, not a limit: when it passes before the task finishes, the engine publishes `slaBreached`, and the task, its lease and its worker carry on (PRD.md:522).

## Setup
- `{task_1}`: **render** on **reports**, created at `T0` with `"sla_deadline": "2026-11-03T10:10:00Z"` (`T0+600s`); timer `sla` for `{task_1}` is armed at `T0+600s` (DESIGN.md:524).
- Claimed at `T0+10s` by `reports-7f9c-1` in `{session_1}` with `{lt_1}`, so `execution_deadline = T0+910s` (set by the claim, G-EXE-10); started at `T0+11s`, heartbeating.

## Exchange 1 — the SLA timer fires (no request)
At `T0+600s` the timer wheel enqueues `slaBreached`; the task is not changed (DESIGN.md:2735).

## Request
At `T0+605s`:
```http
POST /api/task_engine/v1/tasks/heartbeat HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "session_id": "{session_1}", "leases": [ { "task_id": "{task_1}", "lease_token": "{lt_1}" } ] }
```

## Expected response
- `200 OK`; `{task_1}` is `ok`, `state: running`, `cancel_requested: false`.

```json
{ "session_id": "{session_1}", "heartbeat_interval_secs": 10,
  "results": [ { "task_id": "{task_1}", "outcome": "ok", "state": "running", "cancel_requested": false } ] }
```

## Side effects
- history of `{task_1}` gains `slaBreached` with `sla_deadline: "2026-11-03T10:10:00Z"` and `breached_at` in `[T0+600s, T0+601s]`; it is published to the task-events topic.
- metric `te_sla_breached_total{queue="…acme.reports._.render.v1"}` increases by 1.
- task `{task_1}` state stays `running`; lease `{lt_1}` stays valid; `execution_deadline` stays `T0+910s`.
- timer `sla` for `{task_1}` is completed; it does not fire again.
- A later successful `complete` gives `completed` / `success`; the breach does not change the result.
- A task that finishes before `T0+600s` never gets `slaBreached`: finalize deletes its `sla` timer (DESIGN.md:2942).
