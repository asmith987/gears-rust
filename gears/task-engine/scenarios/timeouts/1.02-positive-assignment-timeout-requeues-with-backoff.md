# A claimed task not started within the assignment timeout is requeued as a liveness failure

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-timeouts` (PRD.md:518) · `cpt-cf-task-engine-fr-retry` (PRD.md:786) · DESIGN.md:530, :539, :794, :2764-2775, :2784-2798 · ADR-0003:58 |
| Phase | p1 |
| Test level | Both — E2E with 1–2 s per-task timeouts; integration for exact timing |
| Gaps | G-RTY-01, G-RTY-02, G-EXE-05, G-EXE-10, G-EXE-11 |

A claim sets `assignment_deadline = now + assignment_timeout` (DESIGN.md:530). If the worker never calls `start`, the deadline scan treats it as a lost worker: the task goes to `scheduled` with backoff on the `max_liveness_requeues` budget, not `max_retries`, and it counts toward the blacklist (PRD.md:518). Heartbeats do not extend the deadline (ADR-0003:58). `start` is optional (G-EXE-11), but on a queue with an assignment timeout it is what ends this shorter bound on `claimed`; the execution deadline, set by the claim, bounds `claimed` and `running` alike (G-EXE-10).

## Setup
- `{task_1}`: **render** on **reports** (`assignment_timeout_secs: 60`, retry exponential base 5 s, jitter 0.2), claimed at `T0` by `reports-7f9c-1` in session `{session_1}` with `{lt_1}` (`attempt: 1`), so `assignment_deadline = T0+60s`.
- The worker heartbeats `{session_1}` every 10 s, but never calls `start`.

## Exchange 1 — the deadline scan runs (no request)
Between `T0+60s` and `T0+61s` the deadline scan finds `state_code = claimed AND assignment_deadline < now` and calls `liveness_failure` (DESIGN.md:2775). Say it runs at `T0+61s`.

## Request
At `T0+62s`:
```http
GET /api/task_engine/v1/tasks/{task_1} HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
```

## Expected response
- `200 OK`, `state: scheduled`, `liveness_requeues: 1`, `retry_count: 0`, `attempt: 1`, `assignment: null`.
- `run_after` between `T0+65s` and `T0+66s` (`n = 1`: 5 s, minus up to 20 % jitter).

```json
{ "id": "{task_1}", "state": "scheduled", "attempt": 1, "retry_count": 0, "liveness_requeues": 1,
  "run_after": "2026-11-03T10:01:06Z", "assignment": null, "…": "other fields as in CONVENTIONS §5.1" }
```

## Side effects
- lease `{lt_1}` is invalid: a later `start` from `reports-7f9c-1` returns `409` `LEASE_LOST`, and the next batch heartbeat reports `outcome: lease_lost` for `{task_1}`; `{session_1}` itself stays active.
- `queue_global(reports)` and `queue_tenant(reports, tenant_a)` concurrency used change by `-1`.
- timer `scheduled` for `{task_1}` is armed at its `run_after`; timer `lifetime` stays armed.
- metric `te_lease_expired_total{cause="assignment"}` increases by 1.
- history of `{task_1}` gains `taskRetrying` with `cause: liveness`, `timeout_type: assignment`, `run_after` (G-EXE-05, G-RTY-02). No `taskTimedOut` (the task did not end, DESIGN.md:2799).
- Blacklist (p3): one liveness failure for (`{worker_a}`, `reports-7f9c-1`) on **reports** (DESIGN.md:761).

## Notes
- The transition table (DESIGN.md:539) is authoritative; the state diagram (DESIGN.md:466-513) gains the `claimed → scheduled` edge (G-RTY-01, doc edit only).
- When the liveness budget is used up, the task ends `timed_out` with `timeout_type: assignment` (G-RTY-02).
