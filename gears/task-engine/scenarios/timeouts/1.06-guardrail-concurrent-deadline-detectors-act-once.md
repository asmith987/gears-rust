# When a deadline and a session expiry both find the same task, the task is handled once

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-timeouts` (PRD.md:518, :520-521) · DESIGN.md:543, :554, :797, :2734, :2755-2759, :2775, :2777-2799, :2806-2813 · ADR-0002:76 |
| Phase | p1 |
| Test level | Integration — race of detectors |
| Gaps | G-EXE-05, G-RTY-02, G-RTY-07 |

The session scan, the deadline scan and the timer wheel run in different shards (DESIGN.md:797) and can all find the same lost task. Each acts through a guarded update that repeats the observed `lease_epoch`, `lease_token` and state (DESIGN.md:2780-2782): the first one wins, the second matches no row and rolls back. The task is therefore requeued or ended exactly once.

Representative case: the assignment deadline and the session both expired. Both are liveness failures and both call `liveness_failure`; the task is requeued once and spends one unit of `max_liveness_requeues`.

## Setup
- `{task_1}`: **render** on **reports** (`assignment_timeout_secs: 60`), claimed at `T0` by `reports-7f9c-1` in `{session_1}` with `{lt_1}`; `assignment_deadline = T0+60s`; session `lease_until = T0+30s`. The process dies right after the claim.
- Both scans are paused until `T0+61s` (both shards lag), then run in either order (the test varies it).

## Exchange 1 — both scans run (no request)
At `T0+61s` both scans find `{task_1}`: the session scan through `{session_1}` (DESIGN.md:2755-2759), the deadline scan through `assignment_deadline` (DESIGN.md:2775).

## Request
At `T0+62s`:
```http
GET /api/task_engine/v1/tasks/{task_1} HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
```

## Expected response
- `200 OK`, `state: scheduled`, `liveness_requeues: 1` (not 2), `retry_count: 0`, `attempt: 1`; one `run_after` in `[T0+65s, T0+66s]`.

## Side effects
- Exactly one requeue: `queue_global(reports)` and `queue_tenant(reports, tenant_a)` concurrency used change by `-1` once; one timer `scheduled` for `{task_1}`.
- Blacklist (p3): one liveness failure for `reports-7f9c-1` on **reports** (coalesced per outage, DESIGN.md:2806-2813).
- history of `{task_1}` gains one `taskRetrying` with `cause: liveness`, not two; its `timeout_type` is `heartbeat` when the session scan wins and `assignment` when the deadline scan wins (G-EXE-05, G-RTY-02).
- session `{session_1}` is expired.

## Cases

| Case | Differs from the representative case | Expected | Notes |
|---|---|---|---|
| assignment-and-session | (representative) | one requeue, `liveness_requeues: 1` | DESIGN.md:2775, :2777-2795 |
| lifetime-and-session | `{task_1}` created at `T0` with `"timeouts": { "lifetime_timeout_secs": 600 }`, `running` under `{lt_1}` in `{session_1}`, execution deadline far away; the process dies after its heartbeat at `T0+560s` (`lease_until = T0+590s`); the session-scan shard and the timer-wheel shard are paused until `T0+601s`, then the session scan finds `{session_1}` expired and the timer wheel claims the `lifetime` timer, in an order the test varies; read at `T0+603s` | `200`, `state: dead_lettered`, `result_code: timed_out` in both orders; history gains exactly one `taskTimedOut`, with `timeout_type: lifetime`, and one `taskDeadLettered`, and no `taskRetrying`; `liveness_requeues: 0`; no blacklist strike; lease `{lt_1}` is invalid; slots are released once | G-RTY-07 |

## Notes
- lifetime-and-session: the shared expiry step reads the task's lifetime timer first; when it is due, the task ends `timed_out` (`lifetime`) with no requeue, no `liveness_requeues` increment and no blacklist strike (G-RTY-07). So both orders give the same end state and history. The execution-deadline precedence is in [worker/sessions](../worker/sessions/1.09-guardrail-execution-deadline-wins-over-session-expiry.md).
