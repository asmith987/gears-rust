# Flow: fan-out to children, park on a children wait, resume with counts, and a join successor that ignores failures

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-parent-child` (PRD.md:824-828) · `cpt-cf-task-engine-fr-wait-children` (PRD.md:617-619) · `cpt-cf-task-engine-fr-dependencies` (PRD.md:835-839) · PRD.md:1485, :1528 · DESIGN.md:532-533, :820 |
| Phase | p2 |
| Test level | E2E |
| Depends on | Proposals › Task mutability › Only the parent's worker adds children; Set only in the create request (`on_predecessor_failure`) · Proposals › Waits › Input and children waits stay p2 |
| Gaps | G-CLM-30, G-WAI-14 |

A render job for a 3-page report splits into one child per page. The parent's worker creates the children with its lease token, creates a join task that merges whatever pages succeeded, and parks on a children wait so it holds no slot while the pages render. One page fails for good; the parent resumes with the counts, and the join still runs because its links say `ignore`.

Single-step detail: [children](../hierarchy/children/), [dependencies](../hierarchy/dependencies/), [children waits](../waits/children/).

---

## Setup
- `{task_p}` (**render** on **reports**, `report_id: r-42`) is `running`, held by `reports-7f9c-1` with `{lt_p}`, `attempt: 1`, `lease_epoch: 1`.

## Exchange 1 — Create child page 1 (pages 2 and 3 alike)
```http
POST /api/task_engine/v1/tasks HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json
Idempotency-Key: r-42-page-1

{ "type": "gts.cf.core.tasks.task.v1~acme.reports._.render.v1~",
  "queue": "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1",
  "input": { "report_id": "r-42-p1", "format": "pdf" },
  "parent_task_id": "{task_p}", "parent_lease_token": "{lt_p}" }
```
- `201 Created` → `{task_c1}`, `parent_task_id: "{task_p}"`, `propagate_cancel: true`. Pages 2 and 3 → `{task_c2}`, `{task_c3}`.

## Exchange 2 — Create the join task
```http
POST /api/task_engine/v1/tasks HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json
Idempotency-Key: r-42-join

{ "type": "gts.cf.core.tasks.task.v1~acme.reports._.render.v1~",
  "queue": "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1",
  "input": { "report_id": "r-42-merge", "format": "pdf" },
  "dependency_mode": "all",
  "predecessors": [ { "task_id": "{task_c1}", "on_predecessor_failure": "ignore" },
                    { "task_id": "{task_c2}", "on_predecessor_failure": "ignore" },
                    { "task_id": "{task_c3}", "on_predecessor_failure": "ignore" } ] }
```
- `201 Created` → `{task_j}`, `state: blocked`. It is not a child of `{task_p}` (no `parent_task_id`), so the parent's children wait does not include it.

## Exchange 3 — The parent parks on a children wait
```http
POST /api/task_engine/v1/tasks/{task_p}/wait-conditions HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "lease_token": "{lt_p}", "mode": "all", "park": true, "checkpoint": { "phase": "pages_dispatched" },
  "conditions": [ { "kind": "children" } ] }
```
```json
{ "wait_group": { "id": "{wg_1}", "mode": "all", "parked": true,
                  "conditions": [ { "id": "{wc_1}", "kind": "children", "state": "pending", "timeout_at": null } ] },
  "task_state": "waiting" }
```
- `{task_p}` holds no slot, lease or assignee; it counts toward the deferred depth limit (`deferred`, G-CLM-30). `{lt_p}` is no longer valid.

## Exchange 4 — Children run
- `{task_c1}` and `{task_c2}` complete with `success`.
- `{task_c3}` fails with `fault: task`, `code: INVALID_REPORT` (non-retryable) → `dead_lettered`.
- When `{task_c3}` ends (the last child), `{wc_1}` is satisfied with `{ completed: 2, dead_lettered: 1 }` and `{task_p}` → `queued` with `resume_pending`. In the same cascade `{task_j}` → `queued`: every predecessor has ended, and the failed one counts as satisfied under `ignore`.

## Exchange 5 — A worker claims the resumed parent
```http
POST /api/task_engine/v1/tasks/claim HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "worker_id": "reports-7f9c-2", "session_id": "{session_2}",
  "queues": ["gts.cf.core.tasks.queue.v1~acme.reports._.render.v1"], "max_tasks": 1, "timeout_secs": 30 }
```
```json
{ "session_id": "{session_2}", "heartbeat_interval_secs": 10,
  "claims": [ {
    "task": { "id": "{task_p}", "state": "claimed", "attempt": 1, "context": { "phase": "pages_dispatched" }, "…": "…" },
    "lease": { "lease_token": "{lt_p2}", "lease_epoch": 2, "attempt": 1, "lease_secs": 30 },
    "authority": { "mode": "creator_verified", "checked": [], "checked_at": "2026-11-03T09:59:00Z" },
    "resumed": { "wait_group_id": "{wg_1}", "outcome": "satisfied",
                 "conditions": [ { "id": "{wc_1}", "kind": "children", "state": "satisfied",
                                   "result": { "completed": 2, "failed": 0, "cancelled": 0, "dead_lettered": 1 } } ] } } ] }
```
- `attempt` stays 1 (a resume is not a new attempt, PRD.md:661); `lease_epoch` +1. The resolved group stays until a new group replaces it or the task ends, so a repeated claim after a lost response returns `resumed` again (G-WAI-14).

## Exchange 6 — Parent and join finish
- `{task_p}`: start, then complete with `result_code: warning` and a warning naming page 3 → `completed`.
- `{task_j}` is claimed, started and completed with `success` (it merges pages 1 and 2).

## End state
- `{task_p}` completed (warning), `{task_c1}`/`{task_c2}` completed, `{task_c3}` dead_lettered, `{task_j}` completed.
- History of `{task_p}`: …, waitConditionSet, taskWaiting, waitConditionSatisfied, taskResumed, taskClaimed, taskStarted, taskCompleted.
- With `on_predecessor_failure: cancel` (the default) `{task_j}` would have ended `cancelled` with `dependency_failed` instead.

## Notes
- The order of the two cascades from `{task_c3}`'s terminal transition (resume the parent, unblock the join) is not specified; both happen in or right after that transaction (DESIGN.md:529 inline cascade). Not asserted.
- Children and children waits are p2 (PRD.md:617, :824); in p1 the same requests are refused with `400` ([waits/framework/1.12](../waits/framework/1.12-guardrail-p2-wait-kinds-and-parent-refused-in-p1.md)). The orders-workflow and rating re-rate adopters named by the proposal need this flow.
