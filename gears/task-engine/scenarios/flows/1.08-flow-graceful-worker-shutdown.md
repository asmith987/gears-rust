# Flow: a worker shuts down gracefully, releases its tasks, and another worker picks them up

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-release` (PRD.md:685-689) · PRD.md:661, :1526 · DESIGN.md:546, :703, :732, :1071 · ADR-0017:71 |
| Phase | p1 |
| Test level | E2E |
| Depends on | Proposals › Heartbeats and leases › The SDK releases dropped leases |

A rolling deploy sends `SIGTERM` to `reports-7f9c-1`, which holds two running tasks. The SDK stops claiming, saves a checkpoint for each task and releases them. They go straight back to `queued` with no retry or liveness budget used, no blacklist strike, and the same attempt; `reports-7f9c-2` claims them within the poll interval.

Single-step detail: [release](../worker/release/), [sessions](../worker/sessions/).

---

## Setup
- `reports-7f9c-1` (`{session_1}`) holds `{task_1}` (`running`, `{lt_1}`, `attempt: 2`, `retry_count: 1`) and `{task_2}` (`running`, `{lt_2}`, `attempt: 1`) on **reports**.
- `te_worker_blacklist({worker_a}, reports-7f9c-1, reports)`: `consecutive_failures = 2`.
- `reports-7f9c-2` long-polls **reports**.

## Exchange 1 — Release `{task_1}` with a checkpoint
```http
POST /api/task_engine/v1/tasks/{task_1}/release HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "lease_token": "{lt_1}", "checkpoint": { "pages_done": 7 } }
```
```json
{ "id": "{task_1}", "state": "queued", "attempt": 2, "retry_count": 1, "liveness_requeues": 0,
  "context": { "pages_done": 7 }, "assignment": null, "…": "other fields as in CONVENTIONS §5.1" }
```
- Slots freed at once; history gains taskQueued with `reason: released`, `actor: "{worker_a}"`; `newTask` wakes `reports-7f9c-2`.

## Exchange 2 — Release `{task_2}`
```http
POST /api/task_engine/v1/tasks/{task_2}/release HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "lease_token": "{lt_2}" }
```
- `200 OK`, `queued`, `attempt: 1`.

## Exchange 3 — The other worker's long poll returns both
```http
POST /api/task_engine/v1/tasks/claim HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "worker_id": "reports-7f9c-2", "session_id": "{session_2}",
  "queues": ["gts.cf.core.tasks.queue.v1~acme.reports._.render.v1"], "max_tasks": 2, "timeout_secs": 30 }
```
- `200 OK` with two claims: `{task_1}` with `attempt: 2` (unchanged, `resume_pending`), `lease_epoch` +1, `context: { "pages_done": 7 }`; `{task_2}` with `attempt: 1`.

## Exchange 4 — The old process exits
- It sends no more heartbeats. `{session_1}` holds no tasks, so it expires silently and is deleted by maintenance (ADR-0017:71): no requeue, no liveness failure, no blacklist strike.

## End state
- `{task_1}`: `retry_count: 1`, `liveness_requeues: 0`, `attempt: 2` — unchanged by the shutdown.
- `te_worker_blacklist({worker_a}, reports-7f9c-1, reports)`: `consecutive_failures = 2` (unchanged).
- The engine-side graceful shutdown (PRD.md:1314-1318) is separate: an engine instance finishes in-flight requests and flushes buffered progress within 30 s.

## Notes
- If the process were killed before releasing, its session would expire after one lease and the tasks would go back with liveness backoff and a strike ([1.03](1.03-flow-worker-crash-zombie-fenced.md)).
- A handler that returns without finishing is released by the SDK's heartbeat loop; a REST-only worker must call release itself.
