# Flow: retryable failures → backoff → retries exhausted → dead-lettered → re-enqueue → success

| | |
|---|---|
| Requirement | PRD §8 "Retry with Backoff After Transient Failure" (PRD.md:1452) · `cpt-cf-task-engine-fr-retry` (PRD.md:779-792) · `cpt-cf-task-engine-fr-dead-letter` (PRD.md:799-811) · PRD.md:1482-1484, :1537 · DESIGN.md:536-538, :545, :2854-2866 |
| Phase | p2 (dead-letter) |
| Test level | E2E |
| Gaps | G-EXE-05, G-RTY-03, G-RTY-04, G-RTY-12, G-SEC-11 |

The renderer's storage backend is down. The task fails with a retryable `fault=dependency` error four times: three retries with exponential backoff (5 s, 10 s, 20 s, each shortened by up to 20 % jitter), then the budget is gone and it is dead-lettered. After the outage an operator re-enqueues it, and it succeeds on a fresh budget.

Single-step detail: [retry](../retry/), [dead-letter](../dead-letter/).

---

## Setup
- `{task_1}` on **reports** (`max_retries: 3`, exponential, base 5 s, max 300 s, jitter 0.2, DLQ **dead_letter**), claimed by `reports-7f9c-1` as attempt 1, `{lt_1}`, started.

## Exchange 1 — Attempt 1 fails (`T0`)
```http
POST /api/task_engine/v1/tasks/{task_1}/complete HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{
  "lease_token": "{lt_1}",
  "result_code": "error",
  "error": {
    "domain": "acme.reports",
    "code": "STORAGE_UNAVAILABLE",
    "message": "blob store 503",
    "fault": "dependency",
    "retryable": true
  }
}
```
```json
{ "id": "{task_1}", "state": "scheduled", "attempt": 1, "retry_count": 1, "run_after": "2026-11-03T10:00:05Z",
  "…": "other fields as in CONVENTIONS §5.1" }
```
- `run_after` ∈ [`T0+4s`, `T0+5s`] (the first retry waits at most `base`, jitter only shortens, floor 1 s, G-RTY-04). Slots released; history gains taskRetrying with `cause: reported`, `run_after` and the full `error` (G-EXE-05, G-RTY-03).

## Exchange 2 — Attempts 2 and 3 fail the same way
- Each is a fresh claim (`attempt` 2, then 3; new token, `lease_epoch` +1) followed by the same `complete` with error.
- After attempt 2: `retry_count: 2`, wait ∈ [8 s, 10 s]. After attempt 3: `retry_count: 3`, wait ∈ [16 s, 20 s].

## Exchange 3 — Attempt 4 fails; the budget is used up
```http
POST /api/task_engine/v1/tasks/{task_1}/complete HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{
  "lease_token": "{lt_4}",
  "result_code": "error",
  "error": {
    "domain": "acme.reports",
    "code": "STORAGE_UNAVAILABLE",
    "message": "blob store 503",
    "fault": "dependency",
    "retryable": true
  }
}
```
```json
{ "id": "{task_1}", "state": "dead_lettered", "attempt": 4, "retry_count": 3,
  "queue": "gts.cf.core.tasks.queue.v1~cf.core.tasks.dead_letter.v1",
  "dead_lettered_from": "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1",
  "result": { "result_code": "error",
              "error": { "domain": "acme.reports", "code": "STORAGE_UNAVAILABLE", "message": "blob store 503", "context": null, "fault": "dependency", "retryable": true },
              "output": null, "warnings": [] },
  "…": "other fields as in CONVENTIONS §5.1" }
```
- History gains taskDeadLettered (`queue` = **dead_letter**, `dead_letter_queue` = **dead_letter**, `from_queue` = **reports**, `actor: {worker_a}`, `result_code: error`; field names per G-SEC-11). No `taskFailed`, as in [retry/1.03](../retry/1.03-positive-error-without-retry-ends-failed-or-dead-lettered.md). The worker is not blacklisted (`fault=dependency`).

## Exchange 4 — The operator finds it (after the outage)
```http
GET /api/task_engine/v1/tasks?$filter=state eq 'dead_lettered' and dead_lettered_from eq 'gts.cf.core.tasks.queue.v1~acme.reports._.render.v1'&$orderby=terminal_at desc HTTP/1.1
Host: api.example.com
Authorization: Bearer <admin-token>
```
- `200 OK`, `{task_1}` among the items.

## Exchange 5 — Re-enqueue
```http
POST /api/task_engine/v1/admin/tasks/{task_1}/reenqueue HTTP/1.1
Host: api.example.com
Authorization: Bearer <admin-token>
```
```json
{ "id": "{task_1}", "state": "queued", "queue": "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1",
  "dead_lettered_from": null, "attempt": 4, "retry_count": 0, "liveness_requeues": 0, "result": null,
  "terminal_at": null, "…": "other fields as in CONVENTIONS §5.1" }
```
- Re-enqueue clears `terminal_at`, the result and `dead_lettered_from` (G-RTY-12). Lifetime restarts from now; history gains taskQueued with `reason: reenqueued`, `actor: "{admin}"`.

## Exchange 6 — Attempt 5 succeeds
- Claim → `attempt: 5`; start; complete with `result_code: success` → `200`, `state: completed`.

## End state
- task {task_1} state is completed with `attempt: 5`, `retry_count: 0`.
- History, in order: taskCreated, (taskClaimed, taskStarted, taskRetrying) × 3, taskClaimed, taskStarted, taskDeadLettered, taskQueued (`reenqueued`), taskClaimed, taskStarted, taskCompleted.

## Notes
- A `fault=task` error with `INVALID_REPORT` (in `non_retryable_codes`) would skip the retries and dead-letter at once (PRD.md:781).
