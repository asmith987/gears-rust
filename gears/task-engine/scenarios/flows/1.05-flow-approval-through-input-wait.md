# Flow: an approval step through an input wait answered with `resolve`

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-wait-input` (PRD.md:606-610) · `cpt-cf-task-engine-fr-wait-conditions` (PRD.md:546) · DESIGN.md:819, :1095, :1098 · Proposals › Waits › `resolve` |
| Phase | p2 |
| Test level | E2E |
| Depends on | Proposals › Waits › `resolve` (accepted: own action, safe to repeat); Proposals › Task mutability › `update` covers only tags; `resolve` gets its own action · Proposals › Waits › Input and children waits stay p2 |
| Gaps | G-WAI-05, G-WAI-09, G-WAI-16 |

A billing export needs a human sign-off before it sends data out. The worker parks the task on an input wait; an approval service, which holds only `resolve` on the task, answers it; the task resumes with the answer and finishes. Orders-workflow (approval before fulfillment) is the adopter the Waits proposal names for input waits.

Single-step detail: [input waits](../waits/input/).

---

## Setup
- `{task_1}` (**export**, `period: 2026-10`, on **reports**) is `running`, held by `reports-7f9c-1` with `{lt_1}`.
- `{approver}` (tenant A service), token `<approver-token>`: task `read` and `resolve` on **export**, nothing else.

## Exchange 1 — The worker parks on an input wait
```http
POST /api/task_engine/v1/tasks/{task_1}/wait-conditions HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "lease_token": "{lt_1}", "mode": "all", "park": true, "checkpoint": { "rows": 18233 },
  "conditions": [ { "kind": "input", "prompt": "Approve export of 18233 rows for 2026-10?",
                    "input_schema": { "type": "object", "required": ["approved"],
                                      "properties": { "approved": { "type": "boolean" }, "comment": { "type": "string" } } },
                    "timeout_secs": 86400, "on_timeout": "fail" } ] }
```
```json
{ "wait_group": { "id": "{wg_1}", "mode": "all", "parked": true,
                  "conditions": [ { "id": "{wc_1}", "kind": "input", "state": "pending", "timeout_at": "2026-11-04T10:00:00Z" } ] },
  "task_state": "waiting" }
```

## Exchange 2 — The approval service finds the question
```http
GET /api/task_engine/v1/tasks/{task_1}/wait-conditions HTTP/1.1
Host: api.example.com
Authorization: Bearer <approver-token>
```
- `200 OK` with `{wc_1}`, its `prompt` and `input_schema`.

## Exchange 3 — Approve
```http
POST /api/task_engine/v1/wait-conditions/{wc_1}/resolve HTTP/1.1
Host: api.example.com
Authorization: Bearer <approver-token>
Content-Type: application/json

{ "value": { "approved": true, "comment": "ok by finance" } }
```
```json
{ "condition": { "id": "{wc_1}", "kind": "input", "state": "satisfied", "resolved_at": "2026-11-03T10:20:00Z", "resolved_by": "{approver}" } }
```
- `{task_1}` → `queued` with `resume_pending`; timer wait for {task_1} is removed (one `wait` timer per task, G-WAI-09).

## Exchange 4 — The service retries after a timeout on its side
- The same request again from `{approver}` → `200 OK`, same body, `Idempotency-Replayed: true`, nothing written ([waits/input/1.02](../waits/input/1.02-positive-repeat-with-same-value-succeeds.md)). A different value, or the same value from another subject, → `400` `failed_precondition` with `violations[{ type: "STATE", subject: "ALREADY_RESOLVED" }]` (G-WAI-05, [waits/input/1.04](../waits/input/1.04-negative-resolve-state-refusals.md)).

## Exchange 5 — A worker claims the resumed task
- Claim → `200` with `{task_1}`, `attempt` unchanged, `context: { "rows": 18233 }`, and `resumed.conditions[0].result = { "approved": true, "comment": "ok by finance" }`.
- The worker sends the export and completes with `success`.

## End state
- task {task_1} state is completed.
- History: …, waitConditionSet, taskWaiting, waitConditionSatisfied (`actor: "{approver}"`), taskResumed, taskClaimed, taskStarted, taskCompleted.
- `{approver}` could not have cancelled, re-enqueued or read other types' tasks: `resolve` grants only the answer.

## Notes
- If nobody answers within 24 h, `on_timeout: fail` ends the task `timed_out` and dead-lettered; history records `waitTimedOut` then `taskTimedOut` with `timeout_type: wait` (G-WAI-16).
- Input waits are p2 (PRD.md:606); in p1 the set-wait is refused with `400` ([waits/framework/1.12](../waits/framework/1.12-guardrail-p2-wait-kinds-and-parent-refused-in-p1.md)). Event waits, and an approval service built on them, come later (Proposals › Waits › Event waits after the others).
