# GET /tasks/count counts what the same search would return, capped at search_max_count

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-search` (PRD.md:1139, :1145) · PRD.md:1509 · DESIGN.md:1105, :1174, :2149, :2846-2848 |
| Phase | p1 |
| Test level | E2E |
| Gaps | G-SEC-20, G-RTY-10 |

A page carries no total, so the count is its own endpoint. It takes the same `$filter`, the same window and the same authorization as search. It reads at most `search_max_count + 1` rows per table, so its cost stays bounded for a tenant with millions of tasks.

## Setup
- Tenant A: 12 `failed` **render** tasks created in the last 7 days, 3 created `T0-10d`. Tenant B: 5 `failed` tasks.

## Request
```http
GET /api/task_engine/v1/tasks/count?$filter=state eq 'failed' HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
```

## Expected response
- `200 OK`:
```json
{ "count": 12, "capped": false }
```
- The 3 older tasks are outside the default window; tenant B's 5 are outside the caller's scope.

## Notes
- With several domains each counts up to the cap and the sum is capped (DESIGN.md:2847-2848).
- Count follows search's authorization: an outright `read` denial → `403` `ACTION_DENIED`; a scope that matches nothing → `{ "count": 0, "capped": false }` (G-SEC-20).
- A count whose state filter restricts it to `dead_lettered` has no window, as the search (G-RTY-10).
- Count takes only `$filter`: [count rejects paging and view](1.07-negative-count-rejects-paging-and-view.md).
