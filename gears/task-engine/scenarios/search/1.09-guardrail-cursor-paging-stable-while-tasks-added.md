# Cursor paging stays stable while tasks are being added

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-search` (PRD.md:1138-1139) · PRD.md:1508 · DESIGN.md:1147, :1176, :2829-2844 |
| Phase | p1 |
| Test level | E2E |
| Gaps | G-SEC-26 |

Keyset paging on `(created_at, id)` means a new task never shifts the pages a client is walking: no item is repeated and none is skipped. With the default newest-first order, tasks created after the first page simply do not appear in later pages.

## Setup
- Tenant A has 150 `queued` **render** tasks `{t_1}`…`{t_150}` (`{t_150}` newest), all in the default window.

## Exchange 1 — first page
```http
GET /api/task_engine/v1/tasks?$filter=state eq 'queued'&limit=100&view=tiny HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
```
- `200`; items `{t_150}` … `{t_51}`; `page_info.next_cursor = {cursor_1}`.

## Between the pages
- `{creator_a}` creates 30 more queued tasks `{t_151}`…`{t_180}`.

## Exchange 2 — next page
```http
GET /api/task_engine/v1/tasks?$filter=state eq 'queued'&limit=100&view=tiny&cursor={cursor_1} HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
```
- `200`; items exactly `{t_50}` … `{t_1}`; `next_cursor: null`. None of `{t_151}`…`{t_180}`, no item from page 1.

<!-- No side effects: reads only. -->

## Notes
- The second request repeats `$filter` and sends no `$orderby` and the same `view` (the cursor fixes the order and binds `$filter`, `view` and `$select`; a different one is `400` on `cursor` with `FILTER_MISMATCH` or `FIELD_SELECTION_MISMATCH`, G-SEC-26, `docs/toolkit_unified_system/07_odata_pagination_select_filter.md:578`).
- The default window is anchored at `now` on each request. Whether the cursor pins the window's lower bound of page 1 is not stated; with a 7-day window and fast paging it makes no difference here.
- With several task domains the cursor carries per-domain positions (DESIGN.md:1176); the same assertions hold.
