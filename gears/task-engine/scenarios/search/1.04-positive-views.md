# The view decides which fields each search item carries: tiny, short, long, full

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-search` (PRD.md:1136, :1144, :1147) · DESIGN.md:1163-1172, :2146, :2151 |
| Phase | p1 |
| Test level | E2E |
| Depends on | Proposals › API reads and responses › Bounded responses (accepted: every list embedded at `full` is capped) — row `full` |
| Gaps | G-SEC-04, G-SEC-06, G-SEC-25, G-RTY-11 |

`tiny` is the cheapest view for long lists and polling dashboards. `short` (the default) adds the scheduling fields. `long` decompresses the payload columns and adds the caller's own data to each item, nothing about other tasks. `full` adds the task's recent history, wait conditions, entries and dependencies, each capped so that a page costs at most `$top × (base + caps)`; the complete history is read from the history endpoint.

## Setup
- Tenant A: `{task_1}` (**render**, `queued`) in the default window.

## Request
```http
GET /api/task_engine/v1/tasks?view=tiny HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
```

## Expected response
- `200`; each item has exactly `id`, `state`, `type`.
```json
{ "items": [ { "id": "{task_1}", "state": "queued", "type": "gts.cf.core.tasks.task.v1~acme.reports._.render.v1~" } ],
  "page_info": { "next_cursor": null, "prev_cursor": null, "limit": 25 } }
```

## Notes
- Search items use the task resource's names: `assignment` (DESIGN.md:1168 `assignee`) and `result` (DESIGN.md:1169 `output`), agreed in the wire review (G-SEC-04). `short` also carries `dead_lettered_from` (G-RTY-11).
- With no `limit` the page size is 25 (G-SEC-25).
- `full` caps, agreed (G-SEC-06): events newest 50, entries newest 20, wait conditions of the current group, all dependencies (≤ 64).
- `$select` can only narrow inside the view; a field outside it is refused ([unsupported query](1.06-negative-unsupported-query.md)).
