# Bulk reprioritize changes the priority or urgency of waiting tasks, per task

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-bulk-ops` (PRD.md:1156, :1163) · `cpt-cf-task-engine-fr-priority-dispatch` (PRD.md:396) · PRD.md:398 · DESIGN.md:1115 |
| Phase | p2 |
| Test level | E2E |
| Gaps | G-OPS-14, G-OPS-19 |

An operator moves a tenant's urgent reports ahead of its other work by lowering their priority number. Priority orders only the tenant's own tasks (PRD.md:398), so no `expedite` is needed. Urgency is the only field that ranks tenants against each other (PRD.md:396), so raising it to `critical` is gated by `expedite`, checked per task.

## Setup
- `{task_1}`: `queued`, priority 100. `{task_2}`: `scheduled`, priority 100. `{task_3}`: `completed`. All tenant A on **reports**.

## Request
```http
POST /api/task_engine/v1/tasks/bulk/reprioritize HTTP/1.1
Host: api.example.com
Authorization: Bearer <admin-token>
Content-Type: application/json

{ "task_ids": ["{task_1}", "{task_2}", "{task_3}"], "priority": 10 }
```

## Expected response
- `200 OK`.

```json
{ "results": [
  { "task_id": "{task_1}", "outcome": "succeeded" },
  { "task_id": "{task_2}", "outcome": "succeeded" },
  { "task_id": "{task_3}", "outcome": "invalid_state" }
] }
```

## Cases

| Case | Differs from the representative | Expected outcome | Notes |
|---|---|---|---|
| priority on queued / scheduled | `{task_1}`, `{task_2}` | `succeeded`; task {task_1}.priority advances from 100 to 10, same for {task_2}; history of {task_1} gains taskUpdated with `actor: "{admin}"`, `changes.priority` 100 → 10 (same for {task_2}); {task_1} is now ahead of tenant A's other queued tasks on **reports** at the next claim; tenant B's order is unchanged | PRD.md:398; G-OPS-19 |
| terminal task | `{task_3}` | `invalid_state`; unchanged, no event | see Notes |
| raise to `critical` without `expedite` | caller `{ops_a}` (tenant A operator, token `<ops-a-token>`: task `admin` and `read` in tenant A; `expedite` only for type **export**); `{task_1}` **render** `queued` `normal`; body `{ "task_ids": ["{task_1}", "{task_2}"], "urgency": "critical" }` with `{task_2}` **export** `queued` `normal` | `{task_1}`: `unauthorized`, urgency stays `normal`, no event | PRD.md:396 |
| raise to `critical` with `expedite` | same request, `{task_2}` | `succeeded`; task {task_2}.urgency advances from normal to critical; history of {task_2} gains taskUpdated with `actor: "{ops_a}"`, `changes.urgency` normal → critical; {task_2} is claimed before `normal` tasks of its queue | |

## Side effects
- Per row. Each change records `taskUpdated { actor, changes }` with the old and new value of each changed field (G-OPS-19). Refused tasks are unchanged and gain no event.

## Notes
- Which states accept a new priority is not said. Assumed: any non-terminal state; terminal → `invalid_state`. A `running` task's priority would matter only after a retry.
- Lowering `critical` back to `normal` is assumed to need only `admin`. Not specified.
- An outright PDP denial of `admin` refuses the whole request with `403 ACTION_DENIED` (G-OPS-14); see [1.01](1.01-positive-bulk-cancel-per-task-outcomes.md).
