# Set-wait refusals leave the task and the lease untouched

A set-wait that breaks one of the framework rules is refused as a whole, before any write: the task is not parked, no condition is stored, no checkpoint is applied, and the worker keeps its lease. The rules: a task has one current wait group, and a pending (armed) group cannot be replaced or extended; a group has between 1 and 16 conditions; a timer condition takes no timeout, and `on_timeout` needs a timeout (except on an event condition, whose omitted timeout means `event_waits.max_wait_secs`); set-wait is a worker call fenced by a lease token (an API consumer can no longer park a task after creation); and a checkpoint sent with the wait must keep `input + context + output` within 64 KiB. A `claimed` task that was not started may set a wait (G-WAI-20): see [1.01](1.01-positive-set-wait-parks-task.md) case `from_claimed`.

## Setup
- `{creator_a}` created `{task_1}` (**render**, queue **reports**); `reports-7f9c-1` holds it `running` under `{lt_1}`.
- Representative case `armed_group_pending`: `{task_1}` already has the armed group `{wg_1}` with one timer condition `{wc_1}` (`resume_at` `T0+1h`), set with `park: false`.

## Request

```http
POST /api/task_engine/v1/tasks/{task_1}/wait-conditions HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{
  "lease_token": "{lt_1}",
  "mode": "all",
  "park": true,
  "conditions": [ { "kind": "timer", "resume_at": "2026-11-03T12:00:00Z" } ]
}
```

## Expected response
- `400 Bad Request`, category `failed_precondition`, a plain state conflict (`subject: STATE`) (DESIGN.md:822).

```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.failed_precondition.v1~",
  "title": "Failed Precondition",
  "status": 400,
  "detail": "Task {task_1} already has a pending wait group",
  "instance": "/api/task_engine/v1/tasks/{task_1}/wait-conditions",
  "trace_id": "<trace>",
  "context": {
    "resource_type": "gts.cf.core.tasks.task.v1~", "resource_name": "{task_1}",
    "violations": [ { "type": "STATE", "subject": "STATE", "description": "the armed group {wg_1} is still pending; park it first" } ]
  }
}
```

## Side effects
<!-- No side effects: the request is refused before any write. -->
- `{task_1}` stays `running`; `{lt_1}` stays valid (a heartbeat with it returns `outcome: ok`).
- No `te_wait_conditions` row is written; an existing group (case `armed_group_pending`) is unchanged; `context` is unchanged; no history event.

## Notes
- `missing_lease_token`: the schema requires `lease_token`, so the check runs before any task lookup and reveals nothing about `{task_1}` (G-WAI-01). A caller that sends a token it does not hold gets `409 LEASE_LOST` like any non-holder (G-EXE-09). After the accepted change a consumer request never touches the worker's lease.
- A consumer that wants a task to start waiting sets an initial wait group on create: see [1.04](1.04-positive-initial-wait-group-resumes-created-task.md). The limit of 16 conditions and the empty-group rule apply to that group too (G-WAI-06).
- `checkpoint_over_payload_limit`: PRD.md:260 says a write over the limit "changes nothing"; the task is not parked either.
- A full deferred limit refuses the park with `429`: see [limits/depth](../../limits/depth/1.03-negative-deferred-limit-refuses-every-deferral.md).
- p2 condition kinds in p1: see [1.12](1.12-guardrail-p2-wait-kinds-and-parent-refused-in-p1.md).
