# A task created with an initial wait group starts waiting and resumes like any parked task

A consumer that wants "run this at 10:30" or "run when approved" sets the wait group in the create request. The task starts in `waiting`, holds nothing, and when the group is satisfied it goes to `queued` and is claimed for its **first** attempt with the wait result. The create side is in [tasks/create](../../tasks/create/); this file covers the resume side.

## Setup
- `{creator_a}` sent, at `T0`:

```http
POST /api/task_engine/v1/tasks HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
Content-Type: application/json
Idempotency-Key: 7d1f0c2e-render-r-43

{
  "type": "gts.cf.core.tasks.task.v1~acme.reports._.render.v1~",
  "queue": "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1",
  "input": { "report_id": "r-43", "format": "pdf" },
  "wait": { "mode": "all", "conditions": [ { "kind": "timer", "resume_at": "2026-11-03T10:30:00Z" } ] }
}
```

  and got `201 Created` with `{task_1}` in `state: waiting`, `attempt: 0`, `assignment: null`.
- At `T0+30m` the timer fires and `{task_1}` moves `waiting → queued`.

## Request

```http
POST /api/task_engine/v1/tasks/claim HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "worker_id": "reports-7f9c-1", "session_id": null,
  "queues": ["gts.cf.core.tasks.queue.v1~acme.reports._.render.v1"], "max_tasks": 1, "timeout_secs": 30 }
```

## Expected response
- `200 OK`; first claim: `attempt` 1, `lease_epoch` 1; `resumed` carries the satisfied timer.

```json
{ "session_id": "{session_1}", "heartbeat_interval_secs": 10,
  "claims": [ { "task": { "id": "{task_1}", "state": "claimed", "attempt": 1, "…": "other fields as in CONVENTIONS §5.1" },
    "lease": { "lease_token": "{lt_1}", "lease_epoch": 1, "attempt": 1, "lease_secs": 30 },
    "authority": { "mode": "creator_verified", "checked": [], "checked_at": "2026-11-03T10:00:00Z" },
    "resumed": { "wait_group_id": "{wg_1}", "outcome": "satisfied",
      "conditions": [ { "id": "{wc_1}", "kind": "timer", "state": "satisfied", "result": { "resume_at": "2026-11-03T10:30:00Z" } } ] } } ] }
```

## Side effects
- At create: `{task_1}` joins the deferred set (a deferred admission, G-CRT-01); timer `wait` for `{task_1}` is armed at `2026-11-03T10:30:00Z` (`resume_at` counts from the create, G-WAI-09); no queue timeout timer; lifetime timer armed at `T0+24h`; history of `{task_1}` gains `taskCreated` with `initial_state = waiting`, then `waitConditionSet` (`wait_condition_id = {wc_1}`, `kind = timer`), then `taskWaiting` listing the group (`mode`, `conditions[{wait_condition_id: {wc_1}, kind: timer}]`), the same events as a worker's one-step set (G-CRT-01, G-WAI-12).
- At `T0+30m`: `{task_1}` leaves the deferred set; timer `wait` for `{task_1}` is removed; history of `{task_1}` gains `waitConditionSatisfied` and `taskResumed`; timer `queue_timeout` for `{task_1}` is armed at `T0+1h30m`.
- At the claim: task `{task_1}.attempt` advances from 0 to 1.
- `{wg_1}` stays the task's current group until a worker sets or arms a new one or the task ends; every claim of `{task_1}` until then returns it in `resumed` (G-WAI-14). Its rows stay stored until retention.

## Notes
- `resume_pending` is set only when a worker parked the group, so a task resumed from a create-time group is claimed with `attempt` 1 (G-WAI-19). The `resumed` block comes from the task's current resolved group, not from `resume_pending`.
- An initial group with predecessors or a future `run_after` is refused, and `children` is never allowed in it (G-CRT-01): see [tasks/create](../../tasks/create/). The checks a create-time `event` condition runs (p2) are still open (G-WAI-11).
