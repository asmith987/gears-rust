# Flow: how an `ALL` or `ANY` group is decided by satisfactions and timeouts

Each condition has its own timeout and `on_timeout` (PRD.md:561). The group rule decides what a satisfaction or a timeout does:

- **`ALL`** needs every condition. The first timeout means the group can no longer be satisfied as asked, so it decides the group at once with that condition's `on_timeout`, and the other conditions are cancelled. A task never stays waiting on a group that can no longer be satisfied.
- **`ANY`** needs one condition. The first satisfied condition resumes the task and cancels the rest. A timed-out condition only drops out, even when it says `fail`; when every condition has timed out the group is decided: `fail` if any condition says `fail`, else `resume`, and the resumed worker gets a timeout note for each condition instead of a value.

The representative case is an `ALL` group whose input times out with `fail`.

## Setup
- `{task_1}` (**render**, queue **reports**, DLQ **dead_letter**) is `running` under lease `{lt_1}`.

## Exchange 1 — the worker parks on a timer and an approval, both required (`T0`)

```http
POST /api/task_engine/v1/tasks/{task_1}/wait-conditions HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{
  "lease_token": "{lt_1}",
  "mode": "all",
  "park": true,
  "conditions": [
    { "kind": "timer", "resume_at": "2026-11-03T12:00:00Z" },
    { "kind": "input", "prompt": "Approve the render of r-42?",
      "input_schema": { "type": "object", "required": ["approved"], "properties": { "approved": { "type": "boolean" } } },
      "timeout_secs": 3600, "on_timeout": "fail" }
  ]
}
```

```http
HTTP/1.1 200 OK
Content-Type: application/json

{ "wait_group": { "id": "{wg_1}", "mode": "all", "parked": true,
    "conditions": [ { "id": "{wc_1}", "kind": "timer", "state": "pending", "timeout_at": null },
                    { "id": "{wc_2}", "kind": "input", "state": "pending", "timeout_at": "2026-11-03T11:00:00Z" } ] },
  "task_state": "waiting" }
```

### Case `single_input_timeout_fail`
- `{task_1}` (**reports**) was parked at `T0` on a group with one input condition `{wc_1}`: `timeout_secs: 3600`, `on_timeout: "fail"`; `timeout_at` is `T0+3600s`. No resolve arrives. Clock: `T0+3601s` (the wait timer fires within the timer-accuracy bound, PRD.md:528).
- `GET /tasks/{task_1}` returns the same body as Exchange 2 (`terminal_at` `2026-11-03T11:00:00Z`).
- task `{task_1}` state is `dead_lettered`, result_code `timed_out`; timers `wait` and `lifetime` for `{task_1}` are removed; history gains `waitTimedOut` with `wait_condition_id = {wc_1}`, `on_timeout = fail`, `reason = timeout`, then `taskTimedOut` with `timeout_type = wait` (G-WAI-16), then `taskDeadLettered`; events `waitTimedOut` and `taskTimedOut` for `{task_1}` are published to the task-events topic; `{wc_1}` stays stored as `timed_out` until retention (Proposals › Waits; replaces "live-only", DESIGN.md:1766); subsequent `GET /tasks/{task_1}/wait-conditions` returns `200` listing `{wc_1}` with `state: timed_out` and `result: { "timed_out": true, "reason": "timeout" }`; subsequent `POST /wait-conditions/{wc_1}/resolve` returns `400 failed_precondition` (`subject: STATE`; a timed-out condition cannot be resolved, Proposals › Waits › `resolve`).

### Case `any_first_satisfied` — "run when approved, or tomorrow at the latest"
Exchange 1 — park (`T0`):
```http
POST /api/task_engine/v1/tasks/{task_1}/wait-conditions HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{
  "lease_token": "{lt_1}",
  "mode": "any",
  "park": true,
  "conditions": [
    { "kind": "input", "prompt": "Render r-42 now?",
      "input_schema": { "type": "object", "required": ["approved"], "properties": { "approved": { "type": "boolean" } } } },
    { "kind": "timer", "resume_at": "2026-11-04T10:00:00Z" }
  ]
}
```
→ `200`, `{wg_1}` `mode: any`, `{wc_1}` input and `{wc_2}` timer, both `pending` with `timeout_at: null`, `task_state: waiting`.

Exchange 2 — the creator approves (`T0+10m`):
```http
POST /api/task_engine/v1/wait-conditions/{wc_1}/resolve HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
Content-Type: application/json

{ "value": { "approved": true } }
```
→ `200 { "condition": { "id": "{wc_1}", "kind": "input", "state": "satisfied", "resolved_at": "2026-11-03T10:10:00Z", "resolved_by": "{creator_a}" } }`.

Exchange 3 — a worker claims the resumed task (`T0+10m+1s`, `reports-7f9c-1`, `session_id` `{session_1}`) → `200`, `{lt_2}`, `lease_epoch` 2, `attempt` 1, and:
```json
{ "wait_group_id": "{wg_1}", "outcome": "satisfied",
  "conditions": [ { "id": "{wc_1}", "kind": "input", "state": "satisfied", "result": { "value": { "approved": true } } },
                  { "id": "{wc_2}", "kind": "timer", "state": "cancelled", "result": null } ] }
```
Side effects: at `T0+10m`, in the resolve transaction, `{wc_1}` is `satisfied`, `{wc_2}` is `cancelled`, task `{task_1}` is `queued` with `resume_pending = true`, and timer `wait` for `{task_1}` (armed at `{wc_2}`'s `resume_at`) is removed; history gains `waitConditionSatisfied` (`wait_condition_id = {wc_1}`, `kind = input`) and `taskResumed`; `{task_1}` leaves the deferred set. At `2026-11-04T10:00:00Z` nothing happens to `{task_1}`.

### Case `any_timeouts_one_fail`
Exchange 1 — park on two questions, either answer is enough (`T0`):
```http
POST /api/task_engine/v1/tasks/{task_1}/wait-conditions HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{
  "lease_token": "{lt_1}",
  "mode": "any",
  "park": true,
  "conditions": [
    { "kind": "input", "prompt": "Manager approval",
      "input_schema": { "type": "object", "required": ["approved"], "properties": { "approved": { "type": "boolean" } } },
      "timeout_secs": 600, "on_timeout": "fail" },
    { "kind": "input", "prompt": "Owner approval",
      "input_schema": { "type": "object", "required": ["approved"], "properties": { "approved": { "type": "boolean" } } },
      "timeout_secs": 1800, "on_timeout": "resume" }
  ]
}
```
→ `200`, `{wc_1}` `timeout_at` `2026-11-03T10:10:00Z`, `{wc_2}` `timeout_at` `2026-11-03T10:30:00Z`, `task_state: waiting`.

Exchange 2 — `GET /tasks/{task_1}/wait-conditions` at `T0+10m+1s`:
```json
{ "items": [ { "id": "{wc_1}", "kind": "input", "state": "timed_out", "timeout_at": "2026-11-03T10:10:00Z", "result": { "timed_out": true, "reason": "timeout" } },
             { "id": "{wc_2}", "kind": "input", "state": "pending",   "timeout_at": "2026-11-03T10:30:00Z", "result": null } ],
  "page_info": { "next_cursor": null, "prev_cursor": null, "limit": 25 } }
```
`{task_1}` is still `waiting`.

Exchange 3 — `GET /tasks/{task_1}` at `T0+30m+1s`: `state: dead_lettered`, `result.result_code: timed_out`, `terminal_at: 2026-11-03T10:30:00Z`. `{wc_2}` said `resume`, but `{wc_1}` said `fail`, so the group fails.

Side effects: at `T0+10m` history gains `waitTimedOut` (`{wc_1}`, `on_timeout = fail`, `reason = timeout`), task state unchanged, timer `wait` for `{task_1}` is re-armed at `T0+30m`; at `T0+30m` history gains `waitTimedOut` (`{wc_2}`, `on_timeout = resume`, `reason = timeout`), then `taskTimedOut` (`timeout_type = wait`), then `taskDeadLettered`; `{task_1}` leaves the deferred set; both conditions stay stored as `timed_out` until retention.

### Case `any_timeouts_all_resume`
- Setup: `{task_1}` parked at `T0` with lease `{lt_1}` on `{wg_1}`, `mode: any`: `{wc_1}` input, `timeout_secs: 600`, `on_timeout: resume` (timeout at `T0+10m`); `{wc_2}` input, `timeout_secs: 1800`, `on_timeout: resume` (timeout at `T0+30m`). Nobody answers. At `T0+10m` `{wc_1}` drops out; at `T0+30m` `{wc_2}` times out and the group resolves to `resume`: `{task_1}` → `queued`.
- Claim (`reports-7f9c-1`, `{session_1}`) → `200`, `{lt_2}`, `lease_epoch` 2, `attempt` 1, and:
```json
{ "wait_group_id": "{wg_1}", "outcome": "timed_out",
  "conditions": [ { "id": "{wc_1}", "kind": "input", "state": "timed_out", "result": { "timed_out": true, "reason": "timeout" } },
                  { "id": "{wc_2}", "kind": "input", "state": "timed_out", "result": { "timed_out": true, "reason": "timeout" } } ] }
```
- Side effects: at `T0+10m` history gains `waitTimedOut` (`{wc_1}`, `on_timeout = resume`, `reason = timeout`) and timer `wait` is re-armed at `T0+30m`; at `T0+30m` history gains `waitTimedOut` (`{wc_2}`, `on_timeout = resume`, `reason = timeout`) and `taskResumed`, and no `taskTimedOut` (the task does not end); `{task_1}` leaves the deferred set; timer `queue_timeout` for `{task_1}` is armed at `T0+1h30m`. At the claim `attempt` stays 1 and `lease_epoch` is 2.

## Side effects (representative case)
- At `T0+1h`, in one transaction: `{wc_2}` becomes `timed_out`; `{wc_1}` becomes `cancelled` (DESIGN.md:823, :1773); `finalize()` routes the task to the DLQ with `timed_out` (DESIGN.md:544).
- `{task_1}` leaves the deferred set.
- timer `wait` for `{task_1}` is removed (the one `wait` timer covers the input timeout and the timer condition, G-WAI-09); `{wc_1}` and `{wc_2}` are kept with their final states until retention deletes `{task_1}` (Proposals › Waits › `resolve`; DESIGN.md:1766 "live-only" is on its edit list).
- history of `{task_1}` gains `waitTimedOut` with `wait_condition_id = {wc_2}`, `on_timeout = fail`, `reason = timeout`, then `taskTimedOut` with `timeout_type = wait` (G-WAI-16), then `taskDeadLettered`.
- subsequent `GET /tasks/{task_1}/wait-conditions` returns `200` with `{wc_1}` (`cancelled`) and `{wc_2}` (`timed_out`), oldest first.

## Notes
- With no DLQ on the queue (**bulk**) a `fail` decision ends the task `failed` / `timed_out` (DESIGN.md:496).
- `result.error` for an engine-set `timed_out` is not specified; `null` is assumed.
- ADR-0004:54 and :102 speak of a group timeout; PRD.md:561 and DESIGN.md:365 give each condition its own timeout. The scenario follows the PRD (G-WAI-07).
- When a wait timeout ends the task, `taskTimedOut { timeout_type: wait }` follows `waitTimedOut` (G-WAI-16). `waitTimedOut` carries `reason` (G-WAI-35).
- `GET /tasks/{id}/wait-conditions` is cursor-paged like every growing list (`{ items, page_info }`, CONVENTIONS §5.9) and returns each condition's `result` (G-WAI-08).
- The timeout note is `{ "timed_out": true, "reason": … }` and the `resumed` block follows G-WAI-08. Whether `waitConditionSatisfied` is also written for a group resolved by timeouts is not stated; not asserted.
- `any_first_satisfied` uses `resolve`, which needs the `resolve` action after the accepted change (`update` on `main`, G-WAI-04).
