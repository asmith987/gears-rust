# A resumed task comes back through a new claim, in the same attempt, with the wait result

When the wait is satisfied the task goes back to `queued`. A worker — any worker — claims it again. The claim issues a **new** lease token and raises `lease_epoch`, but `attempt` stays the same: resuming continues the attempt that parked (PRD.md:550, :661). The claim also carries the wait result, so the worker can continue: for an input wait, the value that was provided.

## Setup
- Run [A worker sets a wait and the task is parked](1.01-positive-set-wait-parks-task.md) (`{task_1}` parked at `T0+10s` on timer `{wc_1}`, `resume_at = T0+1h`).
- At `2026-11-03T11:00:00Z` the timer fires: `{wc_1}` becomes `satisfied`, the group is complete, and `{task_1}` moves `waiting → queued` with `resume_pending = true` (DESIGN.md:533).

## Request

```http
POST /api/task_engine/v1/tasks/claim HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "worker_id": "reports-7f9c-2", "session_id": null,
  "queues": ["gts.cf.core.tasks.queue.v1~acme.reports._.render.v1"],
  "max_tasks": 1, "timeout_secs": 30 }
```

## Expected response
- `200 OK`, one claim. A different process than the one that parked is fine.
- `lease.lease_token` is new (`{lt_2}` ≠ `{lt_1}`), `lease_epoch` is 2, `attempt` is still 1.
- `resumed` carries the satisfied group.

```json
{
  "session_id": "{session_2}",
  "heartbeat_interval_secs": 10,
  "claims": [ {
    "task": { "id": "{task_1}", "state": "claimed", "attempt": 1, "…": "other fields as in CONVENTIONS §5.1" },
    "lease": { "lease_token": "{lt_2}", "lease_epoch": 2, "attempt": 1, "lease_secs": 30 },
    "authority": { "mode": "creator_verified", "checked": [], "checked_at": "2026-11-03T10:00:00Z" },
```

## Side effects
- At the resume (case `timer`, `T0+1h`): `{task_1}` leaves the deferred set (hand-over, never refused, DESIGN.md:560); timer `wait` for `{task_1}` is removed; timer `queue_timeout` for `{task_1}` is armed at `T0+2h` (3,600 s); history of `{task_1}` gains `waitConditionSatisfied` (`wait_condition_id = {wc_1}`, `kind = timer`) and `taskResumed`.
- At the claim: task `{task_1}` state is `claimed`; task `{task_1}` lease_epoch is 2; task `{task_1}.attempt` is 1 (`resume_pending` cleared, `attempt` not incremented, DESIGN.md:1491, :2484); `queue_global(reports)` and `queue_tenant(reports, {tenant_a})` used change by +1; timer `queue_timeout` for `{task_1}` is removed.
- At the claim: a new `execution_deadline` with the full execution timeout is set, so the time spent `waiting` is not counted (DESIGN.md:531; the claim sets the deadline, G-EXE-10, G-RTY-22).
- `{wg_1}` stays the task's current group after the claim until a new set or arm makes another group current or the task ends; its rows stay stored until retention either way (G-WAI-14). A second claim of `{task_1}` (after a lost claim response and a liveness requeue) returns the same `resumed` block.
- history of `{task_1}` gains `taskClaimed` (attempt 1, with the claiming `worker_id`).

## Notes
- The `resumed` block and the per-kind `result` follow G-WAI-08.
- One current wait group at a time (G-WAI-14): the resolved parked group stays current until this worker sets or arms a new group or the task ends. Earlier groups are not deleted: `GET /tasks/{task_1}/wait-conditions` lists current and resolved conditions until retention (Proposals › Waits).
