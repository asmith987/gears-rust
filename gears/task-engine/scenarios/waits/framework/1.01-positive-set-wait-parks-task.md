# A worker sets a wait and the task is parked

The worker running a task sets a wait group in one call. The task moves to `waiting` and is **parked**: it gives back its lease, its worker and its concurrency slots, and counts as deferred work until it resumes. This is what lets a task wait for an hour (or a week) without holding capacity. The call can also carry a checkpoint, applied in the same transaction as the park, so the worker that resumes (usually not the one that parked) reads it from `context` and continues where the first one stopped.

## Setup
- `{creator_a}` created `{task_1}` (**render**, queue **reports**, input `{ "report_id": "r-42", "format": "pdf" }`).
- `reports-7f9c-1` claimed it at `T0` (session `{session_1}`, lease `{lt_1}`, `lease_epoch` 1, `attempt` 1) and started it at `T0+5s`. The task is `running`; its `context` is `null`.
- Tenant A is below `tenant_max_deferred_tasks` (100,000).

## Request

```http
POST /api/task_engine/v1/tasks/{task_1}/wait-conditions HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{
  "lease_token": "{lt_1}",
  "mode": "all",
  "park": true,
  "conditions": [
    { "kind": "timer", "resume_at": "2026-11-03T11:00:00Z" }
  ]
}
```

## Expected response
- `200 OK`.
- `task_state` is `waiting`; the group is parked; the timer condition is `pending`.

```json
{
  "wait_group": {
    "id": "{wg_1}",
    "mode": "all",
    "parked": true,
    "conditions": [ { "id": "{wc_1}", "kind": "timer", "state": "pending", "timeout_at": null } ]
  },
  "task_state": "waiting"
}
```

## Side effects
- task `{task_1}` state is `waiting`.
- task `{task_1}.assignment` is `null` (lease token, `session_id`, assignee, `assignment_deadline` and `execution_deadline` cleared, DESIGN.md:532).
- lease `{lt_1}` is invalid (later calls get LEASE_LOST) — see [1.06](1.06-guardrail-old-token-after-park-gets-lease-lost.md).
- task `{task_1}` lease_epoch is 1 (parking keeps the epoch; the next claim adds 1, DESIGN.md:571).
- `queue_global(reports)` used changes by −1; `queue_tenant(reports, {tenant_a})` used changes by −1.
- `{task_1}` joins the deferred set (parking is an admission, PRD.md:452).
- `te_wait_conditions({wc_1})` is present with `kind_code = timer`, `timer_resume_at = T0+1h`, `parked_at = T0+10s` (case `plain`).
- timer `wait` for `{task_1}` is armed at `2026-11-03T11:00:00Z` (case `plain`): the task's one `wait` timer, at the earliest pending deadline (G-WAI-09).
- history of `{task_1}` gains `waitConditionSet` with `wait_condition_id = {wc_1}`, `kind = timer`, `parked = true` (one per condition, G-WAI-12).
- history of `{task_1}` gains `taskWaiting` with `mode = all`, `conditions = [{ wait_condition_id: {wc_1}, kind: timer }]` (one per park, G-WAI-12).
- event `waitConditionSet` and event `taskWaiting` for `{task_1}` are published to the task-events topic (both are in the default `lifecycle` preset, PRD.md:898).
- the lifetime timer of `{task_1}` stays armed (PRD.md:526).
- metric `te_wait_conditions_active{kind="timer"}` increases by 1.

## Notes
- Events (G-WAI-12): `waitConditionSet` once per condition at set; `taskWaiting` once per park with the group's `mode` and condition list. The schemas `task_waiting.v1` and `wait_condition_set.v1` change under the gap's `Remaining`.
- The checkpoint counts against the 64 KiB payload limit (PRD.md:260).
- A checkpoint carried by set-wait records `taskCheckpointed`, like every write that saves one (G-WAI-15).
