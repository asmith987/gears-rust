# Park returns the result at once when the armed group is already satisfied

The reply event arrived while the group was only armed. The match was recorded but the task kept running. When the worker now parks, the engine sees the group is complete: it does **not** park the task, returns the result, and the worker continues under the same lease — no release, no second claim.

## Setup
- Run Exchange 1 of [Flow: arm a wait, start the action, then park](1.11-flow-arm-then-park.md): group `{wg_1}` armed at `T0` with event condition `{wc_1}` (**orders.paid**, `subject_id: o-17`); `{task_1}` is `running` under `{lt_1}`.
- At `T0+1m` the broker delivers event `{bev_1}`: type **orders.paid**, tenant A, `subject: o-17`, `subject_type: gts.acme.orders._.order.v1~`, topic `gts.cf.core.events.topic.v1~acme.orders._.order_events.v1`, partition 3, offset 1042. The consumer marks `{wc_1}` `satisfied` with the header only and does not touch the task (DESIGN.md:919).

## Request

```http
POST /api/task_engine/v1/tasks/{task_1}/wait-conditions/park HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "lease_token": "{lt_1}" }
```

## Expected response
- `200 OK`, `parked: false`, the resolved data in `result`.

```json
{
  "parked": false,
  "result": {
    "wait_group_id": "{wg_1}",
    "outcome": "satisfied",
    "conditions": [ { "id": "{wc_1}", "kind": "event", "state": "satisfied",
      "result": { "event": { "id": "{bev_1}", "type": "gts.cf.core.events.event.v1~acme.orders._.paid.v1~",
        "subject": "o-17", "subject_type": "gts.acme.orders._.order.v1~", "time": "2026-11-03T10:01:00Z",
        "topic": "gts.cf.core.events.topic.v1~acme.orders._.order_events.v1", "partition": 3, "offset": 1042 } } } ]
  }
}
```

## Side effects
- task `{task_1}` state is still `running`; `{lt_1}` stays valid (subsequent `POST /tasks/heartbeat` with it returns `outcome: ok`); task `{task_1}` lease_epoch is unchanged.
- `{wg_1}` is consumed in this call (G-WAI-13): `{wc_1}` stays stored and `GET /tasks/{task_1}/wait-conditions` lists it as `satisfied` (G-WAI-14), but the group is not current, so no claim returns it in `claims[].resumed`.
- `{task_1}` does not join the deferred set; `queue_global(reports)` and `queue_tenant(reports, {tenant_a})` are unchanged.
- history of `{task_1}` already holds `waitConditionSatisfied` (`{wc_1}`, written at `T0+1m`); it gains no `taskWaiting` and no `taskResumed`.
- subsequent `POST /tasks/{task_1}/wait-conditions` with `{lt_1}` and a new group returns `200` (the consumed group is not current, G-WAI-13, G-WAI-14).

## Notes
- The event `data` is never stored or returned (PRD.md:584).
- A one-step set (`park: true`) whose group resolves at once gets the same answer: see [timer 1.01](../timer/1.01-positive-timer-resumes-at-resume-at-past-returns-at-once.md) case `past` (G-WAI-13).
