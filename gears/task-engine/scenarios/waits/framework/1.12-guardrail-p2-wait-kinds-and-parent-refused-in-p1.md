# In p1, input, children and event waits and `parent_task_id` are refused with a clear 400

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-wait-conditions` (PRD.md:546-548) · `cpt-cf-task-engine-fr-wait-input` (PRD.md:606) · `cpt-cf-task-engine-fr-wait-children` (PRD.md:617) · parent/child (PRD.md:824) · DESIGN.md:296-298, :715 |
| Phase | p1 (the refusal); the features themselves are p2 |
| Test level | E2E |
| Depends on | Proposals › Waits › Input and children waits stay p2, and p1 is built for them |
| Gaps | G-WAI-43, G-SEC-21 |

p1 ships the whole wait model (all four kinds), `parent_task_id`, `wait_for_children` and `propagate_cancel` in its schemas, storage and API, so the p2 features arrive without a breaking change. The only p1 kind is `timer`. Until then a request that uses an `input`, `children` or `event` condition, or `parent_task_id`, is refused up front with `400` `FEATURE_NOT_AVAILABLE` on the exact field (G-WAI-43), the same way a type that declares `authz_scope` was refused (DESIGN.md:715). The refusal happens before any write: the task is not parked or created, and a worker keeps its lease.

## Setup
- p1 deployment.
- `reports-7f9c-1` holds `{task_1}` (**render**, queue **reports**) `running` under `{lt_1}`, with no wait group.

## Request
```http
POST /api/task_engine/v1/tasks/{task_1}/wait-conditions HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{
  "lease_token": "{lt_1}",
  "mode": "any",
  "park": true,
  "conditions": [
    { "kind": "timer", "resume_at": "2026-11-03T12:00:00Z" },
    { "kind": "input", "input_schema": { "type": "object", "required": ["approved"], "properties": { "approved": { "type": "boolean" } } }, "prompt": "Approve?", "timeout_secs": 86400, "on_timeout": "fail" }
  ]
}
```

## Expected response
- `400 Bad Request`, category `invalid_argument`, field violation on the condition that uses the p2 feature. The whole group is refused, including its p1 timer.

```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.invalid_argument.v1~",
  "title": "Invalid Argument",
  "status": 400,
  "detail": "input wait conditions are not available yet",
  "instance": "/api/task_engine/v1/tasks/{task_1}/wait-conditions",
  "trace_id": "<trace>",
  "context": { "field_violations": [
    { "field": "/conditions/1/kind", "description": "wait condition kind 'input' is not available in this release", "reason": "FEATURE_NOT_AVAILABLE" } ] }
}
```

## Notes
- The wait model and `parent_task_id` stay in the p1 OpenAPI and schemas; only their use is refused. Clients and the SDK treat wait kinds, result codes and event types as open sets (Proposals › Waits), so adding the p2 values later is not a breaking change.
- `FEATURE_NOT_AVAILABLE` is A (G-WAI-43): a field-violation reason on the exact field, never `context.reason`.
