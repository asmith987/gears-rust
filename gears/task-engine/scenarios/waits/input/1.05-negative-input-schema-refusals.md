# An untrusted input schema is refused at set time

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-wait-input` (PRD.md:610) · DESIGN.md:819, :2116-2119 |
| Phase | p2 |
| Test level | E2E |
| Depends on | Proposals › Task mutability › Set only in the create request (accepted: the worker path of set-wait stays) |
| Gaps | G-CRT-07, G-SEC-21 |

The `input_schema` comes from the caller, so it is untrusted input. It is checked when the wait is set, and a schema that breaks a rule is refused before anything is stored (PRD.md:610, DESIGN.md:819): larger than `input_waits.max_schema_bytes`; nested deeper than `input_waits.max_schema_depth` (a deep schema can make validation slow or blow the stack); a `$ref` that is not local (`#/…`) or a GTS type the caller can see (a URL would make the engine fetch caller-chosen content; the workspace `jsonschema` crate is built without remote resolvers); or a pattern the linear-time `regex` engine cannot run (look-around, back-references), which keeps a later resolve from running an exponential match. The task is not parked and the worker keeps its lease.

## Setup
- Task `{task_1}` (**render**, queue **reports**, tenant A) is `running` under lease `{lt_1}` (epoch 1, attempt 1) held by `{worker_a}` / `reports-7f9c-1`.
- Config `input_waits` as shipped: `max_schema_bytes: 16384`, `max_schema_depth: 32`, `max_prompt_bytes: 4096` (DESIGN.md:2116-2119).
- Clock: T0.

## Request (case `too_large`)
```http
POST /api/task_engine/v1/tasks/{task_1}/wait-conditions HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "lease_token": "{lt_1}", "mode": "all", "park": true,
  "conditions": [ { "kind": "input", "prompt": "Pick a cost centre", "timeout_secs": 86400, "on_timeout": "fail",
      "input_schema": { "type": "object", "required": ["cost_centre"],
        "properties": { "cost_centre": { "enum": ["CC-00001", "CC-00002", "…", "CC-02000"] } } } } ] }
```

## Expected response
- `400 Bad Request`, category `invalid_argument`; the violation on `/conditions/0/input_schema` names the rule (DESIGN.md:819).
```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.invalid_argument.v1~",
  "title": "Invalid Argument",
  "status": 400,
  "detail": "input_schema of condition 0 is refused: larger than input_waits.max_schema_bytes",
  "instance": "/api/task_engine/v1/tasks/{task_1}/wait-conditions",
  "trace_id": "<trace>",
  "context": { "field_violations": [
    { "field": "/conditions/0/input_schema", "description": "serialized schema is 20480 bytes; input_waits.max_schema_bytes is 16384", "reason": "SCHEMA_TOO_LARGE" } ] }
}
```

## Cases

All cases send `"kind": "input", "timeout_secs": 86400, "on_timeout": "fail"` and differ only in `input_schema`.

| Case | `input_schema` | `detail` | `description` | `reason` |
|---|---|---|---|---|
| `too_large` | the enum of 2,000 cost centres above; serializes to 20,480 bytes | `input_schema of condition 0 is refused: larger than input_waits.max_schema_bytes` | `serialized schema is 20480 bytes; input_waits.max_schema_bytes is 16384` | `SCHEMA_TOO_LARGE` |
| `too_deep` | `{ "type": "object", "properties": { "a": { "type": "object", "properties": { "a": { "…": "33 nested levels in total" } } } } }` | `input_schema of condition 0 is refused: nesting deeper than input_waits.max_schema_depth` | `schema nesting depth 33 exceeds input_waits.max_schema_depth (32)` | `TOO_DEEP` |
| `remote_ref` | `{ "$ref": "https://schemas.example.net/approval.json" }` | `input_schema of condition 0 is refused: $ref outside the schema` | `$ref https://schemas.example.net/approval.json is not a local reference or a visible GTS type` | `NOT_ALLOWED` |
| `non_linear_pattern` | `{ "type": "object", "properties": { "code": { "type": "string", "pattern": "^(?=.*[A-Z])(?=.*\\d)[A-Za-z\\d]{8,}$" } } }` | `input_schema of condition 0 is refused: pattern needs backtracking` | `pattern at /properties/code/pattern uses look-ahead, which the linear-time engine does not support` | `NOT_ALLOWED` |

## Side effects
<!-- No side effects: the request is refused before any write ("nothing is stored", DESIGN.md:819). -->
- task {task_1} state is running
- subsequent `POST /tasks/{task_1}/progress` with `{lt_1}` returns `200`

## Notes
- The reasons come from the closed list of CONVENTIONS §6 (G-CRT-07): `SCHEMA_TOO_LARGE` for size, `TOO_DEEP` for nesting, `NOT_ALLOWED` for a remote `$ref` and a non-linear pattern. No decision maps these rules to codes; the mapping is the scenario's choice. Tests should assert category, status, field and that the description names the rule.
- `too_large`: the enum is elided. DESIGN.md:819 says "serialized input_schema" without saying whether it is the bytes as sent or canonical JSON; a test should use a margin well over the limit.
- `too_deep`: how depth is counted (JSON nesting of the document, or schema keywords such as `properties` only) is not defined; the scenario counts JSON object nesting. A test should use a depth well over the limit.
- `remote_ref`: no outbound request is made; the check is static, before any resolver runs. A `$ref` to a GTS type the caller cannot see is refused the same way (PRD.md:610); the docs do not say whether that refusal should look like "unknown type" to avoid revealing types.
- `non_linear_pattern`: `patternProperties` keys are checked the same way (DESIGN.md:819). The docs do not say whether `format: regex` values in the schema are also restricted.
