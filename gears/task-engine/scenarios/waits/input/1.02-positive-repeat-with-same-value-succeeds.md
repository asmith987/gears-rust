# Repeating a resolve with the same value succeeds

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-wait-input` (PRD.md:608) · PRD.md:728 (replay model) · DESIGN.md:1098 |
| Phase | p2 |
| Test level | E2E |
| Depends on | Proposals › Waits › `resolve` › Safe to repeat |
| Gaps | G-WAI-05, G-WAI-14 |

`resolve` carries a request and its reply between services, so a network retry must not look like a failure. The same subject sending the same value again gets the stored result with `Idempotency-Replayed: true`, as completion replay does (DESIGN.md:736). Nothing changes the second time: no second resume, no second event. The stored value is the dedup record, so no idempotency key is needed, and the condition is kept until its task is deleted at retention, so a late retry still finds it (G-WAI-14).

## Setup
- Run [1.01](1.01-positive-resolve-valid-value-resumes-task.md): `{wc_1}` was resolved at T0+5m with `{ "approved": true }`; `{task_1}` is `queued` (not yet claimed).
- Clock: T0+5m+1s. The client did not see the first response and retries.

## Request
```http
POST /api/task_engine/v1/wait-conditions/{wc_1}/resolve HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
Content-Type: application/json

{ "value": { "approved": true } }
```

## Expected response
- `200 OK`, header `Idempotency-Replayed: true`, body = the stored outcome; `resolved_at` is the time of the first resolve.
```http
HTTP/1.1 200 OK
Content-Type: application/json
Idempotency-Replayed: true

{ "condition": { "id": "{wc_1}", "kind": "input", "state": "satisfied", "resolved_at": "2026-11-03T10:05:00Z", "resolved_by": "{creator_a}" } }
```

## Side effects
<!-- No side effects: the replay changes nothing. -->
- history of {task_1} has exactly one waitConditionSatisfied and one taskResumed
- task {task_1} state is queued

## Notes
- "Same value" means canonical-JSON equality (Proposals › Waits › `resolve`).
- The replay holds after the task is claimed again, after a new group becomes current and after the task ends: every condition is kept until retention deletes the task (Proposals › Waits › `resolve`, G-WAI-14). DESIGN.md:1766 (wait rows deleted at the terminal transition) is on the proposal's edit list.
- Another subject sending the same value gets `400` `failed_precondition` `ALREADY_RESOLVED` ([1.04](1.04-negative-resolve-state-refusals.md) case `same_value_other_subject`, G-WAI-05).
