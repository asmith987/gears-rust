# A resolve on a condition that is no longer open to an answer is refused

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-wait-input` (PRD.md:608) · `cpt-cf-task-engine-fr-wait-conditions` (PRD.md:561) · PRD.md:728 · DESIGN.md:823, :920, :1098 ("Resolve wait condition (input)"), :1234, :1766, :1773 |
| Phase | p2 |
| Test level | E2E |
| Depends on | Proposals › Waits › `resolve`; Proposals › Waits › `resolve` › Safe to repeat |
| Gaps | G-WAI-05 |

Only a `pending` **input** condition takes an answer. Once an input condition is satisfied its answer is fixed, so a later resolve with another value, or the same value from another subject, gets `400` `failed_precondition` `ALREADY_RESOLVED` (G-WAI-05), like a completion replay with a different result: two services answering the same question cannot both win, the resumed worker never sees a value change under it, and the audit trail names the one subject who answered (`resolved_by`, Proposals › Waits › `resolve`). A timer, event or children condition is satisfied only by its own trigger; letting a consumer resolve it would let anyone with `resolve` skip a timer or fake an event, so it gets `NOT_RESOLVABLE` (G-WAI-05). And a late answer must not change a decision already taken by a timeout or a sibling: a `timed_out` or `cancelled` condition gets `400` `failed_precondition` `STATE`. In each case the call is refused and the condition is unchanged. (The same value sent again by the same subject succeeds: [1.02](1.02-positive-repeat-with-same-value-succeeds.md).)

## Setup
- Run [1.01](1.01-positive-resolve-valid-value-resumes-task.md): `{wc_1}` was resolved at T0+5m with `{ "approved": true }`.
- Clock: T0+6m. `{creator_a2}` (same rights as `{creator_a}`) sends its own answer.

## Request
```http
POST /api/task_engine/v1/wait-conditions/{wc_1}/resolve HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a2-token>
Content-Type: application/json

{ "value": { "approved": false } }
```

## Expected response
- `400 Bad Request`, category `failed_precondition`, violation `{ type: STATE, subject: ALREADY_RESOLVED }`; `resource_name` is the task (CONVENTIONS §6). No `context.reason`.
```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.failed_precondition.v1~",
  "title": "Failed Precondition",
  "status": 400,
  "detail": "wait condition {wc_1} is already resolved",
  "instance": "/api/task_engine/v1/wait-conditions/{wc_1}/resolve",
  "trace_id": "<trace>",
  "context": { "resource_type": "gts.cf.core.tasks.task.v1~", "resource_name": "{task_1}",
    "violations": [ { "type": "STATE", "subject": "ALREADY_RESOLVED", "description": "wait condition {wc_1} is already satisfied" } ] }
}
```

## Notes
- `ALREADY_RESOLVED` and `NOT_RESOLVABLE` are decided (G-WAI-05): `400 failed_precondition`, not `409`. The error must not echo the stored value or `resolved_by`.
- `non_input_condition`: the kind may be revealed because a caller with `resolve` can act on the task's conditions.
- `after_timed_out`, `after_cancelled`: "cancelled or timed out → `400` `failed_precondition`" (Proposals › Waits › `resolve`); the subject is the plain `STATE`. A resolved condition is kept until its task is deleted at retention (Proposals › Waits › `resolve`, G-WAI-14), so these answers, and `ALREADY_RESOLVED`, hold after a new group becomes current or the task ends too.
