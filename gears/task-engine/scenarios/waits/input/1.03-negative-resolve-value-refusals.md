# A provided value that is invalid or too large is refused and the condition stays open

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-wait-input` (PRD.md:608, :610) · PRD.md:260 · DESIGN.md:724, :819, :1209, :1210, :2142 |
| Phase | p2 |
| Test level | E2E |
| Depends on | Proposals › Waits › `resolve` |
| Gaps | G-WAI-22, G-CRT-07, G-EXE-14 |

The condition is satisfied only by a JSON value valid against its `input_schema` (PRD.md:608), and the provided value is subject to the payload size limit (PRD.md:610), so an input wait cannot be used to push an arbitrarily large blob into the engine. A refused value changes nothing: the condition stays `pending` and the task stays `waiting`, so the caller can answer again.

## Setup
- Same as [1.01](1.01-positive-resolve-valid-value-resumes-task.md) Setup: `{task_1}` is `waiting` on input condition `{wc_1}` whose schema requires `approved: boolean`.
- Clock: T0+5m.

## Request
```http
POST /api/task_engine/v1/wait-conditions/{wc_1}/resolve HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
Content-Type: application/json

{ "value": { "approved": "yes" } }
```

## Expected response
- `400 Bad Request`, category `invalid_argument`; the field violation names `/value/approved` with reason `SCHEMA_VIOLATION`; the description names the failed keyword, never the value (CONVENTIONS §6).
```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.invalid_argument.v1~",
  "title": "Invalid Argument",
  "status": 400,
  "detail": "value does not match the input schema of wait condition {wc_1}",
  "instance": "/api/task_engine/v1/wait-conditions/{wc_1}/resolve",
  "trace_id": "<trace>",
  "context": { "field_violations": [
    { "field": "/value/approved", "description": "fails keyword type (boolean)", "reason": "SCHEMA_VIOLATION" } ] }
}
```

## Cases

| Case | Differs from the representative request | Expected | Notes |
|---|---|---|---|
| `schema_mismatch` | (the representative request) | `400 invalid_argument`, `SCHEMA_VIOLATION` on `/value/approved` | |
| `value_over_payload_limit` | `{wc_1}`'s schema is `{ "type": "object", "properties": { "notes": { "type": "string" } } }`; the task's `input` + `context` are about 200 bytes; `max_payload_size_bytes: 65536` (DESIGN.md:2142); body `{ "value": { "notes": "<70,000 characters of text>" } }` | `413 Content Too Large`, category `invalid_argument` with the transport override (DESIGN.md:1209), `PAYLOAD_TOO_LARGE` on `/value` | G-WAI-22: the value is measured alone |

Body of `value_over_payload_limit`:
```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.invalid_argument.v1~",
  "title": "Invalid Argument",
  "status": 413,
  "detail": "provided value exceeds the payload size limit",
  "instance": "/api/task_engine/v1/wait-conditions/{wc_1}/resolve",
  "trace_id": "<trace>",
  "context": { "field_violations": [
    { "field": "/value", "description": "value is 70,014 bytes; max_payload_size_bytes is 65536", "reason": "PAYLOAD_TOO_LARGE" } ] }
}
```

## Side effects
<!-- No side effects: the request is refused before any write. -->
- `{wc_1}` stays `pending`; subsequent `GET /tasks/{task_1}` returns 200 with `state: waiting`.
- subsequent resolve of `{wc_1}` with a valid value (`{ "approved": true }` in case `schema_mismatch`) returns 200.

## Notes
- `SCHEMA_VIOLATION` and `PAYLOAD_TOO_LARGE` are the decided reasons (CONVENTIONS §6, G-CRT-07). The value is validated against the condition's stored `input_schema` (G-EXE-14).
- A refused attempt is not "a different value" for the repeat rule ([1.04](1.04-negative-resolve-state-refusals.md) case `different_value`): nothing was stored.
- `value_over_payload_limit`: the body (about 70 KB) is under `max_request_body_bytes` (1 MiB), so the refusal comes from the payload rule, not the body cap. PRD.md:260 and DESIGN.md:724 define the limit as the **aggregate** `input + context + output`; the resolve value is measured alone against `max_payload_size_bytes` and stored on the condition, not in the task's aggregate (G-WAI-22).
