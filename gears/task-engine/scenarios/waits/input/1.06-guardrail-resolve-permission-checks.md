# Resolve checks the condition's task: `403` for a reader without `resolve`, `404` for a caller who cannot read it

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-wait-input` (PRD.md:608) · `cpt-cf-task-engine-fr-authz` (PRD.md:918) · DESIGN.md:1008, :1016, :1098, :1199 |
| Phase | p2 |
| Test level | Integration — resolve grant |
| Depends on | Proposals › Task mutability › `update` covers only tags; `resolve` gets its own action · Proposals › Waits › `resolve` |
| Gaps | G-WAI-04, G-SEC-18, G-SEC-19, G-WIRE-15 |

The path names only the condition ID, so the engine first resolves `{wc_1}` to its task and asks the PDP for `resolve` on that task (concrete type **render**, DESIGN.md:1008). The general rules live in [auth/](../../auth/): `403` only for a caller who can already see the task, `404` otherwise (no existence oracle, PRD.md:918, DESIGN.md:1016); `update` grants nothing ([../../auth/1.05](../../auth/1.05-negative-read-but-not-act.md)); a worker cannot resolve ([../../auth/1.13](../../auth/1.13-guardrail-worker-least-privilege.md)); `resolve` alone is enough ([../../auth/1.14](../../auth/1.14-guardrail-resolve-grants-nothing-else.md)). This file covers what is specific to the condition-ID path.

## Setup
- Same as [1.01](1.01-positive-resolve-valid-value-resumes-task.md) Setup: `{task_1}` (tenant A) is `waiting` on input condition `{wc_1}`.
- `{reader_a}` holds only task `read` in tenant A (CONVENTIONS §4).
- Clock: T0+5m.

## Request
```http
POST /api/task_engine/v1/wait-conditions/{wc_1}/resolve HTTP/1.1
Host: api.example.com
Authorization: Bearer <readonly-a-token>
Content-Type: application/json

{ "value": { "approved": true } }
```

## Expected response
- `403 Forbidden`, category `permission_denied`, `context.reason = ACTION_DENIED` (G-SEC-19); the resource named is the task, not the condition.
- The engine made one extra PDP call for `read` to choose `403` over `404` (DESIGN.md:1016).
```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.permission_denied.v1~",
  "title": "Permission Denied",
  "status": 403,
  "detail": "the caller may not resolve wait conditions of this task",
  "instance": "/api/task_engine/v1/wait-conditions/{wc_1}/resolve",
  "trace_id": "<trace>",
  "context": { "reason": "ACTION_DENIED", "resource_type": "gts.cf.core.tasks.task.v1~", "resource_name": "{task_1}" }
}
```

## Cases

| Case | Caller | Expected | Notes |
|---|---|---|---|
| `reader_without_resolve` | `<readonly-a-token>` (`read` only) | `403 permission_denied`, `ACTION_DENIED`, `resource_name: {task_1}` | it can already see the task, so the refusal discloses nothing |
| `other_tenant` | `<creator-b-token>` (`resolve` and `read` in tenant B only) | `404 not_found`, byte-for-byte the shape returned for a random condition ID (only `detail`, `instance`, `trace_id` differ by ID); `context.resource_name: {wc_1}` | must not learn that `{wc_1}` exists, or that it belongs to a waiting task |

Body of `other_tenant`:
```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.not_found.v1~",
  "title": "Not Found",
  "status": 404,
  "detail": "Wait condition {wc_1} not found",
  "instance": "/api/task_engine/v1/wait-conditions/{wc_1}/resolve",
  "trace_id": "<trace>",
  "context": { "resource_name": "{wc_1}" }
}
```

## Side effects
<!-- No side effects: the request is refused before any write. -->
- `{wc_1}` stays `pending`; `{task_1}` stays `waiting`; subsequent `GET /tasks/{task_1}/wait-conditions` by `{reader_a}` returns 200 with `{wc_1}` still `pending`.

## Notes
- The value is not validated first: a schema check before authorization would reveal the schema's shape to a caller that cannot read the task.
- DESIGN.md:1199 lists wait-condition not found under `not_found` but does not name a `resource_type` for a wait condition; `other_tenant` omits it.
- PRD.md:608 and :925 and DESIGN.md:986, :1098 still name `update` for this call; the accepted proposal renames it to `resolve` (`task_resolve.v1`), G-WAI-04. After the change the permission instance `gts.cf.toolkit.authz.permission.v1~cf.task_engine._.task_update.v1` is no longer registered; `schemas/instances/` on `main` still ships it and has no `task_resolve.v1`; branch `docs/task-engine-openapi` adds `task_resolve.v1` and lists `resolve` in PRD.md:922 (G-WAI-04).
- A caller with `resolve` but without `read` finds and resolves the condition (G-SEC-18); that case lives in [../../auth/1.14](../../auth/1.14-guardrail-resolve-grants-nothing-else.md). Only a caller without `resolve` reaches the `read` check that picks `403` or `404`.
- Neither refusal carries a field violation (G-WIRE-15).
