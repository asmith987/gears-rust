# A valid answer to an input wait resumes the parked task

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-wait-input` (PRD.md:606-610) · `cpt-cf-task-engine-fr-wait-conditions` (PRD.md:548-552) · DESIGN.md:815, :819, :1098, :533 |
| Phase | p2 |
| Test level | E2E |
| Depends on | Proposals › Waits › `resolve`; Proposals › Task mutability › `update` covers only tags; `resolve` gets its own action |
| Gaps | G-WAI-04, G-WAI-09, G-WAI-14, G-WAI-21, G-SEC-18 |

An API consumer answers the question a parked task asked. The value is checked against the condition's `input_schema`, stored on the condition, and, because the group has only this condition, the task leaves `waiting` for `queued` in the same transaction. The worker that claims it next gets the value ([framework 1.02](../framework/1.02-positive-resume-claims-new-lease-same-attempt.md), case `input`).

## Setup
- Task `{task_1}` (**render**, queue **reports**, tenant A) was `running` under lease `{lt_1}` (epoch 1, attempt 1) held by `{worker_a}` / `reports-7f9c-1`.
- At T0 the worker set this group, which parked the task (see [waits/framework](../framework/)):

```json
{ "lease_token": "{lt_1}", "mode": "all", "park": true,
  "conditions": [ { "kind": "input", "prompt": "Approve export?", "timeout_secs": 86400, "on_timeout": "fail",
                    "input_schema": { "type": "object", "required": ["approved"], "properties": { "approved": { "type": "boolean" } } } } ] }
```
- The response named group `{wg_1}` with condition `{wc_1}` (`pending`, `timeout_at` T0+86400s). `{task_1}` is `waiting`.
- Clock: T0+5m. `{creator_a}` holds `resolve` on `{task_1}` (`read` is not needed to resolve, G-SEC-18).

## Request
```http
POST /api/task_engine/v1/wait-conditions/{wc_1}/resolve HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
Content-Type: application/json

{ "value": { "approved": true } }
```

## Expected response
- `200 OK`; the condition is `satisfied`.
```json
{ "condition": { "id": "{wc_1}", "kind": "input", "state": "satisfied", "resolved_at": "2026-11-03T10:05:00Z", "resolved_by": "{creator_a}" } }
```

## Side effects
- task {task_1} state is queued
- task {task_1}.assignment is null (still no lease; the next claim issues one)
- wait condition {wc_1} state is satisfied, resolved_by is {creator_a}; the condition is kept until retention deletes {task_1}, also after a new group becomes current or the task ends (Proposals › Waits › `resolve`, G-WAI-14)
- timer wait for {task_1} is removed (`{wc_1}`'s timeout was its only pending deadline, G-WAI-09)
- timer queue_timeout for {task_1} is armed at T0+5m+3600s
- history of {task_1} gains waitConditionSatisfied with `wait_condition_id = {wc_1}`, `kind = input`, `actor = {creator_a}`
- history of {task_1} gains taskResumed
- event waitConditionSatisfied for {task_1} is published to the task-events topic
- event taskResumed for {task_1} is published to the task-events topic
- `te_wait_conditions({wc_1})` is present with `resolved_payload` = the provided value (DESIGN.md:1784)

## Notes
- Today the endpoint needs `update` (DESIGN.md:1098, PRD.md:608); the accepted change replaces it with `resolve` (G-WAI-04).
- The resolve call carries no lease token (DESIGN.md:1081).
- Resolving an input condition of an **armed** (not yet parked) group marks it `satisfied` without changing the task state; the later park returns the value with `parked: false` (G-WAI-21). Not shown here.
