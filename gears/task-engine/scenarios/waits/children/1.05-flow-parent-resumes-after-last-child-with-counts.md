# Flow: a parent parked on its children resumes once, after the last child ends, with counts per terminal state

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-wait-children` (PRD.md:617-619) · PRD.md:1528 · DESIGN.md:820, :2956, :2991-3006 · ADR-0004:85 |
| Phase | p2 |
| Test level | E2E |
| Gaps | G-WAI-08, G-WAI-12, G-WAI-14, G-WAI-15, G-WAI-19 |

The fan-out / fan-in pattern. A running parent creates four children, then parks on a `children` condition and holds no lease or slot while they run. Each child's terminal transition schedules a `children_check` for the parent; only the check after the **last** child ends finds no live child, satisfies the condition with the per-state counts, and resumes the parent. Children that fail, are cancelled or are dead-lettered count as finished too.

## Setup
- Parent `{task_1}` (**render**, **reports**, tenant A) is `running` under lease `{lt_1}` (epoch 1, attempt 1) held by `{worker_a}` / `reports-7f9c-1`.
- At T0 that worker created four children with `parent_task_id: {task_1}` and `parent_lease_token: {lt_1}` (see [hierarchy/children](../../hierarchy/children/)): `{task_2}`, `{task_4}`, `{task_5}` on **reports** (DLQ configured) and `{task_3}` on **bulk** (no DLQ). All are `queued`.

## Exchange 1 — the parent parks on its children (T0+1m)
```http
POST /api/task_engine/v1/tasks/{task_1}/wait-conditions HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "lease_token": "{lt_1}", "mode": "all", "park": true, "checkpoint": { "phase": "fan_in" },
  "conditions": [ { "kind": "children" } ] }
```
```http
HTTP/1.1 200 OK
Content-Type: application/json

{ "wait_group": { "id": "{wg_1}", "mode": "all", "parked": true,
    "conditions": [ { "id": "{wc_1}", "kind": "children", "state": "pending", "timeout_at": null } ] },
  "task_state": "waiting" }
```
- `{lt_1}` is invalid from now on; the parent's concurrency slots are released.

## Exchange 2 — the children end (T0+2m … T0+5m)
- T0+2m `{task_2}` completes `success`; T0+3m `{task_3}` completes with a non-retryable `error` → `failed`; T0+4m `{creator_a}` cancels `{task_4}` (queued) → `cancelled`; after each, `{task_1}` is still `waiting` and `{wc_1}` still `pending`.
- T0+5m the last child, `{task_5}`, reports a non-retryable error:
```http
POST /api/task_engine/v1/tasks/{task_5}/complete HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{
  "lease_token": "{lt_5}",
  "result_code": "error",
  "error": {
    "domain": "acme.reports",
    "code": "INVALID_REPORT",
    "message": "report r-45 has no rows",
    "fault": "task",
    "retryable": false
  }
}
```
```http
HTTP/1.1 200 OK
Content-Type: application/json

{ "id": "{task_5}", "state": "dead_lettered", "…": "other fields as in CONVENTIONS §5.1" }
```

Content-Type: application/json

```

  "claims": [ { "task": { "id": "{task_1}", "state": "claimed", "attempt": 1, "context": { "phase": "fan_in" }, "…": "other fields as in CONVENTIONS §5.1" },

```

## Side effects
- task {task_1} state is waiting from T0+1m to T0+5m, then queued no later than T0+5m+1s (PRD.md:619, timer-accuracy bound)
- `te_timers(children_check for {task_1})` is present after each child's terminal transition, and absent once it fired (DESIGN.md:2996)
- history of {task_1} gains exactly one waitConditionSatisfied (`wait_condition_id = {wc_1}`, `kind = children`) and exactly one taskResumed
- history of {task_1} gains, at T0+1m, taskCheckpointed (the set carried a checkpoint, G-WAI-15), waitConditionSet (`wait_condition_id = {wc_1}`, `kind = children`, `parked = true`) and taskWaiting (`mode = all`, `conditions = [{ wait_condition_id: {wc_1}, kind: children }]`) (G-WAI-12)
- task {task_1} lease_epoch is 2; task {task_1}.attempt is 1 (a worker-set group resumes with the same attempt, G-WAI-19)
- `{wg_1}` stays the task's current group, and its rows are kept until retention; a repeated claim of `{task_1}` (for example after a lost claim response) returns the same `resumed` (G-WAI-14)

## Notes
- The three earlier `children_check` timers find a live child and are no-ops (DESIGN.md:3005).
- Counts come from `te_task_results` rows of the parent's children (DESIGN.md:3003); the four keys are the terminal states of PRD.md:619. The `resumed` and `result` shapes are decided in G-WAI-08.
