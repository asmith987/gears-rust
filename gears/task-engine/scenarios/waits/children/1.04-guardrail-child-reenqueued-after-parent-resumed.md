# A child re-enqueued after its parent resumed counts as unfinished again

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-wait-children` (PRD.md:619) · `cpt-cf-task-engine-fr-parent-child` (PRD.md:826) · DESIGN.md:545, :736, :1233 |
| Phase | p2 |
| Test level | E2E |
| Gaps | G-WAI-14, G-WAI-24, G-WIRE-14 |

An operator may re-enqueue a dead-lettered child (DESIGN.md:545) after the parent's children wait was already resolved, as long as the parent has not ended (G-WAI-24). The re-enqueue does not reopen the resolved children condition: the parent's resume result is a snapshot and does not change. But the child is live again, so a `wait_for_children` parent can no longer complete successfully until it ends (`CHILDREN_PENDING`, PRD.md:826).

## Setup
- As [1.05](1.05-flow-parent-resumes-after-last-child-with-counts.md), except the parent `{task_1}` was created with `wait_for_children: true`. It resumed with counts `{ completed: 1, failed: 1, cancelled: 1, dead_lettered: 1 }` and is now `running` under `{lt_6}` (epoch 2).
- At T0+6m `{admin}` re-enqueued the dead-lettered child: `POST /admin/tasks/{task_5}/reenqueue` → `200`, `{task_5}` is `queued` on **reports** again.
- Clock: T0+7m. The parent's worker finishes.

## Request
```http
POST /api/task_engine/v1/tasks/{task_1}/complete HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "lease_token": "{lt_6}", "result_code": "success", "output": {"url": "https://files.example.com/r-42.pdf"} }
```

## Expected response
- `400 Bad Request`, category `failed_precondition`, violation `{ type: STATE, subject: CHILDREN_PENDING }` (DESIGN.md:1233, G-WIRE-14); the lease is kept.
```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.failed_precondition.v1~",
  "title": "Failed Precondition",
  "status": 400,
  "detail": "task {task_1} has unfinished children",
  "instance": "/api/task_engine/v1/tasks/{task_1}/complete",
  "trace_id": "<trace>",
  "context": { "resource_type": "gts.cf.core.tasks.task.v1~", "resource_name": "{task_1}",
    "violations": [ { "type": "STATE", "subject": "CHILDREN_PENDING", "description": "1 child is not terminal" } ] }
}
```

## Side effects
<!-- No side effects: the completion is refused; the task stays running under {lt_6}. -->
- subsequent `POST /tasks/{task_1}/wait-conditions` with `{lt_6}` and a `children` condition becomes the current group and parks the parent again; `{wg_1}`'s rows stay stored but are no longer current (G-WAI-14)
- the claim result of the earlier resume is unchanged: `{wc_1}` stays `satisfied` with the old counts (G-WAI-24)

## Notes
- G-WAI-24: re-enqueue of a child is allowed while its parent is non-terminal and does not reopen a resolved children condition; when the parent has ended it is refused `400` `failed_precondition` `PARENT_FINISHED` (home: [dead-letter/](../../dead-letter/)).
- The violation description must not reveal more than the count; the caller holds the parent's lease and may read its children.
