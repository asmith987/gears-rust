# The lifetime deadline still ends a task that is waiting

Waiting does not stop the clock that bounds a task's whole life. A timer condition set past the lifetime deadline never gets to fire: the lifetime timeout ends the task `timed_out` first.

## Setup
- `{task_1}` (**render**, queue **reports**, `lifetime_timeout_secs` 86,400, DLQ **dead_letter**) was created at `T0`; lifetime timer armed at `2026-11-04T10:00:00Z`.
- At `T0+1h` its worker parked it on a timer condition `{wc_1}` with `resume_at = 2026-11-05T10:00:00Z` (`200`, task `waiting`).

## Request

```http
GET /api/task_engine/v1/tasks/{task_1} HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
```

(sent at `2026-11-04T10:00:01Z`)

## Expected response
- `200 OK`; the task ended by its lifetime timeout.

```json
{ "id": "{task_1}", "state": "dead_lettered",
  "queue": "gts.cf.core.tasks.queue.v1~cf.core.tasks.dead_letter.v1",
  "dead_lettered_from": "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1",
  "result": { "result_code": "timed_out", "output": null, "error": null, "warnings": [] },
  "terminal_at": "2026-11-04T10:00:00Z", "…": "other fields as in CONVENTIONS §5.1" }
```

## Side effects
- At `2026-11-04T10:00:00Z`: `finalize()` with terminal routing and `timed_out` (DESIGN.md:543); `{task_1}` leaves the deferred set; `{wc_1}` is `cancelled` and stays stored until retention (Proposals › Waits, G-WAI-14); timer `wait` for `{task_1}` (armed at `2026-11-05T10:00:00Z`) is removed.
- history of `{task_1}` gains `taskTimedOut`, then `taskDeadLettered`.
- At `2026-11-05T10:00:00Z` nothing happens to `{task_1}`.

## Notes
- The engine does not reject a `resume_at` beyond the lifetime deadline at set time; the docs give no such rule.
