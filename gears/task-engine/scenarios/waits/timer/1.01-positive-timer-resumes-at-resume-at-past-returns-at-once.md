# A timer condition resumes the task at `resume_at`; a past `resume_at` is satisfied at once without parking

A timer condition is a planned pause: it is satisfied when `resume_at` is reached. The task goes back to `queued` within the timer bound (1 s), with no polling by the worker or the caller. A worker that computes `resume_at` from its own clock, or retries a set-wait after a delay, may name a time that has already passed. That is not an error: the group resolves at once, so the set does not park; it returns the result and the worker keeps its lease (G-WAI-10, G-WAI-13).

## Setup
- `{task_1}` (**render**, queue **reports**) is `running` under `{lt_1}`. Engine time is `T0`.

## Exchange 1 — park for 15 minutes (`T0`)

```http
POST /api/task_engine/v1/tasks/{task_1}/wait-conditions HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "lease_token": "{lt_1}", "mode": "all", "park": true,
  "conditions": [ { "kind": "timer", "resume_at": "2026-11-03T10:15:00Z" } ] }
```

```http
HTTP/1.1 200 OK
Content-Type: application/json

{ "wait_group": { "id": "{wg_1}", "mode": "all", "parked": true,
    "conditions": [ { "id": "{wc_1}", "kind": "timer", "state": "pending", "timeout_at": null } ] },
  "task_state": "waiting" }
```

## Exchange 2 — read the task just after `resume_at` (`T0+15m+1s`)

```http
GET /api/task_engine/v1/tasks/{task_1} HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
```

```http
HTTP/1.1 200 OK
Content-Type: application/json

{ "id": "{task_1}", "state": "queued", "assignment": null, "attempt": 1,
  "updated_at": "2026-11-03T10:15:00Z", "…": "other fields as in CONVENTIONS §5.1" }
```

- The task is `queued` no later than `T0+15m+1s`; it was not `queued` before `T0+15m`.

## Cases

| Case | `resume_at` | Expected | Notes |
|---|---|---|---|
| `future` | `2026-11-03T10:15:00Z` (`T0+15m`) | as above: `200 waiting`; `queued` within 1 s of `resume_at`, never before | G-WAI-09 |
| `past` | `2026-11-03T09:59:00Z` (before `T0`) | `200 { "parked": false, "result": { "wait_group_id": "{wg_1}", "outcome": "satisfied", "conditions": [ { "id": "{wc_1}", "kind": "timer", "state": "satisfied", "result": { "resume_at": "2026-11-03T09:59:00Z" } } ] } }`; `{task_1}` stays `running`; `{lt_1}` stays valid (a heartbeat with it returns `outcome: ok`); the group is consumed in this call: `{wc_1}` stays stored and listed as `satisfied`, but the group is not current, so no claim returns it; no deferred admission, no `wait` timer, no `taskWaiting` or `taskResumed`; concurrency slots unchanged | G-WAI-10, G-WAI-13; same answer as parking a satisfied armed group ([framework 1.03](../framework/1.03-positive-park-returns-result-when-already-satisfied.md)) |
| `past_any_with_future` | `"mode": "any"`, conditions: timer `2026-11-03T09:59:00Z` and timer `2026-11-03T12:00:00Z` | `200`, `parked: false`, `result` lists the first `satisfied` and the second `cancelled` (`result: null`); lease kept | the group resolves at once under `any` (G-WAI-13) |
| `past_all_with_future` | `"mode": "all"`, conditions: timer `2026-11-03T09:59:00Z` and timer `2026-11-03T10:15:00Z` | `200`, `task_state: waiting`, group parked; the task resumes at `T0+15m` as in case `future` | the group does not resolve at once under `all` |

## Side effects (case `future`)
- At `T0`: timer `wait` for `{task_1}` is armed at `T0+15m` (G-WAI-09).
- At `T0+15m`: `{wc_1}` becomes `satisfied`; task `{task_1}` state is `queued` with `resume_pending = true`; `{task_1}` leaves the deferred set; timer `queue_timeout` for `{task_1}` is armed at `T0+1h15m`; timer `wait` for `{task_1}` is removed.
- history of `{task_1}` gains `waitConditionSatisfied` (`wait_condition_id = {wc_1}`, `kind = timer`) and `taskResumed`.
- subsequent claim of `{task_1}` returns `resumed.conditions[0] = { "id": "{wc_1}", "kind": "timer", "state": "satisfied", … }` and `attempt` 1 (see [framework 1.02](../framework/1.02-positive-resume-claims-new-lease-same-attempt.md)).
- metric `te_wait_conditions_active{kind="timer"}` decreases by 1.

## Notes
- Timer conditions and wait timeouts fire from one `wait` timer per task, armed at the earliest pending deadline and re-armed after each fire; they are under the 1 s bound (G-WAI-09; PRD.md:1260 gains them).
- Case `past`: a past `resume_at` is accepted and satisfied at once (G-WAI-10); a set whose group resolves at once behaves like parking a satisfied armed group (G-WAI-13, DESIGN.md:822).
