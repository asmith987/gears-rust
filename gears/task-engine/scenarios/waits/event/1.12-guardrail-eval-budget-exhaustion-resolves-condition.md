# Ten consecutive budget overruns resolve the condition with eval_budget_exceeded

Each evaluation runs under `cel.max_eval_cost` (10,000), charged inside the evaluator. An overrun is no match and adds one to the condition's `eval_failures`; any evaluation that finishes within budget resets it (G-WAI-35). At `event_waits.max_eval_failures` (10) consecutive overruns, the condition resolves as if it had timed out, with reason `eval_budget_exceeded`, and its `on_timeout` applies through the group rule. A task never waits for ever on an expression that cannot finish (PRD.md:599, DESIGN.md:917, ADR-0007:68).

## Setup
- Event fixtures and `{task_1}` as in [positive-1.1](1.01-positive-matching-event-resumes-task-with-header-only.md). `{task_1}` is `waiting` on `{wc_1}`: `orders.paid`, subject `o-17`, `on_timeout: "resume"`, and `match_expression: "data.lines.all(l, data.lines.all(m, l.sku != m.sku || l == m))"` (quadratic in the number of lines).

## Exchange 1 — Ten events `{bev_1}`…`{bev_10}`, tenant A, subject `o-17`, each with 400 `data.lines`
- Events 1–9: each evaluation exceeds the budget → no match; `eval_failures` goes 1, 2, … 9.
- Event 10: `eval_failures` reaches 10 → in the same transaction `{wc_1}` resolves like a timeout with `reason: eval_budget_exceeded`; `on_timeout: resume` resumes the task.

## Exchange 2 — Next claim
- `200 OK`; `claims[0].resumed`:
```json
{ "wait_group_id": "{wg_1}", "outcome": "timed_out",
  "conditions": [ { "id": "{wc_1}", "kind": "event", "state": "timed_out",
    "result": { "timed_out": true, "reason": "eval_budget_exceeded" } } ] }
```

## Side effects
- After event 10: task `{task_1}` state is `queued`; `timer wait for {task_1} is removed` (no pending parked condition is left, G-WAI-09).
- History of `{task_1}` gains `waitTimedOut` with `{ wait_condition_id: {wc_1}, on_timeout: resume, reason: eval_budget_exceeded }`, then `taskResumed` (G-WAI-35).
- `tenant_event_waits(tenant_a)` used changes by −1.
- Metric `te_event_wait_eval_budget_exceeded_total{outcome="no_match"}` increases by 9 and `{outcome="condition_resolved"}` by 1 (DESIGN.md:2307).
- With `on_timeout: "fail"` instead: `{task_1}` ends `dead_lettered`, `result_code` `timed_out` (DESIGN.md:544); history gains `waitTimedOut` with `reason: eval_budget_exceeded` and then `taskDeadLettered`, but no `taskTimedOut` (G-WAI-16).

## Notes
- Any in-budget evaluation (`true` or `false`) resets the counter, and a run-time error is no match that neither counts nor resets (G-WAI-35; see [1.11](1.11-guardrail-runtime-error-is-no-match-and-not-counted.md)). This scenario sends only overrunning events.
- `waitTimedOut` and the claim's `resumed` result both carry `reason`, so a consumer can tell a budget resolution from a timeout (G-WAI-35, G-WAI-08).
