# A redelivered event never satisfies a condition twice, even across task domains

Broker delivery is at-least-once. One `orders.paid` event matches waits in two task domains. The consumer applies it in each domain in a separate transaction that first inserts the event ID into that domain's `te_event_inbox`; the offset is committed last, with the `default` domain. A crash between the two domains causes a redelivery, which the first domain's inbox absorbs (PRD.md:579, :1184, DESIGN.md:925, ADR-0004:56, :80).

## Setup
- Event fixtures as in [positive-1.1](1.01-positive-matching-event-resumes-task-with-header-only.md).
- Two task domains: `default` and `eu` (a domain for queue **bulk**). Tenant A has `{task_1}` (**reports**, domain `default`) waiting on `{wc_1}` and `{task_2}` (**bulk**, domain `eu`) waiting on `{wc_2}`; both: `orders.paid`, subject `o-17`, `mode: all`, one condition each.

## Exchange 1 — `{bev_1}` (tenant A, subject `o-17`) delivered; the node crashes after the `eu` commit
- Domain `eu` (non-default domains go first): `INSERT te_event_inbox({bev_1})` succeeds; `{wc_2}` `satisfied`; `{task_2}` → `queued`; commit.
- The node crashes before the `default` transaction, which would also commit the offset.

## Exchange 2 — `{bev_1}` is redelivered after restart
- Domain `eu`: the inbox insert hits the existing row; the domain is skipped. `{task_2}` is not touched again.
- Domain `default`: inbox insert succeeds; `{wc_1}` `satisfied`; `{task_1}` → `queued`; offset committed in the same transaction.

## Exchange 3 — `{bev_1}` is redelivered once more (broker retry)
- Both inboxes hold `{bev_1}`; nothing changes; the offset advances.

## Side effects
- `te_event_inbox({bev_1})` is present once in each domain.
- History of `{task_2}` gains exactly one `waitConditionSatisfied` and one `taskResumed`; the same for `{task_1}`.
- If `{task_2}` was claimed and parked again on a new `orders.paid` / `o-17` condition between Exchange 1 and 2, the redelivered `{bev_1}` does not satisfy it: the `eu` inbox already holds the ID.

## Notes
- Inbox rows are pruned after `event_consumer.inbox_retention_days` (30, DESIGN.md:2106), which must cover the longest redelivery window.
- The last side-effect bullet follows from DESIGN.md:925 ("if the row exists, the event was already applied there and is skipped"): a new condition never sees an event its domain already applied.
