# A matching event resumes a parked task, and only the event header is kept

A running worker parks its task on an `orders.paid` event for order `o-17`. When the broker delivers that event in tenant A, the engine marks the condition `satisfied`, moves the task `waiting → queued`, and the next claim returns the event **header** only. The event `data` (amount, card details) is never stored or returned (PRD.md:584, DESIGN.md:839).

## Setup
- **Event fixtures** (used by every scenario in this folder):
  - Waitable topic `gts.cf.core.events.topic.v1~acme.orders._.order_events.v1`, listed in `event_consumer.waitable_topics` (DESIGN.md:2104).
  - `gts.cf.core.events.event.v1~acme.orders._.paid.v1~` (**orders.paid**): topic trait = the orders topic, `allowed_subject_types: ["gts.acme.orders._.order.v1~"]`.
  - `gts.cf.core.events.event.v1~acme.orders._.note_added.v1~` (**orders.note_added**): `allowed_subject_types: ["gts.acme.orders._.order.v1~", "gts.acme.orders._.customer.v1~"]`.
  - Non-waitable topic `gts.cf.core.events.topic.v1~acme.audit._.audit_events.v1` with type `gts.cf.core.events.event.v1~acme.audit._.login.v1~`.
  - The PDP allows `{worker_a}` broker `consume`, unconstrained, in tenant A on the orders topic, both orders event types and both subject types.
  - Broker event IDs are written `{bev_1}`, `{bev_2}`.
- `{task_1}` (**render**, queue **reports**, tenant A) is `running`, held by `{worker_a}` / `reports-7f9c-1` with lease `{lt_1}`, `lease_epoch: 1`, `attempt: 1`.

## Expected response
- `200 OK`; `lease.lease_epoch` is `2`, `lease.attempt` is `1` (resume does not start an attempt, PRD.md:661, DESIGN.md:731); the token is new.
- `resumed.conditions[0].result.event` holds exactly the eight header fields; there is no `data` key.
```json
{ "session_id": "{session_2}", "domain": "default", "heartbeat_interval_secs": 10,
  "claims": [ { "task": { "id": "{task_1}", "state": "claimed", "attempt": 1, "…": "other fields as in CONVENTIONS §5.1" },
    "lease": { "lease_token": "{lt_2}", "lease_epoch": 2, "attempt": 1, "lease_secs": 30, "domain": "default" },
    "authority": { "mode": "creator_verified", "checked": [], "checked_at": "2026-11-03T10:00:00Z" },

```

## Side effects
- After Exchange 1: `timer wait for {task_1} is armed at 2026-11-03T11:00:00Z` (the condition's `timeout_at`, G-WAI-09); history of `{task_1}` gains `waitConditionSet` with `{ wait_condition_id: {wc_1}, kind: event, parked: true }`, then `taskWaiting` with `{ mode: all, conditions: [{ wait_condition_id: {wc_1}, kind: event }] }` (G-WAI-12).
- After Exchange 2: task `{task_1}` state is `queued`; `timer wait for {task_1} is removed`; `te_event_inbox({bev_1})` is present in the task's domain.
- History of `{task_1}` gains `waitConditionSatisfied` with `{ wait_condition_id: {wc_1}, kind: event }`, then `taskResumed`.
- `tenant_event_waits(tenant_a)` and `tenant_event_waits_per_type(tenant_a, orders.paid)` used change by −1 when `{wc_1}` leaves `pending` (DESIGN.md:814).
- No stored row or event payload contains `amount` or `card_last4`.
- The resolved group `{wg_1}` stays the task's current group: a repeated claim of `{task_1}` (for example after a lost claim response) returns the same `resumed` block until the worker sets a new group. Its rows are never deleted by a later group or by the task's end; they are kept until retention (G-WAI-14).
