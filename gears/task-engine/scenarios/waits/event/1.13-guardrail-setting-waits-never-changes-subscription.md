# Setting, arming or parking event waits never changes the broker subscription

The engine subscribes once, at startup, with one interest per waitable topic, as a stable consumer group, independent of tenants, types and waits. Setting, arming or parking a wait only inserts rows; it never re-joins, so a thousand tenants arming waits cause no rebalance (PRD.md:581, DESIGN.md:911, :914).

## Setup
- Event fixtures as in [positive-1.1](1.01-positive-matching-event-resumes-task-with-header-only.md). The engine's consumer group `gts.cf.core.events.consumer_group.v1~cf.core.tasks.task_engine.v1` has one subscription with one interest: topic orders, `tenant_id` = root, `barrier_mode: ignore`, `types: ["gts.cf.core.events.event.v1~*"]` (DESIGN.md:911), at topology version `v`.
- 1,000 tenants, each with one `running` task held by its own worker.

## Exchange 1 — Each worker arms an event wait
Each sends `POST /tasks/{id}/wait-conditions` with `park: false` and one `orders.paid` condition with its own `subject_id`, then parks it (see [Arm then park](../framework/1.11-flow-arm-then-park.md)).

## Expected outcome
- Every arm returns `200` as soon as its rows commit; no call waits for a broker join.
- The engine sends no JOIN, LEAVE or interest change to the Event Broker; the subscription's topology version stays `v`; no rebalance occurs.

## Side effects
- `te_wait_conditions` gains 1,000 rows; `tenant_event_waits(<each tenant>)` used changes by +1.
- An `orders.paid` event published after an arm returned matches that arm (ADR-0004:84).

## Notes
- The subscription changes only when the operator changes `event_consumer.waitable_topics` (DESIGN.md:911).
