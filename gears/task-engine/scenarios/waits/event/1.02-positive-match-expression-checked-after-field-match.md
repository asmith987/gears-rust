# A match expression is checked after the field match, against the event data

The condition waits for an `orders.paid` event of order `o-17` **and** `data.amount >= 100`. The engine first applies the subject ID, the effective subject type and the consume filter; only events that pass all three reach the CEL expression. An event with a smaller amount does not match; the next one with `amount: 120.5` does. Only the header is stored, never `data` (PRD.md:594, :598, DESIGN.md:917, ADR-0007:60, :66-67).

## Setup
- Event fixtures and `{task_1}` (`running`, lease `{lt_1}`) as in [positive-1.1](1.01-positive-matching-event-resumes-task-with-header-only.md).

## Exchange 1 — Park with a match expression
```http
POST /api/task_engine/v1/tasks/{task_1}/wait-conditions HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "lease_token": "{lt_1}", "mode": "all", "park": true,
  "conditions": [ { "kind": "event", "event_type": "gts.cf.core.events.event.v1~acme.orders._.paid.v1~",
                    "subject_type": "gts.acme.orders._.order.v1~", "subject_id": "o-17",
                    "match_expression": "data.amount >= 100.0",
                    "timeout_secs": 3600, "on_timeout": "resume" } ] }
```
- `200 OK`, `task_state: "waiting"`, `{wc_1}` `pending`.

## Exchange 2 — Events, in order
| Event (tenant A) | Subject | `data` | Outcome |
|---|---|---|---|
| `{bev_1}` | `o-18` | `{ "amount": 500 }` | no match at the subject filter; expression not evaluated |
| `{bev_2}` | `o-17` | `{ "amount": 40 }` | expression `false` → no match, nothing recorded; `eval_failures` stays `0` (an in-budget evaluation resets it, G-WAI-35) |
| `{bev_3}` | `o-17` | `{ "amount": 120.5 }` | expression `true` → `{wc_1}` `satisfied` |

## Side effects
- After `{bev_3}`: task `{task_1}` state is `queued`; `timer wait for {task_1} is removed`; `resolved_payload` of `{wc_1}` is the header of `{bev_3}` only (no `amount`).
- Only `{bev_3}` writes a `te_event_inbox` row (DESIGN.md:925).
- History of `{task_1}` gains one `waitConditionSatisfied`, then `taskResumed`.
- Metric `te_event_wait_eval_cost` records the cost of `{bev_2}` and `{bev_3}` (DESIGN.md:2306).

## Notes
- The expression sees `data` only in memory and only for events the caller could consume (DESIGN.md:837).
