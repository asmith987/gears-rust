# A condition frees its event-wait places when it times out or its task is cancelled

Each pending event condition holds one place on each applicable `te_tenant_wait_counters` dimension. It gives them back when it leaves `pending` (satisfied, timed out, cancelled) and in the task's terminal transition. So a tenant at its limit can set new waits again once old ones end (PRD.md:585, DESIGN.md:814, :2932).

## Exchange 1 — `{wc_1}` times out at T0+10m
- The task's `wait` timer fires (G-WAI-09): `{wc_1}` → `timed_out`; `{task_1}` → `queued`; history of `{task_1}` gains `waitTimedOut` with `{ wait_condition_id: {wc_1}, on_timeout: resume, reason: timeout }` (G-WAI-35).

## Exchange 2 — Creator cancels `{task_2}`
```http
POST /api/task_engine/v1/tasks/{task_2}/cancel HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
Content-Type: application/json

{ "mode": "requested", "reason": "order abandoned" }
```
- `200 OK`, `{task_2}` `cancelled`, `result_code: "cancelled"` (unleased waiting task, DESIGN.md:550).

## Side effects
- After Exchange 1: `tenant_unkeyed_event_waits_per_type(tenant_a, orders.paid)`, `tenant_event_waits_per_type(tenant_a, orders.paid)` and `tenant_event_waits(tenant_a)` used each change by −1.
- After Exchange 2: the same three change by −1 again (released in `finalize()` step 1); `{wc_2}` state is `cancelled`; its row stays and `GET /tasks/{task_2}/wait-conditions` still lists it until retention (G-WAI-14; DESIGN.md:2942-2943 deletes it, to be changed); `timer wait for {task_2} is removed`.
- Subsequent: a new unkeyed `orders.paid` wait in tenant A returns `200` (twice), not `429`.
