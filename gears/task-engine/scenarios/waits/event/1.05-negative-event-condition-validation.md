# An event condition that can never be satisfied or checked is refused when it is set

On set or arm, the engine validates each event condition: the event type must resolve with the caller's GTS visibility (DESIGN.md:913; a hidden type looks unregistered, G-WAI-29); its topic must be one the engine reads (`event_consumer.waitable_topics`, so a condition on another topic could never be satisfied, PRD.md:581); the condition must have an effective subject type, so the consume check on the subject type can always run (required unless the event type allows exactly one, non-wildcard subject type, PRD.md:579, DESIGN.md:826, G-WAI-30); an explicit `subject_type` must match one of the type's `allowed_subject_types` (GTS pattern match); every condition must expire within `event_waits.max_wait_secs` (default 604,800 s = 7 days), because the consume checks run only once (PRD.md:583, DESIGN.md:836); and a match expression must parse and pass the CEL checker within `cel.max_expression_bytes` (4 KiB), `max_ast_nodes` (256) and `max_ast_depth` (32) (PRD.md:594, ADR-0007:58, DESIGN.md:2391) — at set time, not when an event arrives. All of these run before any PDP call (DESIGN.md:1340; the expression check too, G-WAI-34). A refused condition stores nothing and the worker keeps its lease.

## Setup
- Event fixtures and `{task_1}` (`running`, lease `{lt_1}`) as in [positive-1.1](1.01-positive-matching-event-resumes-task-with-header-only.md). `event_waits.max_wait_secs` is the default `604800`.
- Two more event types on the orders topic, for single cases:
  - `gts.cf.core.events.event.v1~acme.orders._.status_changed.v1~` (**orders.status_changed**): `allowed_subject_types: ["gts.acme.orders._.*"]` (one wildcard entry).
  - `gts.cf.core.events.event.v1~acme.billing._.invoice_paid.v1~` (**invoice_paid**): registered in tenant B and not visible to tenant A.

## Request (case `topic_not_waitable`)
```http
POST /api/task_engine/v1/tasks/{task_1}/wait-conditions HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "lease_token": "{lt_1}", "mode": "all", "park": true,
  "conditions": [ { "kind": "event", "event_type": "gts.cf.core.events.event.v1~acme.audit._.login.v1~", "subject_type": "gts.acme.orders._.order.v1~",
                    "timeout_secs": 3600, "on_timeout": "resume" } ] }
```

## Expected response
- `400 Bad Request`, `invalid_argument`, one field violation on `/conditions/0/event_type` with `reason: EVENT_TOPIC_NOT_WAITABLE`; no `context.reason` (G-WIRE-14).
- Refused before any PDP call (DESIGN.md:1340, G-WAI-34), so no `te_event_wait_authz_total` outcome is recorded (every case).
```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.invalid_argument.v1~",
  "title": "Invalid Argument",
  "status": 400,
  "detail": "Event condition 0: topic of the event type is not waitable",
  "instance": "/api/task_engine/v1/tasks/{task_1}/wait-conditions",
  "trace_id": "<trace>",
  "context": {
    "field_violations": [ { "field": "/conditions/0/event_type", "description": "the event type's topic gts.cf.core.events.topic.v1~acme.audit._.audit_events.v1 is not waitable", "reason": "EVENT_TOPIC_NOT_WAITABLE" } ] }
}
```

## Cases

Each case sends one event condition; the table gives what differs from the representative condition.

| Case | Condition | Field | `reason` | `detail` / `description` |
|---|---|---|---|---|
| `topic_not_waitable` | `event_type` `…acme.audit._.login.v1~` (topic `acme.audit._.audit_events.v1`, not listed) | `/conditions/0/event_type` | `EVENT_TOPIC_NOT_WAITABLE` | as above |
| `unknown_event_type` | `event_type` `gts.cf.core.events.event.v1~acme.orders._.refunded.v1~` (not registered), `subject_type` order, `timeout_secs` 3600, `on_timeout: resume` | `/conditions/0/event_type` | `UNKNOWN_EVENT_TYPE` | `Event condition 0: event type does not resolve` / `unknown event type` |
| `hidden_event_type` | `event_type` **invoice_paid** (exists, hidden from tenant A), `subject_type` order, `timeout_secs` 3600 | `/conditions/0/event_type` | `UNKNOWN_EVENT_TYPE` | byte-identical to `unknown_event_type` apart from the type ID and `trace_id` (G-WAI-29) |
| `subject_type_required` | `event_type` **orders.note_added** (allows two subject types), no `subject_type`, `subject_id: o-17` | `/conditions/0/subject_type` | `EVENT_SUBJECT_TYPE_REQUIRED` | `Event condition 0: subject_type is required for this event type` / `subject_type is required because the event type allows more than one subject type` |
| `subject_type_required_wildcard` | `event_type` **orders.status_changed** (one wildcard entry), no `subject_type`, `subject_id: o-17` | `/conditions/0/subject_type` | `EVENT_SUBJECT_TYPE_REQUIRED` | as `subject_type_required`; a single wildcard entry is not "the single entry" (G-WAI-30) |
| `subject_type_not_allowed` | **orders.paid** with `subject_type: gts.acme.orders._.customer.v1~`, `subject_id: c-9` | `/conditions/0/subject_type` | `EVENT_SUBJECT_TYPE_NOT_ALLOWED` | `Event condition 0: subject type not allowed for this event type` / `subject type gts.acme.orders._.customer.v1~ is not allowed for this event type` |
| `timeout_above_max` | **orders.paid**, subject type order, `subject_id: o-17`, `timeout_secs: 604801` | `/conditions/0/timeout_secs` | `OUT_OF_RANGE` | `Event condition 0: timeout exceeds the maximum` / `must be at most event_waits.max_wait_secs (604800)` |
| `invalid_match_expression` (p3) | **orders.paid**, subject type order, `subject_id: o-17`, `match_expression: "data.amount >= "` | `/conditions/0/match_expression` | `INVALID_MATCH_EXPRESSION` | `Event condition 0: match_expression does not parse` / `syntax error at offset 15` |

All cases answer `400`, `invalid_argument`, in the shape of the representative body: one field violation with the field and `reason` of the row, and no `context.reason`.

## Side effects
- Nothing is stored: no `te_wait_conditions` row, no `te_tenant_wait_counters` change, no history entry.
- Task `{task_1}` state is still `running`; lease `{lt_1}` stays valid (subsequent `POST /tasks/{task_1}/progress` with `{lt_1}` returns `200`).

## Notes
- `topic_not_waitable`: the topic list is operator config (DESIGN.md:2104), so naming the topic in `description` reveals nothing a caller can change. Whether the response may name the topic is not stated; the scenario names it.
- `unknown_event_type` / `hidden_event_type`: the event type resolves with the caller's GTS visibility, and a hidden type gets the same `400` as an unregistered one, so the answer is no oracle (G-WAI-29).
- `subject_type_required`: the same request with `orders.paid` (one non-wildcard allowed subject type) is accepted and stores `gts.acme.orders._.order.v1~` as the effective subject type (DESIGN.md:826, :1779). The request field is `subject_type`, not DESIGN's `event_subject_type` (G-WAI-30).
- `timeout_above_max`: DESIGN.md:1221 names no reason code; the generic `OUT_OF_RANGE` is used and the setting is named in `description`. Timeouts are per condition (PRD.md:561, DESIGN.md:365); ADR-0004:54 still speaks of a *group* timeout (G-WAI-07). A condition without a timeout gets the maximum: [1.03](1.03-positive-no-timeout-gets-max-wait-with-fail.md).
- `invalid_match_expression`: an expression over 4,096 bytes, over 256 AST nodes or deeper than 32 is refused the same way, with the `cel.*` rule named in `description` (G-WAI-34).
- In p1 an event condition is refused earlier, with `FEATURE_NOT_AVAILABLE` on `/conditions/0/kind` (G-WAI-43): [framework/1.12](../framework/1.12-guardrail-p2-wait-kinds-and-parent-refused-in-p1.md).
