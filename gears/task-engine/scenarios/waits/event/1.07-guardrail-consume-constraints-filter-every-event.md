# Decidable consume constraints are stored and keep other events from matching

The PDP allows `consume` on the subject type only for order `o-17` and `o-18` (`subject In [...]`). That constraint is decidable, so the wait is accepted and the constraint is stored as the condition's `event_consume_filter`. An event for another order of the same type never matches, even though the condition itself names no `subject_id` (PRD.md:582, DESIGN.md:830, :917).

## Setup
- Event fixtures and `{task_1}` (`running`, lease `{lt_1}`) as in [positive-1.1](1.01-positive-matching-event-resumes-task-with-header-only.md), except: the PDP answers the subject-type `consume` check for `{worker_a}` with *allow* and one constraint `subject In ["o-17", "o-18"]`.

## Exchange 1 — Set an unkeyed wait
```http
POST /api/task_engine/v1/tasks/{task_1}/wait-conditions HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "lease_token": "{lt_1}", "mode": "all", "park": true,
  "conditions": [ { "kind": "event", "event_type": "gts.cf.core.events.event.v1~acme.orders._.paid.v1~",
                    "subject_type": "gts.acme.orders._.order.v1~", "timeout_secs": 3600, "on_timeout": "resume" } ] }
```
- `200 OK`, `task_state: "waiting"`, condition `{wc_1}` `pending`.

## Exchange 2 — `{bev_1}`: orders.paid, tenant A, subject `o-99`, at T0+1m
- No match: the consume filter rejects it before any expression runs. `{wc_1}` stays `pending`; `{task_1}` stays `waiting`; no `te_event_inbox` row is written (only matched events write one, DESIGN.md:925).

## Exchange 3 — `{bev_2}`: orders.paid, tenant A, subject `o-18`, at T0+2m
- Match: `{wc_1}` is `satisfied` with the header of `{bev_2}`; `{task_1}` moves to `queued`.

## Side effects
- After Exchange 1: `te_wait_conditions({wc_1})` is present with `event_consume_filter` = the `subject In` constraint (DESIGN.md:1780) and `event_subject_id` `NULL`; `tenant_unkeyed_event_waits_per_type(tenant_a, orders.paid)` used changes by +1.
- Metric `te_event_wait_authz_total{outcome="accepted_filtered"}` increases by 1 (DESIGN.md:2304).
- After Exchange 3: history of `{task_1}` gains `waitConditionSatisfied` then `taskResumed`; no history entry exists for `{bev_1}`.

## Notes
- With an unconstrained decision, `event_consume_filter` is `NULL` and `{bev_1}` would have matched.
