# An event wait the caller's broker rights do not fully allow is refused and stores nothing

A wait must not let its caller see more than its own Event Broker subscription with the same filters would. So setting or arming an event condition runs the broker's three subscribe checks with the **caller's** context: `consume` on the topic, the event type, and the effective subject type. The checks run before the transaction opens. The engine accepts a decision only when it can enforce it completely, because it reads events with platform rights. A denied check, a decision with no constraint left after the tenant filter, a decision the engine cannot enforce in memory, and an unreachable PDP all refuse the wait: nothing is stored and the worker keeps its lease (PRD.md:582, DESIGN.md:827-835).

## Setup
- Event fixtures and `{task_1}` (`running`, lease `{lt_1}`) as in [positive-1.1](1.01-positive-matching-event-resumes-task-with-header-only.md), except (case `consume_denied`): the PDP **denies** `{worker_a}` `consume` on `gts.cf.core.events.subject_type.v1~` for `gts.acme.orders._.order.v1~` in tenant A (topic and event-type checks allow).

## Request
```http
POST /api/task_engine/v1/tasks/{task_1}/wait-conditions HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "lease_token": "{lt_1}", "mode": "all", "park": true,
  "conditions": [ { "kind": "event", "event_type": "gts.cf.core.events.event.v1~acme.orders._.paid.v1~",
                    "subject_type": "gts.acme.orders._.order.v1~", "subject_id": "o-17",
                    "timeout_secs": 3600, "on_timeout": "resume" } ] }
```

## Expected response
- `403 Forbidden`, `permission_denied`, `context.reason = "EVENT_CONSUME_DENIED"`.
- The response names the condition index and the failing check (`subject_type`), never a constraint value (DESIGN.md:832). A `403` carries only its reason; the index and check go only into `detail`, with no field violation (G-WAI-25, G-WIRE-15).
```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.permission_denied.v1~",
  "title": "Permission Denied",
  "status": 403,
  "detail": "Event condition 0: consume denied on subject_type",
  "instance": "/api/task_engine/v1/tasks/{task_1}/wait-conditions",
  "trace_id": "<trace>",
  "context": { "reason": "EVENT_CONSUME_DENIED" }
}
```

## Cases

| Case | PDP answer | Request differs | Expected | Metric `te_event_wait_authz_total` | Notes |
|---|---|---|---|---|---|
| `consume_denied` | denies `consume` on the subject type | (the representative request) | `403 permission_denied`, `EVENT_CONSUME_DENIED`, `detail` names condition 0 and `subject_type` | `{outcome="denied"}` +1 | a denial on the topic or the event type behaves the same, with `topic` / `event_type` in `detail` |
| `consume_unverifiable` | allows `consume` on the event type with one constraint `InGroup(subject, "vip-orders")` (a group predicate the engine cannot evaluate in memory); topic and subject-type checks unconstrained | no `subject_id` | `403 permission_denied`, `EVENT_CONSUME_UNVERIFIABLE`; no constraint value in the body | `{outcome="unverifiable"}` +1 | ADR-0004:66 |
| `all_constraints_dropped` | allows `consume` on the event type with two constraints, each with a tenant filter `owner_tenant_id = {tenant_b}` (excludes the task's tenant A); topic and subject-type checks unconstrained | no `subject_id` | `403 permission_denied`, `EVENT_CONSUME_DENIED`, `detail` names condition 0 and `event_type` | `{outcome="denied"}` +1 | DESIGN.md:830; no constraint left, so nothing allows the consume (G-WAI-28) |

## Side effects
- Nothing is stored: no `te_wait_conditions` row, no `te_tenant_wait_counters` change, no history entry (DESIGN.md:835).
- Task `{task_1}` state is still `running`; lease `{lt_1}` stays valid: subsequent `POST /tasks/{task_1}/progress` with `{lt_1}` returns `200`.
- The metric outcome of the row increases by 1 (DESIGN.md:2304).

## Notes
- A decidable constraint is accepted and filters events: [1.07](1.07-guardrail-consume-constraints-filter-every-event.md).
- `consume_denied`: a worker call whose scope no longer covers its task also answers `403` on this endpoint, but with reason `CLAIM_REVOKED`, and it **releases** the task (G-EXE-08). The consume denials keep the lease; the worker branches on `context.reason` (G-WAI-26, G-SEC-19). DESIGN.md:827 still says the consume checks come "on top of the task `claim` / `update` check"; with Proposals › Task mutability only `claim` remains (G-WAI-27, no decision recorded yet).
- `all_constraints_dropped`: DESIGN.md:830 drops a constraint whose tenant filter excludes the task's tenant; when none is left the answer is `EVENT_CONSUME_DENIED`, not `UNVERIFIABLE` (G-WAI-28).
- `pdp_unreachable`: `503` with `Retry-After`, as on every endpoint (G-SEC-01); PRD.md:918's `403` for an unreachable PDP changes to `503` (G-WAI-31).
