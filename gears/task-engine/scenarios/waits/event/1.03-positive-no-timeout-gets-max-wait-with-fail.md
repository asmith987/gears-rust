# An event condition without a timeout gets the maximum, with on_timeout fail

A worker parks on an event without giving a timeout. The engine applies `event_waits.max_wait_secs` (7 days) from park time, and, since the condition sets no action either, `on_timeout = fail` (PRD.md:583, DESIGN.md:836). So no event wait outlives its set-time authorization checks.

## Setup
- Event fixtures and `{task_1}` (`running`, lease `{lt_1}`) as in [positive-1.1](1.01-positive-matching-event-resumes-task-with-header-only.md).
- For this scenario `{task_1}` has `timeouts.lifetime_timeout_secs: 1209600` (14 days), so the lifetime deadline does not come first.

## Request
```http
POST /api/task_engine/v1/tasks/{task_1}/wait-conditions HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "lease_token": "{lt_1}", "mode": "all", "park": true,
  "conditions": [ { "kind": "event", "event_type": "gts.cf.core.events.event.v1~acme.orders._.paid.v1~",
                    "subject_type": "gts.acme.orders._.order.v1~", "subject_id": "o-17" } ] }
```

## Expected response
- `200 OK`; the condition's `timeout_at` is park time + 604,800 s.
```json
{ "wait_group": { "id": "{wg_1}", "mode": "all", "parked": true,
    "conditions": [ { "id": "{wc_1}", "kind": "event", "state": "pending", "timeout_at": "2026-11-10T10:00:00Z" } ] },
  "task_state": "waiting" }
```

## Cases

| Case | Differs from the representative case | Expected | Notes |
|---|---|---|---|
| `no_on_timeout` | (the representative case) | as above | G-WAI-32 |
| `on_timeout_only` | the condition also sends `"on_timeout": "resume"` and still no timeout | `200`, same `timeout_at`; `GET /tasks/{task_1}/wait-conditions` shows `on_timeout: "resume"`; at T0+7d `waitTimedOut` carries `on_timeout: resume` and the task resumes | G-WAI-32: an omitted timeout on an event condition means `event_waits.max_wait_secs`, so `on_timeout` alone is valid |

## Side effects
- `timer wait for {task_1} is armed at 2026-11-10T10:00:00Z` (the task's one `wait` timer, G-WAI-09).
- `GET /tasks/{task_1}/wait-conditions` shows `{wc_1}` with `on_timeout: "fail"` (case `no_on_timeout`).
- Case `no_on_timeout`, if no matching event arrives: at T0+7d history of `{task_1}` gains `waitTimedOut` with `{ wait_condition_id: {wc_1}, on_timeout: fail, reason: timeout }` (G-WAI-35), then `taskTimedOut` with `{ timeout_type: wait }` (G-WAI-16), then `taskDeadLettered`; task `{task_1}` state is `dead_lettered` (the **reports** queue has a DLQ), `result_code` is `timed_out` (DESIGN.md:544).

## Notes
- With the fixture's own `lifetime_timeout_secs: 86400`, the lifetime timeout ends the task at T0+1d first (DESIGN.md:543); lifetime keeps running while waiting (DESIGN.md:554).
- PRD.md:583 says only "gets the maximum"; the `fail` default is DESIGN.md:836. G-WAI-32 makes `fail` the default for every condition with a timeout and no `on_timeout`. For the `event` kind an omitted timeout means `event_waits.max_wait_secs`, so `on_timeout` alone is valid (case `on_timeout_only`); `on_timeout` without a timeout is `400 NOT_ALLOWED` only for the other kinds ([framework 1.07](../framework/1.07-negative-set-wait-refusals.md) case `on_timeout_without_timeout`).
