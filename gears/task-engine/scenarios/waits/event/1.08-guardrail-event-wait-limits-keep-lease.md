# Over a per-tenant event-wait limit, setting a wait is refused and the worker keeps its lease

One consumer serves every tenant, so pending (armed or parked) event conditions are bounded per tenant, on three dimensions (DESIGN.md:814, :1681-1692): all event waits of the tenant, the waits per event type, and the waits **without** `subject_id` per event type (checked against every event of the type, so the tightest: 100 per tenant and event type by default). Set or arm reserves a place on every applicable dimension; when one is full the call is refused with `429` `resource_exhausted`, naming only the full dimension (`event_waits.<dimension>`), never usage figures. Nothing changes and the lease is kept (PRD.md:585, DESIGN.md:814, :1216).

## Setup
- Event fixtures and `{task_1}` (`running`, lease `{lt_1}`) as in [positive-1.1](1.01-positive-matching-event-resumes-task-with-header-only.md).
- Case `unkeyed`: tenant A has 100 pending `orders.paid` conditions without `subject_id` in this domain: `te_tenant_wait_counters(tenant_a, tenant_unkeyed_event_waits_per_type, orders.paid)` has `used = 100`, `limit_value = 100`. The other two dimensions have room.

## Request
```http
POST /api/task_engine/v1/tasks/{task_1}/wait-conditions HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "lease_token": "{lt_1}", "mode": "all", "park": false,
  "conditions": [ { "kind": "event", "event_type": "gts.cf.core.events.event.v1~acme.orders._.paid.v1~",
                    "subject_type": "gts.acme.orders._.order.v1~", "timeout_secs": 3600, "on_timeout": "resume" } ] }
```

## Expected response
- `429 Too Many Requests`, `resource_exhausted`, one violation with `subject: event_waits.unkeyed`; no `context.reason`, no usage figures (G-WIRE-14).
- `Retry-After` is a positive integer in [15, 30] (`retry_after_secs` 30 jittered uniformly in [base/2, base], G-WAI-33, G-SEC-03) and equals `violations[0].retry_after_seconds`.
```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/problem+json
Retry-After: 23
```
```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.resource_exhausted.v1~",
  "title": "Resource Exhausted",
  "status": 429,
  "detail": "Event wait limit reached",
  "instance": "/api/task_engine/v1/tasks/{task_1}/wait-conditions",
  "trace_id": "<trace>",
  "context": {
    "violations": [ { "subject": "event_waits.unkeyed", "description": "pending event waits without subject_id for this event type", "retry_after_seconds": 23 } ] }
}
```

## Side effects
- Nothing is stored; `tenant_event_waits(tenant_a)`, `tenant_event_waits_per_type(tenant_a, orders.paid)` and `tenant_unkeyed_event_waits_per_type(tenant_a, orders.paid)` used are unchanged (the reservation rolls back).
- `{task_1}` stays `running`; `{lt_1}` stays valid.
- Subsequent: after one of the pending conditions is satisfied, times out or is cancelled, the same request returns `200` (PRD.md:585; see [1.04](1.04-positive-cancel-and-timeout-free-wait-places.md)).

## Notes
- The quota subject carries both the limit and its dimension (`event_waits.tenant`, `event_waits.event_type`, `event_waits.unkeyed`), from the closed list of CONVENTIONS §6 (G-WIRE-14, G-CLM-10). No `resource_type`/`resource_name` is set: the limit belongs to the tenant, not to a queue.
- `Retry-After` is the same jittered value as a depth refusal (G-WAI-33, G-SEC-03); places free only when other conditions resolve, so the hint is a back-off, not a promise.
