# A failed predecessor with 250 successors cancels each exactly once, in bounded steps, across a crash

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-dependencies` (PRD.md:839) · DESIGN.md:2156, :2965-2989, :1815-1816 |
| Phase | p2 |
| Test level | Integration — crash mid-cascade |

"Every affected successor MUST be cancelled exactly once, even for large fan-outs and across crashes" (PRD.md:839). The first `cascade_inline_limit` (100) successors are handled in the predecessor's terminal transaction; the rest by a durable `cascade` timer with a resume cursor, each step a guarded update on `blocked`, so replays are no-ops.

## Setup
- `{task_1}` (**render**, queue **bulk**, tenant A) is `running` under `{worker_a}` with `{lt_1}`.
- 250 successors `{task_s001}` … `{task_s250}` (ascending task ID), each `blocked` on `{task_1}` only (`cancel`, `all`).
- `{task_s150}` was cancelled by its creator at `T0−1m` (already terminal).
- The engine instance processing the cascade timer crashes after committing the batch that ends at `{task_s200}`.

## Request
```http
POST /api/task_engine/v1/tasks/{task_1}/complete HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{
  "lease_token": "{lt_1}",
  "result_code": "error",
  "error": {
    "domain": "acme.reports",
    "code": "INVALID_REPORT",
    "message": "source missing",
    "fault": "task",
    "retryable": false
  }
}
```

## Expected response
- `200 OK`, `{task_1}` `failed`, returned after the inline batch only.

## Side effects
- Same transaction: `{task_s001}`…`{task_s100}` state is `cancelled`, result_code `dependency_failed`; `te_timers(cascade for {task_1})` is present, `cascade_kind = successors`, `cascade_after_task_id = {task_s100}`.
- Timer batches: 101-200 commit (skipping `{task_s150}`, whose row is no longer live); after the crash the timer claim expires (`claim_until`) and another instance continues after `{task_s200}` with 201-250, then deletes the timer.
- 249 successors end `cancelled` / `dependency_failed`, each with exactly one `taskCancelled`; `{task_s150}` keeps `result_code: cancelled` and gets no second event.
- The 249 cancelled successors leave the deferred set, each once.
- Each step's batch completes within the timer-accuracy bound of the previous one (DESIGN.md:2988).

## Notes
- A `te_dependencies` row is live-only for the successor; `{task_s150}`'s row was deleted at its own terminal transition (DESIGN.md:1856), so the cascade never sees it.
