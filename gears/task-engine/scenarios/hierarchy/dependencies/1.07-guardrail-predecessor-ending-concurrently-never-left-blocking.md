# A successor created while its predecessor ends is never left `blocked`

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-dependencies` (PRD.md:843) · PRD.md:1544 · DESIGN.md:729, :2624-2637, :2908 |
| Phase | p2 |
| Test level | Integration — race |
| Gaps | G-WAI-36, G-WAI-37 |

The create locks each live predecessor's `te_task_state` row before inserting the link. Either the predecessor's terminal transaction commits first, and the create reads its outcome from `te_task_results`, or the create commits first, and the predecessor's cascade sees the new link through its locking read. A test runs the race many times and accepts only the listed outcomes.

## Setup
- `{task_1}` (**render**, tenant A) is `running` under `{worker_a}` with `{lt_1}`.
- Variant S: the worker completes with `success`. Variant F: it completes with a non-retryable `error` (queue **bulk**, no DLQ → `failed`).
- At the same instant `{creator_a}` creates `{task_2}` with `predecessors: [{ task_id: {task_1}, on_predecessor_failure: cancel }]`.

## Exchange 1 — predecessor completes
```http
POST /api/task_engine/v1/tasks/{task_1}/complete HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "lease_token": "{lt_1}", "result_code": "success", "output": {"url": "https://files.example.com/r-1.pdf"} }
```

## Exchange 2 — concurrent create
```http
POST /api/task_engine/v1/tasks HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
Content-Type: application/json
Idempotency-Key: race-succ-1

{ "type": "gts.cf.core.tasks.task.v1~acme.reports._.render.v1~",
  "queue": "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1",
  "input": { "report_id": "r-2", "format": "pdf" },
  "predecessors": [ { "task_id": "{task_1}", "on_predecessor_failure": "cancel" } ] }
```

## Expected response
| Variant | Complete commits first | Create commits first |
|---|---|---|
| S | `201`, `{task_2}` `queued`, link `outcome: succeeded` | `201` `blocked`; then the completion unblocks it to `queued` |
| F | `400 failed_precondition` `DEPENDENCY_UNSATISFIABLE` (as [1.01](1.01-positive-create-with-predecessors-initial-state.md) case `failed_cancel_all`) | `201` `blocked`; then the failure cancels it with `dependency_failed` |

## Side effects
- Never: `{task_2}` `blocked` with `{task_1}` terminal (PRD.md:843).
- Each of `{task_2}`'s transitions happens exactly once (one `taskCancelled` at most).

## Notes
- PRD.md:843 allows all three outcomes ("satisfied, cancelled … or rejected as unsatisfiable"); the variant table is how they follow from the lock order.
