# Flow: fan out three parts, then join them with a task that tolerates failed parts

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-dependencies` (PRD.md:837, :839) |
| Phase | p2 |
| Test level | E2E |
| Depends on | Proposals › Task mutability › Only the parent's worker adds children (accepted: "a creator creates the child tasks first, then a join task with them as predecessors, using `on_predecessor_failure: ignore`") |
| Gaps | G-WAI-37, G-WAI-41 |

The creator-side replacement for adding children to someone else's task: create the parts, then one join task naming them all with `ignore`, so it runs once every part has ended, whatever the outcome. The join's worker reads the parts' results with its own `read` right.

## Setup
- `{creator_a}` in tenant A; queue **bulk** (no DLQ). Clock T0.

## Exchange 1 — create the parts
Three creates like this one, for `part: 1..3` (`Idempotency-Key: fan-1`, `fan-2`, `fan-3`):
```http
POST /api/task_engine/v1/tasks HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
Content-Type: application/json
Idempotency-Key: fan-1

{ "type": "gts.cf.core.tasks.task.v1~acme.reports._.render.v1~",
  "queue": "gts.cf.core.tasks.queue.v1~acme.reports._.bulk.v1",
  "input": { "report_id": "r-42-p1", "format": "pdf" } }
```
`201 Created` → `{task_1}`, `{task_2}`, `{task_3}`, all `queued`.

## Exchange 2 — create the join
```http
POST /api/task_engine/v1/tasks HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
Content-Type: application/json
Idempotency-Key: fan-join

{ "type": "gts.cf.core.tasks.task.v1~acme.reports._.render.v1~",
  "queue": "gts.cf.core.tasks.queue.v1~acme.reports._.bulk.v1",
  "input": { "report_id": "r-42-joined", "format": "pdf" },
  "predecessors": [
    { "task_id": "{task_1}", "on_predecessor_failure": "ignore" },
    { "task_id": "{task_2}", "on_predecessor_failure": "ignore" },
    { "task_id": "{task_3}", "on_predecessor_failure": "ignore" } ],
  "dependency_mode": "all" }
```
`201 Created` → `{task_4}`, `state: blocked`, three links `outcome: pending`.

## Exchange 3 — parts end
Workers complete `{task_1}` with `success`, `{task_2}` with a non-retryable `error` (→ `failed`), `{task_3}` with `success`. After the last of the three:
```http
GET /api/task_engine/v1/tasks/{task_4} HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
```
```json
{ "id": "{task_4}", "state": "queued",
  "predecessors": [
    { "task_id": "{task_1}", "on_predecessor_failure": "ignore", "outcome": "succeeded" },
    { "task_id": "{task_2}", "on_predecessor_failure": "ignore", "outcome": "failed_ignored" },
    { "task_id": "{task_3}", "on_predecessor_failure": "ignore", "outcome": "succeeded" } ],
  "…": "other fields as in CONVENTIONS §5.1" }
```

## Exchange 4 — the join's worker reads the parts
After claiming `{task_4}`, `{worker_a}` reads each part with its `read` right, e.g.:
```http
GET /api/task_engine/v1/tasks/{task_2} HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
```
`200 OK`: `{task_2}` `failed` with its `result.error`; the same reads of `{task_1}` and `{task_3}` return `completed` with `result.output.url`.

## Side effects
- `{task_4}` is never cancelled; it moves `blocked → queued` in the transaction of the last part to end.
- With `cancel` links instead, `{task_2}`'s failure would have cancelled `{task_4}` with `dependency_failed` ([1.02](1.02-positive-predecessor-outcome-moves-successor.md) case `all_failed_cancel_cascades`).

## Notes
- The engine does not hand the predecessors' results to the join; the worker reads them (a children wait does give counts, but only to a parent: [waits/children](../../waits/children/)).
- Parts and join must be in one task domain: a create looks up predecessors only in its own domain, so a part elsewhere is `404` (G-WAI-41).
- `predecessors[].outcome` tells the join's creator which parts failed without reading them (G-WAI-37).
