# A predecessor's end unblocks, waits on, or cancels its `blocked` successor, by mode and failure rule

Each predecessor's terminal transaction runs `on_predecessor_terminal` for its `blocked` successors (finalize step 8). The outcome depends on the successor's `dependency_mode` and on the link's `on_predecessor_failure`:

- A `completed` predecessor (`success` or `warning`, PRD.md:837) satisfies its link. In `all` mode the successor unblocks when every link is satisfied; in `any` mode the first satisfied link is enough.
- A predecessor that ends `failed`, `cancelled` or `dead_lettered` on a `cancel` link (today's rule, the default) makes an `all` successor unsatisfiable, so it ends `cancelled` / `dependency_failed`, and that terminal transition runs its own cascade, so the successor's successors follow. An `any` successor is cancelled only when every predecessor has failed (PRD.md:839).
- On an `ignore` link the failure counts as satisfied (`outcome: failed_ignored`), in `all` and `any` mode alike: "wait until it has ended, whatever the outcome" (G-WAI-37).

An unblocked successor moves `blocked → queued` in the same transaction, a hand-over that is never refused, or to `scheduled` when its `run_after` is still in the future (`blocked` takes precedence over `run_after` at creation, DESIGN.md:525). The cascade only looks at `blocked` successors (DESIGN.md:2912), so later outcomes never reach a successor that has left `blocked`.

## Setup
- [Create with predecessors](1.01-positive-create-with-predecessors-initial-state.md) case `live`: `{task_3}` is `blocked` on `{task_1}` and `{task_2}` (`all`, both `cancel`).
- `{task_1}` already completed with `success` at `T0+30s` (`{task_3}` stayed `blocked`, link 1 `outcome: succeeded`).
- `{task_2}` is `running` under `{worker_a}` with `{lt_2}`. Clock `T0+60s`.

### Side effects by case
- `all_last_success`: in the same transaction `te_dependencies({task_3}, {task_2})` has `outcome = succeeded` and `{task_3}` advances `blocked → queued`; `{task_3}` leaves the deferred set and joins the queued set (hand-over, never refused, PRD.md:453); timer `queue_timeout` for `{task_3}` is armed at `T0+60s+3600s`; a `newTask` signal is emitted; `GET /tasks/{task_3}` shows both links `outcome: succeeded`; subsequent `POST /tasks/claim` on **reports** can return `{task_3}`; history of `{task_3}` gains no event for the unblock (G-SEC-23).
- `all_success_run_after_future`: `{task_3}.run_after` is `2026-11-03T12:00:00Z`; timer `scheduled` for `{task_3}` is armed at `2026-11-03T12:00:00Z`; `{task_3}` stays in the deferred set (both states are deferred).
- `any_first_success`: `te_dependencies({task_3}, {task_1})` has `outcome = succeeded`; `te_dependencies({task_3}, {task_2})` still has `outcome = pending`.
- `any_all_failed_cancel`: `{task_3}` leaves the deferred set; history of `{task_3}` gains `taskCancelled` with `result_code: dependency_failed` and no `actor`; event `taskCancelled` for `{task_3}` is published to the task-events topic; `te_dependencies` rows of `{task_3}` are absent; `te_task_results.predecessors` of `{task_3}` lists both links with `outcome: failed`.
- `all_failed_cancel_cascades`: `{task_1}` is `failed`; both successors within the inline cascade (2 dependents ≤ `cascade_inline_limit`); history of `{task_2}` and `{task_3}` gains `taskCancelled` with `result_code: dependency_failed`; both leave the deferred set.
- `all_failed_ignore`: `te_dependencies({task_3}, {task_1})` has `outcome = failed_ignored`; timer `queue_timeout` for `{task_3}` is armed; history of `{task_3}` gains no event (no `taskCancelled`, no `taskQueued`; G-SEC-23).

## Notes
- An unblock records no event (G-SEC-23): it is an engine-driven entry into `queued`, explained by the predecessor's own event. `taskQueued` means "returned to its queue" with reason `released`, `reenqueued` or `revoked` (CONVENTIONS §5.10). The unblock is asserted through the state and `predecessors[].outcome`.
- `all_success_run_after_future`: had `{task_1}` completed after 12:00, `{task_3}` would go straight to `queued` (DESIGN.md:527).
- `any_first_success`: if `{task_3}` were already `running` when `{task_2}` fails, it keeps running; `cancel` never reaches a successor that has left `blocked`.
- `any_all_failed_cancel`: after `{task_1}`'s cancel alone, `{task_3}` stayed `blocked`: one failure is not enough in `any` mode (PRD.md:839).
- `all_failed_cancel_cascades`: same outcome when `{task_1}` ends `cancelled` or `dead_lettered`. PRD.md:839 says "cascades to its own successors"; DESIGN.md:2916 says finalize() of the cancelled successor starts its own cascade. Whether `{task_3}` is cancelled in the same transaction or by a following cascade step is not asserted; a test waits one timer-wheel tick.
- `all_failed_ignore`: this is how an operator lets a successor run past a hung predecessor: cancel the predecessor (Proposals › Task mutability, "Instead of removing a dependency"). G-WAI-37 adds the `ignore` branch to `on_predecessor_terminal` (DESIGN.md:2911-2916); in `any` mode an ignored failure satisfies the link and unblocks at once, like a success.
- A large fan-out is cancelled in bounded steps: [1.08](1.08-guardrail-large-fanout-cascade-cancels-each-once.md).
