# Re-enqueueing a failed predecessor does not revive its cancelled successors

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-dependencies` (PRD.md:839) · PRD.md:813 · DESIGN.md:545, :1437 |
| Phase | p2 |
| Test level | E2E |

A predecessor that failed has already cancelled its `cancel` successors with `dependency_failed`. An admin re-enqueue gives the predecessor another run, but the successors stay terminal: "a later re-enqueue does not revive its successors" (PRD.md:839, :813).

## Setup
- `{task_1}` (**render**, queue **reports**, tenant A) ended `dead_lettered`; its successor `{task_2}` (link `cancel`) was cancelled with `dependency_failed` by the cascade.

## Request
```http
POST /api/task_engine/v1/admin/tasks/{task_1}/reenqueue HTTP/1.1
Host: api.example.com
Authorization: Bearer <admin-token>
```

## Expected response
- `200 OK`, `{task_1}` `queued` in **reports** (`dead_lettered_from` cleared).

## Side effects
- task `{task_1}` state is `queued`.
- task `{task_2}` is unchanged: `cancelled`, result_code `dependency_failed`; no new history entry.
- When `{task_1}` later completes with `success`: task `{task_2}` is still unchanged (the cascade only visits `blocked` successors, DESIGN.md:2912, and `{task_2}` has no live `te_dependencies` row).

## Notes
- A successor that wants another try is created again, naming the re-enqueued `{task_1}` (now live) as predecessor.
- Successors with an `ignore` link that already ran are equally unaffected.
