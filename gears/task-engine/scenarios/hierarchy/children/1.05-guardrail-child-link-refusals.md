# A child the caller may not link is refused without revealing anything about the parent

After the accepted change, `parent_task_id` on `POST /tasks` requires `parent_lease_token`; the `update` alternative is gone. The token must match the parent's **current** lease, held by the caller, while the parent is `claimed` or `running` (DESIGN.md:2630-2631). A link authorization failure never reveals more than "no such parent": a wrong or stale token, a parent that is `waiting` or has ended, and a parent in another tenant or hidden by policy all get the same `404` as a missing one, never `403` or `LEASE_LOST` (DESIGN.md:728, :2629). A request without the token is refused by a syntactic check before the parent is looked up, so it says nothing about whether the parent exists either.

## Setup
- `{task_1}` (**render**, queue **reports**, tenant A) was claimed by `{worker_a}` with `{lt_1}`, released, and claimed again with `{lt_2}` (`lease_epoch` 2). It is `running`.
- `{worker_a}` (process `reports-7f9c-2`) still has the old token `{lt_1}`.

## Request
```http
POST /api/task_engine/v1/tasks HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json
Idempotency-Key: child-stale-token-1

{
  "type": "gts.cf.core.tasks.task.v1~acme.reports._.render.v1~",
  "queue": "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1",
  "input": { "report_id": "r-42-part-2", "format": "pdf" },
  "parent_task_id": "{task_1}",
  "parent_lease_token": "{lt_1}"
}
```

## Expected response
- `404 Not Found`, `not_found` with `resource_type` and `resource_name` (the `parent_task_id` as sent) only; no field violation (G-WIRE-15).
- The same body (apart from `resource_name` and `trace_id`) as for a random `parent_task_id`; no `LEASE_LOST`, which would confirm the parent exists.

```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.not_found.v1~",
  "title": "Not Found",
  "status": 404,
  "detail": "Parent task not found",
  "instance": "/api/task_engine/v1/tasks",
  "trace_id": "<trace>",
  "context": { "resource_type": "gts.cf.core.tasks.task.v1~", "resource_name": "{task_1}" }
}
```

## Side effects
<!-- No side effects: the request is refused before any write (no_token) or the create transaction rolls back (all other cases); no task, dedup row or counter change remains. -->
- `waiting_parent`: `{task_1}`'s children are still `{task_2}`…`{task_5}`; `{wc_1}` stays `pending`.

## Notes
- `no_token`: `400 REQUIRED` on `/parent_lease_token`, a syntactic check that does not depend on the parent (G-WAI-02). The `Idempotency-Key` is not consumed: validation runs before the `te_dedup` insert (DESIGN.md:2538, :2586). New work for a running job reaches it through an input wait, and its worker creates the children (Proposals › Task mutability).
- The other cases: the parent check runs inside the create transaction after the dedup insert (DESIGN.md:2586, :2626); the rollback also removes the `te_dedup` row, so the same key can be reused.
- `waiting_parent`: two rules refuse it, either one enough: the parent is `waiting` (DESIGN.md:2628) and the token no longer matches (DESIGN.md:2630-2631). On `main` a caller with `update` on the parent could still try (DESIGN.md:2632, PRD.md:855); that path is removed (G-WAI-02).
- `terminal_parent`: the worker can read `{task_1}` (it has `read`), so a `400 STATE` would be tempting; DESIGN.md:728 and :2629 choose the uniform `404` for every link failure, which this case asserts.
- `foreign_parent`: same result when the parent is in tenant A but a policy hides it from the caller (`{reader_a}`-style scope without the task), or when `{creator_a2}` names `{creator_a}`'s task with a guessed token. Even `{worker_a}`'s real token would not help `{worker_b}`: the token must match a parent visible in the caller's scope and `assignee_subject = ctx.subject_id` (DESIGN.md:2630-2631).
- DESIGN.md:728 and :1200 ask for a field violation on the link `404`; G-WIRE-15 drops it (it would reveal which link exists), so every `404` here carries only `resource_type` and `resource_name`.
