# A child created while its parent is being cancelled is either refused or cancelled, never orphaned

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-link-authz` (PRD.md:855) · PRD.md:1544 · DESIGN.md:729, :2624-2629, :2974, :2908 |
| Phase | p2 |
| Test level | Integration — race |
| Gaps | G-WAI-23, G-WIRE-15 |

The create transaction locks the parent's `te_task_state` row before inserting the child; the parent's terminal transaction reads its children with a locking read. The two serialize, so exactly one of two outcomes happens. A test runs the race many times and accepts only these.

## Setup
- `{task_1}` (**render**, tenant A, `propagate_cancel: true`) is `running` under `{worker_a}` with `{lt_1}`.
- At the same instant, `{admin}` force-cancels `{task_1}` and `{worker_a}` creates a child with `parent_lease_token: {lt_1}`.

## Exchange 1 — forced cancel
```http
POST /api/task_engine/v1/tasks/{task_1}/cancel HTTP/1.1
Host: api.example.com
Authorization: Bearer <admin-token>
Content-Type: application/json

{ "mode": "forced" }
```
`200 OK`, `state: cancelled`, `result_code: forcibly_cancelled`.

## Exchange 2 — concurrent child create
```http
POST /api/task_engine/v1/tasks HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json
Idempotency-Key: race-child-1

{
  "type": "gts.cf.core.tasks.task.v1~acme.reports._.render.v1~",
  "queue": "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1",
  "input": { "report_id": "r-42-race", "format": "pdf" },
  "parent_task_id": "{task_1}",
  "parent_lease_token": "{lt_1}"
}
```

## Expected response
Exactly one of:
- **Cancel commits first** → the create's locking read finds no live parent: `404 Not Found` with only `resource_type` and `resource_name` (as [1.05](1.05-guardrail-child-link-refusals.md) case `terminal_parent`); no child exists.
- **Create commits first** → `201 Created` with `{task_2}` (`queued`, `parent_task_id = {task_1}`); the cancel, which waited on the parent row lock, then sees `{task_2}` in its locking read of children and cancels it in the same transaction in the parent's mode, so `{task_2}` ends `cancelled` / `forcibly_cancelled` (G-WAI-23).

## Side effects
- Never: a live task whose `parent_task_id` is a terminal `{task_1}` with `propagate_cancel: true`.
- Second outcome: task `{task_2}` state is `cancelled`, result_code `forcibly_cancelled`; history of `{task_2}` gains `taskCreated` then `taskCancelled`.
- First outcome: `te_dedup` holds no row for `race-child-1` (rolled back).

## Notes
- The same rule protects a `wait_for_children` parent that completes concurrently: a parent `success` that commits first makes the create `404`; a create that commits first makes the completion `400 CHILDREN_PENDING` ([1.07](1.07-negative-complete-with-children-pending.md)). DESIGN.md:736 does not spell out the lock for this case; it follows from the parent-row lock of DESIGN.md:2627.
