# A child's worker can create grandchildren, up to `max_hierarchy_depth`

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-parent-child` (PRD.md:826) · PRD.md:1606 (open question) |
| Phase | p2 |
| Test level | Both — E2E `grandchild`; integration `too_deep` (needs a chain at the limit) |
| Gaps | G-WAI-39 |

A child is an ordinary task, so its own worker can create children of it in the same way. Each task stores its `hierarchy_depth` (the parent's + 1). A create that would go past `max_hierarchy_depth` (default 10) is refused with `400 TOO_DEEP` on `/parent_task_id` (G-WAI-39), which answers the open question of PRD.md:1606.

## Setup
- `{task_1}` (**render**, tenant A) is `running`; its worker created `{task_2}`.
- `{task_2}` is claimed by `{worker_a}` process `reports-7f9c-2` with `{lt_2}` and `running`.
- `max_hierarchy_depth = 10` (default).

## Request
```http
POST /api/task_engine/v1/tasks HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json
Idempotency-Key: grandchild-1

{
  "type": "gts.cf.core.tasks.task.v1~acme.reports._.render.v1~",
  "queue": "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1",
  "input": { "report_id": "r-42-part-1-page-3", "format": "pdf" },
  "parent_task_id": "{task_2}",
  "parent_lease_token": "{lt_2}"
}
```

## Expected response
- `201 Created`, `Location: /api/task_engine/v1/tasks/{task_3}`; `parent_task_id = {task_2}`, `state: queued`.

```json
{ "id": "{task_3}", "state": "queued", "parent_task_id": "{task_2}", "…": "other fields as in CONVENTIONS §5.1" }
```

## Cases

| Case | Setup differs | Request differs | Expected | Notes |
|---|---|---|---|---|
| `grandchild` | (the representative Setup) | (the representative request) | `201`, as above | |
| `too_deep` | `{task_2}` is at the deepest allowed level: `hierarchy_depth = 10` (a root task has depth 0), `running` under `{lt_2}` | `Idempotency-Key: grandchild-too-deep-1` | `400 invalid_argument`, `TOO_DEEP` on `/parent_task_id` (body below); no task created | G-WAI-39 |
| `too_deep_missing_parent` | as `too_deep` | `parent_task_id` names a task that does not exist | `404 not_found` for the parent, as in [1.05](1.05-guardrail-child-link-refusals.md); not `TOO_DEEP` | G-WAI-39: the depth check runs after the parent lookup |

Body of `too_deep`:
```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.invalid_argument.v1~",
  "title": "Invalid Argument",
  "status": 400,
  "detail": "The task hierarchy would exceed the maximum depth",
  "instance": "/api/task_engine/v1/tasks",
  "trace_id": "<trace>",
  "context": {
    "field_violations": [
      { "field": "/parent_task_id", "description": "the hierarchy may be at most max_hierarchy_depth (10) levels deep", "reason": "TOO_DEEP" }
    ]
  }
}
```

## Side effects
- `grandchild`: task `{task_3}`.parent_task_id is `{task_2}`; its stored `hierarchy_depth` is `{task_2}`'s + 1.
- `grandchild`: a later cancel of `{task_1}` (propagating) cancels `{task_2}`, whose own terminal transition cascades to `{task_3}` (DESIGN.md:2989).
- `too_deep`: the create transaction rolls back; no task, dedup row or counter change remains; `{task_2}` and `{lt_2}` are unchanged.

## Notes
- The depth limit bounds the chain; the cost of a cascade stays bounded by the batched durable cascade (DESIGN.md:2989), not by depth (G-WAI-39).
- A root task has depth 0, so a task at depth 10 can have no children with the default limit (G-WAI-39). The depth check runs after the parent lookup, so a missing parent is still `404` (case `too_deep_missing_parent`).
