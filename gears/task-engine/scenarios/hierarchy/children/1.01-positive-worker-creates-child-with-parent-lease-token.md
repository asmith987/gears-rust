# The parent's worker creates a child with the parent's lease token

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-parent-child` (PRD.md:826) · `cpt-cf-task-engine-fr-link-authz` (PRD.md:855) · DESIGN.md:726, :2626-2632 |
| Phase | p2 |
| Test level | E2E |
| Depends on | Proposals › Task mutability › Only the parent's worker adds children |
| Gaps | G-WAI-02, G-WAI-39, G-WAI-43 |

A running task splits its work by creating child tasks. The only way to attach a child to an existing task is to hold the parent's lease and send its token as `parent_lease_token`; the caller also needs `create` for the child's type and queue. The child is an ordinary task in the parent's tenant, with `parent_task_id` set.

## Setup
- `{task_1}` (**render**, queue **reports**, tenant A) is `running`, claimed by `{worker_a}` (`reports-7f9c-1`) with lease `{lt_1}`, `lease_epoch` 1.
- `{task_1}` was created with `wait_for_children: false`, `propagate_cancel: true`.

## Request
```http
POST /api/task_engine/v1/tasks HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json
Idempotency-Key: child-of-task-1-part-1

{
  "type": "gts.cf.core.tasks.task.v1~acme.reports._.render.v1~",
  "queue": "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1",
  "priority": 100,
  "input": { "report_id": "r-42-part-1", "format": "pdf" },
  "parent_task_id": "{task_1}",
  "parent_lease_token": "{lt_1}"
}
```

## Expected response
- `201 Created`, `Location: /api/task_engine/v1/tasks/{task_2}`.
- The child is `queued` in tenant A, `parent_task_id = {task_1}`, `created_by = {worker_a}`.
- The body never echoes `parent_lease_token` (tokens appear only in claim/accept responses and the holder's requests, DESIGN.md:1081).

```json
{
  "id": "{task_2}",
  "type": "gts.cf.core.tasks.task.v1~acme.reports._.render.v1~",
  "queue": "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1",
  "owner_tenant_id": "{tenant_a}",
  "created_by": "{worker_a}",
  "state": "queued",
  "parent_task_id": "{task_1}",
  "wait_for_children": false,
  "propagate_cancel": true,
  "…": "other fields as in CONVENTIONS §5.1"
}
```

## Side effects
- task `{task_2}` state is `queued`; task `{task_2}`.parent_task_id is `{task_1}`.
- task `{task_1}` is unchanged: still `running`, lease `{lt_1}` still valid, `lease_epoch` 1.
- history of `{task_2}` gains `taskCreated` with `initial_state: queued`, `actor: {worker_a}`.
- timer `queue_timeout` for `{task_2}` is armed at `T0+3600s`; timer `lifetime` for `{task_2}` is armed at `T0+86400s`.
- `{task_2}` joins the queued set.
- `{task_2}`'s stored `hierarchy_depth` is `{task_1}`'s + 1 (limit `max_hierarchy_depth`, G-WAI-39, see [1.02](1.02-positive-nested-children-up-to-max-depth.md)).

## Notes
- The parent's row is locked before the child is inserted (DESIGN.md:2624-2627), so a concurrent end of the parent is either seen (404) or reaches the child: see [1.09](1.09-guardrail-child-created-while-parent-ends-never-orphaned.md).
- DESIGN.md:2631 accepts the token only while the parent is `claimed` or `running`.
- PRD.md:855 and DESIGN.md:2632 still offer `update` on the parent instead of the token; the accepted proposal removes it, and a missing token is `400 REQUIRED` on `/parent_lease_token` (G-WAI-02, [1.05](1.05-guardrail-child-link-refusals.md)).
- In p1 `parent_task_id` on create is refused with `400` `FEATURE_NOT_AVAILABLE` on `/parent_task_id` (G-WAI-43), so this scenario is p2.
