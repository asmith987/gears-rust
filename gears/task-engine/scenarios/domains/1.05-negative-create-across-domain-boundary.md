# A create that would cross a task-domain boundary is rejected (type rule `400`, cross-domain link `404`)

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-task-domains` (PRD.md:1178, :1182) · PRD.md:1505, :1506, :1507 · ADR-0010:35, :61, :63, :80, :81 · DESIGN.md:715, :1200, :1223, :1224, :1997, :2004, :2255 |
| Phase | p3 |
| Test level | E2E — needs a two-domain e2e profile |
| Depends on | Proposals › Task mutability › Only the parent's worker adds children; Proposals › Task mutability › Set only in the create request |
| Gaps | G-OPS-24, G-WAI-41, G-WIRE-14, G-WIRE-15, G-SEC-21 |

Each domain is its own database. Domain type rules keep a class of work in its own database: a type that matches the `system` domain's type patterns may only be placed in that domain's queues, whatever queue the request names, also when the type was registered after startup. A type-rule breach is refused `400 invalid_argument` with `TASK_DOMAIN_MISMATCH` on `/queue`; the check runs after type resolution and before the transaction (DESIGN.md:1997). A parent and its children, and a predecessor and its successor, must live in one database, so completion tracking, cancel propagation, unblocking and `dependency_failed` cascades never cross a database boundary. A create looks up linked tasks only in the new task's domain, so a parent or predecessor in another domain is not found there and gets the uniform `404` (G-WAI-41, G-OPS-24).

## Setup
- Domain config:
  ```yaml
  task_domains:
    - name: system
      queues: ["gts.cf.core.tasks.queue.v1~cf.core.tasks.system.v1"]
      types: ["gts.cf.core.tasks.task.v1~cf.platform.*"]
    - name: heavy
      queues: ["gts.cf.core.tasks.queue.v1~acme.reports._.heavy.v1"]
    - name: default
      queues: ["*"]
  ```
- **heavy** (`gts.cf.core.tasks.queue.v1~acme.reports._.heavy.v1`) is registered like **reports**. **cleanup** (`cf.platform._.tenant_cleanup.v1~`) matches the `system` type rule; **default** and **reports** route to `default`.
- `{platform_worker}` may create **cleanup** tasks.

## Request
```http
POST /api/task_engine/v1/tasks HTTP/1.1
Host: api.example.com
Authorization: Bearer <platform-worker-token>
Content-Type: application/json
Idempotency-Key: cleanup-tenant-a-1

{
  "type": "gts.cf.core.tasks.task.v1~cf.platform._.tenant_cleanup.v1~",
  "queue": "gts.cf.core.tasks.queue.v1~cf.core.tasks.default.v1",
  "input": { "tenant_id": "{tenant_a}" }
}
```

## Expected response
- `400 Bad Request`, `invalid_argument`, field violation on `/queue` with `TASK_DOMAIN_MISMATCH`; no `context.reason`. The detail names the type, the queue, the queue's domain and the type's domain.

```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.invalid_argument.v1~",
  "title": "Invalid Argument",
  "status": 400,
  "detail": "Task type gts.cf.core.tasks.task.v1~cf.platform._.tenant_cleanup.v1~ is restricted to domain system; queue gts.cf.core.tasks.queue.v1~cf.core.tasks.default.v1 is in domain default",
  "instance": "/api/task_engine/v1/tasks",
  "trace_id": "<trace>",
  "context": { "field_violations": [ { "field": "/queue", "description": "type domain system, queue domain default", "reason": "TASK_DOMAIN_MISMATCH" } ] }
}
```

## Notes
- Omitting `queue` falls back to the type's `default_queue` (DESIGN.md:715). **cleanup**'s `default_queue` is **system**, so the representative request without `queue` succeeds in the `system` domain.
- DESIGN.md:1997: "A type whose `default_queue` breaks its rule therefore cannot be created without an explicit queue in its domain." Task types are registered at runtime, so the type rule cannot be checked at startup.
- The same type-rule check runs on bulk move ([bulk move](../bulk/1.04-positive-bulk-move-per-task-outcomes.md)) and on re-enqueue; the re-enqueue refusal lives in [dead-letter/](../dead-letter/1.04-negative-reenqueue-refusals.md).
- Cross-domain links have no reason code: the create never probes other domains, so the link is simply not found (`404`, DESIGN.md:1200; G-WAI-41). The `404` reveals nothing about where the task lives, whether or not the caller may read it.
- `CROSS_DOMAIN` stays a claim-request code (named queues in different domains, CONVENTIONS §5.3); it is not used on create.
