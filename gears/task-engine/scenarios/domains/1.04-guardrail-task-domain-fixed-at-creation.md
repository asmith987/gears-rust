# A task stays in the domain it was created in after its queue is re-routed

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-task-domains` (PRD.md:1180, :1186) · ADR-0010:70-71 · DESIGN.md:1224, :1999, :2835 |
| Phase | p3 |
| Test level | Integration — p3 multi-domain deployment / moves |
| Depends on | Proposals › Domains › Queue-move model (a task's domain is set at creation and never changes) · Proposals › Domains › p1 lays the foundation (read rules) |
| Gaps | G-OPS-22, G-OPS-25, G-RTY-20 |

A queue move applies only to new tasks. A finished task created before the move keeps its rows, its history and its retention in the old database, and stays readable by ID. A domain that no longer routes any queue stays configured for reads, retention and maintenance (G-OPS-22).

## Setup
- Before the change, domain `heavy` routed **heavy** (`gts.cf.core.tasks.queue.v1~acme.reports._.heavy.v1`); `default` caught the rest. **heavy** was then moved to `default` and the move has finished ([1.06](1.06-positive-routing-change-with-live-tasks-starts-a-move.md)); the `heavy` domain stays configured and routes no queue. `{task_1}` (`completed`, `terminal_at = T0-1d`) is stored in `heavy`.
- `{task_2}` is created on **heavy** after the change and lands in `default`.

## Request
```http
GET /api/task_engine/v1/tasks/{task_1} HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
```

## Expected response
- `200 OK`, `{task_1}` unchanged: `state: completed`, `queue` = **heavy**.
- `GET /tasks/{task_1}/events` returns its full history.
- `GET /tasks?$filter=queue eq 'gts.cf.core.tasks.queue.v1~acme.reports._.heavy.v1'` covers the queue's domain set, now `["default"]`, so it returns `{task_2}` only. A search not narrowed to one domain (no queue filter, no type with a type rule) also covers `heavy` and finds `{task_1}` ([1.01](1.01-positive-search-across-domains-stable-cursor.md)). See Notes.

## Side effects
- {task_1}'s rows are not copied to `default`; retention removes them from `heavy` on the `heavy` domain's schedule (the domain stays configured for retention and maintenance, G-OPS-22).

## Notes
- Re-enqueue of a dead-lettered task of the old routing without a `queue` body is refused `400 TASK_DOMAIN_MISMATCH` on `/queue`; that refusal lives in [dead-letter/](../dead-letter/1.04-negative-reenqueue-refusals.md). Re-enqueue may name a dispatch queue routed to the task's domain (G-RTY-20), but `heavy` routes none here, so such a task stays visible as dead-lettered and can never run again; the operator's only option is to create a new task.
- A read by ID probes the configured domains in config order, `default` last (G-OPS-22).
- Not covered by a decision: whether a search by queue should also reach a domain the queue has left that still holds its finished tasks. The accepted proposal says search by queue covers the queue's domain set, and a finished move removes the source from that set (G-OPS-25), so this scenario asserts `{task_2}` only.
- PRD.md:1186 ("a read filtered by queue … uses that one domain") is on the proposal's edit list.
