# During a move, new work goes to the target, linked work stays with its source, and a claim names one domain

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-task-domains` (PRD.md:655, :1182, :1186) · ADR-0010:63-64 · DESIGN.md:703, :1064, :2004 |
| Phase | p3 |
| Test level | Integration — p3 multi-domain deployment / moves |
| Depends on | Proposals › Domains › Queue-move model (placement during a move) · Proposals › Domains › p1 lays the foundation (`domain` on claim and lease) · Proposals › Domains › During a move |
| Gaps | G-OPS-22, G-OPS-25, G-OPS-42, G-RTY-20, G-SEC-21 |

While **heavy** is moving from `heavy` to `default` ([1.06](1.06-positive-routing-change-with-live-tasks-starts-a-move.md)), a plain create goes to the target. A create that must be written in one transaction with a live task in the source (a successor of a source predecessor, a child of a source parent) goes to the source, so one atomic operation still touches one domain (PRD.md:1182). Workers run one claim loop per domain; because **heavy** is in two domains, a claim that names it must say which one.

## Setup
- **heavy** has `domains: ["default", "heavy"]`. `{task_1}` (**render** on **heavy**, `queued`) is in `heavy`.
- Clock `T0`.

## Request
```http
POST /api/task_engine/v1/tasks HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
Content-Type: application/json
Idempotency-Key: 5b0e-heavy-r-77

{ "type": "gts.cf.core.tasks.task.v1~acme.reports._.render.v1~",
  "queue": "gts.cf.core.tasks.queue.v1~acme.reports._.heavy.v1",
  "input": { "report_id": "r-77", "format": "pdf" } }
```

## Expected response
- `201 Created`, `{task_2}` `queued`, stored in `default`.

## Side effects
- `{task_2}` is in the `default` database; `{task_1}` stays in `heavy`.
- `GET /tasks/{task_2}` and `GET /tasks/{task_1}` both return `200` (a read by ID probes the configured domains in config order, `default` last, G-OPS-22).
- `GET /tasks?$filter=queue eq 'gts.cf.core.tasks.queue.v1~acme.reports._.heavy.v1'` returns both (search by queue covers the queue's domain set).

## Notes
- Claim order between the two domains is not defined; the SDK polls the source first so older work tends to drain first (Proposals › Domains › During a move). Exact order returns when the source is empty.
- Concurrency and depth limits during a move: each domain's maintenance leader samples its own use, and each domain enforces the limit minus the other domain's latest sample, so the limit can be exceeded by one sampling interval. This overshoot is accepted (G-OPS-42); not asserted here.
- The move ends when maintenance finds no unfinished task of **heavy** in `heavy`; `te_queue_move_remaining{queue,domain}` shows what is left (G-OPS-25).
- The reason codes `REQUIRED` and `CROSS_DOMAIN` follow CONVENTIONS §5.3 and §6; `TASK_DOMAIN_MISMATCH` is DESIGN's (DESIGN.md:1224). Field paths are JSON Pointers (G-SEC-21).
