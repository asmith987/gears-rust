# One dead-letter queue serves queues in two domains, and DLQ search lists both

Dead-letter queues are not routed. A task dead-lettered from **system** stays in the `system` database; one from **reports** stays in `default`; both name the same `dead_letter` queue. A DLQ search fans out to every domain and merges the results.

## Setup
- Domains `system` (queue **system**) and `default`, as DESIGN.md:2223-2230.
- `{task_1}`: **render** on **reports**, dead-lettered at `T0-2h` (stored in `default`).
- `{task_2}`: **cleanup** on **system**, dead-lettered at `T0-1h` (stored in `system`).
- `{admin}` may read both.

## Request
```http
GET /api/task_engine/v1/tasks?$filter=state eq 'dead_lettered'&$orderby=terminal_at desc&limit=10&view=short HTTP/1.1
Host: api.example.com
Authorization: Bearer <admin-token>
```

## Expected response
- `200 OK`, both tasks, newest `terminal_at` first; both have `queue` = the dead-letter queue and their own `dead_lettered_from`.

```json
{ "items": [
    { "id": "{task_2}", "state": "dead_lettered", "queue": "gts.cf.core.tasks.queue.v1~cf.core.tasks.dead_letter.v1",
      "dead_lettered_from": "gts.cf.core.tasks.queue.v1~cf.core.tasks.system.v1", "terminal_at": "2026-11-03T09:00:00Z" },
```

## Notes
- A search filtered only to `state eq 'dead_lettered'` has no `created_at` window; the set is bounded by retention (G-RTY-10). Listing needs only `read`; re-enqueue needs `admin`.
- `dead_lettered_from` is a filter field and part of the `short` view (G-RTY-11). Adding `and dead_lettered_from eq 'gts.cf.core.tasks.queue.v1~cf.core.tasks.system.v1'` narrows the search to the source queue's domain set, here `system` only (PRD.md:815).
- Dead-letter queues have no domain set: `queue eq 'gts.cf.core.tasks.queue.v1~cf.core.tasks.dead_letter.v1'` searches every configured domain, like the state filter (G-OPS-23).
- `{task_2}` came from **system** (`operated_by: platform`), so the operator reads it with barrier `Ignore` and the PDP decides (G-SEC-15).
