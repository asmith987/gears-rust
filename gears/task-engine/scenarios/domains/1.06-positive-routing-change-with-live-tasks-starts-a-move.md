# A routing change of a queue with live tasks starts a move instead of stopping the queue

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-task-domains` (PRD.md:1176, :1180) · ADR-0010:60, :63-64, :69-71 · DESIGN.md:1053, :1999 |
| Phase | p3 |
| Test level | Integration — p3 multi-domain deployment / moves |
| Depends on | Proposals › Domains › Queue-move model (fixed domain, domain set, placement during a move) |
| Gaps | G-OPS-02, G-OPS-25 |

On `main`, routing **heavy** to another domain while it still has unfinished tasks fails startup, and nothing can drain the queue first. With the accepted queue-move model, the change is an operation instead of an outage: the queue's domain set becomes the target plus the source, new work goes to the target at once, existing work finishes where it is, and producers and workers keep running. Rows are never copied between domains (ADR-0010).

## Setup
- Running config: domain `heavy` routes **heavy** (`gts.cf.core.tasks.queue.v1~acme.reports._.heavy.v1`); `default` catches the rest. **heavy** has 3 `queued` and 1 `running` task in the `heavy` database.
- A new release routes **heavy** to `default` and keeps the `heavy` domain configured (it still routes nothing else). It is rolled out to instance `te-2`.

## Request
```http
GET /api/task_engine/v1/queues/gts.cf.core.tasks.queue.v1~acme.reports._.heavy.v1 HTTP/1.1
Host: api.example.com
Authorization: Bearer <admin-token>
```

## Expected response
- `200 OK`; `domains` lists the target first, then the source: `["default", "heavy"]`. `counts` are shown because `{admin}` holds `configure` on the queue (G-OPS-02).
- `GET /readyz` on `te-2` → `200`: the change does not stop the instance.

```json
{ "id": "gts.cf.core.tasks.queue.v1~acme.reports._.heavy.v1", "kind": "dispatch",
  "domains": ["default", "heavy"],
  "counts": { "queued": 3, "running": 1, "claimed": 0, "scheduled": 0, "blocked": 0, "waiting": 0 },
  "hold": null }
```

## Side effects
- No task is moved, cancelled or requeued; the 4 tasks stay in the `heavy` database and keep their domain (Proposals › Domains: "a task's domain is set at creation and never changes").
- A task created on **heavy** after the change is stored in `default` ([1.07](1.07-positive-placement-and-claims-during-a-move.md)).
- `metric te_queue_move_remaining{queue="…heavy.v1",domain="heavy"}` reports the unfinished tasks left in the source (4 at the start).
- When maintenance finds no unfinished **heavy** task in `heavy`, the move ends and `domains` becomes `["default"]`.

## Cases

| Case | Differs from the representative setup | Expected | Notes |
|---|---|---|---|
| `source_still_configured` | (representative) | queue `domains: ["default", "heavy"]`; instance ready | |
| `no_live_tasks` | **heavy** has only terminal tasks in `heavy` | `domains: ["default"]`; old tasks stay readable by ID ([1.04](1.04-guardrail-task-domain-fixed-at-creation.md)) | nothing to finish in the source |
| `source_domain_removed` | the release removes the `heavy` domain from config entirely | `te-2` is not ready (`/readyz` → `503`) instead of failing startup; the log names the removed domain and its live-task counts | the tasks would be unreachable; PRD.md:1180 and ADR-0010:69 change from "stop startup" to not ready (G-OPS-25) |

## Notes
- A move starts with a routing change while the old domain stays configured, and ends when maintenance finds no unfinished task of the queue in the source (G-OPS-25).
- "A move cannot finish while tasks in other queues of the source keep creating children or successors in the moved queue" (Proposals › Domains › What we give up); `te_queue_move_remaining{queue,domain}` shows what keeps the source busy (G-OPS-25).
