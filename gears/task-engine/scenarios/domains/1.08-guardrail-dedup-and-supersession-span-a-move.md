# Dedup and supersession still hold across the two domains of a move

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-dedup` (PRD.md:319-335) · `cpt-cf-task-engine-fr-idempotent-create` · `cpt-cf-task-engine-fr-task-domains` (PRD.md:1182) |
| Phase | p3 |
| Test level | Integration — p3 multi-domain deployment / moves |
| Depends on | Proposals › Domains › During a move (caller keys, derived dedup, supersession) |
| Gaps | G-OPS-42, G-WIRE-14 |

Dedup and supersession records are per domain. Without care, a replay or a stale revision sent during a move would reach the target, find nothing there, and get through. During a move the engine reads the source's dedup records before inserting in the target, and supersession follows the group's live task or copies the source head on first use, so the same answers come back as before the move.

## Setup
- **heavy** is moving from `heavy` to `default`; the type **metric_job** is routed to **heavy** for this scenario.
- Before the move, `{task_1}` (**metric_job**, `{ "graph_id": "g-1", "metric": "p95", "revision": 5 }`) was created in `heavy` and is `queued`.

## Request
```http
POST /api/task_engine/v1/tasks HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
Content-Type: application/json

{ "type": "gts.cf.core.tasks.task.v1~acme.graph._.metric_job.v1~",
  "queue": "gts.cf.core.tasks.queue.v1~acme.reports._.heavy.v1",
  "input": { "graph_id": "g-1", "metric": "p95", "revision": 5 } }
```

## Expected response
- `409 Conflict`, `already_exists`, `context.resource_name = {task_1}`: the derived identity is held in the source (same answer as [tasks/dedup/1.01](../tasks/dedup/1.01-positive-duplicate-by-derived-identity.md)).

<!-- No side effects: nothing is inserted in either domain. -->

## Cases

| Case | Differs from the representative request | Expected | Notes |
|---|---|---|---|
| `derived_dedup_hit_in_source` | (representative) | `409`, existing `{task_1}` | reads the source's `te_dedup` first |
| `caller_key_replay` | **render** with `Idempotency-Key` `k-1`, first sent before the move (task `{task_3}` in `heavy`) | `409`, `context.resource_name = {task_3}` | same as [tasks/idempotency/1.01](../tasks/idempotency/1.01-positive-replay-returns-409-with-existing-id.md) |
| `higher_revision_supersedes_source_task` | `revision: 6` | `201`, new task; `{task_1}` superseded; the replacement is written in `heavy` with `{task_1}` | "a replacement through supersession" stays with the live task |
| `stale_revision_after_source_ended` | `{task_1}` completed; the group has no live task; `revision: 4` | `400 failed_precondition`, `violations: [{ "type": "STATE", "subject": "STALE_ORDER" }]`, no task named | the source head is read and copied to the target on first use |

## Notes
- Supersession is p2 and domains are p3; the scenario applies when both exist.
- The cross-domain dedup read is best effort: it runs before the target's create transaction, so a duplicate created in the source in the same instant can slip through. This race is accepted and documented (G-OPS-42); the cases here have no concurrent source write.
- `STALE_ORDER` goes in `violations[].subject`, never `context.reason` (G-WIRE-14).
