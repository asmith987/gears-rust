# An event that matches waits in two domains is applied exactly once in each, also after redelivery

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-task-domains` (PRD.md:1184) · PRD.md:885, :1490 · ADR-0010:65, :84 · DESIGN.md:2006 |
| Phase | p3 |
| Test level | Integration — p3 multi-domain deployment / moves |
| Depends on | Proposals › Waits › Event waits after the others (accepted: event waits are p2) |

One consumer group serves all domains; each domain records the event in its own inbox in the same transaction that satisfies its waits, and the offset is committed last. A redelivered event finds the inbox row and changes nothing.

## Setup
- Domains `heavy` (queue **heavy**) and `default`.
- `{task_1}` (**reports**, domain `default`) and `{task_2}` (**heavy**, domain `heavy`), both tenant A, are `waiting` on an event condition: `event_type = gts.cf.core.events.event.v1~acme.orders._.paid.v1~`, `subject_type = gts.acme.orders._.order.v1~`, `subject_id = o-17`, `on_timeout: fail` (`{wc_1}`, `{wc_2}`). Topic `gts.cf.core.events.topic.v1~acme.orders._.order_events.v1` is in `waitable_topics`.

## Exchange 1 — The order service publishes the event (Event Broker)
```http
POST /v1/events HTTP/1.1
Host: broker.example.com
Authorization: Bearer <orders-service-token>
Content-Type: application/json

{ "id": "{evt_1}", "type": "gts.cf.core.events.event.v1~acme.orders._.paid.v1~", "tenant_id": "{tenant_a}",
  "source": "order-service", "subject": "o-17", "subject_type": "gts.acme.orders._.order.v1~",
  "occurred_at": "2026-11-03T10:00:00Z", "data": { "amount_cents": 4299 } }
```
- `202 Accepted`.

## Exchange 2 — Both tasks resumed
```http
GET /api/task_engine/v1/tasks/{task_1}/wait-conditions HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
```
- `200 OK`: `{wc_1}` `state: satisfied`. The same read for `{task_2}` shows `{wc_2}` satisfied. Both tasks are `queued` with `resume_pending`.

## Exchange 3 — The engine's consumer crashes before committing its offset; the broker redelivers `{evt_1}`
```http
GET /api/task_engine/v1/tasks/{task_2}/events?$filter=event_type eq 'waitConditionSatisfied' HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
```
- `200 OK` with exactly one `waitConditionSatisfied` item for `{wc_2}`; `{task_1}`'s history likewise has exactly one.

## Side effects
- `te_event_inbox({evt_1})` is present in the `default` database and in the `heavy` database (one row each).
- task {task_1} state is queued; task {task_2} state is queued; neither is resumed twice.
- The redelivery writes nothing new in either domain.

## Notes
- If `{task_2}` had already been claimed and parked again on a new wait for the same subject, the inbox row would still stop the redelivered event from satisfying it. That follows from dedup on event ID (PRD.md:885) and is assumed.
