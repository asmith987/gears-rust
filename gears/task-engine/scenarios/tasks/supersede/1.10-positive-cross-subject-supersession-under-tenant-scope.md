# Under `tenant` scope, one subject can supersede another subject's task

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-task-supersede` (PRD.md:335) · DESIGN.md:2597-2603 |
| Phase | p2 |
| Test level | E2E |
| Depends on | Proposals › Dedup and supersession › Drop `authz_scope` (only `tenant` is left for cross-subject groups) |
| Gaps | G-CRT-08, G-CRT-15 |

The supersede group shares the dedup scope. Under `tenant` scope the group is shared by every subject in the tenant, so a newer revision from one analyst replaces a job another analyst started, as long as the caller may `cancel` it (PRD.md:335). With `authz_scope` dropped (a type that declares it fails registration, G-CRT-15), `tenant` is the only scope where this happens; under `subject` scope each subject has its own group.

## Setup
- **metric_job** as in [1.01](1.01-positive-higher-order-supersedes-by-old-task-state.md) (`scope: tenant`).
- `{task_1}` (revision 7, **reports**, `created_by = {creator_a}`) is `queued`. `{creator_a2}` holds `create`, `read` and `cancel` on it (fixture policy).

## Request
```http
POST /api/task_engine/v1/tasks HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a2-token>
Content-Type: application/json

{ "type": "gts.cf.core.tasks.task.v1~acme.graph._.metric_job.v1~", "queue": "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1", "input": { "graph_id": "g-1", "metric": "pagerank", "revision": 8 } }
```

## Expected response
- `201 Created` with `{task_2}` (`created_by = {creator_a2}`).

## Side effects
- As [1.01](1.01-positive-higher-order-supersedes-by-old-task-state.md): {task_1} ends `cancelled` / `superseded` with `superseded_by = {task_2}`; its `taskCancelled` names `actor = {creator_a2}`.
- The group head is revision 8; a revision 6 from either subject → `400` `failed_precondition` `STALE_ORDER`.

## Cases

| Case | Differs from the representative request | Expected | Notes |
|---|---|---|---|
| `other_subject_with_cancel` | (representative) | `201`, `{task_1}` superseded | |
| `other_subject_without_cancel` | the PDP denies `cancel` on `{task_1}` to `{creator_a2}` | `403` `SUPERSEDE_CANCEL_DENIED`, nothing changes | home: [1.06](1.06-negative-caller-lacks-cancel-on-old-task.md); G-CRT-08 |

## Notes
- `cancel` is authorized before the create transaction opens (Proposals › Dedup and supersession › No PDP call inside the create transaction).
