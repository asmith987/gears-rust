# How a gracefully superseded task ends: grace expiry and worker reports

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-task-supersede` (PRD.md:328, :336) · `cpt-cf-task-engine-fr-task-cancel` (PRD.md:349) · DESIGN.md:552 · DESIGN.md:1510 · DESIGN.md:2378 (5) · DESIGN.md:2739 · DESIGN.md:2937 |
| Phase | p2 |
| Test level | Both — grace expiry rows |
| Gaps | G-CRT-18, G-CRT-17 |

After a graceful supersession the old task is `running` with `cancel_requested` and `superseded_by` set, and the old worker's token stays valid until it acknowledges (DESIGN.md:2378 (5)). A graceful cancel escalates to forced after `cancel_grace_period_secs` (PRD.md:349); for a supersession the result stays `superseded`: the `cancel_grace` timer finalizes with `superseded_by ? superseded : forcibly_cancelled` (DESIGN.md:2739), and the lease ends. A worker that stops and reports `cancelled`, or reports any `error` (retryable or not), also ends `superseded`, with no retry. A worker that finishes the work and reports `success` or `warning` keeps its result: finished work stands, the task ends `completed`, and `superseded_by` stays set (G-CRT-18).

## Setup
- As [graceful supersession of a running task](1.11-flow-graceful-supersede-running-task.md) after Exchange 1: `{task_1}` (revision 7, **reports**) `running`, held by `{worker_a}` / `reports-7f9c-1` with `{lt_1}`, `cancel_requested`, `superseded_by = {task_2}`, `cancel_grace` timer at `T0+60s`.

## Request
Representative case: grace expiry. None: the worker never acknowledges, the clock reaches `T0+60s` and the engine's timer wheel acts.

## Expected response
- No client response. subsequent `GET /tasks/{task_1}` by `{creator_a}` returns `200` with `state: cancelled`, `result.result_code: superseded`, `superseded_by: {task_2}`.

## Side effects
Representative case:
- task {task_1} state is `cancelled`; task {task_1} result_code is `superseded`.
- lease {lt_1} is invalid (later calls get LEASE_LOST).
- `queue_global(reports) used changes by -1`; `queue_tenant(reports, tenant_a) used changes by -1`.
- history of {task_1} gains `taskCancelled` with `result_code: "superseded"`, `superseded_by: "{task_2}"`, no `actor` (engine-caused).
- subsequent `POST /tasks/{task_1}/complete` with `{lt_1}` returns `409` `LEASE_LOST`.

## Notes
- G-CRT-18 narrows DESIGN.md:1510 ("regardless of the result a `graceful`-mode worker reports"): `success`/`warning` stand; `error` and `cancelled` end `superseded`. `finalize()` (DESIGN.md:2937) gains the `error` case under the gap's `Remaining`.
- A plain (non-supersession) cancel request treats `error` the same way but ends `cancelled`: [cancel/1.04](../cancel/1.04-positive-worker-finishes-normally-after-cancel-request.md).
