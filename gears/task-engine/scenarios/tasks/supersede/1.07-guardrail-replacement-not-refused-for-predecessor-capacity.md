# A replacement is not refused for the queue place its predecessor held

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-queue-depth` (PRD.md:454) · `cpt-cf-task-engine-fr-task-supersede` (PRD.md:328) · DESIGN.md:2612-2621 · DESIGN.md:2667 |
| Phase | p2 |
| Test level | Integration — sampled depth |
| Depends on | Proposals › Limits and counters › Per-tenant depth from periodic counts |
| Gaps | G-CRT-14, G-CLM-24 |

"Supersession frees the replaced task's capacity before the new task is admitted" (PRD.md:454). A tenant at its per-tenant depth limit whose only queued task is revision 7 can still submit revision 8: one task leaves `queued`, one enters, net zero. Inside the create transaction the engine reads the old group head's state; a depth dimension that the old task is counted in, that the new task also enters, and that the supersession leaves in this transaction is not checked for this create. Any other dimension, or an old task that is `claimed`/`running` or in another queue, gets the normal sampled check (G-CRT-14).

## Setup
- **metric_job** as in [1.01](1.01-positive-higher-order-supersedes-by-old-task-state.md).
- Config override for **reports**: `tenant_max_queue_depth: 1`.
- `{task_1}` (revision 7, **reports**) is tenant A's only queued task in **reports**; the latest depth sample shows tenant A at 1 of 1. A create of an unrelated **render** task by `{creator_a}` into **reports** now gets `429` `resource_exhausted`, `violations[].subject: queue_depth.tenant`.

## Request
```http
POST /api/task_engine/v1/tasks HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
Content-Type: application/json

{ "type": "gts.cf.core.tasks.task.v1~acme.graph._.metric_job.v1~", "queue": "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1", "input": { "graph_id": "g-1", "metric": "pagerank", "revision": 8 } }
```

## Expected response
- `201 Created` with `{task_2}`, `state: queued`. Never `429`.

## Side effects
- task {task_1} state is `cancelled`, result_code `superseded`; task {task_2} state is `queued`.
- Tenant A still has exactly one queued task in **reports**.

## Cases

| Case | Old task (revision 7) | Expected | Notes |
|---|---|---|---|
| old queued, same queue | `queued` in **reports** (the representative) | `201`; the `queue_depth.tenant` check is skipped (net 0) | G-CRT-14 |
| old scheduled | `scheduled` in **reports** (created with a future `run_after`); tenant A has one other task `queued` in **reports**, so the sample shows 1 of 1 | `429`, `queue_depth.tenant`, `Retry-After` in [15, 30]; the transaction rolls back: {task_1} stays `scheduled`, no {task_2} | G-CRT-14: the old task leaves the deferred set, the new task enters `queued`; different dimensions, so the normal check applies |
| old running | `running` in **reports** under `{lt_1}`; tenant A has one other task `queued` in **reports** (1 of 1) | `429`, `queue_depth.tenant`; {task_1} keeps running without a cancel request | G-CRT-14: a leased old task is not counted in a depth dimension |

## Notes
- On `main` this works through one net delta per backlog counter row (DESIGN.md:2612-2621). The accepted proposal removes `te_tenant_queue_backlog` and checks a sampled count; G-CRT-14 keeps PRD.md:454 by skipping the dimension the old task leaves. The depth check runs inside the create transaction after the dedup lookup (G-CLM-24), so it can see the old task's state.
- The same skip applies to `queue_depth.queue` and `queue_depth.domain_global` when the old task is `queued` in the same queue.
