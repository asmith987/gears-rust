# Oversized creates are rejected with 413: combined payload over 64 KB, body over 1 MB

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-task-create` (PRD.md:260) · `cpt-cf-task-engine-nfr-payload-size` (PRD.md:1274-1278) · DESIGN.md:263 · DESIGN.md:724 · DESIGN.md:1209 · DESIGN.md:2142 · DESIGN.md:2143 |
| Phase | p1 |
| Test level | E2E |
| Gaps | G-CRT-07, G-CRT-24 |

Two size rules answer `413 Content Too Large` with `invalid_argument` (transport override), at two points of the create check order (G-CRT-24): the body limit first, before the body is parsed; the payload limit together with the schema check, after the type, queue, PDP and `Idempotency-Key` checks. The payload rule limits the combined uncompressed JSON of `input`, `context` and `output` to `max_payload_size_bytes` (65,536). The transport rule protects memory: a declared `Content-Length` over `max_request_body_bytes` (1,048,576) is refused from the headers alone, within 10 ms, without reading the body (PRD.md:1278).

## Setup
- As [Minimal create](1.01-positive-minimal-create-queued.md).
- `<40000 x "a">` and `<30000 x "b">` stand for strings of that many characters.

## Request
Representative case: combined payload over 64 KB. Neither part alone is over the limit; together they are. The body (about 70 KB) is well under the 1 MB body limit, so this is the payload rule, not the transport rule.
```http
POST /api/task_engine/v1/tasks HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
Content-Type: application/json
Idempotency-Key: 7d1f0c2e-render-big

{
  "type": "gts.cf.core.tasks.task.v1~acme.reports._.render.v1~",
  "queue": "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1",
  "input": { "report_id": "r-50", "format": "pdf", "notes": "<40000 x \"a\">" },
  "context": { "prefill": "<30000 x \"b\">" }
}
```

## Expected response
- `413 Content Too Large`, `invalid_argument` (transport override).
```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.invalid_argument.v1~",
  "title": "Invalid Argument",
  "status": 413,
  "detail": "Combined input and context exceed the 65536-byte payload limit",
  "instance": "/api/task_engine/v1/tasks",
  "trace_id": "<trace>",
  "context": { "resource_type": "gts.cf.core.tasks.task.v1~acme.reports._.render.v1~", "field_violations": [ { "field": "/input", "description": "combined payload (input + context) exceeds max_payload_size_bytes", "reason": "PAYLOAD_TOO_LARGE" } ] }
}
```

<!-- No side effects in any case: the request is refused before any write. -->

## Cases

| Case | Differs from the representative request | Expected | Notes |
|---|---|---|---|
| combined payload over 64 KB | the representative | `413`, field violation on `/input`, reason `PAYLOAD_TOO_LARGE` | PRD.md:260, DESIGN.md:724, :2142; exactly 65,536 bytes is accepted ("MUST NOT exceed") |
| body over 1 MB, `Content-Length` declared | key `7d1f0c2e-render-huge`, header `Content-Length: 2097152`; the client sends headers only and holds the body back | `413 Content Too Large`, `invalid_argument`, within 10 ms of the headers, while the client has sent no body byte: `{ "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.invalid_argument.v1~", "title": "Invalid Argument", "status": 413, "detail": "Request body exceeds 1048576 bytes", "instance": "/api/task_engine/v1/tasks", "trace_id": "<trace>", "context": { "resource_type": "gts.cf.core.tasks.task.v1~", "constraint": "request body at most 1048576 bytes" } }` | PRD.md:1276-1278, DESIGN.md:263, :2143; G-CRT-24: the engine's body-limit layer answers first, before parsing |
| body over 1 MB, chunked / HTTP/2 | no `Content-Length`; the client streams more than 1,048,576 bytes | the server stops within one buffer read after byte 1,048,577 and closes before the client finishes; `413` | PRD.md:1278 |

## Notes
- **combined payload**: within the payload step the 64 KiB size check runs before schema validation (G-CRT-24), so the answer is `413` even if the extra `notes` property also breaks **render**'s input schema ([input fails schema](1.09-negative-input-fails-schema.md)). `PAYLOAD_TOO_LARGE` is in the decided reason set (G-CRT-07).
- **body over 1 MB**: the engine's own body-limit layer answers, before parsing, with a platform problem document (G-CRT-24); the `constraint` variant is used because no field is at fault.
