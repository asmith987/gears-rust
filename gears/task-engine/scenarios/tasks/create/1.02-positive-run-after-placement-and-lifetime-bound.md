# `run_after` decides the starting state: future → `scheduled`, past → `queued`, beyond the lifetime → refused

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-delayed-enqueue` (PRD.md:502) · `cpt-cf-task-engine-fr-task-create` (PRD.md:258) · DESIGN.md:523 · DESIGN.md:524 · DESIGN.md:526 |
| Phase | p1 |
| Test level | E2E |
| Gaps | G-CRT-22, G-CRT-26, G-SEC-23 |

Placement uses "`scheduled` if `run_after` is in the future, else `queued`" (PRD.md:258). A task with `run_after` in the future and no predecessors starts in `scheduled`: only the scheduled timer and the creation-relative deadlines are armed, and the queue timeout starts when the task becomes `queued`. A caller that computes a start time which has already passed (clock skew, a slow retry) gets a task that is ready at once, not a rejection; the past value is stored as sent. A `run_after` later than `created_at` + the task's lifetime timeout could never run, so it is refused (G-CRT-22).

## Setup
- As [Minimal create](1.01-positive-minimal-create-queued.md), clock at `T0` (`2026-11-03T10:00:00Z`).

## Request
Representative case: `run_after` two hours ahead.
```http
POST /api/task_engine/v1/tasks HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
Content-Type: application/json
Idempotency-Key: 7d1f0c2e-render-r-43

{
  "type": "gts.cf.core.tasks.task.v1~acme.reports._.render.v1~",
  "queue": "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1",
  "input": { "report_id": "r-43", "format": "csv" },
  "run_after": "2026-11-03T12:00:00Z"
}
```

## Expected response
- `201 Created`; `state` is `scheduled`; `run_after` is `2026-11-03T12:00:00Z`.
- `priority` is `100`, the queue's `default_priority` (no priority sent, G-CRT-26).
```json
{
  "id": "{task_1}",
  "state": "scheduled",
  "priority": 100,
  "run_after": "2026-11-03T12:00:00Z",
  "…": "other fields as in CONVENTIONS §5.1"
}
```

## Side effects
- task {task_1} state is `scheduled`.
- timer `scheduled` for {task_1} is armed at `T0+7200s`.
- timer `lifetime` for {task_1} is armed at `T0+86400s` (measured from creation, PRD.md:526).
- No `queue_timeout` timer yet; it is armed when the scheduled timer fires (DESIGN.md:526).
- history of {task_1} gains `taskCreated` with `initial_state: "scheduled"`; no `taskQueued` (G-SEC-23).
- event `taskCreated` for {task_1} is published to the task-events topic.
- At `T0+7200s`: task {task_1} state is `queued`; timer `queue_timeout` for {task_1} is armed at `T0+7200s+3600s`.

## Notes
- **future**: the task counts toward the tenant's deferred limit (`tenant_max_deferred_tasks`, PRD.md:445), which the accepted proposal checks against a sampled count (Proposals › Limits and counters); no counter row changes.
- **past**: a past `run_after` is stored as sent and the task is `queued` (G-CRT-22).
- **beyond lifetime**: the bound uses the task's resolved lifetime timeout; with no lifetime timeout (`null`) there is no bound. `OUT_OF_RANGE` is the reason ERRORS.md lists for this rule.
