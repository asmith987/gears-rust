# An initial wait group on create puts the task in `waiting`

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-task-create` (PRD.md:258) · `cpt-cf-task-engine-fr-wait-conditions` (PRD.md:548) · `cpt-cf-task-engine-fr-wait-input` (PRD.md:606) · DESIGN.md:532, :533 |
| Phase | p1 (timer); the **input** case is p2 |
| Test level | E2E |
| Depends on | Proposals › Task mutability › Set only in the create request · Proposals › Waits › Input and children waits stay p2 |
| Gaps | G-CRT-01, G-SEC-23, G-SEC-11, G-WAI-06, G-WAI-09, G-WAI-12, G-WAI-43 |

A consumer can no longer park an existing task, so "run at 11:00" or "run when approved" is expressed by creating the task with its wait group (Proposals › Task mutability). The task starts in `waiting`, holds no queue place and no lease, and resumes through `queued` when the group is satisfied. This replaces the consumer path of `POST /tasks/{id}/wait-conditions` (DESIGN.md:1095) and the `queued → waiting` row (DESIGN.md:532).

The rules (G-CRT-01): the group takes the kinds a worker may set in the phase, except `children` (p1: `timer` only; `input` from p2); it has no `park` or `lease_token`; condition timeouts and a timer's `resume_at` count from the create; it may not be combined with predecessors or a future `run_after`; at most 16 conditions, none empty (G-WAI-06). The create is a deferred admission: the task counts in the tenant's deferred set, and a full deferred limit refuses it with `429` `queue_depth.deferred` ([limits/depth/1.03](../../limits/depth/1.03-negative-deferred-limit-refuses-every-deferral.md)). No queue timeout runs until the task is `queued`.

## Setup
- As [Minimal create](1.01-positive-minimal-create-queued.md), clock at `T0`.

## Request
Representative case: a timer wait.
```http
POST /api/task_engine/v1/tasks HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
Content-Type: application/json
Idempotency-Key: 7d1f0c2e-render-r-47

{
  "type": "gts.cf.core.tasks.task.v1~acme.reports._.render.v1~",
  "queue": "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1",
  "input": { "report_id": "r-47", "format": "pdf" },
  "wait": { "mode": "all", "conditions": [ { "kind": "timer", "resume_at": "2026-11-03T11:00:00Z" } ] }
}
```

## Expected response
- `201 Created`, `Location: /api/task_engine/v1/tasks/{task_1}`; `state` is `waiting`; `assignment` is `null`. The body is the task resource; it carries no wait-condition IDs (G-CRT-01).
```json
{ "id": "{task_1}", "state": "waiting", "assignment": null, "run_after": null, "…": "other fields as in CONVENTIONS §5.1" }
```

## Side effects
- task {task_1} state is `waiting`; {task_1} joins tenant A's deferred set.
- timer `wait` for {task_1} is armed at `T0+3600s` (the earliest pending deadline, G-WAI-09); timer `lifetime` for {task_1} is armed at `T0+86400s`.
- No `queue_timeout` timer for {task_1} until it is `queued` (G-CRT-01; DESIGN.md:533).
- history of {task_1} gains, in order: `taskCreated` with `initial_state: "waiting"`, `actor: {creator_a}`; `waitConditionSet` with `wait_condition_id = {wc_1}`, `kind = timer`; `taskWaiting` with `mode = all`, `conditions = [{ wait_condition_id: {wc_1}, kind: timer }]` (the same wait events as a worker set, G-WAI-12). No `taskQueued` (G-SEC-23).
- subsequent `GET /tasks/{task_1}/wait-conditions` returns `200` with one `timer` condition `{wc_1}` in state `pending`.
- At `T0+3600s` the task resumes to `queued` and is claimed for its first attempt: [waits/framework/1.04](../../waits/framework/1.04-positive-initial-wait-group-resumes-created-task.md).

## Notes
- The `wait` shape follows CONVENTIONS §5.8 without `lease_token`/`park`.
- The other refusals of the create-time group (with predecessors or a future `run_after`, an empty or over-long group) have no scenario in this folder yet; [ERRORS.md](../../ERRORS.md) lists `NOT_ALLOWED` on `/wait` for the first.
- `taskCreated.initial_state` gains `waiting` in its schema (G-SEC-11, G-CRT-01).
