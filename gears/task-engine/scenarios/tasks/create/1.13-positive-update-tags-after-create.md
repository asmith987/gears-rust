# Tags can be changed after create; nothing else can

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-tags` (PRD.md:363) · DESIGN.md:746, :1075 · `cpt-cf-task-engine-fr-authz` (PRD.md:925) |
| Phase | p2 |
| Test level | E2E |
| Depends on | Proposals › Task mutability › Set only in the create request ("Tags stay changeable"); Proposals › Task mutability › `update` covers only tags; `resolve` gets its own action |
| Gaps | G-CRT-06, G-SEC-05, G-SEC-19, G-SEC-21, G-SEC-28, G-WIRE-04 |

Tags only affect search, not scheduling, so changing them races with nothing that matters. `PATCH /tasks/{id}/tags` stays, guarded by `update`, which after the accepted change covers tags and nothing else. Keys in `set` are added or replaced, keys in `remove` are deleted, and every other key is left as it was (DESIGN.md:1075). The result must stay within the per-task tag limit (`max_tags_per_task`, 16) and the key and value lengths of create (G-CRT-06). Each change records `taskTagsUpdated` (G-SEC-28).

## Setup
- [Minimal create](1.01-positive-minimal-create-queued.md) made `{task_1}` (**render**, tenant A, `queued`) with `tags: [{ "key": "project", "value": "q4" }, { "key": "team", "value": "bi" }]`.

## Request
```http
PATCH /api/task_engine/v1/tasks/{task_1}/tags HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
Content-Type: application/json

{ "set": [{ "key": "project", "value": "q5" }, { "key": "region", "value": "eu" }], "remove": ["team"] }
```

## Expected response
- `200 OK`, body = the task resource (CONVENTIONS §5.1) with the new tags; every other field is unchanged.

```json
{
  "id": "{task_1}",
  "state": "queued",
  "tags": [{ "key": "project", "value": "q5" }, { "key": "region", "value": "eu" }],
  "updated_at": "2026-11-03T10:00:05Z"
}
```

## Side effects
- `task {task_1}.tags is [{ "key": "project", "value": "q5" }, { "key": "region", "value": "eu" }]`; `state`, `priority`, `predecessors` and the lease (if any) are untouched.
- history of `{task_1}` gains `taskTagsUpdated` with `actor: {creator_a}`, `set: [{ key: "project", value: "q5" }, { key: "region", value: "eu" }]`, `removed: ["team"]`; one event for the whole `PATCH` (G-SEC-28). Refused rows record nothing.
- A search `$filter=has_tag('project', 'q5')` finds `{task_1}`; `has_tag('team', 'bi')` no longer does (G-SEC-05).

## Cases

| Case | Differs from the representative request | Expected | Notes |
|---|---|---|---|
| running task | `{task_1}` is `running` under `{worker_a}` with `{lt_1}` | `200`, tags changed; the lease stays valid (a later `complete` with `{lt_1}` → `200`) | tags never touch scheduling or the lease |
| terminal task | `{task_1}` is `completed` / `success` | `200`, tags changed; `updated_at` does not change (it advances for a live task only, G-SEC-28) | retention unchanged (DESIGN.md:1870 moves tag changes of retained tasks to `te_tags_retained`) |
| same key in set and remove | `{ "set": [{ "key": "team", "value": "x" }], "remove": ["team"] }` | `400` `invalid_argument`, field violation on `/remove/0` (`reason: NOT_ALLOWED`); tags unchanged | DESIGN.md:1075 |
| key twice in set | `{ "set": [{ "key": "team", "value": "x" }, { "key": "team", "value": "y" }] }` | `400` `invalid_argument`, field violation on `/set/1/key` (`reason: DUPLICATE`); tags unchanged | each key at most once (G-WIRE-04) |
| over the tag limit | `{task_1}` has 16 tags; `set` adds a 17th key | `400` `invalid_argument`, field violation on `/set` (`reason: TOO_MANY_TAGS`); tags unchanged | the limit applies to the result of the patch; G-CRT-06 |
| key too long | `set` key of 129 characters | `400`, field violation on `/set/0/key` (`reason: TOO_LONG`) | PRD.md:363; G-CRT-06 |
| empty key | `{ "set": [{ "key": "", "value": "x" }] }` | `400`, field violation on `/set/0/key` (`reason: REQUIRED`) | G-CRT-06 |
| reader | `<readonly-a-token>` | `403` `permission_denied`, `ACTION_DENIED`; tags unchanged | can read, cannot act (PRD.md:918) |
| `resolve`-only subject | `{approver_a}` (task `read` + `resolve`, defined in [auth/1.14](../../auth/1.14-guardrail-resolve-grants-nothing-else.md)) | `403` `ACTION_DENIED`; tags unchanged | `resolve` grants nothing else |
| other tenant | `<creator-b-token>` | `404`, no field violation | no existence oracle (PRD.md:918) |
| worker with `claim` only | `<worker-a-token>`; the fixture worker policy has no `update` | `403` `ACTION_DENIED` | a worker does not need tag changes (least privilege, DESIGN.md:995) |

## Notes
- `update` keeps its permission instance `gts.cf.toolkit.authz.permission.v1~cf.task_engine._.task_update.v1`, narrowed to tags (Proposals › Task mutability › API changes). It no longer allows dependency changes, consumer waits, children without the parent's lease, or resolving input waits ([auth/1.05](../../auth/1.05-negative-read-but-not-act.md), row `update grant does not cover resolve`).
- The response body is the task resource (DESIGN.md:1075 "Returns the updated task"; CONVENTIONS §5.4). A tag change advances `updated_at` of a live task only (G-SEC-28).
- The tag limit applies to the result of the patch (CONVENTIONS §5.4, G-CRT-06). The violation sits on `/set`, the body field that adds the tags; G-CRT-06 names `/tags` for create, where that is the field.
- The repeated key in `set` uses the generic `DUPLICATE`: G-WIRE-04 decides the `400` but names no code.
