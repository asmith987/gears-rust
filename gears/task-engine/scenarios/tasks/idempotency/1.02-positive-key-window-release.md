# A key is held while its task is unfinished and for the 7-day window; then the same key creates a new task

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-idempotent-create` (PRD.md:283) · PRD.md:1510 · DESIGN.md:1719 · DESIGN.md:1729-1731 · DESIGN.md:2374 · ADR-0012:64 |
| Phase | p1 |
| Test level | Integration — 7-day window |
| Gaps | G-CRT-12, G-CRT-13 |

A caller key is held while its task is unfinished and until `created_at + idempotency_key_window_days` (7). After that, the same key creates a new task (PRD.md:283). This keeps the key store bounded; a caller that may retry later must look for the task first. The window is a minimum, not a deadline: a row is never deleted under a live task (`expires_at` stays `NULL`, DESIGN.md:1719). When the task ends, finalize sets `expires_at = min(created_at + window, terminal_at + retention)`; a time already passed deletes the row in the same terminal transaction (G-CRT-13, DESIGN.md:1729). An expired row never blocks a create: on a conflict the create deletes it (guarded by `expires_at < now`) and retries the insert once in the same transaction, whether or not cleanup has run (G-CRT-12).

## Setup
- Representative: at `T0`, `{creator_a}` created `{task_1}` with key `7d1f0c2e-render-r-42` (as [Minimal create](../create/1.01-positive-minimal-create-queued.md)); it completed `success` at `T0+60s`. Clock at `T0+7d+1h` (2026-11-10T11:00:00Z). The effective retention of `{task_1}` is the global 100 days, so the window is not capped.
- For the **unfinished** cases: at `T0`, `{creator_a}` created `{task_1}` of **render** in **adhoc** (as the **engine default** case of [settings resolution](../create/1.03-positive-settings-resolution.md): no queue or lifetime timeout) with key `7d1f0c2e-render-r-45`, input `{ "report_id": "r-45", "format": "pdf" }`, `run_after: "2026-11-13T10:00:00Z"`. It is `scheduled`. Clock at `T0+8d` (2026-11-11T10:00:00Z): past the 7-day window, task still `scheduled`.

## Request
The exact original request.
```http
POST /api/task_engine/v1/tasks HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
Content-Type: application/json
Idempotency-Key: 7d1f0c2e-render-r-42

{
  "type": "gts.cf.core.tasks.task.v1~acme.reports._.render.v1~",
  "queue": "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1",
  "priority": 100,
  "input": { "report_id": "r-42", "format": "pdf" },
  "tags": [{ "key": "project", "value": "q4" }]
}
```

## Expected response
- `201 Created` with a new task `{task_2}` ≠ `{task_1}`.
```json
{ "id": "{task_2}", "state": "queued", "created_at": "2026-11-10T11:00:00Z", "…": "other fields as in CONVENTIONS §5.1" }
```

## Side effects
- task {task_2} state is `queued`; task {task_1} is unchanged (`completed`, still readable by ID).
- The expired `te_dedup` row of {task_1} (`expires_at = T0+7d`) is deleted by the create's guarded delete; the key's row now names {task_2}, with `expires_at = NULL`.

## Notes
- **finished, past the window**: the RetentionService cleanup (DESIGN.md:1731, daily `cleanup_time`) has not run; the create takes the expired row over itself (G-CRT-12). A test runs it before the daily cleanup or with cleanup disabled.
- "Capped at the task's retention" (DESIGN.md:2374) means `expires_at = min(created_at + window, terminal_at + retention)` per task, `NULL` while live (G-CRT-13). With a retention shorter than 7 days the key is released at `terminal_at + retention`.
