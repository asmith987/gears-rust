# A refused create does not hold its key

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-idempotent-create` (PRD.md:281) · `cpt-cf-task-engine-fr-task-create` (PRD.md:253, :260) · DESIGN.md:2586 · DESIGN.md:2667 |
| Phase | p1 |
| Test level | E2E |
| Gaps | G-CLM-24, G-SEC-21 |

The key row is written inside the create transaction (DESIGN.md:2586), so any refusal (validation before the transaction, or a rollback inside it) leaves no key behind. A client that fixes its request and retries with the **same** key gets its task, not a `400` for "different request".

## Setup
- No task exists for key `7d1f0c2e-render-r-65`.

## Exchange 1 — invalid input
```http
POST /api/task_engine/v1/tasks HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
Content-Type: application/json
Idempotency-Key: 7d1f0c2e-render-r-65

{
  "type": "gts.cf.core.tasks.task.v1~acme.reports._.render.v1~",
  "queue": "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1",
  "input": { "format": "pdf" }
}
```
- `400 Bad Request`, `invalid_argument`, `SCHEMA_VIOLATION` on `/input/report_id` (as [create: input fails schema](../create/1.09-negative-input-fails-schema.md)).

## Exchange 2 — corrected request, same key
```http
POST /api/task_engine/v1/tasks HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
Content-Type: application/json
Idempotency-Key: 7d1f0c2e-render-r-65

{
  "type": "gts.cf.core.tasks.task.v1~acme.reports._.render.v1~",
  "queue": "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1",
  "input": { "report_id": "r-65", "format": "pdf" }
}
```
- `201 Created` with `{task_1}`.

## Side effects
- After Exchange 1: no `te_dedup` row for the key.
- After Exchange 2: task {task_1} state is `queued`; the key's `te_dedup` row names {task_1}.

## Notes
- The same holds after a `429` (`queue_depth.*`), a `403`, or a `503`: none of them stores the key. A `429` rolls back the create transaction, because the depth check runs inside it after the key lookup (G-CLM-24).
