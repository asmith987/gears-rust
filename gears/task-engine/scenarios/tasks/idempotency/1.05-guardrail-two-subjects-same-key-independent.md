# Two subjects using the same key get two independent tasks

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-idempotent-create` (PRD.md:278-280) · PRD.md:1511 · DESIGN.md:2372 · DESIGN.md:2573 · ADR-0012:71 |
| Phase | p1 |
| Test level | E2E |

Keys are unique per tenant **and creating subject** (`dedup_key = hash("idempotency-key", created_by, key)`, DESIGN.md:2573). One producer cannot squat on, collide with, or discover another producer's task by guessing its key, even with an identical request.

## Setup
- [Minimal create](../create/1.01-positive-minimal-create-queued.md) at `T0`: `{creator_a}` created `{task_1}` with key `7d1f0c2e-render-r-42`.
- `{creator_a2}` (same tenant A, same grants) sends the identical request with the identical key.

## Request
```http
POST /api/task_engine/v1/tasks HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a2-token>
Content-Type: application/json
Idempotency-Key: 7d1f0c2e-render-r-42

{
  "type": "gts.cf.core.tasks.task.v1~acme.reports._.render.v1~",
  "queue": "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1",
  "priority": 100,
  "input": { "report_id": "r-42", "format": "pdf" },
  "tags": [{ "key": "project", "value": "q4" }]
}
```

## Expected response
- `201 Created` with a **new** task `{task_2}` (`{task_2}` ≠ `{task_1}`), `created_by` = `{creator_a2}`.
- The response contains no reference to `{task_1}`.
```json
{ "id": "{task_2}", "created_by": "{creator_a2}", "state": "queued", "…": "other fields as in CONVENTIONS §5.1" }
```

## Side effects
- task {task_2} state is `queued`; task {task_1} is unchanged.
- Two `te_dedup` rows exist in `{tenant_a}`, one per subject.
- A second send by `{creator_a2}` gets `409` with `resource_name` = `{task_2}`, never `{task_1}`.

## Notes
- A different-request variant by `{creator_a2}` also gets `201`, not `400`: the key is not "reused" across subjects.
