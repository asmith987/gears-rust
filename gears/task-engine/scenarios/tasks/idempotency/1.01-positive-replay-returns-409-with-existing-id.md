# A replay returns 409 `already_exists` with the existing task's ID, whatever happened to the task since

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-idempotent-create` (PRD.md:281-282) · PRD.md:1510 · DESIGN.md:718 · DESIGN.md:1203 · DESIGN.md:2575-2576 · DESIGN.md:2586-2595 · DESIGN.md:2660-2665 · ADR-0012:55 · ADR-0012:72 |
| Phase | p1 |
| Test level | E2E |
| Gaps | G-CRT-25, G-CRT-11, G-CRT-13, G-CRT-24, G-SEC-05 |

A retry of the same request with the same key creates nothing and answers `409` with the ID of the task the key first created (PRD.md:281). The caller treats this as success and reads the task. The engine deliberately does not return a stored `201` (PRD.md:288). The engine compares a replay with the fingerprint of the request **as first accepted** (`te_dedup.request_hash` over type, input and context as sent), never with the task's current row, and fields outside the fingerprint are not compared (PRD.md:282, DESIGN.md:2575). The queue is not in the hash: the key row stores the queue resolved at create, and a retry matches when it names no queue or that queue (G-CRT-11). So progress, a queue change by dead-lettering, completion, or a retry that changes `priority` or `tags` never turn a replay into a new request.

## Setup
- [Minimal create](../create/1.01-positive-minimal-create-queued.md) at `T0` created `{task_1}` with key `7d1f0c2e-render-r-42`, `priority: 100`, `tags: [{ "key": "project", "value": "q4" }]` and no `context`.
- Starting state of `{task_1}` per case (below). Representative: clock at `T0+5s`; `{task_1}` is still `queued`.

## Request
The exact request of the setup, sent again.
```http
POST /api/task_engine/v1/tasks HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
Content-Type: application/json
Idempotency-Key: 7d1f0c2e-render-r-42

{
  "type": "gts.cf.core.tasks.task.v1~acme.reports._.render.v1~",
  "queue": "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1",
  "priority": 100,
  "input": { "report_id": "r-42", "format": "pdf" },
  "tags": [{ "key": "project", "value": "q4" }]
}
```

## Expected response
- `409 Conflict`, `already_exists`, `context.resource_type` = the task base type, `context.resource_name` = `{task_1}` in every case (G-CRT-25).
```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.already_exists.v1~",
  "title": "Already Exists",
  "status": 409,
  "detail": "A task with this idempotency key already exists",
  "instance": "/api/task_engine/v1/tasks",
  "trace_id": "<trace>",
  "context": { "resource_type": "gts.cf.core.tasks.task.v1~", "resource_name": "{task_1}" }
}
```

## Side effects
- No new task: subsequent `GET /tasks?$filter=has_tag('project', 'q4')` by `{creator_a}` returns only {task_1}.
- Representative: task {task_1} is unchanged (`updated_at` still `T0`); history of {task_1} gains no event.

## Notes
- `resource_type` is the task base type, as in the example at DESIGN.md:1191 (G-CRT-25).
- **after checkpoint and completion**: a replay that sends `"context": { "pages_done": 12 }` (the task's current context) is a **different** request and gets `400` ([same key, different request](1.04-negative-same-key-different-request.md)).
- **after dead-lettering**: the same holds after a bulk move to **bulk** (PRD.md:1510). A retry without `queue` also matches; one naming another queue is `400` ([same key, different request](1.04-negative-same-key-different-request.md)).
- **fields outside the fingerprint**: the same holds for `urgency`, `timeouts`, `retry_policy`, `run_after`, `resource_refs`, `wait` and `predecessors`. A caller that needs those changed cancels and recreates with a new key (Proposals › Task mutability › Gives up). A replay with `urgency: critical` still needs `expedite`: the PDP and `expedite` checks come before the dedup lookup (G-CRT-24), so a caller without it gets `403` `EXPEDITE_REQUIRED`.
- A replay is never refused as full: [replay not refused as full](1.06-guardrail-replay-not-refused-as-full.md).
