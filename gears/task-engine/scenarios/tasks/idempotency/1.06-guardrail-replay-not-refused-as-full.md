| | |
|---|---|

"Authorization, validation, and duplicate checks run first, so a replay (`409`) never uses capacity and is never refused as full" (PRD.md:454). A client that retries a create during back-pressure, or whose answer it lost, must learn that its task exists, not be told to back off. This holds whichever depth dimension is full: the sampled depth check runs after the dedup and idempotency lookup, inside the create transaction (G-CLM-24, G-CRT-24). This is the home of the rule; `limits/depth/` links here.

## Setup
- Config override for **reports**: `tenant_max_queue_depth: 1`.
- [Minimal create](../create/1.01-positive-minimal-create-queued.md) at `T0` created `{task_1}` (`queued`) with key `7d1f0c2e-render-r-42`; it is tenant A's only queued task in **reports**.
- Clock at `T0+10s`; the latest per-tenant depth sample shows tenant A at 1 of 1 in **reports**. A new create by `{creator_a}` into **reports** gets `429` `resource_exhausted` with `violations[].subject: queue_depth.tenant` and a `Retry-After` in [15, 30].

## Request
The exact original request.
```http
POST /api/task_engine/v1/tasks HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
Content-Type: application/json
Idempotency-Key: 7d1f0c2e-render-r-42

{
  "type": "gts.cf.core.tasks.task.v1~acme.reports._.render.v1~",
  "queue": "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1",
  "priority": 100,
  "input": { "report_id": "r-42", "format": "pdf" },
  "tags": [{ "key": "project", "value": "q4" }]
}
```

## Expected response
- `409 Conflict`, `already_exists`, `context.resource_name` = `{task_1}`; never `429`, no `Retry-After`.
```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.already_exists.v1~",
  "title": "Already Exists",
  "status": 409,
  "detail": "A task with this idempotency key already exists",
  "instance": "/api/task_engine/v1/tasks",
  "trace_id": "<trace>",
  "context": { "resource_type": "gts.cf.core.tasks.task.v1~", "resource_name": "{task_1}" }
}
```

## Side effects
- No new task. The tenant's queued count in **reports** stays 1. The replay uses no capacity.

## Cases

| Case | Differs from the setup | Expected | Notes |
|---|---|---|---|
| per-tenant depth full | `tenant_max_queue_depth: 1`, tenant A at 1 of 1 (the representative) | `409` naming {task_1}, never `429` | G-CLM-24, G-CRT-14 |
| queue-wide depth full | `tenant_max_queue_depth: 3` and `queue_max_queue_depth: 3` for **reports**; `{task_1}` created with `Idempotency-Key: 9b2e-depth-r-104`, input `{ "report_id": "r-104", "format": "pdf" }` (no `priority`, no `tags`), accepted `queued`; then two more tasks filled **reports** to 3 `queued`, sampled. The request is the exact replay of that first create | `409 Conflict`, `already_exists`, `context.resource_name = "{task_1}"`; not `429` (`queue_depth.queue`) | DESIGN.md:2606-2608; G-CLM-24 |

## Notes
- G-CLM-24 / G-CRT-14: DESIGN checks the sampled queue-wide and domain-wide ceilings **before** the transaction (DESIGN.md:723, :2608). The decision moves every sampled depth check after the dedup lookup, inside the transaction: authorize → validate → dedup lookup → depth → insert. A replay answers `409` before depth is looked at, as PRD.md:454 says; DESIGN.md:723 and :2608 change under the gaps' `Remaining`.
- A domain-wide ceiling that is full gives the same answer by the same rule.
