# The dedup window decides when a finished task releases its identity

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-derived-dedup` (PRD.md:302) · `cpt-cf-task-engine-fr-task-supersede` (PRD.md:329) · DESIGN.md:719 · DESIGN.md:1727 · DESIGN.md:1728 · DESIGN.md:2645-2653 · DESIGN.md:2660-2665 · DESIGN.md:2945-2948 |

`window: active` releases the identity at every terminal outcome, so a failed task can be resubmitted instead of blocking the work forever (PRD.md:302). With `active_or_succeeded`, only a success is reused: a task that completed with `success` or `warning` keeps the identity until its retention ends (`expires_at = terminal_at + retention`), so equal work gets the finished task instead of running again, while a task that ends `failed`, `dead_lettered` or `cancelled` deletes its identity row in the terminal transaction (DESIGN.md:1728). For a supersede type an equal order value after the holder ended is a new task, and the group head moves to it (DESIGN.md:2645).

## Setup
- **metric_job** as in [identity scope](1.04-guardrail-identity-scope.md) (`window: active`); **export** as in [1.01](1.01-positive-duplicate-by-derived-identity.md) (`window: active_or_succeeded`).
- Representative: at `T0`, `{creator_a}` created `{task_1}` of **metric_job** with input `{ "graph_id": "g-1", "metric": "pagerank", "revision": 7 }`. A worker failed it with a non-retryable error at `T0+30s`; it is `dead_lettered` in **dead_letter** (from **default**).

## Request
Representative case: window `active`, holder dead-lettered.
```http
POST /api/task_engine/v1/tasks HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
Content-Type: application/json

{ "type": "gts.cf.core.tasks.task.v1~acme.graph._.metric_job.v1~", "input": { "graph_id": "g-1", "metric": "pagerank", "revision": 7 } }
```

## Expected response
- `201 Created` with `{task_2}` ≠ `{task_1}`.
```json
{ "id": "{task_2}", "state": "queued", "input": { "graph_id": "g-1", "metric": "pagerank", "revision": 7 }, "…": "other fields as in CONVENTIONS §5.1" }
```

## Side effects
- task {task_2} state is `queued`; task {task_1} state is still `dead_lettered`.
- `te_dedup` row for the identity names {task_2}.
- `te_supersede_heads(tenant_a, group)` has `latest_order = 7`, `latest_task_id = {task_2}`.
- subsequent `POST /admin/tasks/{task_1}/reenqueue` by `{admin}` returns `409` `already_exists` naming {task_2} (PRD.md:808, :1537).

## Notes
- **identity expired**: an expired row is taken over at once, whether or not cleanup has run (G-CRT-12).
- `expires_at` is set by finalize; a time already passed deletes the row at once (G-CRT-13). The `100d` retention is the fixture's global retention.
