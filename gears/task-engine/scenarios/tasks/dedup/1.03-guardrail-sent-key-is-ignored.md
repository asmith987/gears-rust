# A key sent for a `dedup` type is ignored: not checked, not stored

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-derived-dedup` (PRD.md:308) · PRD.md:1493 · DESIGN.md:719 · DESIGN.md:2560 |
| Phase | p2 |
| Test level | E2E |

SDKs and gateways attach keys automatically, so for `dedup` types a key is ignored: it changes nothing about the identity, is not compared, and is not stored (PRD.md:308). Two keys do not make two tasks, and one key does not make one task.

## Setup
- **export** as in [1.01](1.01-positive-duplicate-by-derived-identity.md).
- At `T0`, `{creator_a}` created `{task_1}` with input `{ "period": "2026-10" }` and `Idempotency-Key: k-1`.

## Exchange 1 — same identity, different key
```http
POST /api/task_engine/v1/tasks HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
Content-Type: application/json
Idempotency-Key: k-2

{ "type": "gts.cf.core.tasks.task.v1~acme.billing._.export.v1~", "input": { "period": "2026-10" } }
```
- `409 Conflict`, `already_exists`, `context.resource_name` = `{task_1}`.

## Exchange 2 — different identity, the first key again
```http
POST /api/task_engine/v1/tasks HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
Content-Type: application/json
Idempotency-Key: k-1

{ "type": "gts.cf.core.tasks.task.v1~acme.billing._.export.v1~", "input": { "period": "2026-09" } }
```
- `201 Created` with a new task `{task_2}`: no `400` "key reused with a different request".

## Side effects
- After Exchange 2: task {task_2} state is `queued`.
- `te_dedup` holds derived-identity rows for `2026-10` and `2026-09` (`request_hash = NULL`), and no caller-key row for `k-1` or `k-2`.
