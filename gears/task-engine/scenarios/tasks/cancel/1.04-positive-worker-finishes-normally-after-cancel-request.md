# A worker that finishes its work after a cancel request may complete it successfully

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-task-cancel` (PRD.md:348) · DESIGN.md:534, :737 |
| Phase | p1 |
| Test level | E2E |
| Gaps | G-RTY-17 |

`requested` asks the worker to stop; it does not forbid finishing. A worker that is already writing its result when it sees the flag can complete with `success` or `warning`; the task is `completed`, not `cancelled`. An `error` after a cancel request, retryable or not, ends the task `cancelled` instead: the cancel wins over a retry (G-RTY-17).

## Setup
- `{task_1}`: **render** on **reports**, `running` under `{lt_1}`, `cancel_requested: true` after [1.02](1.02-positive-cancel-of-leased-task-by-mode.md).

## Request
```http
POST /api/task_engine/v1/tasks/{task_1}/complete HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "lease_token": "{lt_1}", "result_code": "success", "output": {"url": "https://files.example.com/r-42.pdf"} }
```

## Expected response
- `200 OK`, `state: completed`, `result.result_code: success`, `cancel_requested: true`.

## Side effects
- history of `{task_1}` gains `taskCompleted` (`result_code: success`); no `taskCancelled`.
- Successors see a successful predecessor.

## Cases

| Case | Request (differs from the representative) | Expected | Notes |
|---|---|---|---|
| success | (representative) | `200`, `completed` / `success` | G-RTY-17 |
| warning | `"result_code": "warning"` with the same output and one warning | `200`, `completed` / `warning`; `taskCompleted` | G-RTY-17 |
| retryable-error | `"result_code": "error"`, `"error": { "domain": "acme.reports", "code": "RENDER_TIMEOUT", "message": "renderer timed out", "fault": "dependency", "retryable": true }`, no output | `200`, `state: cancelled`, `result.result_code: cancelled` with the reported `error` recorded; `retry_count` stays `0`; no `scheduled` timer, no `taskRetrying`, not dead-lettered; history gains `taskCancelled` | G-RTY-17 |
| non-retryable-error | as retryable-error with `"code": "INVALID_REPORT"`, `"retryable": false` | `200`, `cancelled` / `cancelled` with the error recorded; not dead-lettered | G-RTY-17 |

## Notes
- G-RTY-17 decides: after a cancel request `success`/`warning` end the task `completed`; any `error` ends it `cancelled` with the error recorded, no retry, no DLQ. After a `graceful` cancel the same holds until the grace timer fires. A graceful supersession is different: `error` ends the task `superseded` ([supersede/1.02](../supersede/1.02-positive-graceful-supersession-endings.md), G-CRT-18).
- The explicit acknowledgement, `complete` with `result_code: cancelled`, is [1.10](1.10-flow-worker-acknowledges-cancel-request.md).
