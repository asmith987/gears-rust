# A cancel of a leased task flags it for requested and graceful, and ends it at once for forced

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-task-cancel` (PRD.md:348-350) · `cpt-cf-task-engine-fr-heartbeat` (PRD.md:674) · `cpt-cf-task-engine-fr-lease-fencing` (PRD.md:722) · DESIGN.md:501, :549, :551, :577, :738, :1208, :2155 · ADR-0003:32 · PRD.md:828 |
| Phase | p1 |
| Test level | E2E |
| Gaps | G-RTY-15, G-RTY-19, G-RTY-21, G-WIRE-08, G-WIRE-19, G-SEC-11 |

A leased task has a worker to ask (PRD.md:348-350):

- `requested` sets `cancel_requested`; the worker learns it on its next heartbeat and ends the task itself. The task stays `running`, its lease stays valid, and no timer is armed: a worker that ignores the request runs until it finishes or its execution timeout fires.
- `graceful` is `requested` with a deadline: it also arms a `cancel_grace` timer at `now + cancel_grace_period_secs` (60 s, DESIGN.md:2155). Its expiry is the flow [1.11](1.11-flow-graceful-cancel-forced-after-grace-period.md).
- `forced` is the emergency stop: the engine ends the task immediately with `forcibly_cancelled`, without waiting for the worker. The lease token is cleared (DESIGN.md:577), so the old holder's next write gets `LEASE_LOST`.

## Setup
- `{task_1}`: **render** on **reports**, `running` under `{lt_1}` in `{session_1}` of `reports-7f9c-1` since `T0+1s`.

## Request
At `T0+100s`:
```http
POST /api/task_engine/v1/tasks/{task_1}/cancel HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
Content-Type: application/json

{ "mode": "requested" }
```

## Expected response
- `202 Accepted`, task resource with `state: running`, `cancel_requested: true` and `cancel_request` set (CONVENTIONS §5.5; G-WIRE-08, G-WIRE-19).

```json
{ "id": "{task_1}", "state": "running", "cancel_requested": true,
  "cancel_request": { "mode": "requested", "requested_by": "{creator_a}", "requested_at": "2026-11-03T10:01:40Z",
                      "reason": null, "grace_until": null, "superseded_by": null },
  "result": null, "…": "other fields as in CONVENTIONS §5.1" }
```

## Side effects
- Representative case:
  - task `{task_1}`.cancel_requested advances from `false` to `true`; state stays `running`.
  - lease `{lt_1}` stays valid; no `cancel_grace` timer is armed; slots stay held.
  - history of `{task_1}` gains `taskCancelRequested` (`mode: requested`, `actor: {creator_a}`); it is published (G-RTY-15).
  - subsequent batch heartbeat for `{task_1}` returns `outcome: ok`, `cancel_requested: true` (continued in [1.10](1.10-flow-worker-acknowledges-cancel-request.md)).

## Notes
- The same holds for a `claimed` task not yet started. Its worker may then acknowledge with `complete` `result_code: cancelled` without calling `start` (G-RTY-21, G-EXE-11; DESIGN.md:535 gains the `claimed → cancelled` edge).
- forced: a forced parent cancel does not wait for its children; each unfinished child is still cancelled exactly once (PRD.md:828): see [hierarchy](../../hierarchy/children/).
- graceful: the grace period is the engine-wide `cancel_grace_period_secs` in p1; no per-queue, per-type or per-request value (G-RTY-19). PRD.md:349 "configurable" means this setting.
- A task created `cancellable: false`: [1.09](1.09-guardrail-cancellable-false-allows-only-forced.md).
