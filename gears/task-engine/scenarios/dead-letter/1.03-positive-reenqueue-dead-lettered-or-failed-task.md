# Re-enqueue puts a dead-lettered or failed task back in its queue with fresh budgets

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-dead-letter` (PRD.md:801, :803-811) · DESIGN.md:545, :558, :575, :733, :1128 · `task_queued.v1` schema · PRD.md:1484, :1537 |
| Phase | p2 |
| Test level | E2E |
| Gaps | G-RTY-12, G-RTY-20, G-EXE-24, G-OPS-20 |

An administrator re-enqueues a `dead_lettered` or `failed` task (PRD.md:803). In one step the engine moves it back to the queue it came from (`dead_lettered_from`, or the current queue for a `failed` task without a DLQ) or to the dispatch queue named in an optional `queue` body field (G-RTY-20), resets both retry budgets while `attempt` keeps counting, clears the old result, `terminal_at` and `dead_lettered_from` but keeps the context (G-RTY-12), restarts the lifetime timeout from now, keeps the SLA deadline only if it is still in the future (PRD.md:807), and records `taskQueued` with reason `reenqueued` (PRD.md:803-811). The refusals are in [1.04](1.04-negative-reenqueue-refusals.md).

## Setup
- `{task_1}`: **render**, dead-lettered from **reports** at `T0+230s` (as in [1.01](1.01-positive-dead-lettered-task-parked-in-dlq.md)) with `attempt: 4`, `retry_count: 3`, `liveness_requeues: 1`, `context: { "page": 12 }` (a checkpoint), `sla_deadline: "2026-11-03T12:00:00Z"`, lifetime 86,400 s.
- Clock at `T0+3600s`.

## Request
```http
POST /api/task_engine/v1/admin/tasks/{task_1}/reenqueue HTTP/1.1
Host: api.example.com
Authorization: Bearer <admin-token>
```

## Expected response
- `200 OK`, task resource:
  - `state: queued`, `queue` = **reports**, `dead_lettered_from: null`;
  - `retry_count: 0`, `liveness_requeues: 0`, `attempt: 4` (the next claim makes it 5);
  - `result: null`, `context` unchanged, `sla_deadline` unchanged (still in the future), `terminal_at: null`.

```json
{
  "id": "{task_1}",
  "state": "queued",
  "queue": "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1",
  "dead_lettered_from": null,
  "attempt": 4,
  "retry_count": 0,
  "liveness_requeues": 0,
  "context": { "page": 12 },
  "result": null,
  "sla_deadline": "2026-11-03T12:00:00Z",
  "assignment": null,
  "terminal_at": null,
  "…": "other fields as in CONVENTIONS §5.1"
}
```

## Side effects
- Every case: the task is in `te_task_state` again and absent from `te_task_results` (DESIGN.md:545); timer `lifetime` for `{task_1}` is armed at `T0+3600s + 86400s`; timer `queue_timeout` at `T0+7200s`; history of `{task_1}` gains `taskQueued` with `reason: reenqueued`, `actor: {admin}`, no `run_after` (claimable now, G-EXE-24); it is not published under the default `lifecycle` preset.
- Representative case:
  - timer `sla` at `2026-11-03T12:00:00Z`.
  - The task passes depth admission into tenant A's queued set on **reports** (DESIGN.md:558).
  - `lease_epoch` is unchanged; no lease token is set (DESIGN.md:575).
  - The `taskQueued` record has `queue` **reports**, `attempt: 4`.
  - metric `te_dlq_size{queue="…dead_letter.v1"}` decreases by 1.
  - subsequent claim on **reports** returns `{task_1}` with `attempt: 5` and `lease_epoch` one higher.

## Notes
- Re-enqueue clears `terminal_at`, the result fields and `dead_lettered_from`; a passed `sla_deadline` is cleared (PRD.md:807), a future one is kept with its timer (G-RTY-12).
- explicit-queue: a re-enqueue into another queue re-resolves settings like a move (G-RTY-20, G-OPS-20).
- Successors already cancelled when the task was dead-lettered stay cancelled: [1.06](1.06-guardrail-reenqueue-does-not-revive-successors.md).
