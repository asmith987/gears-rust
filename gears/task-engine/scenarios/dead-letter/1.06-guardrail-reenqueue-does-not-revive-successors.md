# Re-enqueue does not revive successors already cancelled with dependency_failed

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-dead-letter` (PRD.md:813) · `cpt-cf-task-engine-fr-dependencies` (PRD.md:839) · DESIGN.md:529 |
| Phase | p2 |
| Test level | E2E |
| Depends on | Proposals › Task mutability › Set only in the create request (accepted: `on_predecessor_failure`) |

When a predecessor is dead-lettered, a successor linked with `on_predecessor_failure: cancel` is cancelled `dependency_failed` at once (PRD.md:839). Bringing the predecessor back later does not undo that: successors stay cancelled (PRD.md:813), and the predecessor's later success does not reach them.

## Setup
- `{task_1}`: **render** on **reports**; `{task_2}`: **render**, created with `"predecessors": [ { "task_id": "{task_1}", "on_predecessor_failure": "cancel" } ]`, `blocked`.
- `{task_1}` is dead-lettered at `T0+230s`; in that transaction `{task_2}` becomes `cancelled` / `dependency_failed`.

## Exchange 1 — re-enqueue the predecessor
```http
POST /api/task_engine/v1/admin/tasks/{task_1}/reenqueue HTTP/1.1
Host: api.example.com
Authorization: Bearer <admin-token>
```
- `200 OK`, `{task_1}` `state: queued` (as in [1.03](1.03-positive-reenqueue-dead-lettered-or-failed-task.md)).

## Exchange 2 — the predecessor then succeeds, and the successor is read
`{task_1}` is claimed, started and completed `success`. Then:
```http
GET /api/task_engine/v1/tasks/{task_2} HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
```

## Expected response
- `200 OK`, `{task_2}` `state: cancelled`, `result.result_code: dependency_failed`, unchanged since `T0+230s`.

## Side effects
- history of `{task_2}` gains nothing after its `taskCancelled` (`result_code: dependency_failed`).
- No `te_dependencies` row links `{task_2}` to `{task_1}` any more (copied to `te_task_results.predecessors` at finalize, DESIGN.md:2943-2944).

## Notes
- A successor linked with `on_predecessor_failure: ignore` already ran when `{task_1}` was dead-lettered; re-enqueue does not run it again.
