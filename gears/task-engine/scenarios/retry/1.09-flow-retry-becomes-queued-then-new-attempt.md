# A scheduled retry becomes queued at run_after, and the next claim starts attempt 2

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-usecase-retry` (PRD.md:1452-1471) · `cpt-cf-task-engine-fr-retry` (PRD.md:792) · DESIGN.md:526, :731, :755, :1388-1391 |
| Phase | p1 |
| Test level | E2E |
| Gaps | G-SEC-23 |

The retry scheduled in [1.01](1.01-positive-retryable-error-schedules-retry.md) waits in `scheduled` until its `run_after`. The scheduled timer then moves it to `queued` with a fresh queue timeout. Only the next claim bumps `attempt` (PRD.md:1482); `retry_count` does not change on the way.

## Setup
- Run [1.01](1.01-positive-retryable-error-schedules-retry.md). `{task_1}` is `scheduled`, `run_after` inside `[T0+34s, T0+35s]`, `attempt: 1`, `retry_count: 1`.

## Exchange 1 — still scheduled before run_after
At `T0+33s`:
```http
GET /api/task_engine/v1/tasks/{task_1} HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
```
- `200 OK`, `state: scheduled`. A claim on **reports** now does not return `{task_1}`.

## Exchange 2 — the scheduled timer fires (no request)
The timer wheel fires the `scheduled` timer at `run_after` (within 1 s, PRD.md:1260): `scheduled → queued` (DESIGN.md:526, :2736).

## Exchange 3 — claim again
At `T0+37s`:
```http
POST /api/task_engine/v1/tasks/claim HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "worker_id": "reports-7f9c-2", "session_id": null,
  "queues": ["gts.cf.core.tasks.queue.v1~acme.reports._.render.v1"], "max_tasks": 1, "timeout_secs": 30 }
```

## Expected response
- `200 OK`; `claims[0].task.id = {task_1}`, `state: claimed`, `attempt: 2`, `retry_count: 1`.
- `claims[0].lease`: a new `lease_token` `{lt_2}` ≠ `{lt_1}`, `lease_epoch: 2`, `attempt: 2` (DESIGN.md:569).

```json
{ "session_id": "{session_2}", "domain": "default", "heartbeat_interval_secs": 10,
  "claims": [ { "task": { "id": "{task_1}", "state": "claimed", "attempt": 2, "retry_count": 1, "…": "other fields as in CONVENTIONS §5.1" },
                "lease": { "lease_token": "{lt_2}", "lease_epoch": 2, "attempt": 2, "lease_secs": 30, "domain": "default" },
                "authority": { "mode": "creator_verified", "checked": [], "checked_at": "2026-11-03T10:00:37Z" },
                "resumed": null } ] }
```

## Side effects
- After exchange 2: timer `scheduled` for `{task_1}` is removed; timer `queue_timeout` for `{task_1}` is armed at `run_after + 3600s`; history of `{task_1}` gains no event: the engine-driven move from `scheduled` to `queued` is explained by the earlier `taskRetrying` (G-SEC-23).
- After exchange 3: timer `queue_timeout` for `{task_1}` is removed; history gains `taskClaimed` with `attempt: 2`.
- timer `lifetime` for `{task_1}` stays armed at `T0+86400s` throughout.
