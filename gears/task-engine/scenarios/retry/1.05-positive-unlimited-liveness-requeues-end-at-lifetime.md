# max_liveness_requeues 0 requeues without limit until the lifetime timeout ends the task

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-retry` (PRD.md:786) · `cpt-cf-task-engine-fr-timeouts` (PRD.md:521) · DESIGN.md:539, :543, :2784, :2734 · queue schema `max_liveness_requeues` |
| Phase | p1 |
| Test level | Integration — lifetime clock |
| Gaps | G-EXE-05, G-RTY-06 |

`max_liveness_requeues: 0` means unlimited, bounded only by the lifetime timeout (PRD.md:786). It is allowed only for platform types with an effective lifetime timeout (G-RTY-06). The task keeps coming back after any number of lost workers, more than the default of 20, until its lifetime deadline ends it `timed_out`.

## Setup
- `{task_1}`: **cleanup** (platform-owned) on **system**, owner tenant root, created by `{platform_worker}` at `T0` with
  `"timeouts": { "lifetime_timeout_secs": 3600 }` and
  `"retry_policy": { "max_retries": 3, "max_liveness_requeues": 0, "strategy": "fixed", "base_interval_secs": 1, "max_interval_secs": 1, "jitter_factor": 0, "non_retryable_codes": [] }`.
- **system** as shipped: DLQ **dead_letter**, `lifetime_timeout_secs: 3600` (`schemas/instances/…system.v1.json`); the request repeats the lifetime for clarity.
- Every attempt is claimed by `{platform_worker}` (`platform-ops-1`), started, and lost by session expiry (as in [Session expiry](../worker/sessions/1.10-flow-session-expiry-requeues-tasks.md)); one cycle takes about 35 s.

## Exchange 1 — after the 25th expiry
At about `T0+900s`:
```http
GET /api/task_engine/v1/tasks/{task_1} HTTP/1.1
Host: api.example.com
Authorization: Bearer <platform-worker-token>
```
- `200 OK`, `state: scheduled`, `liveness_requeues: 25`, `retry_count: 0`, `attempt: 25`. It was requeued past 20 with no terminal outcome.

## Exchange 2 — the lifetime timer fires (no request)
At `T0+3600s` the `lifetime` timer fires, whatever state the task is in (claimed, running, scheduled or queued), and calls `finalize(timed_out, dlq_or_failed)` (DESIGN.md:2734).

## Expected response
`GET /tasks/{task_1}` at `T0+3601s`:
- `200 OK`, `state: dead_lettered`, `result.result_code: timed_out`, `dead_lettered_from` = **system**.

```json
{ "id": "{task_1}", "state": "dead_lettered", "retry_count": 0,
  "result": { "result_code": "timed_out", "output": null, "error": null, "warnings": [] },
  "terminal_at": "2026-11-03T11:00:00Z", "…": "other fields as in CONVENTIONS §5.1" }
```

## Side effects
- Each requeue before `T0+3600s`: history of `{task_1}` gains `taskRetrying` with `cause: liveness`, `timeout_type: heartbeat` (G-EXE-05).
- history of `{task_1}` gains `taskTimedOut` with `timeout_type: lifetime` and `taskDeadLettered` with `result_code: timed_out`; both are published.
- If the task held a lease at `T0+3600s`, that lease is invalid and its slots are released.

## Notes
- Unlimited (`0`) is above any numeric cap (G-RTY-06): the same policy on the tenant-owned **render** is refused (`400`, [1.07](1.07-negative-unlimited-liveness-requeues-without-lifetime.md)), and a `0` that a tenant-owned task inherits from its type or queue is clamped to `trust_limits.tenant_owned.max_liveness_requeues` (20).
