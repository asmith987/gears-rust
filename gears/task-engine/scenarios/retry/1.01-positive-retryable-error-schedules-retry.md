# A retryable error with budget left schedules a retry after the base backoff

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-retry` (PRD.md:781, :790, :792) · DESIGN.md:538, :1380-1386, :2854-2866 · ADR-0002:62 |
| Phase | p1 |
| Test level | Both — E2E with `base_interval_secs: 1` (the 1 s floor makes the wait exactly 1 s); integration for the jitter window |
| Gaps | G-EXE-05, G-RTY-03, G-RTY-04 |

A worker reports an error that it marks `retryable` and whose code is not in `non_retryable_codes`. With retry budget left, the engine moves the task straight to `scheduled` with a backoff `run_after`; it never passes through `failed`. `retry_count` goes up by one, `attempt` stays where it is until the next claim, and `taskRetrying { cause: reported }` is recorded with the full error and published with its summary.

## Setup
- `{task_1}`: **render** on **reports** in `{tenant_a}` (retry `exponential`, `base_interval_secs: 5`, `max_interval_secs: 300`, `jitter_factor: 0.2`, `max_retries: 3`, `non_retryable_codes: ["INVALID_REPORT"]`), `retry_count: 0`, `liveness_requeues: 0`.
- Claimed by `reports-7f9c-1` at `T0` with lease `{lt_1}` (`attempt: 1`, `lease_epoch: 1`) as in [Claim one task](../worker/claim/1.01-positive-claim-single-task.md), and started at `T0+1s`.

## Request
At `T0+30s`:
```http
POST /api/task_engine/v1/tasks/{task_1}/complete HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{
  "lease_token": "{lt_1}",
  "result_code": "error",
  "error": {
    "domain": "acme.reports",
    "code": "RENDER_TIMEOUT",
    "message": "renderer timed out",
    "fault": "dependency",
    "retryable": true
  }
}
```

## Expected response
- `200 OK`, task resource with `state: scheduled` (CONVENTIONS §5.4).
- `retry_count: 1`, `liveness_requeues: 0`, `attempt: 1` (bumped only by a claim, DESIGN.md:538, :731).
- `run_after` = `T0+30s` + `compute_backoff(n = 1)`: at most `base` = 5 s, shortened by jitter to between 4 s and 5 s, so between `T0+34s` and `T0+35s` (PRD.md:790, DESIGN.md:2862; G-RTY-04).
- `result` is `null`: unfinished tasks carry no result code (PRD.md:1030). The error is read from the task's history (G-RTY-03). `assignment` is `null`.

```json
{
  "id": "{task_1}",
  "state": "scheduled",
  "attempt": 1,
  "retry_count": 1,
  "liveness_requeues": 0,
  "run_after": "2026-11-03T10:00:35Z",
  "result": null,
  "assignment": null,
  "…": "other fields as in CONVENTIONS §5.1"
}
```

## Side effects
- task `{task_1}` state is `scheduled`; it never held state `failed` (no `taskFailed` in its history).
- lease `{lt_1}` is invalid (later calls get LEASE_LOST) (DESIGN.md:574).
- `queue_global(reports)` concurrency used changes by `-1`; `queue_tenant(reports, tenant_a)` concurrency used changes by `-1`.
- The task joins tenant A's deferred set as a re-entry, never refused (DESIGN.md:559).
- timer `scheduled` for `{task_1}` is armed at its `run_after`; timer `lifetime` for `{task_1}` is kept at `T0+86400s` (DESIGN.md:538).
- history of `{task_1}` gains `taskRetrying` with `cause: reported`, `attempt: 1`, `run_after`, and the full error `{ domain: "acme.reports", code: "RENDER_TIMEOUT", message: "renderer timed out", context: null, fault: "dependency", retryable: true }`, as returned by `GET /tasks/{task_1}/events` (G-RTY-03, G-EXE-05).
- event `taskRetrying` for `{task_1}` is published to the task-events topic with `cause: reported` and the error summary only (`domain`, `code`, `fault`, `retryable`; no `message`, no `context`).
- metric `te_tasks_retried_total{queue="…acme.reports._.render.v1"}` increases by 1.

## Notes
- The `run_after` shown is one value inside the jitter window; a test asserts the window `[T0+34s, T0+35s]`. PRD.md:1483 "the first retry waits `base`" is reworded to "at most `base`", and every computed backoff has a 1 s floor (G-RTY-04).
