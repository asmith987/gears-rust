# A retry policy on the request wins over the type and the queue, and is taken whole

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-retry` (PRD.md:781) · `cpt-cf-task-engine-fr-gts-task-type` (PRD.md:980) · DESIGN.md:715 |
| Phase | p1 |
| Test level | E2E |
| Gaps | G-CRT-04, G-EXE-05, G-OPS-13 |

A retry policy is taken whole from the first level that has one (PRD.md:980): request, then type trait, then queue. Nothing is merged, so the queue's `non_retryable_codes: ["INVALID_REPORT"]` does **not** apply to a task that brings its own policy. Type-over-queue resolution is shown in [Type defaults](../tasks/create/1.03-positive-settings-resolution.md).

## Setup
- Type **thumbnail** with its `retry_policy` trait, as defined in [Type defaults](../tasks/create/1.03-positive-settings-resolution.md); `default_queue` **reports**.

## Exchange 1 — create with a full policy
```http
POST /api/task_engine/v1/tasks HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
Content-Type: application/json
Idempotency-Key: 9c41-thumb-r-44

{
  "type": "gts.cf.core.tasks.task.v1~acme.reports._.thumbnail.v1~",
  "input": { "report_id": "r-44" },
  "retry_policy": { "max_retries": 2, "max_liveness_requeues": 5, "strategy": "fixed",
                    "base_interval_secs": 3, "max_interval_secs": 3, "jitter_factor": 0, "non_retryable_codes": [] }
}
```
- `201 Created`; `retry_policy` is exactly the request's policy; `queue` is **reports**.

```json
{ "id": "{task_1}", "queue": "gts.cf.core.tasks.queue.v1~acme.reports._.render.v1",
  "retry_policy": { "max_retries": 2, "max_liveness_requeues": 5, "strategy": "fixed", "base_interval_secs": 3,
                    "max_interval_secs": 3, "jitter_factor": 0, "non_retryable_codes": [] },
  "…": "other fields as in CONVENTIONS §5.1" }
```

## Exchange 2 — the worker reports INVALID_REPORT as retryable
After claim (`{lt_1}`) and start, at `F_1`:
```http
POST /api/task_engine/v1/tasks/{task_1}/complete HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{
  "lease_token": "{lt_1}",
  "result_code": "error",
  "error": {
    "domain": "acme.reports",
    "code": "INVALID_REPORT",
    "message": "no sections",
    "fault": "task",
    "retryable": true
  }
}
```

## Expected response
- `200 OK`, `state: scheduled`, `retry_count: 1`, `run_after = F_1 + 3s`: the code is retried, because the task's own list is empty (compare [1.03](1.03-positive-error-without-retry-ends-failed-or-dead-lettered.md), where the queue's list applies).

## Side effects
- history of `{task_1}` gains `taskRetrying` with `cause: reported`, `error.code: INVALID_REPORT`; timer `scheduled` for `{task_1}` is armed at `F_1+3s`.
- Later changes to the type trait or the queue policy do not change `{task_1}`: settings are resolved and stored at create (DESIGN.md:715; G-CRT-04, G-OPS-13).

## Notes
- A request policy must carry the schema's required fields (`max_retries`, `strategy`, `base_interval_secs`, `max_interval_secs`), else `400`; omitted optional fields (`max_liveness_requeues` 20, `jitter_factor` 0, `non_retryable_codes` []) take the schema defaults, never the queue's values (G-CRT-04). The `400` is shown in [placement and trust-limit refusals](../tasks/create/1.12-negative-placement-and-trust-limit-refusals.md).
