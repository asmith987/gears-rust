# Lost workers never use the retry budget: four lease expiries, then still three retries

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-retry` (PRD.md:783-788) · `cpt-cf-task-engine-fr-heartbeat` (PRD.md:678) · DESIGN.md:538-539, :2784-2797, :2866 · PRD.md:1516 |
| Phase | p1 |
| Test level | Integration — four lease expiries |
| Gaps | G-EXE-05, G-RTY-03 |

PRD acceptance (PRD.md:1516): with `max_retries = 3`, a task survives more than three lease expiries and still gets three retries after reported failures. Each budget also computes its backoff from its **own** count (PRD.md:788), so the first reported failure after four requeues waits `base`, not `base × 2^4`.

## Setup
- `{task_1}`: **render** on **reports** (`max_retries: 3`, `max_liveness_requeues: 20`, `exponential`, base 5 s, max 300 s, jitter 0.2), created at `T0`.
- "Expiry" below means: the attempt is claimed and started, then its worker process dies and the session scan requeues it, as in [Session expiry](../worker/sessions/1.10-flow-session-expiry-requeues-tasks.md).
- "Failure" means: the attempt is claimed and started, then completes with the retryable `RENDER_TIMEOUT` error of [1.01](1.01-positive-retryable-error-schedules-retry.md).

## Exchange 1 — four expiries in a row (no request)
| Attempt | Event | `liveness_requeues` | `retry_count` | Backoff n | Wait (before jitter) | State after |
|---|---|---|---|---|---|---|
| 1 | expiry | 1 | 0 | 1 | 5 s | `scheduled` |
| 2 | expiry | 2 | 0 | 2 | 10 s | `scheduled` |
| 3 | expiry | 3 | 0 | 3 | 20 s | `scheduled` |
| 4 | expiry | 4 | 0 | 4 | 40 s | `scheduled` |

## Exchange 2 — attempt 5 fails with a retryable error
```http
POST /api/task_engine/v1/tasks/{task_1}/complete HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{
  "lease_token": "{lt_5}",
  "result_code": "error",
  "error": {
    "domain": "acme.reports",
    "code": "RENDER_TIMEOUT",
    "message": "renderer timed out",
    "fault": "dependency",
    "retryable": true
  }
}
```
- `200 OK`, `state: scheduled`, `attempt: 5`, `retry_count: 1`, `liveness_requeues: 4`.
- `run_after` is the failure time plus 4–5 s: `n = retry_count + 1 = 1`, independent of the four requeues (DESIGN.md:2866).

```json
{ "id": "{task_1}", "state": "scheduled", "attempt": 5, "retry_count": 1, "liveness_requeues": 4,
  "run_after": "<failure time + 4..5 s>", "…": "other fields as in CONVENTIONS §5.1" }
```

## Exchange 3 — attempts 6 and 7 fail the same way
- Each `200 OK`, `state: scheduled`; `retry_count` 2 then 3; waits 8–10 s then 16–20 s; `liveness_requeues` stays 4.

## Exchange 4 — attempt 8 fails the same way
- `200 OK`, `state: dead_lettered`, `result.result_code: error`, `retry_count: 3`, `liveness_requeues: 4`, `attempt: 8` (as in [Terminal error outcomes, exhausted-with-dlq](1.03-positive-error-without-retry-ends-failed-or-dead-lettered.md)).

## Side effects
- Over the whole flow: four liveness requeues and three retries; the task reached `scheduled` seven times and never `failed`.
- history of `{task_1}` gains `taskClaimed` eight times (attempts 1–8); `taskRetrying` seven times: four with `cause: liveness`, `timeout_type: heartbeat`, `error: null` (G-EXE-05), then three with `cause: reported` and the full error (G-RTY-03); one `taskDeadLettered`, and no `taskTimedOut`.
- Blacklist (p3): one liveness failure is recorded per expiry for the worker that lost the task; reported failures with `fault: dependency` add none (DESIGN.md:761).
