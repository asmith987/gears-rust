# Retry backoff follows the strategy, stops at max_interval, is only shortened by jitter, never drops below 1 s, and never overflows

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-retry` (PRD.md:786, :790) · DESIGN.md:2784-2786, :2854-2866 · queue schema `retry_policy` (`jitter_factor`) · PRD.md:1483 |
| Phase | p1 |
| Test level | Integration — backoff math (mostly unit) |
| Gaps | G-RTY-04, G-RTY-06 |

`compute_backoff(n)` gives the wait before a retry or a liveness requeue. `n` is the budget's own count after this failure (`n = retry_count + 1`, DESIGN.md:2866). The raw wait depends on the strategy (PRD.md:790, DESIGN.md:2857-2858):

- `fixed`: `base`;
- `linear`: `base × n`;
- `exponential`: `base × 2^(n−1)`;

then it is capped at `max_interval_secs` (`d`), and jitter takes a random part of up to `jitter_factor` off it, so the wait is drawn from `[d × (1 − jitter_factor), d]` and never exceeds `max_interval_secs` (DESIGN.md:2860-2861). Every computed wait has a floor of 1 s (G-RTY-04), so `jitter_factor: 1` ("full jitter") draws from `[1 s, d]`. The arithmetic saturates with the exponent capped at 62 (DESIGN.md:2856-2859), so a huge count gives exactly `max_interval_secs`.

The representative case is exponential with a cap and no jitter, so the sequence is exact. Each other case changes the policy (or the trigger) and is tested on its own.

## Setup
- `{task_1}`: **render** on **reports**, created at `T0` with its own policy (taken whole, see [1.06](1.06-positive-task-retry-policy-taken-whole.md)):
  `"retry_policy": { "max_retries": 6, "max_liveness_requeues": 20, "strategy": "exponential", "base_interval_secs": 5, "max_interval_secs": 30, "jitter_factor": 0, "non_retryable_codes": [] }`.
- Each attempt is claimed and started, then fails with the request below. `F_n` is the time of the n-th failure report.

## Request (each failure, with the current lease)
```http
POST /api/task_engine/v1/tasks/{task_1}/complete HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{
  "lease_token": "{lt_n}",

    "code": "RENDER_TIMEOUT",

    "fault": "dependency",
    "retryable": true
  }
}
```

## Expected response
- Each call returns `200 OK` with `state: scheduled` and:

| Failure | `retry_count` after | `n` | Raw wait `5 × 2^(n−1)` | Wait used | `run_after` |
|---|---|---|---|---|---|
| 1 | 1 | 1 | 5 s | 5 s | `F_1+5s` |
| 2 | 2 | 2 | 10 s | 10 s | `F_2+10s` |
| 3 | 3 | 3 | 20 s | 20 s | `F_3+20s` |
| 4 | 4 | 4 | 40 s | **30 s** (cap) | `F_4+30s` |
| 5 | 5 | 5 | 80 s | **30 s** (cap) | `F_5+30s` |
| 6 | 6 | 6 | 160 s | **30 s** (cap) | `F_6+30s` |

```json
{ "id": "{task_1}", "state": "scheduled", "retry_count": 4, "run_after": "<F_4 + 30s>", "…": "other fields as in CONVENTIONS §5.1" }
```

## Side effects
- Each failure: history of `{task_1}` gains `taskRetrying` with that `run_after`; timer `scheduled` for `{task_1}` is armed at that `run_after`.
- The 7th failure has no budget left and follows [Terminal error outcomes](1.03-positive-error-without-retry-ends-failed-or-dead-lettered.md).

## Notes
- Jitter cases: tests check the window, not one value. A seeded RNG makes a failing case reproducible.
- PRD.md:1483 and DESIGN.md:2866 "the first retry waits `base`" are reworded to "at most `base`"; the 1 s floor rules out a zero wait (G-RTY-04).
- huge-count: only the unlimited liveness budget (`max_liveness_requeues: 0`) can reach such counts; retry budgets are capped by trust limits (DESIGN.md:2195, :2200). Unlimited is allowed only for platform types with an effective lifetime timeout; an explicit `0` on a tenant-owned type is `400` (G-RTY-06, [1.07](1.07-negative-unlimited-liveness-requeues-without-lifetime.md)). Reaching 70 by real expiries is equivalent but slow. The same holds for `linear` (`base.saturating_mul(n)`, DESIGN.md:2858). A unit test of `compute_backoff` with `n = u32::MAX` should accompany this case.
