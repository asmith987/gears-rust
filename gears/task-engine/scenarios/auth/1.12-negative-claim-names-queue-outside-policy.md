# A claim naming a queue the worker's queue policy excludes is refused with 403

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-resource-path-access` (PRD.md:943) · PRD.md:1531 · DESIGN.md:1009, :2407 · ADR-0016:72, :97 |
| Phase | p1 |
| Test level | Integration — queue policy |
| Gaps | G-SEC-16, G-CLM-14, G-SEC-19 |

Claims are authorized once on the base type. The engine then checks the compiled scope in memory: a named queue is provably excluded when every OR'd constraint has a `queue_id` filter that does not contain it. Any provably excluded queue refuses the whole claim with `403` `QUEUE_NOT_PERMITTED`, before a session opens. Everything else is filtered in SQL, so a worker never receives a task from a queue outside its grant.

## Setup
- PDP: `{worker_a}` task `claim` allowed only with `queue_id eq gts.cf.core.tasks.queue.v1~acme.reports._.render.v1`.
- `{task_5}` (**render**, tenant A) `queued` in **bulk**; no task queued in **reports**.

## Request
```http
POST /api/task_engine/v1/tasks/claim HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "worker_id": "reports-7f9c-1", "session_id": null,
  "queues": ["gts.cf.core.tasks.queue.v1~acme.reports._.render.v1", "gts.cf.core.tasks.queue.v1~acme.reports._.bulk.v1"],
  "max_tasks": 1, "timeout_secs": 2 }
```

## Expected response
- `403 Forbidden` at once (no long-poll wait), category `permission_denied`, `context.reason = "QUEUE_NOT_PERMITTED"`, naming **bulk**. No field violations; the queue's position goes only into `detail`.
```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.permission_denied.v1~",
  "title": "Permission Denied",
  "status": 403,
  "detail": "Not allowed to claim from queue 1",
  "instance": "/api/task_engine/v1/tasks/claim",
  "trace_id": "<trace>",
  "context": {
    "resource_type": "gts.cf.core.tasks.queue.v1~",
    "resource_name": "gts.cf.core.tasks.queue.v1~acme.reports._.bulk.v1",
    "reason": "QUEUE_NOT_PERMITTED"
  }
}
```

## Side effects
- `task {task_5} state is queued`; no session is opened or renewed.

## Cases

| Case | Differs from the representative request | Expected | Notes |
|---|---|---|---|
| one excluded queue among allowed ones | (representative) | `403` `QUEUE_NOT_PERMITTED` naming **bulk** | G-CLM-14 |
| only excluded queues | `queues` names only **bulk** | `403` `QUEUE_NOT_PERMITTED` naming **bulk** | G-SEC-16 |
| only allowed queues | `queues` names only **reports** | `204 No Content` after the 2 s timeout; `{task_5}` not returned | |
| constraint without a queue filter | PDP adds a second OR'd constraint `type_id eq gts.cf.core.tasks.task.v1~acme.billing._.export.v1~` (no `queue_id`); representative request | `204 No Content` after the timeout; `{task_5}` (**render**) not returned | the second constraint "may match" **bulk**, so nothing is provably excluded and SQL filters the candidates (G-CLM-14) |

## Notes
- The check is conservative: a constraint without a `queue_id` filter, or with one the engine cannot evaluate in memory, counts as "may match" (G-CLM-14).
- `resource_type` names the queue base type and `resource_name` the excluded queue; the closed `403` reason list is in CONVENTIONS §6 (G-SEC-19).
- The same rule from the claim side: [../worker/claim/1.09](../worker/claim/1.09-guardrail-queue-policy-limits-what-worker-receives.md).
