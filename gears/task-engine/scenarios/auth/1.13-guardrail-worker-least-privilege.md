# A worker with only claim, read and create cannot cancel, resolve or administer

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-authz` least privilege (PRD.md:925) · DESIGN.md:989-991, :995, :1073, :1098, :1119, :1128 |
| Phase | p1 (row `resolve an input wait`: p2) |
| Test level | Integration — action-level grants |
| Depends on | Proposals › Task mutability › `update` covers only tags; `resolve` gets its own action · Proposals › Waits › `resolve` — row `resolve an input wait` |
| Gaps | G-SEC-19, G-OPS-14, G-SEC-18 |

Workers need `claim` (and `read` for their own reads); nothing more. A worker that wants a task gone reports a result through its lease, or releases it. It cannot cancel, even the task it holds, cannot approve its own task's question, and cannot move work to another identity or bring dead tasks back. A compromised worker is contained by these refusals. Because the worker may read the task, each refusal is `403`, not `404`.

## Setup
- `{task_1}` (**render**, tenant A) is `running`, held by `{worker_a}` (`reports-7f9c-1`, `{lt_1}`).
- `{worker_a}` has task `claim`, `read`, `create` (fixture), no `cancel`, `resolve` or `admin`.

## Request
```http
POST /api/task_engine/v1/tasks/{task_1}/cancel HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{ "mode": "forced" }
```

## Expected response
- `403 Forbidden`, category `permission_denied`, `context.reason = "ACTION_DENIED"` (the worker may read the task, so not `404`).

## Side effects
- `task {task_1} state is running`; `lease {lt_1}` stays valid; the history gains nothing.

## Cases

| Case | Differs from the representative request | Expected | Notes |
|---|---|---|---|
| cancel | (representative) | `403` `ACTION_DENIED` | the worker's way out is `POST /tasks/{task_1}/complete` with `result_code: cancelled` only after a cancel request, or `POST /tasks/{task_1}/release` ([../worker/](../worker/)) |
| resolve an input wait | `{task_1}` (**export**) is `waiting` on input condition `{wc_1}` (`input_schema` requires `approved: boolean`), set by `{worker_a}` before parking; `POST /wait-conditions/{wc_1}/resolve` `{ "value": { "approved": true } }` | `403` `ACTION_DENIED`; `{wc_1}` stays `pending`; `task {task_1} state is waiting`; the history gains nothing | needs `resolve` (DESIGN.md:995). The worker can read the task, so `403`; resolve is exempt from the `404` rule only for a caller that holds `resolve` (G-SEC-18). On `main` the action is `update` (DESIGN.md:1098); the accepted change replaces it with `resolve` |
| reassign | `POST /tasks/{task_1}/reassign` `{ "subject_id": "{worker_a}", "worker_id": "reports-7f9c-2" }` | `403` `ACTION_DENIED`; `task {task_1} lease_epoch` is unchanged; the history gains no `taskReassigned` | needs `admin` (DESIGN.md:991, :1073) |
| re-enqueue | `POST /admin/tasks/{id}/reenqueue` on a dead-lettered task `{worker_a}` can read | `403` `ACTION_DENIED` | needs `admin` (DESIGN.md:1128) |
| bulk retry | `POST /tasks/bulk/retry` naming `{task_1}` | `403` `ACTION_DENIED` for the whole request; nothing changes | `{worker_a}` holds no `admin` at all, an outright denial of the action on the base type; a policy that grants it only on some tasks gives per-task `unauthorized` instead (G-OPS-14; [../bulk/](../bulk/)) |
