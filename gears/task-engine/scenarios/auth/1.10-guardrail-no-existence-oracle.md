# A task the caller may not read answers exactly like a missing task (no existence oracle)

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-authz` (PRD.md:918) · DESIGN.md:1015-1016, :1191, :1199 |
| Phase | p1 |
| Test level | Both — E2E: other-tenant task = missing task; integration: same-tenant unreadable rows |
| Gaps | G-SEC-18, G-WIRE-15 |

A caller must not learn that a task ID exists when it may not read it. A task of another tenant, a task hidden by policy, and an ID that was never used all get the same `404`, on every single-task route and with any action. The body names only the ID the caller sent and the base task type, never the task's concrete type, queue or tenant.

## Setup
- `{task_1}` (**render**, tenant A, `queued`) exists, with entry `{entry_1}` and wait condition `{wc_1}`.
- `{task_404}` is a UUID v7 that was never assigned.

## Request
```http
GET /api/task_engine/v1/tasks/{task_1} HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-b-token>
```

## Expected response
- `404 Not Found`, category `not_found`.
```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.not_found.v1~",
  "title": "Not Found",
  "status": 404,
  "detail": "Task with ID {task_1} not found",
  "instance": "/api/task_engine/v1/tasks/{task_1}",
  "trace_id": "<trace>",
  "context": { "resource_type": "gts.cf.core.tasks.task.v1~", "resource_name": "{task_1}" }
}
```

## Side effects
<!-- No side effects: reads and refused calls change nothing. -->

## Cases

Every row is by `{creator_b}` unless it says otherwise, and every row's body equals the representative's except the ID in `detail`, `instance` and `context.resource_name` and the path in `instance`.

| Case | Differs from the representative request | Expected | Notes |
|---|---|---|---|
| foreign task | (representative) | `404` | |
| never-used ID | `GET /tasks/{task_404}` | `404`, body identical to the representative except the ID | the comparison test: byte-identical apart from the ID |
| hidden by policy | `{creator_a2}` (tenant A) whose PDP policy denies `read` on `{task_1}` | `404` | |
| history | `GET /tasks/{task_1}/events` | `404` | |
| entries | `GET /tasks/{task_1}/entries`, `GET /tasks/{task_1}/entries/{entry_1}` | `404` | |
| wait conditions | `GET /tasks/{task_1}/wait-conditions` | `404` | |
| cancel | `POST /tasks/{task_1}/cancel` `{ "mode": "requested" }` | `404`, never `403`; `task {task_1} state is queued` | `{creator_b}` may not `read` `{task_1}`, so the denial is reported as `404` (DESIGN.md:1016) |

## Notes
- A `404` carries only `resource_type` and `resource_name`, never a field violation (G-WIRE-15).
- `context.resource_type` is always the base type `gts.cf.core.tasks.task.v1~` (DESIGN.md:1191): echoing the concrete type would itself reveal the task.
- The one exemption is `POST /wait-conditions/{id}/resolve`: a caller with `resolve` finds and resolves the condition without `read` (G-SEC-18). Every other route applies the rule to a subject with no task `read` at all: a resolve-only subject ([resolve grants nothing else](1.14-guardrail-resolve-grants-nothing-else.md)) and a queue-only viewer ([queue read](1.15-guardrail-queue-read-grants-no-task-data.md)). The full cross-tenant sweep (writes, bulk, search, claim) is the [isolation flow](1.16-flow-tenant-isolation-three-tenants.md). A task removed by retention answers the same `404` ([../tasks/read/1.03](../tasks/read/1.03-negative-retention-removed-task-is-not-found.md)).
