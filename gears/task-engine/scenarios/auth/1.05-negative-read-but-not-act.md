# A caller who may read the target but not perform the action gets 403

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-authz` (PRD.md:918, :922, :923, :925) · `cpt-cf-task-engine-fr-resource-path-access` (PRD.md:943) · `cpt-cf-task-engine-fr-authn` (PRD.md:909) · DESIGN.md:986, :990, :993, :1016, :1098, :1129-1130, :2350, :2376 · `schemas/instances/…task_update.v1.json` · `schemas/instances/…queue_configure.v1.json` |
| Phase | p1 (row `update grant does not cover resolve`: p2) |
| Test level | Integration — action-level 403: static-authz is tenant-only |
| Depends on | Proposals › Task mutability › `update` covers only tags; `resolve` gets its own action — row `update grant does not cover resolve` |
| Gaps | G-SEC-17, G-SEC-19, G-WIRE-15 |

`403` is reserved for a caller who can already see the target. Here `{reader_a}` holds only task `read` in tenant A, so the engine's extra `read` check on the denial path succeeds and the answer is `403`, not `404`. The rows show the other ways a readable target meets a missing right: a token whose scopes do not cover the action, and a policy that still grants the removed `update` action. Queue `configure` refusals live with the queue endpoints.

## Setup
- `{task_1}` (**render**, tenant A, `queued`) exists.
- `{reader_a}` has task `read` only (fixture `<readonly-a-token>`).

## Request
```http
POST /api/task_engine/v1/tasks/{task_1}/cancel HTTP/1.1
Host: api.example.com
Authorization: Bearer <readonly-a-token>
Content-Type: application/json

{ "mode": "requested", "reason": "not needed" }
```

## Expected response
- `403 Forbidden`, category `permission_denied`, `context.reason = "ACTION_DENIED"`.
```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.permission_denied.v1~",
  "title": "Permission Denied",
  "status": 403,
  "detail": "Not allowed to cancel this task",
  "instance": "/api/task_engine/v1/tasks/{task_1}/cancel",
  "trace_id": "<trace>",
  "context": { "resource_type": "gts.cf.core.tasks.task.v1~", "reason": "ACTION_DENIED" }
}
```

## Side effects
- The request is refused before any write: `task {task_1} state is queued`, `cancel_requested` stays `false`, and the history gains nothing.

## Cases

| Case | Differs from the representative request | Expected | Notes |
|---|---|---|---|
| read-only subject cancels | (representative) | `403` `ACTION_DENIED` | |
| token scopes cap the grant | `<creator-a-ro-token>`: a token of `{creator_a}` (PDP grants `create`, `read`, `update`, `cancel`, `resolve`) issued with read-only scopes; body `{ "mode": "requested" }` | `403` `ACTION_DENIED` (the token can still read the task, so `403`, not `404`); `GET /tasks/{task_1}` with the same token → `200` | the PEP passes `token_scopes` and the PDP applies them as a ceiling (DESIGN.md:2350; G-SEC-17) |

The engine registers `gts.cf.toolkit.authz.permission.v1~cf.task_engine._.task_resolve.v1` at startup next to `…task_update.v1` | resolve asks the PDP for `resolve` only; `update` covers tags only (DESIGN.md:986, :1098 on `main` still say `update`) |

## Notes
- A plain action denial has reason `ACTION_DENIED`, from the closed `403` reason list (G-SEC-19). A `403` carries no field violations (G-WIRE-15).
- PDP internals (policy names, constraints) never appear in `detail` or `context` (PRD.md:918).
- Token scopes: the PDP enforces the scope ceiling; the engine passes `token_scopes` and has no scope logic of its own. The engine documents suggested scope names for policy authors (`tasks:read`, `tasks:write`, `tasks:work`, `tasks:admin`); the read-only token here carries `tasks:read` only (G-SEC-17).
- `update` now covers only `PATCH /tasks/{id}/tags` ([../tasks/create/1.13](../tasks/create/1.13-positive-update-tags-after-create.md)). The other endpoints it used to guard are removed (`POST/DELETE /tasks/{id}/dependencies`, consumer `POST /tasks/{id}/wait-conditions`); their guardrails live with create and hierarchy. Adding a child with `update` on the parent is gone too: a child needs `parent_lease_token` ([../hierarchy/](../hierarchy/)).
- Queue `configure` checks (hold, release, `POST /admin/config`, `GET /admin/config/{version}`) are endpoint-specific and live in [../queues/1.03-negative-queue-action-required.md](../queues/1.03-negative-queue-action-required.md).
