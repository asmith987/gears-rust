# Reads see only the tenants the PDP scope allows, with barriers respected outside platform-operated queues

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-tenant-scoping` (PRD.md:934) · `cpt-cf-task-engine-fr-authz` (PRD.md:918) · `cpt-cf-task-engine-fr-worker-principals` (PRD.md:954-955) · DESIGN.md:976-978, :1012, :1020, :2348, :2362 · ADR-0016:74 |
| Phase | p1 |
| Test level | Integration — PDP tenant constraints, barriers |
| Gaps | G-SEC-14, G-SEC-15 |

Tenant hierarchy reaches tasks only through PDP constraints. A subject of A whose policy returns `owner_tenant_id` in the subtree of A sees A1's tasks; a policy limited to `owner_tenant_id eq A` does not; a subject of A1 never sees A's tasks. The PDP's tenant constraints are the only tenant scope: the AuthZ resolver builds them from the Tenant Resolver, and the engine makes no second resolver call (G-SEC-14). Requests send `barrier_mode: respect`, so an operator in the root tenant does not see tasks of tenant C, behind a barrier. The exception is operations on tasks in `operated_by: platform` queues, which send `Ignore` and let the PDP decide (G-SEC-15).

## Setup
- `{task_1}` (**render**, tenant A), `{task_4}` (**render**, tenant A1). Both `queued`, created inside the default window.
- PDP: for `{creator_a}`, task `read` returns `owner_tenant_id InTenantSubtree({tenant_a})`. For `{reader_a}`, `read` returns `owner_tenant_id eq {tenant_a}`.
- `{creator_a1}` (`<creator-a1-token>`): same grants as `{creator_a}`, in tenant A1.

## Request
```http
GET /api/task_engine/v1/tasks?view=tiny HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
```

## Expected response
- `200`; `items` holds `{task_4}` then `{task_1}` (newest first). `GET /tasks/{task_4}` → `200` with `"owner_tenant_id": "{tenant_a1}"`.

## Notes
- The subtree is resolved by the Tenant Resolver with `barrier_mode: respect` (DESIGN.md:1020); a barrier inside the subtree hides that tenant as in the last row.
- Subtree visibility is a policy choice, not an engine default (G-SEC-14). DESIGN compiles the PDP constraints into `AccessScope` (DESIGN.md:978, :2348); nothing is intersected on top.
- Operator actions follow the same rule: read, search filtered to platform queues only, cancel, re-enqueue (for a dead-lettered task, by its `dead_lettered_from` queue) and reassign send `Ignore` on tasks of `operated_by: platform` queues and let the PDP decide; tasks of tenant-operated queues behind a barrier stay out of reach (G-SEC-15).
- Claims on platform-operated queues are the one exception: [platform worker](1.03-positive-platform-worker-crosses-barrier-only-on-platform-queues.md).
