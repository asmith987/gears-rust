# With the Event Broker down, task operations continue and events are delivered later, in order

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-event-publishing` (PRD.md:884, :887) · DESIGN.md:872-878, :1053, :2291 |
| Phase | p1 |
| Test level | Integration — broker outage + ordered catch-up |
| Gaps | G-RTY-15 |

Publishing is off the correctness path. Events are enqueued in the outbox of the task's domain in the same transaction as the state change; delivery waits for the broker. Readiness stays green.

## Setup
- The Event Broker is unreachable from `T0` to `T0+10m`.

## Exchange 1 — create during the outage
- `POST /tasks` by `{creator_a}` (CONVENTIONS §5.2) → `201`, `{task_1}`.

## Exchange 2 — cancel during the outage
- `POST /tasks/{task_1}/cancel` `{ "mode": "requested" }` → `200`, `state: cancelled`.

## Exchange 3 — read the history during the outage
- `GET /tasks/{task_1}/events` → `200` with `taskCreated`, `taskCancelled` (an unleased task is cancelled at once, so no `taskCancelRequested`).

## Side effects
- `metric te_outbox_pending{domain="default"}` rises during the outage and returns to 0 after `T0+10m`.
- After the broker is back: `event taskCreated for {task_1} is published to the task-events topic`, then `taskCancelled`, in that order, with the history's event IDs.
- The gateway's `/readyz` stays ready throughout.

## Notes
- Back-pressure and retention of undelivered events belong to the platform outbox, not the engine (PRD.md:887).
- An immediate cancel records only `taskCancelled` with `actor` and `mode` (G-RTY-15).
