# Events never carry lease tokens, task payloads, or an error's message and context

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-nfr-data-protection` (PRD.md:1360) · DESIGN.md:875, :1081, :2344, :2354 · `schemas/types/` (`…task_failed.v1~`, `…task_retrying.v1~`) |
| Phase | p1 |
| Test level | E2E |
| Gaps | G-EXE-05, G-RTY-03 |

Lease tokens appear only in claim and accept responses and the holder's requests. Input, context, output and entry payloads never leave the engine through events: every event schema is closed (`additionalProperties: false`) with no payload field. A worker's error `message` and `context` are free text that may echo payload data; they stay readable on the task through the API, and the broker never receives them: published failure events carry only the error's `domain`, `code`, `fault` and `retryable`.

## Setup
- `{task_1}` (**bulk** queue, no DLQ, `max_retries` used up) fails: `{worker_a}` completes it with `result_code: error`, `error: { "domain": "acme.reports", "code": "RENDER_TIMEOUT", "message": "renderer timed out on jane.doe@example.com", "context": { "row": 17 }, "fault": "dependency", "retryable": true }`.

## Expected broker publish
```json
{ "type": "gts.cf.core.events.event.v1~cf.core.tasks.task_failed.v1~",
  "tenant_id": "{tenant_a}", "subject": "{task_1}",
  "data": { "task_id": "{task_1}", "result_code": "error", "attempt": 4, "actor": "{worker_a}",
            "error": { "domain": "acme.reports", "code": "RENDER_TIMEOUT", "fault": "dependency", "retryable": true } } }
```
- `data.error` has no `message` and no `context`; no member of the event contains `jane.doe@example.com`.

## Side effects
- `event taskFailed for {task_1} is published to the task-events topic`.
- `GET /tasks/{task_1}` returns the full `result.error`, `message` and `context` included, to callers with `read`.

## Cases

| Case | Differs from the representative | Expected | Notes |
|---|---|---|---|
| failure event error fields | (representative) | `data.error` has only `domain`, `code`, `fault`, `retryable` | |
| retrying event | an attempt fails with retries left | every published `taskRetrying` event (`cause: reported`) has an `error` with the same four fields; the history item of the same event carries the full `error`, `message` and `context` included, for callers with `read` | G-EXE-05, G-RTY-03 |
| token and payloads | `{task_1}` with input `{ "report_id": "r-42", "format": "pdf" }` is created, claimed (`{lt_1}`), checkpointed with `{ "page": 12 }`, and completed with output `{ "url": "https://files.example.com/r-42.pdf" }` | no published event and no history item contains `{lt_1}`, `r-42`, `"page": 12` or the output URL. `taskClaimed` carries `assignee`, `assignee_subject`, `attempt`, `lease_until` and no token; `taskCheckpointed` carries `attempt` and no context | asserts the content of events already produced |

## Notes
- `resource_refs` (IDs the creator chose) are published on purpose (PRD.md:372); they are references, not payload.
- The history (`GET /tasks/{id}/events`) is local and authorized. Its `taskRetrying` items store the full error, because that is the only place a retried attempt's error can be read (G-RTY-03). No decision covers the history `taskFailed` item; it is assumed to have the published shape, since the full error is on the task's `result`.
- Error bodies follow the same rule: see the data-protection section of [ERRORS.md](../ERRORS.md).
