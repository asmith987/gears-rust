# The publishing policy decides which events reach the broker; the history always records everything

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-event-publishing-config` (PRD.md:898) · PRD.md:870, :877 · DESIGN.md:1839, :2047, :2217-2221 |
| Phase | p1 — the default-preset rows; the `per_type` rows are p2 |
| Test level | Integration — per-type publishing policy matrix |
| Gaps | G-EXE-05, G-EXE-24, G-OPS-05, G-SEC-12 |

Without configuration, the `lifecycle` preset publishes every event type except the frequent execution events `taskQueued`, `taskClaimed`, `taskStarted`, `taskCheckpointed` and `taskProgressed`. High-volume types can publish only their outcome: a type matching a `per_type` pattern uses its list; unmatched types fall back to `default`. The local history always records everything.

## Setup
- No `event_policies` configured. `{task_1}` runs the lifecycle of [history complete](1.01-positive-history-complete-and-ordered.md) (create, claim, start, checkpoint, complete), with one `taskProgressed` (mode `all`).

## Expected outcome
- Published to the task-events topic: `taskCreated`, `taskCompleted`.
- Not published: `taskClaimed`, `taskStarted`, `taskCheckpointed`, `taskProgressed`.
- `GET /tasks/{task_1}/events` returns all six.

## Side effects
- `event taskCreated for {task_1} is published to the task-events topic`; `event taskCompleted for {task_1} is published …`.
- `event taskClaimed for {task_1} is not published`; the same for `taskStarted`, `taskCheckpointed`, `taskProgressed`.

## Cases

Config of the `per_type` rows:
```yaml
event_policies:
  default: lifecycle
  per_type:
    - pattern: "gts.cf.core.tasks.task.v1~acme.reports.*"
      events: [taskCompleted, taskFailed]
```

| Case | Differs from the representative | Expected | Notes |
|---|---|---|---|
| default preset | (representative) | `taskCreated`, `taskCompleted` published; execution events not | G-SEC-12 |
| release under the preset | the worker releases the task | `taskQueued { reason: released }` recorded in the history and not published | G-EXE-24 |
| liveness requeue under the preset | the session expires and the task is requeued | `taskRetrying { cause: liveness, timeout_type: heartbeat }` recorded and published (not one of the five excluded types) | G-EXE-05 |
| per-type pattern matches (p2) | config above; `{task_1}` (**render**, matches) is created, then cancelled by `{creator_a}` | nothing published: `event taskCreated for {task_1} is not published`; `event taskCancelled for {task_1} is not published` (neither is in its list); history complete | |
| no pattern matches (p2) | config above; `{task_2}` (**export**, no match) is created, then cancelled by `{creator_a}` | `lifecycle`: `event taskCreated for {task_2} is published to the task-events topic`; `event taskCancelled for {task_2} is published …`; history complete | |

## Notes
- p1 publishes the `lifecycle` preset for every type with no configuration; `per_type` policies are p2 (G-SEC-12).
- The per-policy transition filter of PRD.md:898 is dropped: a policy is an event-type list (G-SEC-12). In p2, overlapping `per_type` patterns use the G-CLM-21 specificity rule (exact ID, then longest literal prefix), and `event_policies` change through `POST /admin/config`.
- Events without a task type (`queueHeld`, `queueReleased`) use the engine-wide default policy (G-OPS-05).
