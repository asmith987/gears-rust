# A redelivered event keeps its event ID, so consumers can deduplicate

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-event-publishing` (PRD.md:883, :885) · DESIGN.md:875, :1839 |
| Phase | p1 |

Delivery is at-least-once. A consumer that sees the same event twice can tell, because both copies carry the history's event ID. The engine's own event-wait matcher deduplicates the same way.

## Setup
- `{task_1}` completed (`{evt_5}`). The outbox relay crashes after the broker accepted `{evt_5}` and before it recorded delivery, then restarts.

## Expected broker publish
- `taskCompleted` for `{task_1}` reaches the topic twice; both copies have `id = {evt_5}` and identical `data`.

## Side effects
- History of {task_1} has exactly one `taskCompleted` (`{evt_5}`).
- A consumer keyed on `id` processes it once.

## Notes
- The SDK's idempotent producer (`ProducerMode::Monotonic`, DESIGN.md:876) may already drop the second copy at the broker; the consumer rule holds either way.
- The published `id` equals the history event ID through `TypedEvent::event_id()`, which ships in p1 with #5491 (G-SEC-09); like [1.03](1.03-positive-lifecycle-event-published-under-publishing-subject.md), the test needs #5491 merged.
