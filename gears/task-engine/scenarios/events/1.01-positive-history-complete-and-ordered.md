# The task history records every change, in order, with id, time, actor, type and payload

| | |
|---|---|

| Phase | p1 |
| Test level | E2E |

The history is the engine's audit trail. It is written in the same transaction as each state change, so it can never disagree with the task, and it is complete whatever the publishing policy says.

## Setup
- `{creator_a}` created `{task_1}` (**render**) at `T0`; `{worker_a}` claimed it at `T0+5s` (`reports-7f9c-1`), started it at `T0+6s`, checkpointed at `T0+20s`, and completed it with `success` at `T0+40s`.

## Request
```http
GET /api/task_engine/v1/tasks/{task_1}/events HTTP/1.1
Host: api.example.com
Authorization: Bearer <creator-a-token>
```

## Expected response
- `200`; items oldest first by event ID; default page size 25; each has a unique `id`, `event_type` (camelCase), `actor`, `timestamp`, `payload`.
```json
{
  "items": [
```

## Notes
- Payload keys follow `schemas/types/…task_<name>.v1~.schema.json`. No item carries a lease token, the input, the context or the output.
- Order: oldest first by `id` (UUID v7, `ix_te_events_task`, DESIGN.md:1837), no `$orderby` (G-SEC-07).
- A create records only `taskCreated` with `initial_state`, never `taskQueued` (G-SEC-23). The checkpoint call records `taskCheckpointed` (every call that carries a checkpoint does, G-WAI-15).
- `actor` is the causing subject, `null` for engine-caused events (G-WIRE-10); schemas name it `actor` everywhere (G-SEC-11).
