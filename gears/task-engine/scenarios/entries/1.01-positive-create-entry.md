# The lease holder or an API consumer records an immutable entry on a task

| | |
|---|---|
| Requirement | `cpt-cf-task-engine-fr-task-entries` (PRD.md:632: "Workers and users") · `cpt-cf-task-engine-fr-gts-entry-type` (PRD.md:1055, :1057) · DESIGN.md:393-399, :591, :984, :989, :1087, :1430, :1439, :1441, :1749-1762, :2255 · `schemas/types/gts.cf.core.tasks.entry.v1~` ("consuming gears MAY register further kinds"), `…entry_work.v1~`, `…entry_note.v1~`, `…entry_observation.v1~` |
| Phase | p1 |
| Test level | E2E |
| Gaps | G-EXE-18, G-EXE-19, G-EXE-21 |

An entry is an immutable, timestamped record attached to a task. The holder writes one with its `lease_token` and needs only `claim`; any other user or service sends no token and needs `create` on the task instead (DESIGN.md:984, :1087). The engine resolves the entry type, validates `payload` against its schema, and stores the creator from the security context. Entries live in their own append-only ring table, not in the task row.

## Setup
- `{task_1}` (`running`) on **reports**, created by `{creator_a}`, held by `{worker_a}` (`reports-7f9c-1`) with `{lt_1}`.

## Request
Representative case (**worker, built-in type**), at `T0+15s`:
```http
POST /api/task_engine/v1/tasks/{task_1}/entries HTTP/1.1
Host: api.example.com
Authorization: Bearer <worker-a-token>
Content-Type: application/json

{
  "lease_token": "{lt_1}",
  "type": "gts.cf.core.tasks.entry.v1~cf.core.tasks.entry_work.v1~",
  "payload": { "action": "render_pages", "summary": "rendered 12 pages", "details": { "pages": 12 } }
}
```

## Expected response
- `201 Created`, `Location: /api/task_engine/v1/tasks/{task_1}/entries/{entry_1}`, the entry; `creator` is the caller's subject, set by the engine.

```json
{
  "id": "{entry_1}",
  "task_id": "{task_1}",
  "type": "gts.cf.core.tasks.entry.v1~cf.core.tasks.entry_work.v1~",
  "creator": "{worker_a}",
  "payload": { "action": "render_pages", "summary": "rendered 12 pages", "details": { "pages": 12 } },
  "created_at": "2026-11-03T10:00:15Z"
}
```

## Side effects
- `te_task_entries({entry_1})` is present with `owner_tenant_id = {tenant_a}`.
- The task's `entry_count` grows by 1 in the entry transaction (limit `max_entries_per_task`, 1000, G-EXE-21); no other task field changes.
- The task payload is not changed (no `revision` bump; entries are not part of the task's 64 KB payload); the worker's lease is unaffected.
- No lifecycle event: entries are not in the PRD §5.10 event list (PRD.md:879).
- The response never echoes `lease_token`.
